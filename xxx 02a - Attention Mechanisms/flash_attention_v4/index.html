    FlashAttention-4¶

    Opening Briefing¶

    FlashAttention-4 is the first attention kernel to break the petaflop barrier, achieving 1,613 TFLOP/s (~71% utilization) on NVIDIA's Blackwell B200 GPU. But the raw number obscures the real contribution: FA4 is a case study in what happens when hardware scaling becomes asymmetric and kernel engineers must redesign algorithms around the bottlenecks that didn't scale, rather than the resources that did.

    The core observation is precise: Blackwell doubled tensor-core throughput from Hopper (~1 PFLOP/s to ~2.25 PFLOP/s BF16), but shared-memory bandwidth and non-matmul units (SFUs, general ALUs) stayed roughly flat. This means the softmax exponential — computed on special function units — and shared-memory data movement became the dominant bottlenecks, not the matrix multiplications themselves. FA4's entire design philosophy follows from this single asymmetry: co-design the algorithm and kernel pipeline so that tensor cores, SFUs, FMA units, and memory stages overlap maximally, with no single resource becoming a serialization point.

    Three structural innovations make this concrete. First, a five-role warp specialization pipeline with ping-pong scheduling across two query tiles achieves ~94% execution slot utilization by ensuring that while one tile's softmax computes, the other tile's MMA proceeds. Second, a hybrid software-emulated exponential distributes the softmax bottleneck across both hardware SFUs and FMA units (via a degree-3 polynomial approximation), breaking the SFU serialization that would otherwise cap throughput at well below petaflop. Third, a conditional rescaling strategy with threshold tau reduces numerical-stability rescaling operations by approximately 10x compared to FA3, eliminating a per-iteration tax that compounds across long sequences.

    The result: 1.1–1.3x faster than cuDNN 9.13, 2.1–2.7x faster than Triton implementations, and a generational leap from FA3 (which does not run on Blackwell). FA4 is implemented entirely in CuTe-DSL (Python DSL from NVIDIA CUTLASS) rather than C++ templates, cutting compile times 20–30x — a practical shift that makes kernel iteration feasible during development rather than requiring overnight builds.

    Paper: "FlashAttention-4: Algorithm and Kernel Pipelining Co-Design for Asymmetric Hardware Scaling" (arXiv 2603.05451, March 5, 2026). Authors: Ted Zadouri (Princeton), Markus Hoehnerbach (Meta), Jay Shah (Colfax Research), Timmy Liu (NVIDIA), Vijay Thakkar (Meta/Georgia Tech), Tri Dao (Princeton/Together AI).

    The Asymmetric Scaling Problem¶

    Why FA3 Cannot Simply Run on Blackwell¶

    FA3 was designed for Hopper (H100) and does not run on Blackwell. Conversely, FA4 targets Blackwell exclusively. This is not a portability failure — it reflects fundamentally different hardware trade-offs:

    Resource H100 (Hopper) B200 (Blackwell) Scaling Factor
    BF16 tensor-core throughput ~1 PFLOP/s ~2.25 PFLOP/s ~2.25x
    Shared memory bandwidth Baseline Baseline ~1x
    Special Function Units (SFUs) Baseline Baseline ~1x
    General-purpose ALUs Baseline Baseline ~1x
    TMEM per SM — 256 KB New resource

    The consequence: a kernel designed to keep tensor cores busy on Hopper will, on Blackwell, find tensor cores idle waiting for softmax (SFU-bound in forward pass) or shared-memory traffic (backward pass). FA4 attacks both bottlenecks simultaneously.

    The Bottleneck Shift¶

    • Forward pass bottleneck: The softmax exponential (exp(x)) computed on SFU hardware units. SFUs did not scale with tensor cores, so doubling matmul throughput just means the kernel spends proportionally more time waiting for exponentials.
    • Backward pass bottleneck: Shared memory traffic for the five chained MMAs per iteration. With tensor cores 2.25x faster, shared memory bandwidth becomes the constraining resource.

    Key: FA4's design philosophy is not "make matmuls faster" — tensor cores are already fast enough. It is "redistribute work away from the bottleneck units (SFUs, shared memory) onto underutilized resources (FMA units, TMEM, 2-CTA tiling)."

    Blackwell Architecture Features Exploited¶

    Tensor Memory (TMEM)¶

    Each of Blackwell's 148 SMs contains 256 KB of warp-synchronous scratchpad storage directly wired into tensor cores. FA4 stores intermediate accumulators (S, P, dP, dS, dQ) in TMEM rather than registers — dramatically reducing register pressure compared to FA3.

    5th Generation Asynchronous Tensor Cores¶

    The tcgen05.mma instruction is fully asynchronous and accumulates directly in TMEM. The largest single-CTA tile is 128x256x16 — approximately 2x the area of Hopper's WGMMA atom. This enables larger tiles per operation, reducing iteration count and synchronization overhead.

    2-CTA MMA Mode¶

    Executes one unified MMA across paired CTAs in the same cluster, spanning both TMEM spaces. This enables 256x256x16 tiles by splitting M and N dimensions. The practical effect: reduced redundant shared-memory traffic and lower per-CTA footprint — critical for the backward pass where shared-memory bandwidth is the bottleneck.

    Forward Pass: Five-Role Warp Specialization¶

    The forward kernel assigns five distinct roles to warp groups, all executing concurrently within each CTA:

    Role Warp Count Function
    Load warps — Stream Q tiles into shared memory; orchestrate K/V tile loads from global memory via TMA (Tensor Memory Accelerator)
    MMA warps — Execute matmuls on tensor cores via tcgen05.mma.cta_group::1; compute unnormalized attention scores; accumulate value-weighted outputs in TMEM
    Softmax warps 8 (2 warpgroups of 4) Compute normalized attention scores with hybrid exponential strategy; synchronized to prevent simultaneous exponential computation competing for SFU resources
    Correction warps 4 Monitor scaling factors; conditionally rescale previous outputs only when the max jump exceeds threshold tau — reduces rescaling ~10x vs FA3
    Epilogue warps 1–2 Final output storage from shared memory to global memory via TMA

    Ping-Pong Scheduling¶

    The pipeline processes two query tiles per CTA (128 tokens each) in alternating fashion. While one tile's softmax is computing (SFU-bound), the other tile's MMA proceeds (tensor-core-bound). This achieves ~94% execution slot utilization by ensuring neither resource type waits for the other.

    Hybrid Software-Emulated Exponential¶

    The key innovation for breaking the SFU bottleneck. Rather than relying solely on the hardware MUFU.EX2 special function unit:

    • Hardware SFU handles a portion of exponential computations
    • FMA units execute a degree-3 polynomial approximation (Horner's method for 2^x) for the remaining values
    • This distributes the exponential workload across otherwise underutilized FMA compute units
    • Maintains BF16 precision parity with pure hardware outputs

    Conditional Rescaling (Threshold Tau)¶

    In standard online softmax (FA1–FA3), every time the running maximum changes, all previous accumulated outputs must be rescaled. FA4 introduces a threshold-gated rescaling: correction warps only trigger rescaling when the max jump exceeds a configurable threshold tau. In practice this eliminates ~90% of rescaling operations — a significant reduction in non-matmul work that would otherwise serialize on general ALUs.

    Backward Pass Innovations¶

    The backward pass chains five MMAs per iteration (recomputing S, computing QK^T and PV gradient operations for dQ, dK, dP, dV) plus element-wise softmax. This makes it even more sensitive to the shared-memory bottleneck.

    TMEM Reuse Strategy¶

    Intermediate accumulators share TMEM columns to minimize storage: S and P share one column set; dP, dS, dQ share another. This relieves register pressure that would otherwise force register spills to local memory.

    2-CTA Backward Mode¶

    Each CTA stages half of operand B, reducing shared-memory operand-B traffic by ~50%. DSMEM (distributed shared memory) exchange resolves the dQ reduction-axis mismatch between paired CTAs. This also halves global atomic reductions for dQ accumulation — critical for deterministic mode.

    Deterministic Mode¶

    Serializes global dQ accumulation with semaphore-style locking and memory fencing. Despite the serialization overhead, achieves 85–90% of nondeterministic throughput through:

    • CTA swizzling to improve L2 cache locality
    • Shortest-processing-time-first ordering to minimize tail latency from load imbalance

    Scheduling and Load Balancing¶

    Longest-Processing-Time-First (LPT)¶

    Causal masking creates triangular workloads — some CTAs process full tiles while others hit mostly-masked tiles and finish early. FA4 mitigates this load imbalance by reversing mblock iteration order and swizzling batch-heads into L2-sized sections.

    Variable Sequence Length Sorting¶

    A preprocessing kernel sorts batches by maximum per-worktile execution time. The sort result is cached to eliminate overhead on subsequent calls with the same batch shape.

    GQA/MQA Optimization¶

    For grouped-query and multi-query attention, all query heads sharing a KV head are traversed together, maximizing KV tile reuse in shared memory and reducing redundant global memory loads.

    Performance¶

    Forward Pass (BF16, B200)¶

    Comparison Speedup
    vs cuDNN 9.13 1.1–1.3x
    vs Triton implementations 2.1–2.7x
    vs FA2 (at seqlen 32,768) 3.6x
    vs FA3 (generational, not same GPU) ~2–3x
    • Peak throughput: 1,613 TFLOP/s (~71% utilization)
    • Execution slot utilization: ~94% via ping-pong warp scheduling

    Backward Pass (BF16, B200)¶

    • 3.15x faster than FA2 at sequence length 32,768
    • Deterministic mode: 85–90% the speed of nondeterministic backward
    • Consistent outperformance on large sequence lengths

    Key: FA4 is the first attention kernel to break the petaflop barrier. The 71% utilization figure is notable because attention involves significant non-matmul work (softmax, rescaling, masking) — pure GEMM kernels achieve higher utilization but perform simpler computation.

    Supported Attention Variants¶

    Variant Forward Backward
    Standard (non-causal) Supported Supported
    Causal masking Supported (with LPT scheduling) Supported
    GQA (Grouped-Query Attention) Supported Not yet supported
    MQA (Multi-Query Attention) Supported Not yet supported
    Variable sequence length (varlen) Supported (with sorting) Supported
    DeepSeek V3 config (192, 128 head dims) Tested Tested

    Via FlexAttention backend: sliding window, ALiBi, document masking, soft-capping, and arbitrary custom attention patterns are supported through the PyTorch FlexAttention + FA4 integration.

    Note: FP8 support is not present in FA4. FP8 was a feature of FA3 on Hopper. FA4 focuses exclusively on BF16 on Blackwell.

    Implementation: CuTe-DSL¶

    FA4 marks a major departure from FA3's C++ CUTLASS template approach. The entire kernel is implemented in CuTe-DSL, a Python DSL from the NVIDIA CUTLASS team that lowers directly to PTX:

    • 20–30x faster compile times compared to C++ template metaprogramming
    • Full low-level control preserved (inline PTX, barrier management, TMEM allocation)
    • Python-level expressivity makes kernel development and iteration practical during research cycles

    This is architecturally significant: the compile-time barrier was a real obstacle to kernel experimentation in FA3. CuTe-DSL makes it feasible to iterate on kernel designs in minutes rather than hours.

    Ecosystem Integration¶

    PyTorch FlexAttention (March 5, 2026)¶

    FA4 is available as a backend for FlexAttention on Hopper and Blackwell GPUs:

    • Set kernel_options={"BACKEND": "FLASH"} to activate
    • PyTorch auto-generates CuTeDSL score/mask modification functions and JIT-instantiates FA4
    • 1.2x to 3.2x speedup over the Triton FlexAttention backend on compute-bound workloads
    • Supports custom attention patterns (ALiBi, sliding window, document masking, soft-capping, arbitrary combinations)
    • Requires recent PyTorch nightly + FlashAttention main branch

    vLLM v0.17.0 (March 2026)¶

    • FA4 backend integrated via PR #32974
    • Release includes 699 commits from 272 contributors
    • Also includes PyTorch 2.10.0 upgrade
    • Benefits Hopper and Blackwell GPU deployments

    Implications for Inference Engineering¶

    What FA4 Means for Serving Infrastructure¶

    1. Blackwell ROI case strengthened: FA4's 71% utilization on B200 vs FA3's ~35–40% on H100 means Blackwell GPUs deliver significantly more useful attention throughput per dollar — but only with FA4-enabled serving stacks (vLLM v0.17+)
    2. Long-context serving becomes cheaper: The 3.6x speedup over FA2 at 32K sequence lengths directly reduces per-token latency for long-context workloads, making 128K+ context windows more economically viable
    3. Prefill phase acceleration: Attention is compute-bound during prefill; FA4's petaflop throughput primarily benefits TTFT (time to first token) for long prompts
    4. Backward pass matters for fine-tuning: The 3.15x backward speedup over FA2 reduces fine-tuning cost on Blackwell hardware, making on-device adaptation more practical

    The Broader Lesson: Asymmetric Scaling as a Design Pattern¶

    FA4 demonstrates a pattern that will recur in future hardware generations: when one resource scales faster than others, the kernel must be redesigned around the lagging resources, not the fast ones. This implies that attention kernel engineering is not a solved problem — each new GPU architecture will likely require a new FlashAttention variant tailored to its specific asymmetries.

    Key: FA4 is not just "FA3 on new hardware." It is a ground-up redesign driven by the insight that Blackwell's tensor cores are no longer the bottleneck. The algorithm-kernel co-design methodology — identifying which hardware resources constrain throughput and redistributing work away from them — is the transferable contribution, applicable beyond attention to any memory- or compute-asymmetric kernel.
