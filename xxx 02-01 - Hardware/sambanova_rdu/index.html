    SambaNova Systems: RDU Architecture and Inference Platform¶

    Opening Briefing¶

    SambaNova Systems (founded 2017) builds Reconfigurable Dataflow Units (RDUs) — CGRA-style accelerators purpose-built for LLM inference rather than training. Their architectural thesis: inference's dominant bottleneck is data movement and memory hierarchy management, not raw peak FLOPs — especially when workloads require frequent switching among multiple models (routing, tool-use, expert selection, agent loops). The current production chip is SN40L (4th gen, 2023); the upcoming SN50 (5th gen, shipping 2H 2026) is positioned as "purpose-built for agentic inference." SambaNova raised a $350M Series E in Feb 2026 alongside the SN50 announcement and Intel collaboration (SambaNova press release, Feb 2026).

    SN40L Architecture (4th Generation)¶

    The SN40L is the most technically disclosed RDU, with an academic-style architecture paper (arXiv 2405.07518, May 2024) and Hot Chips 2024 presentation.

    Fabrication and Packaging¶

    TSMC 5nm, packaged as a 2.5D CoWoS chiplet design with two reconfigurable dataflow dies ("RDDs") plus HBM on the same interposer. A die-to-die interface allows streaming between dies without going through off-chip memory.

    Compute: Tile-Based CGRA¶

    The chip is a coarse-grained reconfigurable array (CGRA) of tiles:

    • Pattern Compute Units (PCUs) — configurable between an output-stationary systolic array and a pipelined SIMD-style core. Support BF16/FP32/INT32/INT8 compute datatypes (Hot Chips 2024). 1,040 PCUs per socket, yielding 638 BF16 TFLOPS peak.
    • Pattern Memory Units (PMUs) — large on-chip SRAM scratchpads with flexible addressing, scalar ALU pipelines for address generation, programmable banking/predication, and data alignment units supporting transpose/layout conversions at high bandwidth.
    • Address Generation and Coalescing Units (AGCUs) — portals to off-chip memory (HBM, DDR, remote).
    • Reconfigurable Dataflow Network (RDN) — three physical fabrics (vector, scalar, control) implemented as a mesh of non-blocking switches with compiler-configured routing tables via a place-and-route compilation step.

    Three-Tier Memory Hierarchy¶

    The defining architectural feature — designed for multi-model residency and fast switching:

    Tier Capacity Bandwidth Role
    On-chip SRAM 520 MiB "hundreds of TB/s" (on-chip) Active compute operands, intermediate activations
    HBM 64 GiB ~2 TB/s per socket Hot model weights, KV-cache
    DDR Up to 1.5 TiB per socket >200 GB/s per socket Multi-model residency; warm model storage

    The DDR tier is directly attached (not accessed through a host CPU), and aggregate DDR-to-HBM load bandwidth exceeds >1 TB/s per node — enabling model-switch times claimed at "microseconds" rather than the seconds typical of GPU-based model reloading.

    Programming Model: Dataflow Execution and Deep Fusion¶

    LLM inference is a huge graph of tensor operations (normalization, projections, attention, MLP, residual adds) executed repeatedly. On conventional hardware, each operation is typically a kernel launched on the accelerator, and between kernels, intermediate tensors often get materialized — written to HBM so the next kernel can read them back. This write-read cycle is the dominant cost because modern accelerators are compute-rich but memory-bandwidth-limited (the memory wall). The bottleneck is not arithmetic throughput but keeping compute units fed with data.

    Fusion combines multiple operations into one execution unit so intermediates stay in fast on-chip storage rather than bouncing through HBM. Shallow fusion combines a few adjacent ops (e.g., bias + gelu). Deep fusion takes a much larger chain and makes it behave like a continuous streaming assembly line — data enters stage A, partial results flow to B, then C, then D, without full HBM writeout between stages. The deeper the fusion, the higher the operational intensity (useful arithmetic per byte moved).

    The RDU is a dataflow machine designed for deep fusion: execution is organized around how data moves through a graph of operations, not around a "launch op A, then op B" sequence. The SN40L compiler performs place-and-route on the model graph — mapping operators to PCUs/PMUs, configuring RDN routing tables, deciding which buffers stay on-chip, how tensors stream between stages, and where to apply data/tensor/pipeline parallelism. This is closer to hardware synthesis than traditional kernel programming. SambaNova claims an entire Llama 3.1 8B decoder can be fused into a single dataflow kernel and called repeatedly without launch overhead (SambaNova, "Why SN40L Is the Best for Inference", sambanova.ai).

    Why this differs from GPU execution: On NVIDIA GPUs, work is distributed across Streaming Multiprocessors (SMs), each with limited local resources (registers, shared memory, cache). A typical execution for x → layernorm → linear → gelu → linear launches separate kernels with each intermediate tensor materialized to HBM between stages. Good GPU stacks reduce this with fusion, custom kernels, persistent kernels, and FlashAttention — so the right view is not "GPUs are dumb" but that the default execution style tends toward many kernels and significant memory traffic unless the compiler/runtime works very hard to avoid it. SambaNova's architecture avoids more materialization by keeping intermediates in distributed SRAM and streaming them between fused stages on-chip, producing long fused pipelines (e.g., RMSNorm → QKV projection → attention → output projection → MLP → residual add as one persistent streaming graph) with pipeline parallelism across tokens (stage A on token t+1, stage B on token t, stage C on token t-1) (SN40L architecture paper, arXiv 2405.07518).

    Scale-Up and Interconnects¶

    • 8-socket SN40L node: used for Composition of Experts (CoE) deployment comparisons against DGX A100/H100
    • SambaRack: 16 RDUs per node as 8 dual-RDU modules ("SN40L-2 / XRDUs"), each with BMC for power control/telemetry, plus x86 host module running RHEL
    • Network: Ethernet-based (Juniper QFX5130 data switch, Juniper EX-series management switch) — notably not a proprietary interconnect. Independently confirmed at Argonne ALCF AI testbed ("Metis" deployment).
    • Power: air-cooled, ~10 kW per rack class (vendor claim, confirmed in partner announcements)

    SN50 (5th Generation) — What Is Known¶

    SN50 is positioned as "purpose-built for agentic inference" with stated deltas vs SN40L:

    • 5x more compute per accelerator
    • 4x more network bandwidth
    • "Agentic caching" — prompt/input token caching in memory to reduce prefill time and TTFT
    • 20 kW/rack class, air-cooled
    • Scale-out to 256 accelerators across racks over "multi-TB/s interconnect"
    • Claims: 10T+ parameter models, 10M+ context lengths (vendor claim; no independent validation)
    • FP8 performance claims appear in vendor footnotes, but chip-level datatype support not fully disclosed
    • SoftBank announced as first customer (Japan deployment); Intel as multi-year collaboration partner

    Gap: low-level SN50 specs (process node, exact SRAM/HBM/DDR sizes, per-chip bandwidth, TDP, instruction-level numeric formats) not published. Shipping 2H 2026 (SambaNova press release, Feb 2026).

    Composition of Experts (CoE)¶

    SambaNova's distinctive framing: future workloads are compositions of multiple specialized models rather than a single monolith. "Composition of Experts" describes sequences where many small expert models are selected and run, with switching overhead becoming first-order cost. This is distinct from MoE (weight sparsity within one model) — CoE is system-level sparsity across multiple independently-trained models orchestrated in agent-style call chains.

    The thesis is strongest in this regime because two things compound: smaller expert workloads have lower operational intensity (GPU utilization drops), and switching among many models is slow/expensive on conventional hardware. The three-tier memory hierarchy addresses both — many models stay resident in DDR, hot models in HBM, active layers in SRAM. Switching means promoting from DDR to HBM rather than reloading from storage. High fusion depth keeps operational intensity up even for small experts. This is the deeper reason SambaNova frames inference as a data-movement problem: the claim applies not just to one dense forward pass but to production serving where systems are agentic, multi-step, and multi-model (SN40L architecture paper, arXiv 2405.07518).

    Competitive Positioning: RDU vs GPU vs Groq LPU¶

    The Core Distinction: SambaNova vs Groq¶

    SambaNova is not "novel because it uses dataflow" while Groq does not. Both are compiler-first, inference-native, stream/dataflow-oriented departures from GPU-style SIMT execution. Groq's Tensor Streaming Processor (TSP/LPU) uses functionally sliced execution, interleaved memory and compute, producer-consumer streams, static scheduling, and deterministic execution (Groq, "Think Fast: A Tensor Streaming Processor", ISCA 2020). SambaNova's RDU maps the model graph onto a programmable grid of compute and memory units with streaming pipelines. Same anti-GPU instinct, different optimization axis:

    • Groq = deterministic tensor streaming machine. Center of gravity is determinism: a single-core software-defined machine, static scheduling, no reactive elements (caches, arbiters), and direct chip-to-chip coordination so many chips behave like one precisely timed execution fabric. The compiler schedules everything ahead of time; the rack is meant to behave like one logical core. On-chip SRAM (230 MB) serves as primary weight storage, not cache. Novelty: "time is fully choreographed" (Groq, "LPU Architecture", groq.com).
    • SambaNova = reconfigurable graph-and-memory machine. Center of gravity is graph mapping + memory hierarchy: a reconfigurable grid of PCUs/PMUs, fused streaming across operators, and a three-tier memory system (SRAM/HBM/DDR) designed to reduce off-chip movement and keep models resident. Novelty: "the graph is laid out spatially, and memory movement is architected as a first-class problem."

    The most defensible contrast: Groq mainly makes time deterministic; SambaNova mainly makes graph execution and model residency flexible. This produces materially different product theses — Groq's "single fast deterministic stream processor" story vs SambaNova's "large models, long context, multiple models in parallel, hot-swapping for agentic workloads" story. One further historical difference: SambaNova has framed its architecture as serving both training and inference (the SN40L paper explicitly describes the RDU as co-designed for enterprise inference and training), whereas Groq frames itself as inference-only from inception — though SambaNova's SN50 messaging is now clearly inference-first (SN40L paper, arXiv 2405.07518; Groq architecture pages).

    Comparison Table¶

    Dimension SambaNova RDU NVIDIA GPU Groq LPU
    Architecture Compiler-mapped dataflow CGRA SIMT (warps, CUDA) Deterministic, compiler-scheduled single-core
    Primary lever Operator fusion + streaming + three-tier memory for multi-model Low-precision (FP8/FP4) + inference compilers (TensorRT) + batch scaling Large on-chip SRAM + high on-die bandwidth + deterministic latency
    Optimization axis Graph execution flexibility + model residency Ecosystem breadth + precision scaling Time determinism + single-core choreography
    Multi-model story Multi-model residency in DDR, microsecond switching Model reloading or large-batch multiplexing Not a primary emphasis
    On-chip SRAM 520 MiB (SN40L) ~50 MB L2 (H100) 230 MB (primary weight storage)
    Interconnect Ethernet-based NVLink/NVSwitch (proprietary, high-BW) RealScale (proprietary, chip-to-chip coordination)
    Software ecosystem Compiler P&R + SambaStack (Kubernetes) CUDA + TensorRT + Triton (massive ecosystem) GroqWare SDK + ONNX
    Training support Yes (SN40L paper describes training + inference) Yes (primary training platform) No (inference-only from inception)

    All three expose OpenAI-compatible endpoints: SambaNova (SambaCloud), Groq (GroqCloud), NVIDIA (via cloud providers/Triton). SambaNova offers a three-tier deployment model: SambaCloud API → SambaStack hosted (managed K8s + hardware) → SambaStack on-prem.

    Independent Benchmarks and Performance Evidence¶

    Artificial Analysis Hardware Benchmarking (DeepSeek R1 0528, Jan 2026)¶

    SN40L-16 system benchmarked independently:

    Metric SambaNova SN40L-16 Context
    Single-user peak output speed 269 tokens/s >3x the peak output speed of NVIDIA B200 with TensorRT-LLM in same benchmark
    System throughput at >=256 concurrent ~4,700 tokens/s Exceeds measured NVIDIA systems across most tested concurrency levels

    Provider Benchmarking (API-level)¶

    • Llama 3.1 Instruct 8B: SambaNova ~631 t/s; Groq ~676 t/s (Artificial Analysis snapshot)
    • Llama 3.1 Instruct 405B: SambaNova 114 t/s, citing Artificial Analysis — framed as fastest among benchmarked providers at the time

    Comparison Points¶

    • NVIDIA Blackwell: single DGX (8 GPUs) claims >250 tokens/s per user or >30,000 tokens/s max throughput on DeepSeek-R1 671B — different test harness, not directly comparable (NVIDIA developer blog)
    • Groq: Llama 3 8B at 877 t/s, Llama 3 70B at 284 t/s, Llama 3.3 70B at 276 t/s (Groq blogs citing Artificial Analysis, 2024)

    Gaps¶

    • No MLPerf submissions: SambaNova not among MLPerf Inference v5.0 submitters (MLCommons, Apr 2025)
    • No SN50 independent benchmarks: hardware not yet shipping
    • Hourly pricing not comparable: SambaNova accelerators not offered as standard on-demand endpoints (noted by Artificial Analysis)

    Pricing and TCO¶

    Provider Model Input ($/M tokens) Output ($/M tokens)
    SambaNova DeepSeek V3-0324 $1.00 $1.50
    Groq Llama 3.3 70B $0.59 $0.79

    Inference cost decomposes to: (hardware $/hr + power + ops) / (useful tokens/hr at target SLO). Each vendor targets different terms: SambaNova reduces the numerator via air-cooled low-power racks (10-20 kW) and the denominator via multi-model residency and streaming fusion. NVIDIA targets via lower precision (FP8/FP4 Transformer Engine) and inference compilers (TensorRT-LLM + Triton/vLLM). Groq targets via deterministic scheduling and batch-independent per-request behavior.

    Observability and Operations¶

    • SambaStudio: Grafana-based endpoint monitoring; Prometheus exporter references in legacy docs
    • SambaRack: BMC per module for power control and telemetry
    • Fault management: Patent (US20240264896A1) describes monitoring tiles, switches, PCIe links with centralized health management
    • SambaStack: Kubernetes-operated inference platform (hosted or on-prem) for model lifecycle, user/access management, checkpoint deployment, speculative decoding options

    Model Support¶

    SambaCloud supports dense transformers, MoE, reasoning-tuned, and multimodal models with context lengths at 128k-160k. Current model list includes DeepSeek variants, Meta Llama family, Qwen variants, "OpenAI gpt-oss-120b", Whisper-Large-v3, and Llama 4 Maverick preview (multimodal image). SambaNova advertises inference "without quantization" (BF16/FP16-class) for quality retention (SambaCloud docs; SambaNova blog).

    Key: SambaNova's architectural bet is that inference TCO will be dominated by multi-model switching costs as agentic workflows proliferate. The three-tier memory hierarchy (SRAM/HBM/DDR with direct DDR attachment) is the core differentiator — enabling many models to stay resident and switch in microseconds rather than seconds. The main risks: NVIDIA's ecosystem breadth and low-precision toolchain may outpace architectural advantages, SN50 claims lack independent validation, and the CUDA software moat remains the industry's strongest lock-in. The main opportunity: if agentic inference workloads grow as projected, multi-model residency and fast-switching become load-bearing infrastructure rather than a niche optimization.
