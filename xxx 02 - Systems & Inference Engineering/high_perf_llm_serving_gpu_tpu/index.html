    High-Performance LLM Serving on GPU and TPU: Technical Guide¶

    Opening Briefing¶

    The defining bottleneck in production LLM inference is not compute — it is memory bandwidth during autoregressive decode. A single H100 SXM delivers 3.35 teraflops of FP16 compute but only 3.35 TB/s of HBM3 bandwidth, meaning that during the token-generation phase, when each forward pass reads the entire KV cache but performs comparatively little arithmetic, the GPU's streaming multiprocessors sit largely idle waiting on memory. This inversion — where the most expensive hardware in the rack is gated by a bus, not by ALUs — restructures every optimization decision from kernel selection to cluster topology.

    The practical consequence is that serving-stack engineering matters as much as model architecture. PagedAttention, introduced by vLLM, reduced KV cache waste by roughly 10x by treating GPU memory like virtual memory pages, which directly translates to higher batch sizes and thus better arithmetic-intensity during decode. TensorRT-LLM's kernel fusion and FP8 quantization on Hopper squeeze both sides of the roofline — shrinking memory traffic per token while raising the compute ceiling. But these framework-level wins evaporate if the host OS introduces TLB misses on model weights (hence 1 GB hugepages), if NUMA-remote memory access adds 40-60 ns per cache line fetch to the prefill pipeline, or if Kubernetes schedules a tensor-parallel workload across GPUs on different NUMA nodes. The stack is deeply coupled: a misconfigured irqbalance daemon redistributing NVMe interrupts away from the GPU's local cores can measurably degrade model-load times and, during checkpoint-based warm starts, add seconds of latency that autoscalers interpret as capacity shortfall.

    The second-order implication is that operational discipline becomes a performance variable. Disabling NUMA balancing, pinning interrupt affinity, setting the CPU governor to performance mode, and using NVMe polling queues are not optional hardening steps — they are load-bearing components of the inference latency budget. Similarly, security measures like TLS termination at a gateway proxy rather than on the GPU host, or running non-root containers with SELinux in enforcing mode, cost microseconds or nothing at all, while neglecting them creates attack surface that eventually forces costly architectural retreats.

    This document treats the full vertical — from kernel boot parameters and driver persistence mode through serving-framework selection, container image construction, Kubernetes topology-aware scheduling, and DCGM-driven autoscaling — as a single co-optimized system. Each section provides specific commands, configuration values, and the causal reasoning behind them, so that the gap between a working deployment and a well-tuned one can be closed methodically rather than by trial and error.

    1. Supported Operating Systems¶

    • Recommended: 64-bit Linux — Ubuntu LTS (20.04, 22.04), RHEL / Rocky / AlmaLinux, CentOS, SLES
    • Ubuntu LTS preferred (base of NVIDIA DGX OS); RHEL/Rocky favored for enterprise/HPC stability
    • Windows Server (2016/2019/2022): drivers exist but Linux ecosystem is far more mature; use WSL2 if Windows is mandatory
    • Production recommendation: Linux always

    2. Kernel & System-Level Optimizations¶

    Optimization Setting Why
    CPU Frequency Governor cpupower frequency-set -g performance Locks max frequency; prevents throttling during inference preprocessing/I/O
    CPU Pinning isolcpus kernel param or K8s cpuManagerPolicy: static Dedicated cores for inference threads; eliminates context switches
    NUMA Balancing kernel.numa_balancing=0 (sysctl) Disables automatic page migration overhead; bind GPU threads to GPU's NUMA node with numactl --cpunodebind
    Transparent Huge Pages madvise or always 2 MB pages reduce TLB misses; for very large models consider 1 GB hugepages via kernel cmdline default_hugepagesz=1G hugepages=16
    I/O Scheduler echo none > /sys/block/nvme0n1/queue/scheduler noop/none for NVMe — firmware handles optimization; removes kernel queuing overhead
    Kernel Mitigations mitigations=off (boot param) — use with caution Disables Spectre/Meltdown patches; a few percent gain but exposes vulnerabilities; only for air-gapped servers

    Key: Goal is ensuring the OS is never the bottleneck: CPUs at full speed, hugepage-friendly memory, NUMA locality respected for GPU data paths.

    3. GPU Driver & Toolkit Setup¶

    NVIDIA GPU Stack¶

    Component Details
    NVIDIA Driver Version 525+ for A100/H100; install via nvidia-driver-535 or CUDA Toolkit's driver; verify with nvidia-smi; enable persistence mode nvidia-smi -pm 1
    CUDA Toolkit Match driver (CUDA 12.2 or 11.8 for Ampere); set PATH and LD_LIBRARY_PATH; verify with nvcc --version
    cuDNN Optimized tensor kernels for transformer ops; install matching CUDA version
    cuBLAS/cuBLASLt Dense linear algebra acceleration
    TensorRT Inference compiler — kernel fusion, quantization (FP16/INT8/FP8); libraries in /usr/lib/x86_64-linux-gnu
    TensorRT-LLM High-level Python API for LLM-specific TensorRT engines; supports GQA, multi-stream execution, KV cache, FP8
    NCCL Multi-GPU collective communications; enable RDMA (InfiniBand/RoCE) via NVIDIA Fabric Manager for multi-node
    MIG Enable with nvidia-smi -mig 1; create instances via nvidia-smi mig; A100 40G splits into 7 x ~5GB instances

    Additional: NVIDIA cutlass or FasterTransformer for custom kernels. Always test with sample workload to confirm GPU utilization is high and no kernel capability warnings appear.

    4. TPU Setup (Cloud TPU)¶

    • Cloud-only: Google Cloud TPU v4/v5 — no on-premises deployment for v4+; TPU Pods reside in Google data centers
    • TPU VM: Create via gcloud (e.g., v4-8 or v5-8 slice); SSH in to find TPU drivers and libtpu runtime pre-installed; use tpu-vm-base images
    • Frameworks: TPUs use XLA — supported via TensorFlow (with XLA), JAX, or PyTorch XLA; HuggingFace optimum-tpu for Transformer models
    • Serving on TPU: vLLM has TPU mode (vllm serve --tensor-parallel-size N --target-device=tpu); also HuggingFace TGI compiled for TPU; or Vertex AI TPU inference server
    • TPU tuning: Lock CPU processes to NUMA node 0 (TPU v4 host recommendation); use large batch sizes to fully utilize matrix units
    • Multi-host (Pods): For models exceeding one chip — use JAX with pjit or TensorFlow parallelism; Google handles interconnect topology in the slice

    5. LLM Serving Frameworks¶

    Framework Key Strength Multi-GPU Quantization Install
    vLLM PagedAttention, high batch concurrency, memory efficiency Tensor parallelism (--tensor-parallel-size N) AWQ, GPTQ, FP16 auto pip install vllm
    TGI (HuggingFace) Production-ready C++/Rust server, multi-threaded, streaming --num-shard N GPTQ, bitsandbytes Docker ghcr.io/huggingface/text-generation-inference or pip
    DeepSpeed-Inference ZeRO-Inference, pipeline parallelism, kernel optimizations mp_size=N INT8, SmoothQuant pip install deepspeed
    FasterTransformer NVIDIA C++ optimized kernels, beam search, FP16/BF16 Tensor + pipeline parallelism INT8, FP8 Docker from NGC or build from source
    TensorRT-LLM Maximum NVIDIA GPU performance, kernel fusion, FP8 Multi-GPU support FP16, INT8, FP8 NGC container or build from source
    Transformers + Accelerate Simplest setup, good for dev/testing device_map="auto" bitsandbytes, model.half() pip install transformers accelerate

    Key: Choose vLLM for many parallel requests + memory efficiency, TGI for production-ready multi-user serving, DeepSpeed for huge models needing multi-GPU optimizations, TensorRT-LLM for absolute peak NVIDIA performance. Most teams start with TGI or vLLM and add TensorRT if needed.

    Local & Multi-Backend Serving¶

    Tool Key Capability Details
    llama-swap (March 2026) Lightweight multi-backend model serving Single executable + config file; supports llama.cpp, ik_llama.cpp, and other providers; UI for testing models, checking performance, and viewing logs; model grouping, forced configuration settings, policy definitions; advantage over llama-server router mode: supports multiple backends (llama-server limited to llama.cpp only)
    ik_llama.cpp CPU and hybrid CPU+GPU inference Chunked delta net implementation; significantly faster than mainline llama.cpp for CPU-only or hybrid CPU+GPU setups
    Open WebUI Open Terminal Agentic workflows on single GPU Dockerized sandbox with live file browser and render canvas; native tool calling; enables agentic workflows on single GPU (e.g., Qwen3.5-35B on 3090)

    Constrained Decoding & Parsing¶

    • llama.cpp autoparser (March 2026): automatic parser generator integrated into mainline; extracts parsing logic directly from Jinja templates (leveraging ngxson's Jinja system + aldehir's PEG parser); supports typical model templates without additional definitions or recompilation; phase-aware parsing resolves tool-calling parameter ordering issues; contrasts with LM Studio's Harmony parser which lacks phase state tracking (causes recursive traps, phase confusion, read_file loops)

    Consumer GPU Offloading¶

    • LM Studio MoE offload parameter (March 2026): enables running Qwen-3.5-35B 4_K_M with 262k context window on a 4070Ti, eliminating need for llama.cpp in some setups

    Configuration essentials: - Enable FP16 or lower precision (all frameworks support it) - Set --tensor-parallel-size to match allocated GPU count (vLLM will underutilize if mismatched) - Profile setup: GPU memory should be close to full; SMs should stay busy during generation (not just prefill) - If GPU utilization drops during decode, consider FlashAttention or FasterTransformer kernels

    6. Containerization Best Practices¶

    Base Images¶

    • Use NVIDIA NGC images (e.g., nvcr.io/nvidia/pytorch:<version>-py3) with CUDA, cuDNN pre-installed
    • Container should NOT include NVIDIA driver — NVIDIA Container Toolkit injects host's /dev/nvidia* devices and driver .so files
    • Install NVIDIA Container Toolkit on host; use --gpus all flag with Docker

    Image Optimization¶

    • Multi-stage builds: Compile in one stage, copy binaries to slim runtime image; run pip cache purge to shrink layers
    • Model weights: Either bake into image (large but self-contained) or mount via volume/NFS/cloud storage
    • Read-only caching layers: Use shared tmpfs for multiple instances loading same model from RAM
    • Lean images: Strip unnecessary packages, disable non-essential services (no cron, no DBus)

    Runtime Configuration¶

    • Set OMP_NUM_THREADS=1 (PyTorch) or TF_INTRA_OP_THREADS=1 / TF_INTER_OP_THREADS=4 (TensorFlow)
    • Use --cpuset-cpus for CPU pinning or let K8s CPU Manager handle it
    • Run as non-root via SecurityContext in K8s (NVIDIA toolkit handles GPU device permissions)
    • For latency-critical services: hostNetwork: true in K8s (avoids bridge overhead)

    HPC Environments¶

    • Singularity/Apptainer: Rootless container runtime; auto-binds /usr/bin/nvidia-smi and driver libs; use --nv flag; same OS base as host recommended

    Verification¶

    • Test with nvidia-smi inside container; profile with nsys or nvprof if bottleneck suspected
    • Docker overhead on GPU compute: a few percent at most
    • Use NVIDIA GPU Operator on K8s to auto-provision drivers + device plugin on nodes

    7. Kubernetes Scheduling & GPU Management¶

    GPU Scheduling¶

    • NVIDIA Device Plugin advertises nvidia.com/gpu resources; pods request via resources: limits: nvidia.com/gpu: 1
    • For multi-GPU models: request exact GPU count (e.g., 4 GPUs); K8s schedules whole GPUs by default (no sharing)
    • MIG in K8s: Device plugin advertises MIG types (e.g., nvidia.com/mig-1g.5gb); configure MIG mode before K8s sees resources (GPU Operator can automate)

    Topology & NUMA Awareness¶

    • Enable Topology Manager in kubelet (--topology-manager-policy=best-effort or restricted)
    • Enable CPU Manager (--cpu-manager-policy=static) for dedicated core allocation
    • With restricted policy: pod fails to schedule if CPU and GPU can't be co-located on same NUMA node — ensures zero cross-NUMA latency

    Performance-Aware Scheduling¶

    • Gang schedulers (Volcano, KubeRay) for distributed inference spanning multiple pods/nodes — all-or-nothing placement
    • Label GPU nodes with capabilities (gpu-model=A100 vs V100); use node selectors/affinities to route H100-optimized FP8 models to H100 nodes only
    • PriorityClasses: Production inference > research batch jobs; lower-priority jobs evict when cluster is full

    Autoscaling¶

    • Horizontal Pod Autoscaler (HPA): Scale on custom metrics — requests/sec, p95 latency, queue length (via Prometheus Adapter)
    • Cluster Autoscaler: Add GPU nodes from pool when workload queue grows; watch for cold-start latency (loading 30GB model takes tens of seconds)
    • Lazy loading or warm standby pods to mitigate cold starts
    • GPU runtime state snapshots: Cold-starting Qwen-32B on H100 in ~1.5s via full GPU runtime state restoration (weights, CUDA context, memory layout) from snapshot

    Multi-Node GPU Communication¶

    • Configure Cluster Network for RDMA or host networking with InfiniBand
    • Use secondary networks (Multus CNI) for InfiniBand interfaces alongside regular cluster network
    • Set NCCL_SOCKET_IFNAME or NCCL_IB_HCA env vars in pods for NCCL interface control

    GPU Operator¶

    • Auto-installs drivers, device plugin, GPU Feature Discovery (labels nodes with GPU type), DCGM Exporter for monitoring
    • Recommended for large clusters — ensures right driver-CUDA combo; labels like nvidia.com/gpu.present=true, nvidia.com/gpu.count=8

    Resource Quotas¶

    • Set per-namespace GPU quotas to prevent one team consuming all GPUs
    • Use PriorityClasses so production inference pods preempt research workloads

    8. Networking & Disk I/O Tuning¶

    Model Loading I/O¶

    • Use fast local NVMe SSDs (several GB/s read throughput) for model weights
    • Linux page cache auto-caches on first load — subsequent loads/restarts are faster
    • For multiple instances of same model on one node: use shared tmpfs (memory filesystem) — read from disk once, serve from RAM
    • Preload models into RAM with vmtouch or dd for explicit page caching

    NVMe Tuning¶

    • I/O scheduler: noop/none for NVMe
    • Pin NVMe interrupts to cores on same NUMA node: /proc/irq/*/smp_affinity
    • Interrupt coalescing: nvme set-feature /dev/nvme0 -f 0x8 -v 0x00000107 (threshold 8, time 100us) — reduces CPU overhead at cost of ~0.1ms latency
    • NVMe polling: nvme_poll_queues module option — CPU polls for completions instead of interrupts; effective when CPUs are idle waiting on I/O

    Network Tuning¶

    • Jumbo frames: MTU 9000 on data network; reduces overhead for large transfers
    • HTTP/2 or gRPC for serving traffic — efficient for many small messages
    • Interrupt affinity: Disable irqbalance; manually pin NIC IRQs to NUMA-local cores; use set_irq_affinity.sh for Mellanox ConnectX
    • NIC ring buffers: ethtool -G to increase RX/TX ring buffer sizes if drops detected
    • Receive Side Scaling (RSS): Spread incoming connections across multiple queues/cores
    • RDMA: NCCL auto-uses RDMA if available (InfiniBand/RoCE); enable GPU Direct RDMA (NVreg_EnableGpuDirectRDMA=1)

    Connection Tuning¶

    • net.core.somaxconn — increase for high-connection services
    • ulimit -n — ensure open files limit is high
    • Use HTTP keep-alive or gRPC persistent streams to avoid reconnect overhead
    • Client-side: compress large prompts with gzip

    9. Monitoring & Observability¶

    Metrics Stack: Prometheus + Grafana + DCGM + Node Exporter¶

    Layer Tool Key Metrics
    GPU hardware NVIDIA DCGM Exporter (deployed by GPU Operator) GPU utilization %, memory used, temperature, power draw, ECC error counts
    Application Instrument model server (vLLM/TGI built-in) or custom Prometheus endpoint Throughput (req/sec), latency (p50/p90/p99), queue size/wait time, tokens/sec
    System Prometheus Node Exporter CPU usage, memory, disk I/O rates, network traffic, I/O wait, context switches
    Logs ELK (Elasticsearch/Kibana) or Grafana Loki Model load events, errors, timeouts
    Traces Jaeger or OpenTelemetry Request-level latency through multi-service pipeline

    Grafana Dashboard Layout¶

    1. GPU Stats Panel: Per-GPU util%, memory, compute vs copy engine utilization
    2. Throughput/Latency Panel: Request rate and latency percentiles over time
    3. CPU/Memory Panel: Host-level bottleneck detection
    4. I/O Panel: Disk read/write throughput (especially during model load) and network throughput

    Alerting¶

    • GPU utilization near 0 for sustained period → service stuck or no traffic
    • GPU at 100% + increasing latency → need to scale
    • GPU memory OOM events (DCGM reports)
    • ECC memory errors, thermal throttling (PerfCap in nvidia-smi)
    • TPU metrics: Cloud Monitoring for TPU utilization, MXU utilization, memory pressure

    Health Checks¶

    • HTTP /healthz endpoint — returns OK if server is up and model loaded
    • Optional: periodic sample inference as deep health check

    Profiling¶

    • Nsight Systems / Nsight Compute for kernel-level GPU profiling (staging/maintenance only)
    • Feed DCGM metrics into HPA for auto-scaling decisions

    10. Security Hardening Without Performance Loss¶

    Key: Adopt defense-in-depth that avoids heavy performance-killing measures. Segment networks, minimize privileges, keep software updated — these have essentially zero performance penalty. Concrete example: a team put GPU inference servers behind Nginx for TLS/auth offload — GPU machines saw only plaintext on fast internal network; end-to-end latency impact was only 1-2ms.

    Zero/Low-Cost Security Measures¶

    Measure Performance Impact Details
    Least privilege None Non-root containers; restrict GPU device access to serving process only; K8s PodSecurityPolicies
    Network segmentation None (may improve) Separate VLAN/subnet for GPU servers ("inferencing DMZ"); only API port open for ingress
    Firewall/DDoS Negligible iptables/nftables with xdp offloads; rate limiter or Cloud Armor in front
    Secure boot + firmware None UEFI Secure Boot; NVIDIA A100 hardware root-of-trust for firmware integrity
    SELinux/AppArmor Few percent (not on GPU path) Enforcing mode with tuned policies; CUDA libraries have appropriate SELinux contexts in RHEL
    Disk encryption Negligible AES-NI hardware acceleration; encrypt model files at rest; ensure memory zeroed on release
    API auth Microseconds/request OAuth tokens or API keys; offload to gateway (Kong, Envoy) to keep model server hot path clean
    Secret management None K8s secrets or Vault; never bake keys into images
    Audit logging Negligible Log model loads, container starts, critical syscalls (auditd/falco watching narrow event set)
    Disable swap None Prevents swapping model to disk (performance disaster); ensure sufficient RAM

    Measures with Some Cost¶

    • Trusted Execution Environments (AMD SEV, Intel TDX): Single-digit percent overhead for memory encryption; evaluate if processing sensitive inputs
    • Kata Containers / gVisor: Syscall overhead (mainly CPU path); minor for GPU-bound workloads
    • MIG for multi-tenant isolation: Strong fault isolation but not a full security boundary against side-channel attacks; for hostile multi-tenant, use vGPU (NVIDIA vCS/GRID) with per-VM virtual GPU
    • Kernel Spectre/Meltdown mitigations: Keep enabled unless air-gapped; few percent cost
