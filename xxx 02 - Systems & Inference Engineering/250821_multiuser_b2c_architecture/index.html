    Multi-User B2C App Architectural Guidance¶

    Full-stack reference architecture for a multi-user B2C generative-AI application. Balances rapid delivery, security/compliance, and cost-efficiency.

    Opening Briefing¶

    The defining architectural tension in multi-user generative-AI applications is not microservices versus monolith, nor is it which LLM provider to call. It is that every interesting design decision is downstream of a single economic reality: unmanaged token consumption at B2C scale will bankrupt the product before it finds market fit. A naive deployment serving 50,000 daily active users at 1,500 tokens per request reaches 750 million tokens per day, which at GPT-3.5 pricing alone translates to roughly $45,000 per month. The entire system architecture — caching layers, model routing, prompt engineering, even the authorization model — must be understood as a token-cost containment system that happens to also serve users.

    This constraint produces a specific technical shape. Semantic caching with normalized prompt hashing (incorporating prompt version and model ID into the key) targets 10-20% LLM hit rates, while request coalescing via Redis locks ensures concurrent identical queries share a single upstream call. Policy-based model routing splits traffic between GPT-3.5 for free-tier users and GPT-4 for paid subscribers, making the billing tier an architectural boundary rather than merely a product decision. The modular monolith pattern is not a compromise but a deliberate choice: at fewer than ten engineers, in-process function calls and domain events eliminate the network overhead and operational complexity that would otherwise consume the same team bandwidth needed to tune prompt templates, manage embedding lifecycles, and build the evaluation harness that keeps hallucination rates in check.

    The second structural insight is that PostgreSQL Row-Level Security operates as the trust boundary, not just a data-access convenience. Setting app.current_tenant per connection and forcing RLS on a non-superuser role means tenant isolation is enforced at the database engine level, surviving any application-layer bug. This decision cascades: it dictates pooled tenancy with a tenant_id column, constrains connection pooling to tenant-aware session variables, and makes the path from shared-schema to schema-per-tenant a migration rather than a rewrite. Combined with the STRIDE-informed principle of treating the LLM itself as an untrusted actor — where tool-call outputs are validated, prompt injection inputs are structurally separated from system instructions, and a remote kill-switch can disable generative features entirely — the architecture establishes defense in depth across both the data plane and the inference plane.

    What follows is the full reference design: component selection with explicit trade-offs, the generative-AI pattern catalog from batching through guardrails, security and compliance posture mapped to OWASP and STRIDE, observability with LLM-specific telemetry (tokens per span, cost per day, prompt hash attribution), and a 30/60/90-day delivery roadmap that sequences the vertical slice, hardening, and scale phases against concrete milestones.

    Reference Architecture Overview¶

    Key: Start with a modular monolith fronted by a Backend-for-Frontend (BFF). Core AI logic lives server-side, never directly exposed to clients. Ship a vertical slice fast, extract microservices later via the Strangler Fig pattern.

    Component Technology Role
    Web client Next.js (React) PWA UI/UX, calls backend over HTTPS
    Mobile client React Native / Flutter Same API surface as web
    API Gateway / BFF Node.js Express / Fastify Auth, rate limiting, SSR, routing
    Backend monolith NestJS / Fastify (TypeScript) Auth, business logic, AI orchestration
    Primary DB PostgreSQL (RDS / Cloud SQL) User data, content, metadata; RLS for tenant isolation
    Vector DB PGVector (start) or Qdrant/Weaviate/Pinecone Semantic search, hybrid search (dense + BM25)
    Cache Redis Session tokens, config flags, semantic LLM response cache
    Object storage S3 + CDN (CloudFront) User uploads via pre-signed URLs
    Queue AWS SQS / RabbitMQ Async jobs, event bus, Transactional Outbox Pattern
    LLM OpenAI GPT-4/3.5 (primary), Anthropic (fallback) Generative responses
    Auth provider Auth0 / Cognito / Firebase Auth OIDC, social login, passkeys
    Payments Stripe Subscriptions, webhooks
    Observability OpenTelemetry -> Prometheus/Grafana or Datadog Logs, metrics, distributed traces

    Data flow: Clients -> BFF -> Monolith -> {Postgres, VectorDB, Redis, S3, LLM API, Queue}. No direct DB or LLM access from clients.

    Core Decisions & Trade-Offs¶

    Monolith vs Microservices¶

    • Modular monolith for <10 devs. High cohesion, clear module boundaries (auth, payments, AI, content).
    • Internal comms via function calls + domain events (in-memory). Strangler Fig to extract services later.
    • Defer microservices until specific scaling bottlenecks appear.

    Backend Language¶

    • TypeScript + Node.js (NestJS or Fastify) recommended for full-stack JS teams. Shared types with frontend, huge ecosystem.
    • Go (Fiber, chi) for max performance. Python (FastAPI) for ML integration.
    • Async, non-blocking I/O required.

    API Style¶

    • RESTful JSON API with /api/v1/... versioning as primary interface.
    • REST with OpenAPI spec; add GraphQL/tRPC only if needed for complex client querying.
    • All writes idempotent via Idempotency-Key header. Cursor-based pagination.
    • Rate limiting per IP/user token (e.g., 100 req/min; adaptive quotas for AI endpoints).

    Identity & Authentication¶

    • OAuth 2.0 / OIDC with external IdP (Auth0, Cognito, Firebase Auth).
    • Authorization Code flow with PKCE for web/mobile.
    • Refresh token rotation: each refresh invalidates the previous token.
    • Short-lived JWTs (access tokens), HttpOnly cookies, secure storage on mobile.
    • WebAuthn passkeys for phishing-resistant passwordless login. Amazon: 175M passkeys created; industry data shows 98% login success vs 32% for passwords.
    • Magic link login as alternative.

    Authorization & Multi-Tenancy¶

    • Layered RBAC + ABAC model.
    • PostgreSQL Row Level Security (RLS) for tenant data isolation: SET app.current_tenant = '<tenant-uuid>' on each connection.
    • Pooled tenancy (shared schema, tenant_id column) to start. Migrate to schema-per-tenant or separate DB for enterprise customers later.
    • Connect as non-superuser to avoid bypassing RLS. FORCE ROW LEVEL SECURITY on tables.
    ALTER TABLE items ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON items
  USING (tenant_id = current_setting('app.current_tenant'));

    Primary Database (PostgreSQL)¶

    • ACID, JSONB, full-text search, CTEs, window functions.
    • Cloud-native deployment (RDS/Cloud SQL), automatic backups, PITR, multi-AZ.
    • Partitioning time-series tables (events, logs) by month.
    • Connection pool mandatory (PgBouncer / RDS Proxy, pool size 5-10 per instance).
    • Read replicas for scaling reads. Eventual consistency <1s lag acceptable.
    • Indexes: monitor via pg_stat_statements. VACUUM and auto-analyze.
    • Logical Decoding / CDC via Debezium for syncing to analytics/search.

    Vector Search & AI Data¶

    • Start with pgvector in Postgres; graduate to Qdrant/Weaviate/Pinecone at scale.
    • Hybrid search: dense embeddings + BM25 keyword scoring. Merge via RRF (Reciprocal Rank Fusion) or weighted score. Optional cross-encoder reranking.
    • OpenAI text-embedding-ada-002 (1536-dim). Chunk text to ~500 tokens, store sparse vector (BM25) alongside.
    • Embedding lifecycle: background job re-embeds on doc update; TTL for stale embeddings.
    • HNSW or IVFFlat index on embeddings.

    Caching Strategy¶

    • Redis as cache tier: application-level caching, session caching, AI response caching.
    • Semantic cache: hash normalized prompt (lowercase, strip whitespace, include prompt version + model ID) -> cached answer. Keys like chat:answer:{promptHash}.
    • Cache TTL: DB query results ~5 min, AI answers ~1 hour.
    • Request coalescing: lock on key (e.g., explain:42) so concurrent identical requests share one LLM call.
    • CDN edge caching for public GET endpoints and static content.

    LLM Vendor & Integration¶

    • Abstract LLM service module for multi-vendor support. Primary: OpenAI. Fallback: Anthropic.
    • Policy-based routing: cheaper model for trivial queries, premium model for complex.
    • Retry with exponential backoff on transient errors. Circuit breaker (5 failures -> stop calling, queue or return graceful error).

    Generative AI Patterns¶

    Pattern Detail
    Batching Batch embedding calls (100 texts per API call)
    Streaming SSE / text/event-stream for token-by-token output, first token <500ms
    Prompt Templates Version-controlled templates with placeholders; version ID in prompt for A/B eval
    RAG Top-N chunks from vector DB injected into system prompt. Guardrail instructions in system prompt. User input in data fields to prevent prompt injection
    Session Memory Sliding window (last N turns) + rolling summary of older messages. Token budget ~2000 tokens per session context
    Tool Use / Function Calling JSON schema interfaces, sandboxed execution, idempotent tool calls, security layer validates LLM tool requests
    Context Length Guard Truncate/summarize if input + retrieved context nears model limit

    Key: Compute a cache key from normalized prompt to avoid redundant LLM calls. Include prompt version + model ID in key so stale answers are never reused after model/prompt changes.

    Guardrails for LLM¶

    • OpenAI function calling to constrain model actions (e.g., Calculator function for math).
    • Timeout: 10s for normal queries; abort and queue for background if hanging.
    • Cost control: estimate tokens per request (e.g., ~2600 total for GPT-3.5 = ~$0.005). Track usage per user in DB, enforce free tier quota (e.g., 50 queries/day).

    Memory Management¶

    • Store full conversation in DB. Send last 4 messages + summary to model.
    • Generate summaries via separate LLM call after every ~10 messages.
    • Vector-store old turns for retrieval if user references earlier context.

    Evals & Monitoring AI Quality¶

    • Offline test prompts (golden dataset) run periodically or in CI.
    • User feedback loop: thumbs up/down on answers; inspect high-downvote prompts.
    • A/B testing new models/prompts on small % of traffic.
    • Hallucination / toxicity checks: secondary classifier or moderation endpoint.
    • Model change log for prompt template and model version changes.

    Latency Optimization¶

    • Target: end-to-end <2s for normal answers. First token <500ms via streaming.
    • Speculative decoding: simultaneously call faster model; use if slower model's output isn't better.
    • Parallel operations: call external APIs concurrently after gathering context.
    • Minimize payload to LLM: omit irrelevant context, use IDs instead of long names.

    Cost Management¶

    • Log input/output tokens per request with model type. Alert if daily spend exceeds threshold.
    • Graceful degradation: if budget near exhaustion, switch to cheaper model or enforce stricter rate limits.
    • Per-tenant isolation of LLM concurrency limits.

    Security, Privacy & Compliance¶

    Application Security (OWASP Top 10)¶

    • Injection: parameterized queries / ORM. No shell commands with user input. LLM prompt injection: user content kept separate from system instructions, allow-list for tool commands.
    • Broken Auth/Session: robust OAuth, refresh token rotation, strong hashing (Argon2/bcrypt).
    • Sensitive Data Exposure: TLS everywhere, encryption at rest (RDS, S3), least-privilege module access, never log secrets/PII.
    • XSS: React auto-escapes; CSP (default-src 'self'; script-src only our domains). DOMPurify for any LLM/user HTML.
    • CSRF: SameSite cookies (Lax or Strict); Bearer token for API.
    • Supply Chain: pin versions, Sigstore/cosign for container images, npm audit in CI, SBOM.

    LLM-Specific Safety¶

    • Input filtering: catch "<ignore all instructions>", base64-encoded variants before LLM.
    • Output filtering: block/redact disallowed content (hate speech, etc.) via moderation endpoint.
    • Kill-switch: feature flag to remotely disable AI response feature.
    • For minors (<13): disable unsafe prompts, possibly route to more censored model.

    Threat Modeling (STRIDE)¶

    Threat Mitigation
    Spoofing Signed JWTs, mTLS between services
    Tampering Encrypted transit + rest, append-only audit logs, DB checksums
    Repudiation Audit logs with timestamps for all user/admin actions
    Information Disclosure Least privilege, scrub stack traces, no PII in error responses
    Denial of Service Rate limiting, auto-scaling, per-user LLM quota, Cloudflare/AWS Shield
    Elevation of Privilege Auth checks on every admin route, hide admin UI for non-admins, treat LLM as untrusted

    Data Privacy & Compliance¶

    • GDPR/CCPA: Right to Access (export), Right to Erasure (cascade delete + scramble logs). Data residency (EU servers for EU users).
    • COPPA: disallow <13 or require parental consent. Minimal data on young users.
    • SOC2 readiness: role-based access, logging, annual security training. Target Type I around month 6.
    • DPIA template for new features involving personal data. STRIDE threat modeling.
    • Audit logging: append-only table (audit_log), log all admin + system data access.

    Secrets & Key Management¶

    • All secrets in cloud secrets manager (AWS Secrets Manager / Vault). Never in code.
    • Envelope encryption via KMS for sensitive DB columns.
    • Key rotation schedule: JWT signing keys yearly, DB credentials per best practice, KMS CMK auto-rotation.
    • Short-lived credentials: IAM auth for RDS where feasible; STS tokens for AWS resources.

    Observability & Operational Excellence¶

    Logging¶

    • Structured JSON logs: timestamp, severity, request/trace ID, user ID, event details.
    • Centralized store (CloudWatch Logs / ELK / Datadog). Never log credit cards, passwords.

    Distributed Tracing¶

    • OpenTelemetry spans from request through DB, vector search, LLM call.
    • Custom attributes on LLM span: prompt_tokens, response_tokens, model name, prompt hash.

    Metrics¶

    Category Metrics
    RED (per endpoint) Rate (req/s), Errors (count/%), Duration (p50/p90/p99)
    USE (system) CPU, memory, DB connections, cache hit/miss, queue depth
    LLM Tokens/s, cost/day, success vs error rate
    Business AI chats/day, DAU, conversion funnel

    Alerting¶

    • High error rate (>5% in 5 min) -> page on-call.
    • LLM cost spike -> alert to investigate.
    • p95 latency >5s -> alert (vector DB or LLM issue).
    • DB CPU >80% for 10 min -> scale alert.
    • Multiple failed logins -> security alert.

    SLOs & Error Budgets¶

    • Chat response SLO: 99% success, 95% delivered <4s. Error budget: 1% failure, 5% slow.
    • Auth SLO: 99.9% login success <1s.
    • Review monthly; if budget nearly exhausted, freeze features and harden.

    Incident Response & Runbooks¶

    • "LLM API down": switch to backup model, serve cached answers, banner to users.
    • "DB connection issues": failover to replica (auto with multi-AZ RDS).
    • "Memory leak": roll restart, then profile.
    • "Security incident (leaked key)": revoke immediately, replace, redeploy, assess impact.
    • Severity levels: Sev1 = major outage (notify all), Sev3 = minor (fix next business day).

    Deployment & Ops¶

    • Canary releases: route small % to new version, watch error/latency metrics.
    • Blue-green deploy for instant rollback.
    • Feature flags (LaunchDarkly or config JSON) for risky features.
    • IaC (Terraform/Pulumi) for all infrastructure. CI/CD via GitHub Actions.
    • Chaos engineering in staging: shut down Redis, simulate LLM high latency, verify graceful degradation.

    Frontend & Mobile¶

    Web (Next.js 13+)¶

    • App Router with Server Components and SSR for SEO-critical pages.
    • SSG/ISR for marketing/landing pages. CSR for interactive dashboard.
    • React Query (TanStack Query) for data fetching, caching, stale-while-revalidate.
    • Core Web Vitals: TTFB p95 <200ms, automatic code-splitting, lazy image loading (<Image>), prefetching linked pages.

    Mobile (React Native + Expo)¶

    • Offline-first for certain features (local SQLite via WatermelonDB/Expo SQLite).
    • Conflict resolution: last-write-wins for MVP.
    • Certificate Pinning for API calls. Sensitive data in secure keychain. Device auth for PII screens.
    • Push notifications: APNS (iOS), FCM (Android) via Expo.

    Real-Time¶

    • WebSockets or SSE for streaming chat responses. Web: EventSource/fetch streaming. RN: fetch stream or socket.

    Performance & Cost Management¶

    Capacity Assumptions¶

    • Target: 50,000 DAU year 1, peak 200 concurrent requests.
    • ~500k LLM requests/day, ~6 req/s steady, ~25 req/s peak.
    • Latency goals: web page <1s initial, full load <2s; AI first token 1-2s, full answer <5s (p95).

    Backend Throughput¶

    • Node.js instance handles ~50 req/s. 2-4 instances for peak.
    • Auto-scale: CPU >70% or queue latency increase -> scale up.
    • Load testing with k6/JMeter: simulate 100 concurrent chat users, stress test to find bottlenecks.

    Token Budgeting¶

    • 500k LLM req/day x 1500 tokens avg = 750M tokens/day.
    • At $0.002/1K tokens (GPT-3.5): ~$1500/day or ~$45k/month.
    • Target: <$10k/month at initial scale via caching, shorter prompts, cheaper models for low-tier users.
    • GPT-3.5 for free tier, GPT-4 for paid. Batch embeddings (100 per call).

    Monthly Cost Breakdown (MVP)¶

    Item Estimate
    LLM $5k
    Infra (servers, DB, cache) $1.5k
    Monitoring $500
    Total ~$7k/month

    Caching Efficacy Targets¶

    • Redis DB cache: high hit rate on common queries (5 min TTL).
    • LLM result cache: 10-20% hit rate target.
    • CDN: >90% hit for static assets.

    Graceful Degradation¶

    • LLM down: show message, disable input, serve cached Q&As.
    • Budget exhausted: switch to cheaper model, enforce stricter rate limits.
    • Set monthly cap on API usage; if hit, system stops calling LLM and notifies users.

    Delivery Roadmap (30/60/90 Day Plan)¶

    Day 0-30: MVP Vertical Slice¶

    Week 1-2: Repo setup, CI/CD, cloud infra (VPC, RDS Postgres, Redis, EC2/container), baseline Auth0 integration, Next.js frontend skeleton, NestJS backend skeleton, basic GET /api/hello protected endpoint.

    Week 3-4: Core AI feature (POST /api/v1/chat/completions -> OpenAI), vector search (pgvector or Qdrant) with retrieval, Redis caching for AI responses, request coalescing, streaming chat UI, conversation history, security tasks (rate limiting, CORS, SameSite cookies), compliance basics (privacy policy, account deletion), OpenTelemetry traces, unit tests, basic load test.

    Optionally: Stripe Checkout for subscription (or flag everyone as "paid user" initially).

    Key: End of Day 30 = MVP v1.0: deployed on production URL, user can sign up, log in, chat with AI using retrieval. Basic security in place, minimal observability.

    Day 31-60: Hardening & Feature Completion¶

    Week 5-6: Load testing (k6, 100 concurrent chats), CDN, OpenTelemetry Collector + Jaeger/APM, content moderation (input/output filtering), feature flags, UI/UX polish (loading states, error messages, mobile app parity), multi-turn conversation context with summarization.

    Week 7-8: Security audit (OWASP ASVS checklist, CSP, HSTS, X-Frame-Options), secrets rotation, data deletion (GDPR compliance), Stripe full integration (webhooks, upgrade/downgrade, usage limits), FAQ/help in vector DB, E2E tests (Playwright/Cypress), chaos test (disable Redis/vector DB in staging).

    Key: End of Day 60 = Beta Launch v1.5: all critical features, compliance checks passed, observability in place, ready for real users.

    Day 61-90: Scale, Optimize, Iterate¶

    Week 9-10: Integrate beta feedback, performance/cost optimization (more caching, smaller models, read replicas), automate ops (backup/restore scripts, IaC for all manual infra), chaos testing in staging.

    Week 11-12: Third-party security test / pentest-lite, cross-region DB replication, final load test (2x expected), launch prep (on-call schedule, status page, monitoring dashboards).

    Key: End of Day 90 = Version 2.0 ready for general launch: stable, tested with real users, scalable architecture, monitoring and on-call in place.

    Post-90 Days: Growth features, mobile offline mode, SOC2 Type I (~month 6), modularize into microservices if bottlenecks appear, fine-tune/self-host models if cost-justified.

    Checklists¶

    Pre-Launch Security Checklist¶

    • OAuth flow with PKCE, state param verified; refresh tokens HttpOnly
    • RLS policies verified (query as one tenant, can't see others)
    • All APIs validate inputs (schema validation library)
    • Output encoding: tested XSS with <script>alert()</script>
    • No critical vulns in npm audit
    • Secrets not in repo, loaded from secure storage
    • TLS + HSTS header, no mixed content
    • CSP set, <img src=javascript:...> blocked
    • Security headers: X-Frame-Options SAMEORIGIN, X-Content-Type-Options nosniff
    • Rate limiting tested (HTTP 429 on burst)
    • No debug endpoints in prod, admin panel behind auth
    • LLM prompt injection tested ("Ignore all instructions" blocked/detected)
    • DB encryption + S3 encryption enabled
    • Backups scheduled and tested restore
    • Privacy policy, terms accessible; COPPA if minors; GDPR DSR tested
    • Incident response plan documented

    Pre-Launch Performance Checklist¶

    • Load tested at 2x expected volume, no crashes
    • p95 latency under targets (5s for chat)
    • Stress test: identified bottleneck and scaling plan
    • Cache working (hits increase under load)
    • Queue: DLQ captures poison messages, backlog monitored
    • Failure injection: LLM offline -> graceful error message
    • Cold start / deploy impact < X seconds downtime (blue-green or canary)

    Day-2 Operations Checklist¶

    • Dashboards live (latency, errors, traffic, costs)
    • Alerts tested (force 500, verify alert received)
    • On-call schedule defined
    • Runbooks stored and recently verified
    • Scaling procedures documented (AWS ASG / push button)
    • Weekly cost review cadence set
    • Feature flag kill-switch tested in prod
    • Support channel (email/Discord) for bug reports

    Risk Assessment¶

    Risk Mitigation
    LLM API outage (e.g., OpenAI down for a day) Backup model / provider; degrade to cached Q&As
    Viral growth overloads system Rate limiting + queuing; quickly scale via IaC
    Prompt injection -> offensive public output Content moderation on outputs, user feedback channel, curated prompt allow-list
    Data leak (cross-tenant) RLS thoroughly tested; testing phase attempts cross-access
    High latency / cost from inefficient prompts Monitor token usage; trim context; optimize prompts
    Team burnout Enforce rest after launch; rotate on-call; rely on automation

    Appendices¶

    A. Database Schema (ERD)¶

    CREATE TABLE tenants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  email TEXT UNIQUE NOT NULL,
  name TEXT,
  role TEXT CHECK(role IN ('user','admin')) DEFAULT 'user',
  auth_provider_id TEXT,
  created_at TIMESTAMPTZ DEFAULT now(),
  last_login TIMESTAMPTZ
);

CREATE TABLE conversations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL,
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  conversation_id UUID REFERENCES conversations(id) ON DELETE CASCADE,
  role TEXT CHECK(role IN ('user','assistant','system')),
  content TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE doc_embeddings (
  id BIGSERIAL PRIMARY KEY,
  tenant_id UUID,
  doc_id UUID,
  content TEXT,
  embedding VECTOR(1536),
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ivfflat_idx ON doc_embeddings USING ivfflat (embedding vector_cosine_ops) WITH (lists=100);

CREATE TABLE audit_log (
  id BIGSERIAL PRIMARY KEY,
  timestamp TIMESTAMPTZ DEFAULT now(),
  actor_id UUID,
  action TEXT,
  details JSONB
);

    RLS policies on conversations, messages, and doc_embeddings enforce tenant/owner isolation.

    B. Redis Cache Key Strategy¶

    Key Pattern Purpose TTL
    session:{sessionId} User session/token mapping Session duration
    ai:completion:{promptHash} -> {answer, timestamp} AI response cache ~1 hour
    tenant:{tid}:recent_docs Cached doc list per tenant ~1 day
    myapp:ai_answer:{hash} Global AI answer cache ~1 hour
    myapp:user:{userID}:conversation:{convID}:last_n Recent messages cache Short

    Cache invalidation: short TTLs (simpler), or version tags per doc. Admin API/command to clear all caches on model upgrade or deployment.
