    GPU & Datacenter Infrastructure¶

    Opening Briefing¶

    The defining constraint of modern AI infrastructure is not raw compute but rather the isolation-utilization trade-off: every mechanism that guarantees one tenant cannot interfere with another simultaneously reduces the fraction of silicon doing useful work. This tension governs decisions from GPU partitioning all the way up through API-layer metering, and it explains why the industry's most consequential hardware advances are not faster chips but smarter ways to share them. NVIDIA's Multi-Instance GPU technology, which firmware-partitions an H100 into up to seven isolated instances each with dedicated streaming multiprocessors, memory controllers, and L2 cache, delivers as much as a 7x improvement in aggregate utilization over whole-GPU passthrough while maintaining hardware-enforced separation that software time-slicing cannot match. MIG carries no additional licensing cost, whereas vGPU requires per-GPU datacenter licenses — a detail that reshapes the economics of every multi-tenant GPU cloud built on Ampere or Hopper silicon.

    Groq's Language Processing Unit offers a structurally different resolution to the same tension. By replacing HBM with 230 MB of on-chip SRAM per die running at 80 TB/s internal bandwidth, and by scheduling every operation and data movement at compile time rather than runtime, the LPU eliminates caches, branch predictors, and kernel launch variability entirely. The result is that tail latency equals average latency — a property no GPU architecture can claim. A single GroqRack packs 64 chips into a standard 42U cabinet delivering 48 POPS INT8 at roughly 30 kW, air-cooled, with no liquid plumbing or exotic networking. The RealScale interconnect connects all 64 chips via 704 direct links in a switchless mesh with 1.6 microsecond end-to-end latency and 3.2 TB/s bisection bandwidth, and it has been proven at 20,000 LPUs operating as a single cluster. Groq stood up that Saudi deployment in eight days. The European demo pod took thirty-four. These timelines are not marketing; they follow directly from deterministic hardware that requires no runtime debugging.

    The second-order consequence is that capacity planning becomes arithmetic rather than stochastic modeling. When every token costs a fixed, compile-time-known number of cycles, doubling racks exactly doubles throughput, SLA guarantees reduce to simple multiplication, and billing can be tied to precise per-token attribution without the high-cardinality observability burden that Together AI and others have publicly described as a major engineering challenge on GPU-based stacks. This predictability collapses the distance between raw infrastructure and commercial service: the same isolation, metering, and multi-tenancy patterns that define a GPU IaaS platform reappear at the API layer of a vLLM-based inference business, differing only in the abstraction boundary.

    This document traces that full arc — from GPU virtualization and datacenter fabric through purpose-built inference silicon to the billing and compliance machinery required to sell tokens commercially — treating them as layers of a single system rather than independent domains.

    Part I — GPU-as-a-Service Stack¶

    1. GPU Virtualization & Server Virtualization¶

    Access Modes¶

    Mode Description Isolation Sharing
    Bare-metal (BMaaS) Tenant gets entire physical node with GPUs Strongest (no shared HW) None
    VM (passthrough) Full GPU assigned to one VM via PCIe passthrough Strong (hypervisor boundary) None — 1 GPU = 1 tenant
    NVIDIA vGPU Software time-slices or partitions GPU memory across VMs/containers Moderate (framebuffer isolation, not full compute isolation) Yes — multiple tenants per GPU
    NVIDIA MIG Hardware-partitions A100/H100 into up to 7 isolated instances with dedicated SMs, memory, cache Strong (firmware-enforced) Yes — hardware-level

    Key: MIG is the game-changer for multi-tenancy — hardware-enforced isolation, predictable performance (no time-slicing jitter), up to 7x better utilization by right-sizing GPU slices to workloads. Available on A100/H100 only. Older GPUs use vGPU (requires NVIDIA datacenter licenses) or passthrough.

    Hypervisors¶

    • KVM/QEMU (open-source, Linux built-in) — robust, free, used by most private GPU clouds
    • Xen — historically used by AWS
    • VMware ESXi/vSphere — commercial, polished management, live migration, licensing cost
    • Both KVM and Xen support PCIe GPU passthrough; for vGPU/MIG, hypervisor loads NVIDIA drivers

    Bare-Metal Provisioning¶

    • OpenStack Ironic — bare-metal provisioning service for "hard isolation" scenarios
    • HPE OneView, Canonical MAAS — vendor tools for physical GPU node allocation on demand

    2. Container & VM Orchestration Layer¶

    VM Orchestration — OpenStack¶

    • Nova compute service supports GPU passthrough and vGPU flavors
    • Neutron handles multi-tenant networking; Keystone provides identity/RBAC
    • Horizon dashboard for self-service (can be extended to show GPU-specific resources)
    • Operators define GPU flavors (e.g., "1 GPU", "1 MIG slice") — tenants launch via web/API

    Container Orchestration — Kubernetes¶

    • NVIDIA K8s device plugin advertises GPUs to scheduler; supports MIG partitions as discrete devices
    • Containerized AI workflows (TensorFlow/PyTorch in Docker) make K8s a natural fit
    • Red Hat OpenShift — enterprise K8s positioned as multi-tenant GPU-as-a-Service platform

    Integration Patterns¶

    • K8s-first: Everything as containers on a multi-tenant K8s cluster
    • VM-first (OpenStack): Mimic AWS-like IaaS — tenants get GPU VMs, possibly running K8s inside
    • Hybrid: OpenStack provisions GPU-backed VMs, each running K8s nodes; tenants get whole VMs or K8s clusters on demand

    Other Orchestrators¶

    • OpenShift — K8s + multitenancy + pipeline integration (commercial)
    • VMware vSphere/vCenter — VM management with BitFusion GPU sharing (proprietary)
    • OpenNebula, CloudStack — simpler open-source alternatives to OpenStack
    • Rancher, Kubeflow — container platforms / ML toolkit on K8s

    3. Resource Provisioning & Scheduling¶

    GPU Scheduling in Kubernetes¶

    Scheduler Type Key Feature
    Default K8s scheduler Built-in GPU-aware resource counting only
    Kueue (Kubernetes Elastic Queue) Extension Quota-based fair sharing, multi-tenancy via quotas, queuing when resources full
    Volcano Extension Gang scheduling, topology-aware placement, virtual GPU slicing, backfilling

    HPC Schedulers¶

    • Slurm — widely used in HPC/AI clusters; integrates with MIG; supports fair share, preemption
    • PBS Pro, IBM Spectrum LSF, Grid Engine — alternatives for batch environments

    Dynamic Provisioning & Autoscaling¶

    • KEDA (Kubernetes Event-Driven Autoscaling) — scales GPU nodes based on queue metrics (pending jobs in Kueue)
    • Scale-up latency: GPU node provisioning takes minutes — use warm pools or over-provision
    • Goal: don't pay for idle GPUs

    Resource Quotas & Fairness¶

    • OpenStack: tenant quotas on GPU instance count
    • K8s: ResourceQuota, LimitRange, Kueue scheduler quotas per namespace/tenant
    • Multi-tenant GPU orchestration improves aggregate utilization by 30-40% through intelligent packing

    Workload Placement¶

    • Multi-GPU jobs need NVLink-connected GPUs on same server — topology-aware scheduling critical
    • K8s topology spread constraints; Slurm can constrain to same network switch for parallel jobs

    4. Multitenancy & Isolation Mechanisms¶

    Isolation Spectrum¶

    Dimension Hard Isolation Soft Isolation
    Compute Dedicated physical servers/VMs, separate K8s clusters Shared K8s cluster with namespaces + quotas
    GPU Passthrough (whole GPU per tenant) or MIG (firmware-enforced) vGPU time-slicing (framebuffer isolation only)
    Network Separate VLANs/NICs, dedicated InfiniBand PKeys, physical separation VXLAN overlays, K8s NetworkPolicy, EVPN virtual routers
    Storage Separate Ceph pools, dedicated credentials, per-tenant encryption keys Namespace-scoped volumes, access controls, VRF

    GPU Isolation Details¶

    • MIG: Each slice has own SMs, memory, cache — firmware guarantees; one tenant's high memory usage won't starve others
    • vGPU: Isolates framebuffers and contexts but time-sliced compute isn't fully isolated
    • Without MIG/vGPU: Dedicate whole GPUs to tenants (passthrough) to prevent data leakage

    Compute Isolation Enhancements¶

    • Kata Containers — lightweight VMs wrapping containers for extra isolation layer
    • gVisor — user-space kernel for container sandboxing
    • Separate node pools per tenant or even separate K8s clusters

    RBAC & Auth¶

    • OpenStack Keystone or LDAP/AD for identity
    • Hierarchical RBAC: org admins see all projects, project users see only their resources
    • SSO/OAuth support for enterprise integration

    Resource Throttling¶

    • CPU/RAM cgroups, GPU time quotas, disk IOPS limits per tenant
    • MIG or vGPU QoS caps ensure no single container exceeds its GPU share

    5. Billing & Metering¶

    Usage Metering¶

    • Track per-tenant GPU-hours at minimum; also CPU hours, memory GB, network egress, storage GB
    • OpenStack: Ceilometer telemetry service collects resource usage events; extend for GPU allocation metering
    • Kubernetes: Prometheus metrics (GPU utilization, pod lifetimes) aggregated per tenant namespace; Kubecost for cost reports

    Billing for Shared GPUs (MIG)¶

    • Bill per GPU-memory fraction or per MIG slice (e.g., 20% of GPU = 0.2 GPU-hour)
    • Alternative: bill based on actual utilization via NVIDIA DCGM (Data Center GPU Manager) per-process metrics
    • Simpler approach: treat allocated fraction as billable unit (like vCPUs)

    Commercial Metering¶

    • Rafay platform: built-in GPU usage metering + cost attribution APIs, chargeback enforcement, integrates with finance systems
    • CloudKitty (open-source): converts Ceilometer metrics to bills (e.g., X GPU-hours at $Y/hr)
    • Stripe integration for public cloud; internal accounting for private cloud

    Licensing Costs¶

    • NVIDIA vGPU requires per-GPU datacenter licenses — pass to tenant or absorb in price
    • MIG has no extra license cost (built into A100/H100)

    6. Storage & Networking for GPU Workloads¶

    Storage¶

    Type Solution Use Case
    Local NVMe Direct-attached SSDs Cache, scratch, data shuffling during training
    Distributed parallel FS Lustre, BeeGFS, IBM Spectrum Scale (GPFS) Multi-petabyte shared datasets, multi-node training
    Object storage MinIO (S3-compatible), Ceph RGW Datasets, model checkpoints (write-once-read-many)
    Block storage Ceph RBD, OpenStack Cinder VM/container persistent volumes
    GPUDirect Storage (GDS) NVIDIA GDS DMA from NVMe/NIC directly to GPU memory, bypassing CPU

    Key: Storage goal is to keep GPUs fed with data. Parallel filesystems (Lustre, BeeGFS) deliver tens of GB/s aggregate bandwidth. GPUDirect Storage eliminates CPU overhead for streaming large batches.

    Networking¶

    Scope Technology Bandwidth Notes
    Intra-server GPU NVLink/NVSwitch 900 GB/s (H100) Mandatory for tensor parallelism
    Inter-node GPU InfiniBand NDR 400 Gb/s Best for distributed training; RDMA; requires IB fabric management
    Inter-node GPU RoCEv2 Ethernet 100-200 GbE Easier IP integration; lossless Ethernet fabric needed; adaptive routing
    Tenant overlay EVPN/VXLAN — Per-tenant L2 networks; firewalls/security groups at virtual router
    Client access Standard Ethernet — Frontend for API/portal access; direct connect for high-bandwidth data push

    Topology¶

    • Non-blocking leaf-spine fabric (100GbE or IB in Clos topology) — avoid oversubscription
    • Schedule TP groups on NVLink-connected GPUs; avoid PCIe-only paths
    • SR-IOV for VMs/containers to get near line-rate NIC performance

    7. Security & Access Control¶

    Defense in Depth Layers¶

    Layer Mechanism
    Authentication Keystone / LDAP / AD / SSO (SAML/OAuth); per-user/project API tokens
    Authorization (RBAC) Hierarchical roles (admin, member) in OpenStack projects / K8s namespaces
    API security TLS on all APIs; audit logging on all API calls
    Image security Container/VM image scanning; curated base image catalog with NVIDIA drivers
    GPU isolation MIG (firmware-enforced), IOMMU, SR-IOV for device-level address space isolation
    Compute isolation VMs, Kata Containers, gVisor for container workloads
    Network isolation VLAN/VXLAN segmentation, K8s NetworkPolicy, InfiniBand PKey partitioning
    Storage encryption At-rest encryption (Ceph, LUKS volumes); KMS integration (Vault or cloud KMS)
    In-transit encryption TLS/IPsec for Ethernet; IB uses partition keys (not encrypted by default)
    Hardware security Secure boot, TPMs, firmware attestation on server hardware
    Monitoring/auditing GPU utilization anomaly detection; API audit logs; console session recording
    Multi-tenancy policies Affinity/anti-affinity rules to prevent co-tenancy on same host (compliance)

    8. Developer/User Access Portal & APIs¶

    Portal Features¶

    • Self-service GUI: Launch GPU instances, attach volumes, view usage — OpenStack Horizon or custom portal
    • Service catalog: Pre-built environments (PyTorch + CUDA images), MIG size options ("small GPU 10GB", "medium 20GB", "full GPU")
    • Jupyter notebooks: One-click notebook environments on GPU pods/VMs (Kubeflow Notebook Controller)
    • Project/team management: Invite members, assign roles, view combined usage; SAML/SSO integration
    • Notifications: "Job completed", "80% of GPU quota reached", usage reports downloadable
    • Documentation & support: Docs, examples, support channel

    APIs & CLI¶

    • OpenStack REST APIs + CLI; K8s APIs + kubectl
    • Custom CLI for GPU cloud (e.g., "submit training job with 4 GPUs" without low-level K8s details)
    • Terraform providers for infrastructure-as-code

    Commercial Portals¶

    • NVIDIA Base Command Platform — polished web UI for DGX GPU clusters (job scheduling, dataset management)
    • NVIDIA DGX Spark (Asus Ascent GX10) — 128 GB DDR5 consumer-grade unit capable of running Qwen3.5-122B locally at 100 W; benchmarked at 27-29 tok/s generation and 1,500 tok/s prefill at 200K context (March 2026)
    • Rafay — branded developer portals and service catalogs for GPU environments
    • Morpheus Data / CloudBolt — cloud management portals supporting VMware/OpenStack
    • Open OnDemand — open-source HPC portal (job submission, VNC sessions) adaptable for GPU

    9. Early Hyperscaler vs Modern GPU Stack¶

    Aspect Early (AWS/GCP ~2014) Modern GPU IaaS (2020s)
    GPU Virtualization Dedicated GPU per VM (passthrough only); no MIG; vGPU only for graphics MIG splits 1 GPU into 7 isolated instances; vGPU for time-slicing; fractional GPU billing
    Orchestration Proprietary VM orchestration (EC2 control plane); manual workload management K8s + cloud-native orchestration; auto-scaling GPU nodes; Kueue/Volcano for fair scheduling
    GPU Sharing 1 tenant per GPU; no fractional billing; GPU context switching within one VM only Fractional allocation as first-class; MIG/vGPU enable "GPU-small" instances; time-sliced sharing achieves >90% utilization
    Architecture Basic infrastructure — 10 Gbps Ethernet, general-purpose storage (EBS), single instances AI-optimized full stack — 100 Gbps+ Ethernet/InfiniBand with RDMA, parallel FS (Lustre), NVLink, distributed training support, integrated monitoring

    Key: A new GPU cloud built today can leapfrog what AWS/GCP started with by leveraging MIG, K8s orchestration, high-speed interconnects, and specialized scheduling — operating GPUs "as a service" rather than just raw VMs.

    10. Open-Source vs Commercial Components¶

    Component Open-Source Commercial Trade-off
    Hypervisor KVM/QEMU, Xen VMware ESXi Free + flexible vs polished + licensed + live migration
    GPU Partitioning MIG (free on A100/H100), MPS, K8s device plugins NVIDIA vGPU (GRID), Run:AI, VMware BitFusion MIG = HW isolation but A100/H100 only; vGPU = broader GPU support but licensing cost
    GPU Kernel Libraries Bastile (CUDA kernel library built on cuTile; claims faster performance than Liger for Qwen3 workloads; includes FlashAttention backward kernel; optimizations adapted from TileGym) NVIDIA cuDNN, cuBLAS Open-source kernel libraries narrowing gap with vendor-optimized libraries
    VM Orchestration OpenStack (Nova, Neutron, Cinder), CloudStack, OpenNebula VMware vCloud, HPE GreenLake OpenStack = feature-rich + free but complex; commercial = easier OOB but expensive
    Container Orchestration Kubernetes, OKD, Rancher, Kubeflow OpenShift, VMware Tanzu, Google Anthos, NVIDIA Base Command/DGX Cloud Upstream K8s = full control; enterprise distros add security/monitoring at subscription cost
    Scheduling Slurm, Volcano, Kueue, Apache YuniKorn, Airflow/Argo IBM LSF, Altair PBS Pro, Run:AI, AWS Batch Open-source = powerful but needs tuning; commercial = better GUIs/support
    Multitenancy/Isolation Linux cgroups/namespaces, SELinux, K8s NetworkPolicy, Kata Containers, Keycloak/Dex Rafay, Aarna GPU Cloud Management, VMware NSX, Cisco ACI Open-source covers most needs but requires ops expertise; commercial = pre-integrated
    Monitoring/Metering Prometheus + Grafana, Ceilometer/Gnocchi, ELK Stack, Kubecost Datadog, NewRelic, CloudWatch, NVIDIA Base Command Manager, Cisco Intersight Open-source = capable but scale/tuning required; commercial = turnkey GPU metrics
    Storage Ceph, Lustre, BeeGFS, MinIO, NFS DDN, WekaIO, VAST, NetApp, Dell EMC, Cloudian Open-source = low cost but tuning expertise needed; commercial = peak performance + support
    Networking Cumulus/SONiC, FRR, Open vSwitch/OVN, Calico/Cilium Cisco/Juniper, NVIDIA/Mellanox InfiniBand, VMware NSX, Cisco ACI InfiniBand = top GPU performance (NVIDIA ecosystem); Ethernet = multi-vendor flexibility
    User Portal OpenStack Horizon, K8s Dashboard, Open OnDemand, JupyterHub, custom React/Angular Rafay, Morpheus/CloudBolt, NVIDIA Base Command, vendor consoles Custom = maximum flexibility; commercial CMPs = faster time-to-market

    Key: The practical sweet spot is a hybrid approach — open-source foundation (KVM + OpenStack + K8s + Ceph + Prometheus) with selective commercial additions where they add significant value (e.g., NVIDIA vGPU licenses for older GPUs, OpenShift for enterprise security, commercial parallel FS for peak storage performance).

    AMD as Nvidia's Closest Competitor¶

    AMD is the only credible alternative to Nvidia for large-scale GPU training and inference, but the gap remains significant — and it is primarily a software gap, not a hardware gap. AMD's MI300X offers competitive specifications on paper (192 GB HBM3 memory, 5.3 TB/s memory bandwidth — exceeding the H100 on both counts), yet real-world performance consistently lags because ROCm, AMD's CUDA competitor, lacks the maturity, library breadth, and developer ecosystem that CUDA has built over two decades. Models that run out of the box on CUDA frequently require porting effort, debugging, and performance tuning on ROCm, and many third-party frameworks and tools still treat AMD support as experimental.

    AMD's most promising path is inference workloads, where the software requirements are simpler (fewer custom kernels, more standardized operations) and AMD's memory bandwidth advantages translate more directly into throughput gains. For training — especially distributed training across hundreds of GPUs requiring tight NCCL-equivalent communication — the software gap remains a serious obstacle. AMD's investment in kernel competitions and open-source tooling (see below) reflects a deliberate strategy to close the ecosystem gap through community engagement rather than trying to match Nvidia's internal library development dollar-for-dollar.

    GPU Kernel Ecosystem Development¶

    • AMD $1.1M kernel competition (GPU MODE, March 2026): targets MI355X GPUs for optimizing DeepSeek-R1-0528 and GPT-OSS-120B workloads. Phase 1 focuses on MXFP4 MoE, MLA Decode, and MXFP4 GEMM kernels. Submissions via Popcorn CLI without requiring MI355X hardware (remote evaluation infrastructure provided). This competition exemplifies AMD's strategy of leveraging open-source community contributions to narrow the kernel optimization gap with Nvidia's proprietary libraries.
    • Apple Neural Engine LoRA training (March 2026): demonstrated LoRA fine-tuning running entirely on Apple's Neural Engine at ~2.8 W, 192 gradient dispatches without GPU fallback. Known quirks: matmul compiles but doesn't execute, tensor spatial dimensions need multiples of 16, silent compilation failures after ~119 builds

    Why Alternative Silicon Is So Hard: Nvidia's Full-Stack Moat¶

    Before examining Groq's architecture, it is worth understanding the competitive landscape any alternative inference chip enters. Nvidia's dominance does not rest on any single component but on owning the entire stack end-to-end: chips (A100/H100/B200), intra-node interconnects (NVLink/NVSwitch), datacenter networking (Mellanox-derived InfiniBand and Spectrum-X Ethernet), software (the CUDA ecosystem with decades of libraries, frameworks, and developer tooling), and now custom silicon (Grace CPU for tightly coupled CPU-GPU nodes). Each layer reinforces the others — NVLink is designed for Nvidia GPUs, CUDA is optimized for Nvidia architectures, InfiniBand drivers integrate with NCCL — creating a platform where leaving any single layer means losing the benefits of all the others. The real moat is not performance on any benchmark but the integrated platform lock-in that makes migration painful and risky.

    This lock-in shapes the economics of every chip startup attempting to compete. The odds of a new entrant succeeding against Nvidia are estimated at less than 1%. The capital barrier alone is daunting: reaching tape-out and production for a competitive datacenter accelerator requires $500M or more before a single chip ships to a customer. Beyond capital, the software ecosystem gap is nearly insurmountable — CUDA has accumulated decades of optimized libraries (cuDNN, cuBLAS, CUTLASS, TensorRT, Triton), and replicating even a fraction of that ecosystem takes years. Customer risk aversion compounds the problem: procurement teams default to Nvidia because nobody gets fired for buying the market leader. Even well-funded startups — Graphcore (raised over $700M), Habana (acquired by Intel for $2B), SambaNova (raised $1.1B+) — have struggled to capture meaningful market share against this combination of capital requirements, ecosystem depth, and buyer inertia.

    Groq's strategy for navigating these barriers is instructive: rather than competing head-to-head on training (Nvidia's strongest position), Groq targets inference-only workloads where the software requirements are narrower, the performance metric (latency) is more differentiated, and the deterministic architecture offers a structural advantage no GPU can match.

    1. LPU Architecture Principles¶

    Principle Details
    Single-core, assembly-line execution One massive core with hundreds of functional units in Superlanes; instructions flow one direction, data flows orthogonally (systolic array); no complex on-chip control
    On-chip SRAM as primary memory 230 MB SRAM per GroqChip; ~80 TB/s internal memory bandwidth; no external DRAM; weights stored on-die; enables tensor parallelism across chips
    Deterministic, static scheduling Custom compiler schedules all ops and data movement at compile time; no caches, no branch predictors, no runtime kernel launch variability; every cycle accounted for; zero run-to-run variation
    Minimalistic inference-only design Purpose-built for linear algebra (matmuls); no training overhead; 10x better energy efficiency than GPUs per inference
    Compiler-first development Compiler designed before the chip hardware; hardware is straightforward for compiler to control; GroqFlow + SDK take models from frameworks and compile to optimized LPU binaries

    Key: Deterministic execution means fully predictable latency — tail latency equals average latency. Performance can be calculated in advance, simplifying capacity planning.

    Benchmarks¶

    Metric Result

    Key Performance Characteristics¶

    • Batch=1 excellence — single inference fully utilizes the LPU; no need to accumulate batches to hide memory latency (as GPUs require); latency does not suffer at batch=1
    • Tail latency ≈ average latency — deterministic execution eliminates jitter
    • Consistent latency under load — no cache misses or context switching; maintains performance as utilization increases
    • No speculative decoding needed — raw speed sufficient; simplifies serving stack
    • Multi-threaded decoding supported but hardware speed alone often sufficient

    Model Scaling¶

    • Models exceeding single chip's 230 MB SRAM are pipelined across multiple LPUs via RealScale
    • 64-chip GroqRack = ~14 GB SRAM total → hosts 100B+ parameter models at INT8 (~1 byte/param)
    • 4,000 LPUs ≈ 920 GB SRAM → supports 0.5-1 trillion parameter models
    • Practical LLM deployments: 70B Llama runs on 8-16 LPUs (quantized); GPT-3 175B on a handful of GroqNodes

    Model Optimization¶

    • GroqFlow compiles models from PyTorch/TensorFlow (often via ONNX) to LPU binaries
    • INT8 quantization with calibration — minimal accuracy loss; 4x throughput vs FP16; hardware natively benefits from INT8
    • TruePoint format maintains FP32 precision in INT representation
    • Supports Mixture-of-Experts (MoE) — compiler routes tokens to expert shards across chips
    • MLAgility tool for automated benchmarking across models
    • Model loading is an event (binary loaded to SRAM); switching models requires PCIe transfer (seconds) — better to pin models to dedicated LPU groups for multi-model serving

    Key: For LLM inference, performance tuning on Groq is about ensuring the model fits in on-chip memory and choosing the right number of LPUs. Once compiled, latency per token is fixed and predictable.

    Energy Supply: The Datacenter Buildout Bottleneck¶

    The limiting factor for AI datacenter expansion is increasingly energy supply, not chip supply. As hyperscalers and inference providers scale to hundreds of megawatts per site, the question of where the power comes from becomes as important as the hardware inside the facility. The practical near-term answer is natural gas, not nuclear. Nuclear power plants take 10-15 years to permit and build; natural gas plants can be operational in 2-3 years, and gas turbine efficiency has improved dramatically in recent generations. The AI infrastructure buildout is happening now — the 2025-2028 energy crunch cannot wait for nuclear timelines. Datacenter operators are actively signing long-term gas contracts and building on-site generation capacity to secure power for new facilities. Nuclear remains a compelling long-term play for baseload clean energy, but it will not meaningfully contribute to the current wave of AI datacenter construction. This energy reality favors architectures like Groq's that deliver more inference throughput per watt — a 30 kW air-cooled rack that rivals GPU clusters consuming 2-3x the power represents a structural advantage as energy becomes the binding constraint.

    Key: GroqRack clusters are high-power, high-cooling but standard infrastructure — no liquid cooling, no exotic networking. Comparable to 8xA100 GPU racks in power density. Air cooling simplifies and accelerates deployment. As energy supply becomes the primary bottleneck for datacenter expansion, power efficiency per token of inference is an increasingly important competitive dimension.

    AI Infrastructure Capex: Buildout, Not Bubble¶

    The competitive landscape above sits atop a wave of AI infrastructure spending that shows no signs of slowing. Hyperscalers are collectively investing $150B+ annually in AI infrastructure, a figure that invites "bubble" comparisons but is better understood as a generational infrastructure buildout rather than speculation. Three structural factors support sustained investment: (a) inference demand is growing faster than training demand — every deployed model generates ongoing compute costs that scale with user adoption, meaning the installed base of inference capacity must continuously expand; (b) enterprise AI deployment is still early — most large organizations are in pilot or early production phases, with massive latent demand yet to materialize; and (c) AI infrastructure ROI compounds — each generation of more capable models makes the underlying infrastructure more valuable, as the same GPU cluster or inference rack serves increasingly capable (and monetizable) applications. For inference service providers, this capex environment is favorable: it means the addressable market is expanding, hardware costs are declining on a per-token basis with each generation, and customers are building AI into core workflows rather than running one-off experiments. The risk is not that spending will collapse but that it will consolidate — favoring providers who can demonstrate clear cost, performance, or flexibility advantages over commodity alternatives.

    Key: Compete on cost and flexibility via open-source models (like Together AI and Groq). Emphasize model selection freedom, easy API switching (OpenAI compatibility), and performance optimizations. But to win enterprise deals, match bigger platforms on security, SLAs, and support. Consider positioning as either a specialist (inference/fine-tuning focus like Fireworks/Together) or a broader platform (like Anyscale/Northflank for full-stack needs).
