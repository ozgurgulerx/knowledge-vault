    AI Infra Basics — GPU Inference Observability & Optimization¶

    A compact first-principles mental model of the GPU inference stack — from CUDA kernels and compilers up through LLM serving runtimes: what each layer does, what its metrics measure, and where real 2026 bottlenecks come from.

    1) CUDA kernel vs compiler¶

    CUDA kernel¶

    A kernel is the small unit of work that runs on the GPU — a function launched from the CPU that the GPU executes across many threads in parallel.

    • A CUDA kernel = the actual function executed on GPU cores (SMs)
    • Written in CUDA C/C++ (or generated by frameworks)
    • Launched across many threads in parallel
    __global__ void matmul(float* A, float* B, float* C) { ... }

    In inference: each op (matmul, attention, layernorm) → one or more kernels. Performance = how efficient these kernels are.

    Execution hierarchy. The GPU runs a kernel as a grid of thread blocks, each block containing many threads, with threads grouped physically into warps of 32 (the unit the scheduler actually issues). CPU-side code is the host, GPU-side is the device, and a kernel launch is the host telling the device to execute a parallel function:

    vector_add<<<grid, block>>>(a, b, c);  // host launches vector_add on device

    Each GPU thread runs the same code on different data (SIMT). A bad kernel wastes memory bandwidth, SM occupancy, warp time, or tensor cores — which is why Nsight looks at warp stalls, memory coalescing, branch divergence, and register pressure (see §5, §7).

    Concrete LLM kernels. An LLM forward pass is ultimately a sequence of launches: GEMM (cuBLAS), fused attention (FlashAttention), layernorm, softmax, KV-cache read/write, activation fusions. Frameworks like PyTorch, TensorRT-LLM, Triton, and cuBLAS all eventually resolve to CUDA kernel launches.

    A kernel is not the whole model. It is a low-level building block the runtime orchestrates into layers, which the compiler and serving runtime (§9) schedule across time and GPUs.

    The PyTorch compiler stack — precise mental model¶

    "PyTorch is the compiler" is too coarse. The accurate layering (PyTorch 2.x docs, 2026):

    • Python — the language
    • PyTorch — framework / runtime / operator system. ATen is its foundational tensor-op layer; the dispatcher routes each op to the right backend kernel (CPU/CUDA, autograd, autocast)
    • torch.compile — the compiler entry point
    • TorchDynamo — Python-level JIT tracer. Hooks CPython's frame evaluation API, rewrites bytecode, and extracts PyTorch op sequences into an FX graph (ATen IR)
    • AOT Autograd — captures backward graph ahead of time (training only; irrelevant for pure inference)
    • TorchInductor — default backend compiler. Lowers the captured graph into optimized code
    • Triton — GPU kernel language/compiler used by Inductor for GPU codegen; on CPU, Inductor emits C++/OpenMP
    • CUDA kernels — the actual GPU work units that execute on SMs

    Eager mode vs compiled mode¶

    Eager mode (default, no torch.compile): PyTorch runs each op immediately via the dispatcher. One op → one kernel launch → next op.

    Python → PyTorch op → ATen/dispatcher → CUDA kernel → next op → next kernel

    Every pointwise op is a separate launch with intermediate memory writes — the main reason eager mode is slow for bandwidth-bound workloads (PyTorch tuning docs flag this explicitly).

    Compiled mode (torch.compile): Dynamo captures a region of Python into an FX/ATen graph, then a backend compiles it.

    Python → TorchDynamo (FX/ATen graph) → TorchInductor → Triton codegen → fused kernels

    Capture and codegen are distinct phases — PyTorch's aot_eager path captures forward+backward graphs but executes them eagerly, proving the two concerns are separable.

    Why compilation helps: for y = gelu(x @ W + b), eager mode launches 3 kernels with intermediate memory traffic. Compiled mode can fuse eligible pieces into fewer kernels, cutting launch overhead and memory movement.

    Graph breaks — compilation is not all-or-nothing¶

    When Dynamo hits untraceable Python (unsupported ops, messy control flow), a graph break occurs: it compiles the graph accumulated so far, runs the unsupported region eagerly, then resumes tracing with a new graph. Compiled PyTorch is usually a hybrid of compiled regions + eager fallback, which is why some models see huge speedups from torch.compile while others barely move.

    Alternative inference backends¶

    torch.compile can delegate to other backends via backend="...". For inference, backend="tensorrt" (Torch-TensorRT) hands the graph to NVIDIA's TensorRT — an SDK containing an inference optimizer + runtime. In that path, PyTorch delegates final low-level optimization to a specialized stack.

    Python + PyTorch model
  → TorchDynamo capture
  → FX / ATen graph
  → TorchInductor | TensorRT | TVM | OpenVINO
  → GPU kernels / optimized runtime

    Key difference¶

    Concept Role
    Kernel execution unit on GPU SMs
    Compiler graph capture + kernel generator/optimizer
    Dynamo graph capture (Python bytecode → FX)
    Inductor default graph compiler (FX → GPU/CPU code)
    Triton GPU kernel codegen language used by Inductor
    TensorRT alternative inference backend (optimizer + runtime SDK)

    2) SM occupancy¶

    Definition: % of GPU Streaming Multiprocessor (SM) capacity actively used.

    Formula (conceptual):

    occupancy = active warps / max warps

    Why it matters:

    • Low occupancy → GPU idle
    • High occupancy → better latency hiding

    BUT:

    • 100% ≠ optimal
    • Register pressure / memory stalls can dominate

    In LLM inference: attention kernels are often memory-bound, so occupancy alone is misleading.

    3) Memory throughput¶

    Definition: rate at which data moves between:

    • HBM ↔ SM
    • L2 ↔ registers

    Measured in GB/s or TB/s.

    Why it matters — LLMs are often:

    memory bandwidth bound, not compute bound

    Example: you're waiting for KV cache reads, not FLOPs.

    4) Heartbeat counters¶

    Not a strict CUDA term — systems-level telemetry.

    Meaning: periodic signals showing:

    • GPU alive
    • workload progressing
    • no deadlocks

    Used in distributed inference systems and schedulers (Ray, Kubernetes GPU operators).

    GPU node → "I'm alive, batch 42 processing, latency 12ms"

    5) GPU kernel introspection¶

    Deep inspection of:

    • execution time per kernel
    • memory access patterns
    • warp efficiency
    • stalls (memory / sync / dependency)

    Tools:

    • NVIDIA Nsight Systems
    • NVIDIA Nsight Compute

    Outputs: timeline, stall reasons, achieved occupancy, memory utilization.

    6) APM (Application Performance Monitoring)¶

    System-level monitoring: latency, throughput, error rates, GPU utilization.

    Examples: Datadog, Prometheus.

    APM ≠ kernel-level:

    Layer Tool
    System APM
    GPU Nsight
    Model custom metrics

    7) Warp stalls¶

    GPU threads execute in warps (32 threads). A stall = waiting.

    Types:

    • memory stall
    • execution dependency stall
    • barrier stall

    Adjacent term — RDMA verbs: low-level networking ops (InfiniBand) used in multi-node inference. Different layer, same "infra plumbing" family.

    8) First-principles bottleneck stack¶

    Inference bottlenecks come from:

    Model graph (PyTorch / HF Transformers)
   ↓
Compiler (torch.compile → Inductor / Triton / TensorRT)
   ↓
CUDA kernels (GEMM, attention, layernorm, KV ops)
   ↓
SM execution (occupancy, warps)
   ↓
Memory system (HBM bandwidth, KV cache traffic)
   ↓
Serving runtime (batching, KV cache mgmt, routing — §9)
   ↓
Cluster / networking (TP/PP collectives, RDMA)

    Metrics map:

    Layer Metric
    Kernel execution time
    SM occupancy
    Memory throughput, KV traffic
    Warp stall reasons
    Runtime TTFT, ITL, cache hit rate
    System APM
    Cluster heartbeat, collective time

    9) LLM serving runtime — prefill, decode, KV cache, routing¶

    Once kernels and compilers are decent, the next frontier is above the compiler layer: how a serving runtime keeps many GPUs busy across many concurrent users while managing KV cache, batching, and cross-GPU work. This is where vLLM, TensorRT-LLM, and NVIDIA Dynamo live.

    Disambiguation. NVIDIA Dynamo (LLM serving framework) is a completely separate project from TorchDynamo (the PyTorch graph-capture layer in §1). Same name, different layer — NVIDIA Dynamo sits at the serving runtime layer, TorchDynamo sits at the compiler layer.

    9.1) The 4-layer mental model¶

    "PyTorch compiles my model and runs it" is too coarse for LLM inference. The accurate layering is four distinct jobs:

    Layer Job Examples
    1. Authoring define model semantics Python, HF Transformers, PyTorch
    2. Compiler capture + lower graphs into optimized code torch.compile, TorchDynamo, Inductor, Triton, TensorRT
    3. Kernels actual GPU work units CUDA kernels, cuBLAS GEMM, FlashAttention
    4. Serving runtime batch, schedule, cache, route across users/GPUs vLLM, TensorRT-LLM, NVIDIA Dynamo

    Layers 1-3 determine how fast one token computes. Layer 4 determines how many concurrent user tokens you sustain per GPU — and in production economics, layer 4 usually dominates.

    9.2) Prefill vs decode — the core asymmetry¶

    LLM inference has two structurally different phases:

    • Prefill — process the full prompt in parallel, build the initial KV cache. Dense matmuls over all prompt tokens at once. Compute-bound (big GEMMs fill the SMs).
    • Decode — generate one token at a time, reusing and extending the KV cache. Each step is a tiny matmul + a huge KV cache read. Memory-bound (HBM bandwidth dominates; SMs sit mostly idle).
    Prefill:  [prompt tokens] ──big GEMMs──▶ [initial KV cache]     (compute-bound)
Decode:   [1 new token] + [huge KV cache read] ──▶ [next token]  (memory-bound)

    This asymmetry is the root cause of most LLM serving optimizations. Because prefill and decode have opposite bottlenecks, co-locating them on the same worker with the same config wastes GPU capacity in both phases.

    9.3) Disaggregated serving — split prefill and decode¶

    Run prefill and decode as separate worker pools, each scaled and tuned independently (NVIDIA Dynamo's core architectural recommendation).

    • Prefill workers — large batches, optimized for compute density
    • Decode workers — many concurrent streams, optimized for memory bandwidth and KV cache layout

    Performance impact. Dramatically higher sustained throughput and cleaner TTFT/ITL separation. A co-located worker either underutilizes SMs during decode, or decode traffic blocks prefill and TTFT blows up.

    Power impact. Decode runs at low arithmetic intensity (mostly memory shuffling), so disaggregation enables per-pool DVFS/power tuning — a decode worker shouldn't burn compute headroom it can't use. Prefill pools can run at max clocks; decode pools can clock down SMs and still hit the same ITL.

    9.4) KV cache — why it dominates decode¶

    The KV cache stores key/value projections for every token seen so far, so decode steps don't recompute them. Size scales roughly as:

    KV_bytes ≈ 2 · layers · heads · head_dim · seq_len · batch · dtype_bytes

    For long contexts it rapidly becomes the largest memory consumer on the GPU — often bigger than the model weights themselves. Consequences:

    • KV cache eats HBM → caps batch size → caps throughput
    • KV cache reads dominate decode bandwidth → decode is memory-bound
    • KV cache layout (contiguous vs paged, fp16 vs fp8, quantized) matters more than kernel micro-optimization

    9.5) PagedAttention, continuous batching, prefix caching (vLLM)¶

    Three vLLM innovations that reshape KV cache + batching:

    • PagedAttention — instead of allocating KV cache as one contiguous block per request (fragments memory, forces over-allocation), split it into fixed-size pages like OS virtual memory. Requests grow their cache page-by-page. Massively cuts fragmentation and unlocks higher effective batch size.
    • Continuous batching (NVIDIA calls it in-flight batching in TensorRT-LLM) — instead of waiting for all requests in a batch to finish before admitting new ones, retire finished sequences and admit new ones every iteration. Keeps the decode GPU always full.
    • Prefix caching — if a new request shares a prompt prefix with an earlier one (system prompt, few-shot examples, multi-turn conversation), reuse its cached KV blocks and skip redundant prefill compute.

    Performance impact. Order-of-magnitude higher throughput per GPU vs naive static batching. These are the features that made vLLM the default open-source serving runtime.

    9.6) KV cache-aware routing¶

    When you have many decode workers, each holding different KV state, routing a request to the worker that already has its relevant KV blocks beats blind load-balancing. NVIDIA Dynamo's router picks workers using two signals:

    • Cache overlap score — how much of the new request's prefix is already cached on each worker
    • Load — current worker utilization

    Tuning knobs:

    • kv-overlap-score-weight — increase for prefill-heavy workloads (prefix reuse is the big win); decrease for decode-heavy workloads (load balance matters more)
    • router_temperature — near 0.0 for deterministic "best worker" selection; raise it to inject randomness and avoid saturating one hot worker

    Performance impact. Skipping redundant prefill on shared prefixes cuts both TTFT and total compute. But it's a tradeoff — pushing too hard on cache reuse creates load imbalance, which blows out tail latency. NVIDIA's tuning guidance says to start from defaults, measure TTFT and ITL, then iteratively adjust.

    9.7) KV cache offloading across memory tiers¶

    When HBM is the bottleneck, move cold KV blocks to cheaper tiers:

    GPU HBM  ←→  host DRAM  ←→  local NVMe  ←→  remote storage
(fastest, scarcest)                          (slowest, abundant)

    Lets you support longer contexts and more concurrent users than raw HBM allows. Performance impact: TTFT improves for conversations whose cache would otherwise be evicted and recomputed; TCO improves because you fit more users per GPU. Cost: offload/reload traffic eats PCIe and interconnect bandwidth, so the eviction policy matters.

    9.8) Tensor parallelism tuning¶

    Tensor parallelism (TP) splits each weight matrix across multiple GPUs and reduces results via collective ops (all-reduce, all-gather). It's how you fit models bigger than one GPU's memory — and how you get more aggregate HBM bandwidth per forward pass.

    The optimal TP degree differs between prefill and decode because their bottlenecks differ:

    • Prefill prefers lower TP — big GEMMs already saturate compute; higher TP adds all-reduce communication overhead not amortized by more work.
    • Decode prefers higher TP — each step is memory-bound, so splitting across more GPUs adds aggregate HBM bandwidth, and the small matmul cost is trivial.

    This is a second independent reason to disaggregate prefill and decode: they want different TP shapes.

    NVIDIA Dynamo exposes a profiler + AIConfigurator + SLA planner that does pre-deployment search over TP degree, worker counts, and parallelization mappings against target TTFT/ITL SLAs. The profiling run can take 2–4 hours because it systematically tests combinations under load — which tells you how non-trivial this knob is in production. Optimal TP depends on model size, prefill/decode mix, SLA, KV-cache pressure, interconnect topology, and worker count simultaneously.

    Performance impact. Wrong TP can cost 2–5× throughput or blow past latency SLAs. Right TP per phase is one of the largest wins available from deployment-time tuning alone.

    Power impact. Higher TP spreads a memory-bound decode workload over more GPUs, which lowers per-GPU utilization — potentially worse perf/W unless you refill the freed capacity with more concurrent streams. This is why high-TP-decode is usually paired with aggressive continuous batching.

    9.9) Where the compiler ends and the runtime begins¶

    Compilers (torch.compile, TensorRT, TensorRT-LLM's engine builder) optimize one forward pass: fuse ops, pick kernels, cut launch overhead. They do not decide:

    • how to batch concurrent requests
    • where KV cache blocks live (HBM/DRAM/NVMe)
    • which worker handles which request
    • how to interleave prefill and decode
    • how to reuse cached prefixes across users
    • what TP degree to run per phase

    Those are runtime responsibilities. Once kernels are decent, the biggest remaining wins in production LLM serving come from KV cache policy, batching policy, prefix reuse, routing, and prefill/decode architecture — not from squeezing another 5% out of a kernel.

    10) What matters in 2026 (non-obvious insight)¶

    Kernel optimization is becoming less important than data movement + scheduling.

    Why:

    • LLM inference = KV cache + batching + routing (§9)
    • bottleneck = memory + orchestration, not FLOPs

    The winners are not just better kernels, but better batching policies, KV cache layout, prefix reuse, prefill/decode disaggregation, and cross-GPU routing. This is where serving-runtime optimizers (NVIDIA Dynamo, vLLM, TensorRT-LLM, PerfFlux-style control loops) diverge sharply from kernel profilers (Nsight) — they operate at different layers, and in 2026 the serving-runtime layer is where the remaining gains live.

    11) Clean mental model (glossary)¶

    Compiler stack (§1)

    • Kernel — GPU work unit; a parallel function launched by the host
    • Compiler — graph capture + kernel generator/optimizer
    • TorchDynamo — PyTorch graph capture (Python bytecode → FX/ATen graph)
    • Inductor — PyTorch default backend compiler
    • Triton — GPU kernel codegen language used by Inductor
    • Graph break — Dynamo falls back to eager for untraceable Python
    • Eager vs compiled — op-by-op dispatch vs graph-capture + fused execution

    GPU telemetry (§2–§7)

    • Occupancy — active warps / max warps (utilization proxy)
    • Throughput — HBM ↔ SM data rate (GB/s)
    • Warp stall — threads waiting on memory / dependency / barrier
    • Introspection — per-kernel profiling (Nsight Systems/Compute)
    • APM — system-level monitoring (Datadog, Prometheus)
    • Heartbeat — liveness/progress signal from distributed workers

    Serving runtime (§9)

    • Prefill — prompt processing phase; compute-bound; builds KV cache
    • Decode — token generation phase; memory-bound; reads KV cache
    • KV cache — stored key/value projections; often larger than model weights
    • PagedAttention — fixed-size KV cache pages (vLLM); cuts fragmentation
    • Continuous / in-flight batching — retire + admit requests every iteration
    • Prefix caching — reuse KV blocks across requests sharing a prompt prefix
    • Disaggregated serving — prefill and decode run as separate worker pools
    • KV-aware routing — send request to worker holding its cached prefix
    • KV offload — spill cold KV blocks to DRAM/NVMe/remote storage
    • Tensor parallelism (TP) — split each weight matrix across GPUs; different optimal degree for prefill vs decode
    • TTFT — time to first token (prefill-dominated)
    • ITL / TPOT — inter-token latency / time per output token (decode-dominated)
    • NVIDIA Dynamo — LLM serving framework (≠ TorchDynamo)
