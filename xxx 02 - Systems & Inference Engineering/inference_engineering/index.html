    Inference Engineering¶

    Opening Briefing¶

    The defining misconception in LLM deployment is that inference performance is a GPU compute problem. It is not. Autoregressive token generation is memory-bandwidth bound, not compute bound: throughput during the decode phase scales with GB/s of HBM bandwidth, not TFLOPS of matrix units. An H100 delivers 3,958 TFLOPS at FP8 with sparsity, yet a single decoding step for a 70B model reads 140 GB of weights through 3.35 TB/s of HBM3 and waits. This inversion means that the entire optimization stack — from OS kernel tuning to serving runtime selection to quantization strategy — is fundamentally an exercise in memory system engineering, not in unlocking more arithmetic.

    The consequences run deeper than GPU selection. PagedAttention, vLLM's core contribution, applies operating system virtual memory principles — page tables, copy-on-write, demand paging — directly to the KV cache, cutting memory waste from 60-80% to under 4% and enabling up to 24x throughput gains. But the OS layer beneath the serving runtime matters just as much and is far less visible. The choice of userspace memory allocator alone introduces 10-18 GB of RSS variance on identical workloads: glibc malloc's arena fragmentation silently consumes memory that could hold thousands of additional KV cache pages. Transparent Huge Pages in their default mode inject 10-100ms compaction stalls into tail latency. NUMA misalignment between CPU cores and GPU PCIe root complexes adds microseconds per DMA transfer that compound across millions of token-generation steps. These are not exotic tuning opportunities; they are baseline correctness requirements for production inference.

    The prefill/decode phase split creates a second structural tension that shapes every architectural decision downstream. Prefill is compute-bound and parallelizable; decode is sequential and memory-bound. System-level benchmarks now confirm that >70% of end-to-end inference time is spent in the decode phase, making decode optimization the dominant lever for throughput gains (arXiv, Mar 2026). The three highest-impact decode-phase interventions — KV cache locality, token-level parallelism, and speculative decoding — collectively deliver 2–4x throughput improvement without increasing FLOPS, reinforcing that this is a memory-system and scheduling problem, not a compute problem. Continuous batching (ORCA-style iteration-level scheduling) resolves the static batching waste of 50-90% GPU idle time, but introduces new scheduling complexity — chunked prefill to prevent long-prompt starvation, preemption policies for SLA-tiered tenants, and token-bucket fairness across a shared GPU fleet. Speculative decoding attacks the decode bottleneck from a different angle, converting sequential token generation into parallel verification at the cost of draft-model overhead, yielding 1.5-2.5x speedups without altering the output distribution. However, recent benchmarks indicate speculative decoding is hitting scaling limits: gains plateau beyond ~2–3× speedup, constrained by misprediction rates and KV cache duplication overhead. The next step requires hybrid approaches — speculative decoding combined with KV-sharing and partial verification — rather than pure speculation trees (arXiv, 2026).

    This document treats inference engineering as what it actually is: a full-stack systems discipline spanning GPU hardware and interconnects, kernel memory management, serving runtimes and schedulers, quantization and precision formats, multi-GPU topology, Kubernetes orchestration, and production observability. As of early 2026, the evidence is unambiguous: performance is dominated by software — schedulers, memory orchestration, and kernel fusion — not by hardware generation (arXiv, Mar 2026). It is organized in two parts — core concepts covering the layered architecture from hardware through workload patterns, followed by production-grade operational concerns from driver setup through security hardening — and is designed to serve as both a technical reference and an architectural reasoning framework for teams building inference infrastructure at scale.

    1. Layered Landscape Map¶

    1.1 Hardware Layer¶

    • GPUs: NVIDIA H100 (80 GB HBM3, 3.35 TB/s), A100 (80 GB HBM2e, 2 TB/s), L4 (24 GB, inference-optimized)
    • Interconnects: NVLink 4.0 (900 GB/s bidirectional per H100), NVSwitch, InfiniBand NDR (400 Gb/s)
    • Memory wall: Autoregressive decoding is memory-bandwidth bound, not compute bound -- throughput scales with GB/s, not TFLOPS
    • TPUs: Google TPU v5e (low-cost inference), v5p (training); HBM capacity and inter-chip interconnect (ICI) differ from GPU ecosystem

    1.2 Kernel & Compiler Layer¶

    • FlashAttention (v1/v2/v3/v4): Fuses Q/K/V into a single kernel; reduces HBM reads from O(N^2) to O(N); 2-4x wall-clock speedup. FlashAttention 4 integrated into vLLM v0.17.0 (March 2026). FA4 on Blackwell (B200): 1.3× faster than cuDNN kernels, 2.7× faster than Triton implementations, achieves ~71% theoretical GPU utilization (~1613 TFLOP/s). Key insight: Blackwell doubled tensor-core throughput but shared-memory bandwidth and non-matmul units did not scale proportionally — kernel scheduling and algorithm-kernel co-design (pipelining compute and memory stages) become the optimization frontier, not raw FLOPS (arXiv, FlashAttention-4, Mar 2026)
    • TensorRT-LLM: NVIDIA's compiler for LLM inference; kernel fusion, quantization, in-flight batching
    • CUDA Graphs: Capture and replay GPU kernel sequences to eliminate CPU launch overhead; critical for small-batch latency
    • Triton (OpenAI): Python-based GPU kernel language; used in FlashAttention, custom fused kernels
    • vLLM Triton Attention Backend: ~800-line single-source attention kernel targeting NVIDIA/AMD/Intel from one codebase; claims H100 parity with SOTA and ~5.8x speedup on MI300 vs earlier implementations; uses Q-blocks, tiled softmax for decode, and persistent kernels for CUDA graph compatibility; now the default attention backend on ROCm
    • KernelAgent (Meta/PyTorch, March 2026): Closed-loop multi-agent workflow guided by GPU performance signals for Triton kernel optimization; 2.02x speedup vs correctness-focused baseline, 1.56x faster than out-of-box torch.compile, 88.7% roofline efficiency on H100; code open-sourced
    • IndexCache for DeepSeek Sparse Attention: Production sparse-attention stacks like DeepSeek recompute sparse-attention index information (which tokens attend to which) at every transformer layer, even though the index patterns are largely redundant across layers. IndexCache eliminates this redundancy by reusing index information across layers, yielding ~1.2× end-to-end speedup on GLM-5 (744B) with matching quality. On a 30B-scale model at 200K context, removing 75% of indexers via IndexCache produces 1.82× prefill and 1.48× decode speedup — a significant gain from minimal code change, which is exactly the practical optimization profile labs now prioritize over clean-sheet kernel rewrites (@realYushiBai, Mar 2026)
    • HF kernels library (Hugging Face, Mar 2026): Hugging Face released a new kernels library designed to make custom GPU kernels more shareable and easier to integrate via the Hub — lowering the pain of writing and distributing fused/custom kernels without hand-rolling installation scripts or build systems. The library provides a standardized packaging and discovery mechanism so that kernel authors can publish optimized kernels (e.g., fused attention variants, custom layernorm) and consumers can install and use them with minimal friction, analogous to how model weights are shared on the Hub today (ariG23498, HF, Mar 2026)
    • Kernel optimization stack (practical sequence): The emerging practical guidance for kernel-level optimization follows a three-step sequence: (1) close idle gaps between kernel launches (reduce CPU-side overhead, use CUDA graphs); (2) fuse ops with torch.compile to eliminate redundant memory round-trips; (3) only fall back to hand-written custom kernels where torch.compile fusion is insufficient. This hierarchy reflects the maturation of compiler-driven optimization — most teams should exhaust steps 1 and 2 before investing in custom kernel development (AINews, Mar 2026)
    • CUDA linear attention kernel (eliebakouch, Apr 2026): New open-source CUDA kernel for linear attention — provides a native GPU implementation for linear-complexity attention variants, reducing the gap between FlashAttention-optimized softmax attention and sub-quadratic alternatives. Relevant for teams exploring efficient attention beyond standard softmax in hybrid architectures (AINews, Apr 2026)
    • Kernel fusion ceiling — register pressure: Aggressive kernel fusion is hitting diminishing returns due to register pressure — fused kernels that combine too many operations exhaust the GPU register file, causing register spills to local memory and reducing SM occupancy. The result is that additional fusion can decrease performance rather than improve it. This represents a hardware-imposed ceiling: further fusion gains require larger register files in future GPU architectures, not just better compiler heuristics. Teams should profile register usage and occupancy when evaluating fusion strategies, as the optimal fusion granularity is now a function of register budget, not just memory traffic reduction (arXiv, 2026)

    1.4 Model & Architecture Layer¶

    • GQA (Grouped Query Attention): Llama 2 70B uses 8 KV heads vs 64 Q heads -- 8x KV cache reduction
    • MQA (Multi-Query Attention): Single KV head shared across all Q heads (Falcon, PaLM)
    • MoE (Mixture of Experts): Mixtral 8x7B activates 2 of 8 experts per token -- 12.9B active params from 46.7B total
    • SSMs (State Space Models): Mamba -- O(n) sequence processing, no KV cache, constant memory per token
    • Axolotl v0.16.x (winglian, Apr 2026): MoE + LoRA fine-tuning breakthrough — claimed 15x faster and 40x less memory for MoE fine-tuning. GRPO async training is 58% faster. Includes docs overhaul and Gemma 4 support. Significant for teams fine-tuning MoE models with LoRA adapters under memory constraints (AINews, Apr 2026)
    • turbopuffer — multi-vector columns (Apr 2026): turbopuffer now supports multiple vector columns per document with different dimensions, types, and indexes per column — relevant for retrieval-augmented inference where documents need multi-representation indexing (e.g., dense + sparse + late-interaction embeddings on the same document) (turbopuffer, AINews, Apr 2026)

    1.5 Workload & Product Layer¶

    Inference phase specialization. The inference stack is fragmenting into distinct workloads with fundamentally different hardware profiles: prefill is compute-bound and benefits from dense matrix math (high TFLOPS), decode is memory-bandwidth-bound and benefits from high-bandwidth memory (high GB/s), and wide reasoning (many parallel chains evaluated simultaneously, as in o3-style reasoning models) benefits from fast compute with cheap tokens. Each phase has a different optimal chip architecture, which is driving the industry toward heterogeneous datacenters where different chip types handle different inference phases rather than one GPU doing everything (see Section 5 for the business implications).

    Two scaling paradigms are emerging around how compute is consumed at serving time:

    • Fast compute — minimize latency per token; optimize for interactive use cases where a human is waiting (chatbots, code completion, search). The constraint is time-to-first-token and inter-token latency.
    • Wide compute — maximize parallel reasoning chains; optimize for throughput of many concurrent inference streams. Reasoning models like o3 generate many parallel chains and pick the best result. This is fundamentally different from serving a chatbot — it demands cheap tokens at scale rather than minimal latency per token.

    These paradigms map onto different product categories:

    • Chatbot: Latency-sensitive, variable length, bursty; optimize TTFT. Archetypical fast compute workload.
    • Batch/offline: Throughput-sensitive; maximize tokens/sec/GPU
    • Code completion: Very low latency (<200ms TTFT), short outputs, high prefix sharing. Fast compute.
    • RAG: Long input context (retrieval chunks), moderate output; prefill-heavy
    • Agents: Multi-turn, tool-calling, variable compute per step
    • Reasoning / search: Many parallel inference chains evaluated and ranked. Archetypical wide compute workload — cost per token matters more than latency per token. Models like o3 may spawn dozens of parallel chains per query, making throughput-optimized hardware (or inference-specialized chips) the natural fit.

    2. OS & Memory Layer¶

    How Linux memory management directly impacts LLM inference latency, memory efficiency, and throughput.

    2.1 OS & Kernel Tuning¶

    Recommended: 64-bit Linux -- Ubuntu LTS (base of NVIDIA DGX OS) or RHEL/Rocky for enterprise/HPC. Windows only via WSL2 if mandatory.

    Optimization Setting Why
    CPU Frequency cpupower frequency-set -g performance Locks max frequency; prevents throttling during inference I/O
    CPU Pinning isolcpus or K8s cpuManagerPolicy: static Dedicated cores; eliminates context switches
    NUMA Balancing kernel.numa_balancing=0 Disables page migration overhead; bind with numactl --cpunodebind
    I/O Scheduler echo none > /sys/block/nvme0n1/queue/scheduler NVMe firmware handles optimization; removes kernel queuing
    Kernel Mitigations mitigations=off (air-gapped only) Disables Spectre/Meltdown; a few percent gain but exposes vulnerabilities

    Goal: ensure the OS is never the bottleneck -- CPUs at full speed, hugepage-friendly memory, NUMA locality respected for GPU data paths.

    2.2 CPU Pages, Huge Pages, and THP¶

    Page Type Size TLB Coverage per Entry Use Case
    Standard 4 KB 4 KB Default; fine-grained
    Huge (2M) 2 MB 2 MB (512x more) Model weights, KV cache
    Huge (1G) 1 GB 1 GB Very large contiguous allocations
    • TLB misses dominate memory access cost for large models -- huge pages cut TLB miss rates by 30-70%

    THP Modes:

    • always -- Aggressively promotes; causes 10-100ms latency spikes from compaction stalls. Avoid in production.
    • madvise -- Only promotes on explicit request. Recommended.
    • never -- Safe fallback if latency spikes observed.

    Use madvise mode. Explicit huge page reservation (hugeadm --pool-pages-min) for weight buffers gives deterministic performance without compaction jitter.

    2.3 DMA, IOMMU, and Pinned Memory¶

    • IOMMU translates device virtual addresses to physical -- adds overhead on every DMA transaction
    • Bare-metal GPU servers: disable with intel_iommu=off for max performance
    • Pinned memory (cudaHostAlloc / mlock) prevents OS from swapping pages -- mandatory for stable GPU DMA transfers
    • Non-pinned memory causes unpredictable delays when OS swaps pages mid-transfer

    Model Loading Performance:

    Scenario Time (8B model)
    Cold load from S3/SSD ~23-35 seconds
    NVIDIA Model Streamer (32 threads, S3) ~4.8 seconds
    Warm cache (DRAM) Tens of GB/s throughput

    Pinned memory + huge pages + parallel streaming dramatically reduce cold-start latency. Pre-warm models in page cache for sub-second subsequent loads.

    2.4 Memory Allocators¶

    Allocator Behavior Impact
    glibc malloc Default; many arenas; fragments heavily 10-18 GB RSS variance; memory not returned to OS
    jemalloc Background scavenging; size-class bins 30-40% lower post-peak RSS; more predictable
    mimalloc Segment-based; minimal fragmentation 5x higher throughput vs glibc in some benchmarks
    • Cap glibc arenas: MALLOC_ARENA_MAX=2
    • Switch to jemalloc: LD_PRELOAD=/usr/lib/libjemalloc.so -- drop-in replacement for vLLM
    • jemalloc tuning: background_thread:true,dirty_decay_ms:1000

    Default glibc malloc is the silent killer of memory predictability in inference. Switch to jemalloc or mimalloc for production vLLM deployments.

    2.5 Linux Page Cache -- Cold vs Warm Loads¶

    Load Type Latency Source
    Cold start 30+ seconds Disk/NVMe/network
    Warm start Sub-second DRAM (tens of GB/s)

    Warm-Start Strategies:

    • Persistent model process -- keep vLLM running; don't restart between requests
    • Preload/warmup -- MAP_POPULATE loads entire file on mmap()
    • mlock() -- pins model pages in RAM; prevents eviction
    • vmtouch -- CLI tool to pre-warm files into page cache
    • Fast NVMe -- reduces cold-start penalty when cache misses unavoidable

    2.6 SLMs as OS/Runtime Diagnostic Probes¶

    1-4B parameter models act as scalpels for performance testing -- small enough to isolate OS overhead from model compute.

    Test What It Reveals
    Toggle THP modes Compaction stall impact on tail latency
    Swap allocators RSS stability, fragmentation patterns
    Cold vs warm loads Page cache effectiveness
    CPU affinity / taskset NUMA effects, scheduling overhead

    SLMs are the cheapest, fastest way to diagnose whether performance problems originate in the OS/runtime layer vs the model/framework layer.

    3. Deep Technical Topics¶

    3.1 PagedAttention & KV Cache Management¶

    PagedAttention (vLLM):

    • KV cache divided into fixed-size blocks (e.g., 16-128 tokens)
    • Block table maps logical to physical blocks (like OS page tables)
    • Eliminates internal fragmentation -- memory waste drops from 60-80% to <4% (pre-vLLM systems used only 20-40% of KV-cache space for actual token states; rest lost to internal fragmentation, reserved-but-unused space, and external fragmentation)
    • Enables copy-on-write for parallel sampling (beam search, best-of-n) -- 55% memory reduction. Multiple outputs from the same prompt share prefix KV blocks via reference counts; blocks are copied only when branches diverge, cutting both memory and redundant prompt compute
    • Up to 24x throughput over naive model.generate(), up to 3.5x over HuggingFace TGI at time of publication
    • PagedAttention is the enabling kernel: attention operates over non-contiguous KV blocks -- without this, paging would be elegant but not useful for attention workloads
    • Design philosophy: throughput first, latency second. vLLM explicitly prioritized throughput because throughput reduces serving cost; they distinguish "pure latency optimizations" from approaches that trade throughput for latency

    Key: The deepest contribution of vLLM is not PagedAttention alone but memory virtualization + scheduler/coherence model for dynamic decoding workloads. The core insight: training stacks assumed static tensor layouts; serving needed dynamic memory allocation semantics. Autoregressive generation behaves more like an OS process tree than a training batch. Autoregressive inference is a dynamic memory-management problem disguised as a deep-learning problem. This paging logic generalizes beyond transformers -- it helps whenever output length is unknown and state grows dynamically, making it a useful first-principles lens for future agent/runtime design.

    vLLM as end-to-end engine: front-end, scheduler, centralized block-table management, GPU-side cache engine, Python/HuggingFace integration, CUDA kernels for PagedAttention, Megatron-LM for model parallel execution, Ray for cluster/control-plane management.

    What vLLM solved and what remains: vLLM solved the first major systems problem (KV-cache layout policy) when the community was still overly focused on model weights, quantization, and GPU horsepower. Later serving bottlenecks extend beyond this: prefill vs decode separation, multi-tenant QoS, long-context prefix reuse across users, speculative decoding, disaggregated inference, heterogeneous memory hierarchies, and agentic workloads with bursty/irregular traffic.

    KV Memory Formula:

    KV Memory = 2 x num_layers x num_heads x head_dim x context_length x bytes_per_value

    max_model_len as Capacity Lever:

    • A model supporting 128K context but serving 4K-avg requests wastes 32x memory if not tuned
    • Set to p99 of real usage sequence length distribution

    Prefix Caching:

    • System prompt KV cache computed once, shared across requests
    • SGLang's RadixAttention uses a radix tree for automatic prefix matching
    • Saves 20-80% prefill compute for shared-prefix workloads

    KV Cache as Competitive Battleground:

    KV-cache management is becoming the critical bottleneck and differentiator in production inference. At scale, the cost of inference is dominated by KV-cache memory, not compute — the memory required to hold attention state for concurrent requests dwarfs the arithmetic cost of generating tokens. Companies that solve KV-cache efficiency (compression, offloading, sharing across requests) gain massive cost advantages, because each byte saved in KV-cache translates directly into higher concurrency or longer context windows on the same hardware. This is also why inference-specialized chips (Groq, Cerebras) focus heavily on memory architecture: their competitive thesis is that purpose-built memory hierarchies can serve KV-cache-heavy workloads far more efficiently than general-purpose GPUs.

    KV Cache Compression:

    KV cache memory footprint scales linearly with context length and dominates HBM usage at long contexts (>32k tokens), making compression effectively mandatory for production long-context serving (arXiv, Mar 2026). The primary techniques, in order of maturity:

    • Quantized KV: Store K/V in FP8, INT4, or FP4 (2-4x memory savings, <1% quality loss). INT4/FP4 KV quantization is increasingly the default for long-context deployments.
    • Low-rank KV compression: Projects key/value representations into a lower-dimensional subspace, reducing per-head memory proportionally. Effective when combined with quantization for compounding savings (arXiv, Mar 2026).
    • Eviction policies: LRU, attention-score-aware eviction (StreamingLLM keeps attention sinks + recent window). Attention-aware policies outperform naive LRU by retaining tokens that carry disproportionate attention mass. Notably, smart eviction alone (attention-aware + recency-weighted) achieves ~2–3× memory reduction with minimal quality loss — and in some workloads outperforms quantization-only compression, suggesting that what you keep matters more than how you compress it (arXiv, 2026).
    • Multi-tier: Hot KV in HBM, warm in CPU DRAM, cold in SSD (with async prefetch)

    When properly tuned, these techniques yield a 2–8x effective memory capacity increase with minimal perplexity degradation — the lower end from quantization alone, the upper end from combining low-rank compression with quantization and eviction (arXiv, Mar 2026).

    KV Cache Recomputation:

    An emerging alternative to storing and compressing KV cache is selective recomputation — discarding KV entries and recomputing them on demand when needed. Recent results show ~30–50% memory reduction at a cost of ~10–20% additional compute (arXiv, KV recomputation tradeoffs, Mar 2026). The viability of this tradeoff reflects a fundamental shift in the compute-memory cost ratio: compute is now provably cheaper than memory in practice, making it economically rational to spend FLOPS to save bytes. Recomputation is not a wholesale replacement for KV caching — it works best as a selective strategy, applied to low-reuse KV entries (tokens unlikely to be attended to again) while keeping high-reuse entries cached. Combined with quantization and eviction, recomputation adds a third lever to the KV memory management toolkit: compress what you keep, evict what's cold, recompute what's cheap.

    3.2 Continuous Batching & Scheduling¶

    Static vs Continuous:

    • Static: All sequences padded to max length, batch waits for slowest -- 50-90% GPU waste
    • Continuous (ORCA): Sequences enter/exit batch at each iteration; new requests fill freed slots immediately

    Batching diminishing returns: While continuous batching delivers 2–10x throughput over static batching, throughput gains from increasing batch size hit a knee at approximately batch size 8–32 (depending on model size and context length). Beyond this point, marginal throughput gains drop below ~10% while latency penalties exceed ~50%, driven by KV cache memory pressure that spikes non-linearly as concurrent sequences compete for HBM capacity (hyperscaler performance traces, 2026). This reinforces the decode-phase specialization trend — batching alone cannot overcome the memory-bandwidth wall, and the diminishing-returns knee is a practical ceiling that shapes capacity planning and autoscaling targets.

    TTFT Anatomy:

    TTFT = queue_delay + tokenization + prefill_compute + misc_overhead
    • Prefill compute is the dominant term for long prompts (GPU-bound)

    Chunked Prefill:

    • Long prompts split into chunks interleaved with decode steps
    • Prevents long-prompt prefill from starving decode of concurrent requests
    • Control via max_num_batched_tokens

    Scheduling Strategies:

    • FCFS: Simple but head-of-line blocking from long sequences
    • Shortest-Job-First: Lower average latency, starvation risk
    • Priority queues: Per-tier SLAs (premium < 500ms TTFT, free < 2s TTFT)
    • Preemption: Swap or recompute KV cache of low-priority requests under memory pressure

    Fairness:

    • Token-bucket rate limiting per tenant
    • Max-min fairness across tenants when GPU is saturated
    • Weighted fair queuing based on tier/SLA

    Token-Level Load Balancing (Micro-Scheduling):

    A finer-grained scheduling approach is emerging that moves beyond batch-level or iteration-level load balancing to token-level dynamic routing across GPUs. Instead of assigning entire requests or batches to specific devices, individual tokens are routed dynamically based on real-time GPU utilization and memory pressure. The effect is smoother utilization across the GPU fleet and reduced tail latency — spikes from uneven request lengths or variable expert activation patterns are absorbed by redistributing work at the token granularity. This is effectively micro-scheduling inside inference: the same principle that continuous batching applied at the request level, now applied at the token level. Early results show meaningful tail-latency reduction in MoE inference where expert activation patterns create inherently uneven load distribution across devices (arXiv, token-level scheduling, Mar 2026).

    3.3 Speculative & Parallel Decoding¶

    Speculative Decoding:

    1. Draft model (small, fast) generates k candidate tokens autoregressively
    2. Target model (large) verifies all k tokens in a single forward pass
    3. Accept longest matching prefix; reject and resample at first divergence

    4. Guarantee: Output distribution identical to target model (rejection sampling)

    5. Typical speedup: 1.5-2.5x for well-matched draft/target pairs

    6. Speculative decoding is one of the three decode-phase optimizations (alongside KV cache locality and token-level parallelism) that together deliver 2–4x throughput gains without additional FLOPS — confirming its role as a core systems-level technique, not an optional enhancement (arXiv, Mar 2026)

    Medusa: Adds multiple prediction heads to the target model (no separate draft model). Each head predicts token at position +1, +2, ... +k. Tree-structured verification. Requires fine-tuning heads (~1-2 GPU-hours).

    Lookahead Decoding: Jacobi iteration over future positions. No draft model; trades compute for parallelism.

    3.4 Multi-GPU / Multi-Node Inference¶

    Strategy Splits Communication Best For
    Tensor Parallelism (TP) Each layer split across GPUs AllReduce per layer (NVLink) Intra-node, latency-sensitive
    Pipeline Parallelism (PP) Consecutive layers on different GPUs Point-to-point between stages Inter-node, throughput
    Expert Parallelism (EP) MoE experts across GPUs All-to-all for token routing MoE models (Mixtral)
    Sequence Parallelism (SP) Long sequence split across GPUs Ring attention Very long context (>128K)

    Practical Guidelines:

    • TP degree <= 8 (single NVLink domain) for latency; going inter-node kills latency
    • PP adds pipeline bubbles -- fill with microbatching
    • Llama 2 70B: TP=4 on 4xA100-80G or TP=2 on 2xH100-80G
    • Mixtral 8x7B: EP across GPUs, 2 active experts routed per token

    3.7 Batch Inference: AI ETL Pipelines¶

    Batch inference — running a trained model over a large corpus of inputs (images, text, PDFs, audio) to produce predictions or transformations at scale — has become an AI data pipeline problem driven by unstructured and multimodal data, not just rows in tables. The workload category is underhyped compared with chatbots but is likely where a large share of enterprise AI value lands: enrichment, cleaning, extraction, classification, summarization, synthetic labeling, and multimodal processing.

    Key: What Spark was to structured data pipelines, Ray is becoming for heterogeneous ML/LLM inference pipelines. Modern batch inference is a heterogeneous distributed pipeline problem: cluster orchestration layer + specialized model runtime + streaming dataflow.

    The core systems problem is heterogeneous orchestration. Modern pipelines are not "GPU all the way down":

    read on CPU -> preprocess on CPU -> infer on GPU -> postprocess/write on CPU

    The GPU stage is expensive, so the real operational objective is to keep GPUs saturated while everything else feeds them efficiently. If S3/IO is slower than GPU inference, the correct move is to scale CPU-side reading/preprocessing until GPUs are fed continuously — fix starvation before buying more GPU.

    The durable systems architecture:

    Layer Role Examples
    Cluster orchestration Distributed dataflow, CPU/GPU scheduling, streaming Ray / Ray Data, or Ray-like
    Model runtime Efficient intra-GPU inference (continuous batching, KV-cache) vLLM, SGLang, TensorRT-LLM
    Storage Data source/sink Object storage, lakehouse

    Two-layer batching for LLMs — the key architectural pattern: Ray Data handles dataset-level parallelism (distributing inputs across cluster), while vLLM handles intra-GPU continuous batching (efficient token generation). Ray batches across the cluster; vLLM batches inside the model runtime.

    Ray Data specifics:

    • Lazy execution — pipeline definition happens first, actual execution on materialize, take, or equivalent terminal operations. Enables pipelining/streaming instead of eagerly loading everything into memory
    • Python-first: read_*, map, map_batches, write_* style API
    • map vs map_batches: use map when input sizes vary (e.g., images of different dimensions that don't fit clean batched tensor processing)
    • Logical partitioning, not hard physical isolation — user code can still OOM; memory management remains the user's responsibility

    Tuning:

    • Batch as much as possible until you hit memory limits, then back off
    • Scale CPU-side reading/preprocessing to match GPU throughput
    • Monitor via Ray dashboard: inspect map_batches stages, track progress, tune batch size, GPU count, and concurrency

    What production batch LLM systems still struggle with (undersold in vendor talks):

    • Tokenizer/detokenizer overhead at scale
    • KV-cache pressure across long-running jobs
    • Prefill vs decode imbalance in batch workloads
    • Network overhead at large cluster scale
    • Fault semantics in long-running LLM jobs (checkpointing, retries)
    • Data quality, prompt determinism, and eval loops
    • Cost governance when LLM output quality is noisy

    Why Ray over Spark for this workload: Spark was built for data-parallel compute, not GPU-heavy heterogeneous inference. Ray is more natural for CPU/GPU mixed stages, actor-based model loading, Python-native ML stacks, and dynamic distributed execution.

    4. Cluster & Infrastructure Challenges¶

    4.1 Capacity Planning¶

    Key metrics: Tokens/sec/GPU, TTFT p99, $/1M tokens, GPU utilization % (target >70%)

    Sizing formula:

    Required GPUs = (peak_concurrent_requests x avg_tokens_per_request x model_params_bytes)
                / (GPU_memory x batch_efficiency x utilization_target)

    Model memory footprint:

    Model FP16 Memory INT4 Memory Min GPUs (A100-80G)
    Llama 2 7B 14 GB 3.5 GB 1
    Llama 2 70B 140 GB 35 GB 2 (INT4) or 4 (FP16)
    Mixtral 8x7B 93 GB 24 GB 2 (INT4)

    4.2 Scheduling, Isolation & QoS¶

    • Kubernetes + GPU operator: NVIDIA device plugin, MIG for A100 partitioning
    • Time-sharing vs space-sharing: MPS for small models sharing a GPU vs dedicated GPU per model
    • SLA tiers: Platinum (<200ms TTFT), Gold (<500ms), Silver (<2s)
    • Admission control: Reject or queue when GPU memory/compute saturated
    • Noisy neighbor prevention: Memory limits, compute time caps, request-level isolation

    4.3 Autoscaling¶

    • Scaling signals: GPU utilization, queue depth, TTFT p95, pending requests
    • Scale-up latency: GPU node provisioning takes 2-10 minutes -- must over-provision or use warm pools
    • Predictive scaling: Time-of-day patterns, event-driven pre-scaling
    • Scale-to-zero: Possible for low-traffic models with serverless GPU (Modal, Replicate, RunPod)
    • KV cache migration: On scale-down, drain in-flight requests before removing GPU

    4.4 Networking & Topology¶

    • Intra-node: NVLink/NVSwitch (900 GB/s) -- mandatory for tensor parallelism
    • Inter-node: InfiniBand NDR 400 Gb/s or RoCE -- needed for PP, EP
    • GPU topology awareness: Schedule TP groups on NVLink-connected GPUs; avoid PCIe-only paths. Cluster experiments show that topology-aware placement yields 20–40% throughput gains with no hardware change — the key principle is to minimize cross-rack attention traffic rather than increase per-GPU compute. Network-aware scheduling is now a first-order performance lever, with impact comparable to hardware generation upgrades (arXiv, 2026)
    • NCCL tuning: Ring vs tree allreduce, chunk size, threading model
    • KV-aware scheduling: A newer optimization layer that colocates KV-heavy requests on the same GPU to reduce cache duplication, and uses dynamic KV pinning to avoid eviction thrash. Production measurements show ~20–35% reduction in $/token with no hardware change — effectively making memory locality scheduling a first-class cost primitive alongside topology-aware placement (arXiv / production inference teams, 2026)

    4.5 Structured Sparsity for Decode Acceleration¶

    Block and structured sparsity (hardware-aligned patterns where zeros are organized into contiguous blocks matching tensor core dimensions) is finally delivering meaningful speedups: ~2–3× decode throughput improvement with acceptable accuracy after post-sparsity fine-tuning. Unstructured sparsity remains impractical — irregular zero patterns don't map to hardware efficiently and produce minimal real speedup. The key requirement for structured sparsity to work is compile-time layout alignment with tensor cores: the sparsity pattern must be decided before inference, not dynamically, and the memory layout must guarantee that sparse blocks map directly to the hardware's GEMM units. This makes structured sparsity a build-time optimization rather than a runtime one (arXiv, 2025–2026).

    4.6 Reliability & Failure Modes¶

    Failure Mitigation
    Single GPU failure Health checks, request retry, redundant replicas
    Node failure K8s pod anti-affinity, PodDisruptionBudget
    GPU memory OOM Memory monitoring, admission control, preemptive eviction
    NVLink failure Topology health checks, node cordon
    Model loading failure Model cache on local NVMe, pre-pulled images

    Graceful degradation: Fallback to smaller/quantized model, circuit breaker with backoff, request shedding by priority, partial response on timeout.

    The heterogeneous datacenter thesis. As inference workloads fragment into distinct phases with different hardware profiles (see Section 1.5), the datacenter itself becomes a design variable. Future inference infrastructure will mix GPU types and custom silicon within the same cluster: expensive flagship GPUs (H100, B200) handle training and compute-heavy prefill, cheaper or older GPUs handle memory-bandwidth-bound decode, and inference-specialized chips (Groq, Cerebras, or custom ASICs) handle specific workloads like wide reasoning where the goal is cheap tokens at massive parallelism. This is a structural shift away from homogeneous GPU fleets and creates opportunities for orchestration layers that can intelligently route work across heterogeneous hardware, as well as for chip startups targeting specific inference phases rather than competing with NVIDIA across the board.

    Top 3 by market gap and defensibility:

    1. Observability & Cost Analytics -- every team running inference needs this; no dominant player yet
    2. Long Context & Memory Management -- context windows have been stuck at ~1M tokens since Gemini's Feb 2024 launch, with growth under one order of magnitude in two years — far slower than cost, speed, or quality improvements. The bottleneck is physical: a global HBM and DRAM shortage means there is not enough memory at inference sites to absorb more context, leading to what swyx and Doug O'Laughlin call "context rationing" — the thesis that context window access will be tiered and priced as a scarce resource rather than expanded freely, and that windows will not meaningfully exceed 1M in the next two years (swyx and Doug O'Laughlin, Latent Space podcast, Mar 2026). This reframes the opportunity from "build for ever-longer windows" to "maximize utility within a hard ceiling," favoring compression, semantic caching, and intelligent retrieval over brute-force context expansion
    3. QoS Orchestration & Heterogeneous Routing -- enterprises need SLA guarantees across multiple models/providers, and as datacenters become heterogeneous, intelligent routing across chip types becomes a critical orchestration problem

    7. Precision Formats & Hardware Support¶

    7.1 NVIDIA (Ampere / Hopper)¶

    Format A100 Throughput H100 Throughput Notes
    FP32 ~19.5 TFLOPS -- Baseline; universally supported
    TF32 156 TFLOPS (312 w/ sparsity) -- 19-bit; FP32 range, FP16-like precision; auto on tensor cores
    FP16 / BF16 ~312 TFLOPS -- 20x over FP32; native Ampere+
    INT8 ~624 TOPS 2-3 PTOPS 32x over FP32; 4x memory reduction
    FP8 -- 3,958 TFLOPS (w/ sparsity) Hopper only; ~6x A100 FP16; Transformer Engine auto-manages
    INT4 Supported on Hopper -- Emerging; non-trivial accuracy challenges

    7.2 AMD Instinct¶

    • MI250X (CDNA2): ~383 TFLOPS/TOPS in BF16/INT8/INT4 -- roughly 4x FP32 speedup
    • MI300 (CDNA3): Adds FP8, FP4/FP6 mixed formats, structured sparsity

    7.3 Google TPUs¶

    • v2/v3: BF16 primary in matrix units; FP32 accumulation
    • v4i (inference): INT8 alongside BF16
    • Google reports no significant precision loss using BF16 vs FP32; Edge TPU is entirely INT8

    7.4 Numeric Formats Reference¶

    Format Bits Range Key Properties
    FP32 32 +-3.4e38 Gold standard; slowest, most memory
    FP16 16 +-6.55e4 Half memory; limited dynamic range (needs loss scaling)
    BF16 16 +-3.4e38 Same range as FP32 with 7-bit fraction; no loss scaling needed; training default on TPUs
    INT8 8 -128 to 127 4x memory reduction; requires quantization mapping
    FP8 8 ~+-448 (E5M2) New in H100/CDNA3; pushing memory/compute efficiency further
    INT4 4 -8 to 7 8x memory reduction; requires mixed strategies (W4A8/W4A16)

    FP16/BF16 are half-precision. FP8 halves memory again but needs careful software handling. INT4 explored via GPTQ/AWQ with non-trivial accuracy challenges.

    8. Quantization Deep Dive¶

    8.1 Methods Summary¶

    Method Type Bits Quality Impact
    GPTQ Weight-only, post-training W4 <1% on most benchmarks
    AWQ Weight-only, activation-aware W4 Slightly better than GPTQ
    SmoothQuant Weight + activation W8A8 <1%, good for batch inference
    FP8 (E4M3/E5M2) Weight + activation 8-bit float Near-lossless on H100
    GGUF Q4_K_M Weight-only, k-quant Mixed 4-bit Good quality/size tradeoff

    INT4 weight-only quantization (GPTQ/AWQ) is the production sweet spot -- halves GPU memory with minimal quality loss. FP8 on H100 is near-free performance.

    8.2 Accuracy Strategies for INT8¶

    Strategy Description Quality
    Per-channel scaling Separate scale factors per output channel Greatly reduces quantization error
    Calibration & clipping Percentile clipping (e.g., top 0.1% outliers) Better range utilization
    QAT Fine-tune with simulated quantization; torch.quantization.prepare_qat Best accuracy (<1% drop); expensive
    LLM.int8() Decompose matmul into INT8 + FP16 parts for outlier values Zero degradation on 175B models
    SmoothQuant Smooth outlier activations by migrating difficulty to weights First W8A8 of GPT-3/OPT with negligible loss
    AWQ Activation-aware 4-bit weight quantization INT4 weights with small accuracy drop

    With modern techniques, INT8 accuracy gap is sub-1% on most NLP benchmarks. Example: BERT SQuAD F1 drops 87.97 -> 87.52 (delta 0.45) for 4x model size reduction.

    8.3 Memory Savings¶

    Model FP32 FP16/BF16 INT8
    10B params ~40 GB ~20 GB ~10 GB
    BLOOM-176B ~704 GB ~352 GB ~176 GB

    8.4 Throughput & Latency¶

    • A100 INT8 (624 TOPS) is 32x its FP32 (19.5 TFLOPS)
    • BERT-Large on A100: ORT + TensorRT INT8 achieves 7x faster vs PyTorch FP32; batch-1 latency <2ms
    • Quantization can deploy on single GPU instead of multi-GPU -- eliminates inter-GPU communication overhead

    8.5 Deployment Workflow (PTQ)¶

    1. Train/fine-tune in FP32 or mixed precision
    2. Calibrate on representative data (hundreds to thousands of samples)
    3. Quantize weights (and optionally activations)
    4. Validate accuracy on held-out set
    5. Deploy on optimized runtime (TensorRT, ORT, OpenVINO, TFLite)

    8.6 Mixed Deployment (Hybrid Precision)¶

    • Most layers in INT8; keep FP16/FP32 for:
    • Softmax, LayerNorm (summation-heavy, precision-sensitive)
    • First/last layers (embedding input, final logit output)
    • TensorRT Model Optimizer supports per-layer "W4A8" schemes

    8.7 Memory Headroom Uses¶

    • Increase batch size for higher throughput
    • Run multiple model instances (multi-tenant)
    • Load larger models in same memory budget
    • Enable larger context windows

    8.8 Framework Support¶

    Framework FP16/BF16 INT8 Notes
    PyTorch autocast / AMP PTQ + QAT APIs; FBGEMM/QNNPACK Full gamut
    TensorFlow mixed_precision API TFLite for INT8 with calibration XLA optimized
    JAX XLA BF16/FP16 Research code; no full PTQ flow BF16 default on TPU
    TensorRT Strong FP16 FP32-accuracy INT8 via calibration + selective fallback Maximum NVIDIA performance
    ONNX Runtime FP16 quantize_dynamic/quantize_static; 7x speedup on BERT-Large TensorRT EP delegation
    HuggingFace .half(), accelerate LLM.int8() via bitsandbytes, 4-bit experimental load_in_8bit=True
    DeepSpeed Mixed precision ZeroQuant compression Efficient CPU/GPU
    OpenVINO FP16 INT8 PTQ + runtime CPU-side deployment

    8.9 Sparsity (Complementary)¶

    • NVIDIA Ampere/Hopper: 2:4 structured sparsity -- additional ~2x throughput on top of FP16/INT8
    • Pruning + quantization could yield ~4x over FP16 alone; exploiting in LLMs while preserving accuracy is active research

    9. Low Precision in Training¶

    • FP16 with loss scaling: Linear layers in FP16, accumulation in FP32; prevents gradient underflow. GPT-3 trained on V100s with FP16.
    • BF16 (preferred on Ampere+/TPUs): No loss scaling needed. PaLM trained on TPU-v4 with BF16. Speeds up training by 2x+, halves memory.
    • FP8 in training: H100 Transformer Engine auto-uses FP8 for dot-products; up to 4x faster vs FP16.
    • 8-bit Adam: Stores optimizer states in INT8 with block-wise scaling -- saves up to 8.5 GB for 1.5B model, no accuracy loss.

    10. Containerization Best Practices¶

    Base images: NVIDIA NGC (nvcr.io/nvidia/pytorch:<version>-py3) with CUDA/cuDNN pre-installed. Container should NOT include NVIDIA driver -- Container Toolkit injects host devices.

    Image optimization:

    • Multi-stage builds; pip cache purge to shrink layers
    • Model weights: bake into image or mount via volume/NFS/cloud storage
    • Shared tmpfs for multiple instances loading same model from RAM

    Runtime:

    • OMP_NUM_THREADS=1 (PyTorch); --cpuset-cpus for CPU pinning
    • Non-root via SecurityContext; hostNetwork: true for latency-critical services
    • Singularity/Apptainer for HPC: rootless, --nv flag for GPU

    Verification: nvidia-smi inside container; profile with nsys. Docker overhead: a few percent at most.

    12.1 Model Loading¶

    • Preload with vmtouch or dd; pin with mlock

    12.2 NVMe Tuning¶

    • I/O scheduler: noop/none
    • Pin interrupts to NUMA-local cores via /proc/irq/*/smp_affinity

    12.3 Network Tuning¶

    • Jumbo frames (MTU 9000); HTTP/2 or gRPC for serving
    • Disable irqbalance; manually pin NIC IRQs to NUMA-local cores
    • Increase RX/TX ring buffers (ethtool -G); enable RSS
    • GPU Direct RDMA (NVreg_EnableGpuDirectRDMA=1) for NCCL

    Appendix A: Learning Path (Beginner to Expert)¶

    Beginner¶

    1. Transformer Fundamentals -- Self-attention, tokens, why transformers work. Resources: Karpathy's intro, The Illustrated Transformer.
    2. Basic LLM Inference -- Install HuggingFace Transformers, run text generation with GPT-2 or 1.3B LLaMA. Observe sequential generation, memory usage, latency per token.
    3. Inference Challenges -- 70B model in FP16 needs ~140GB for weights alone. Memory fragmentation, underutilized GPU compute, inability to handle concurrent requests.
    4. Introduction to vLLM -- PagedAttention, dynamic batching, OpenAI-compatible API. Read "What is vLLM?" (F22 Labs).
    5. Hands-On vLLM (Basic) -- Install, serve TinyLlama, generate via LLM.generate(). Observe automatic batching.

    Intermediate¶

    1. vLLM Architecture Deep Dive -- Engine, scheduler, KV Cache Manager, PagedAttention internals. Read "Inside vLLM" (vLLM Blog).
    2. Request Flow -- Trace REST API to engine in vLLM GitHub. Read "Life of an Inference Request (vLLM V1)".
    3. Continuous Batching Experiments -- Send 5-10 concurrent requests, measure throughput vs sequential.
    4. vLLM API Mastery -- SamplingParams, streaming, prefix caching, guided decoding. Build a multi-user chat server.
    5. Ecosystem Integration -- HuggingFace Hub models in vLLM, compare with TGI (C++ optimized, 3x throughput on long prompts in some benchmarks).
    6. DeepSpeed & Offloading -- ZeRO-Inference: host weights on CPU/NVMe, stream to GPU. Serve 30B model on 16GB GPU.
    7. Quantization Practice -- Load AWQ INT4 models in vLLM, measure memory/throughput vs FP16.
    8. Transformer Variants -- RoPE, MQA/GQA, FlashAttention and their inference performance implications.

    Advanced¶

    1. Distributed Inference -- Data, Pipeline, Tensor, Expert parallelism. Serve 70B via TP across 2+ GPUs.
    2. vLLM Distributed Design -- MultiProcExecutor, multi-node, llm-d scheduler, TP+PP composition.
    3. Compiled Kernels -- TensorRT-LLM engine conversion, benchmark against vLLM. FasterTransformer with Triton Inference Server.
    4. Engine Benchmarking -- Compare TGI, vLLM, TensorRT-LLM, FasterTransformer under controlled conditions (13B, 10 concurrent, 512 tokens). Also explore FlexGen for CPU/NVMe offloading.
    5. Key Papers -- PagedAttention (SOSP 2023), ORCA (USENIX 2023), Speculative Decoding (2023).
    6. Custom Kernels -- FlashAttention, xFormers, OpenAI Triton. Write a Triton kernel for softmax or layernorm.

    Expert¶

    1. Hardware-Aware Optimization -- H100 Transformer Engine (FP8/FP16 auto-management, up to 30x faster inference vs A100). Profile compute-bound vs memory-bound. Alternative hardware: TPU v4, Inferentia2, AMD MI300.
    2. End-to-End System Design -- Full-stack serving for millions of users: containerized vLLM, KServe on K8s, QPS-based autoscaling, multi-model serving via MIG, failure handling.
    3. Open-Source Contributions -- Tackle vLLM scheduler fairness, new attention variants, multi-node scheduling (llm-d).
    4. Research Tracking -- MLSys, OSDI, arXiv weekly. Watch: KV cache offloading (SpecOffload), cross-device scheduling, 256K+ context serving.
    5. Capstone: Custom Serving Stack -- Combine vLLM scheduling + TensorRT-LLM kernels + speculative decoding in a unified API. Benchmark against existing solutions.
