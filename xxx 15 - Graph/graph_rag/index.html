    Graph RAG¶

    See also: Awesome-GraphRAG Survey | RAG Guide | RAG Evals | Knowledge Graph RAG (concept map) | Graph Data Models

    Opening Briefing¶

    GraphRAG addresses the two structural failure modes of baseline RAG: multi-hop reasoning (evidence distributed across documents, no single chunk suffices) and corpus-level sensemaking (themes, structure, and narratives that no individual passage can represent). The approach builds entity-relation graphs from source documents, partitions them into communities, generates summaries, and retrieves via graph traversal rather than embedding similarity alone.

    The critical nuance: GraphRAG is not automatically better than high-quality hybrid retrieval. "GraphRAG under Fire" (2025) demonstrated that graph indexing adds substantial cost and latency without accuracy gains when queries are already well-served by chunk retrieval. The decision boundary is structural — use graphs when queries need structure (relations, temporal constraints, corpus-level themes), not as a default.

    The most significant recent development is adaptive routing between dense and graph-based retrieval. EA-GraphRAG (2026) showed that GraphRAG achieves 13.4% lower accuracy than vanilla RAG on simple single-hop queries and 16.6% lower on time-sensitive queries — but dominates on multi-hop reasoning. The solution is not to choose one paradigm but to route dynamically based on query complexity.

    A cross-method empirical analysis spanning 12 GraphRAG implementations, 5 graph types, 8 operator classes, and 6 datasets reinforces this with sharper specifics. Three findings stand out. First, richer graphs do not reliably outperform simpler ones — Rich Knowledge Graphs (RKG) and Textual Knowledge Graphs (TKG) contain the most semantic information yet do not consistently beat standard KG or even tree structures; RAPTOR (tree + clustering) achieves top-1 accuracy on several datasets, and HippoRAG (standard KG + Personalized PageRank) often matches or beats advanced RKG systems. Second, retrieval operators matter more than graph type as predictors of quality — methods combining graph topology with statistical ranking (link + PPR) and community-based approaches (LGraphRAG for cross-page reasoning) consistently outperform systems with richer graphs but weaker operators. Third, there is a clear cost-performance Pareto frontier: RAPTOR, HippoRAG, and FastGraphRAG sit on the frontier (high accuracy, reasonable cost), while ToG, KGP, and DALK are off it (expensive and underperforming). Mid-sized datasets (1–3M tokens) are the sweet spot for GraphRAG — at this scale, graph construction remains tractable and structural cues guide retrieval effectively; beyond 5–15M tokens, graph density increases disproportionately and multi-hop traversal becomes less discriminative. Critically, abstract and specific QA require different architectures: RAPTOR/HippoRAG/FastGraphRAG excel at specific factual retrieval (strong node indexing, edge weighting, one-hop relatedness), while LGraphRAG/RGraphRAG/VGraphRAG excel at abstract cross-page reasoning (relationship-rich graphs, community operations) (Fanghua Yu, "What Really Matters to Better GraphRAG Implementation?", Dec 2025).

    GraphRAG Reference Architecture¶

    GraphRAG (From Local to Global) is the canonical reference design:

    1. Entity/relationship extraction from source documents (LLM-driven NER/RE)
    2. Graph construction — heterogeneous graph with entity nodes, passage nodes, relation edges
    3. Community detection — hierarchical clustering (Leiden algorithm)
    4. Community summarization — bottom-up LLM-generated summaries per community
    5. Query-time retrieval via:
    6. Local search — start from query-relevant entities, fan out to neighbours/claims/text units
    7. Global search — compose answers from community summaries for corpus-level questions
    8. DRIFT mode — combines local search with community context

    Key: Indexing is expensive. GraphRAG behaves like an offline compilation step plus a query-time "decoding" step. Defaults may underperform on your domain without tuning. Treat indexing as a batch job and amortize across many queries.

    EA-GraphRAG: Adaptive Routing Between Dense and Graph Retrieval¶

    Paper: "Use Graph When It Needs: Efficiently and Adaptively Integrating RAG with Graphs" (Dong et al., Hong Kong PolyU, Feb 2026)

    Core Insight¶

    GraphRAG and dense RAG have complementary strengths across query complexity:

    Query Type Dense RAG GraphRAG Winner
    Single-hop factual (e.g., "When is GoT season 8?") Strong — direct passage match Weak — retrieves generic entity articles instead of specific facts Dense RAG
    Time-sensitive queries Strong 16.6% lower accuracy Dense RAG
    Multi-hop reasoning (e.g., "Death date of the director of film X?") Weak — retrieves unrelated biographies Strong — traverses entity chains GraphRAG
    Corpus-level sensemaking Weak Strong — community summaries GraphRAG

    Three-Component Architecture¶

    Query → Syntactic Feature Constructor → MLP Complexity Scorer → Router
                                                                  ↓
                                              ┌─────────────────────────────────┐
                                              │ s(q) ≥ τH → Graph retrieval    │
                                              │ s(q) ≤ τL → Dense retrieval    │
                                              │ τL < s(q) < τH → Fusion (RRF)  │
                                              └─────────────────────────────────┘

    1. Syntactic Feature Constructor

    Extracts ~85 features across four dimensions from the query:

    • Syntactic structure — constituency parse tree analysis (sentence complexity, T-unit metrics, clause ratios)
    • Dependency-based — max/avg dependency distances, long-range dependency counts, tree imbalance
    • Semantic & lexical — named entity counts/types, entity density, lexical diversity, question-type markers
    • Interaction features — tree depth/width, branching factors, tokens per clause, connector density

    Uses mutual information-based feature selection to identify the most discriminative features.

    2. MLP Adapter (Complexity Scorer)

    • Architecture: feature attention → 256 → 128 → 64 → output attention → sigmoid
    • Residual connections where dimensions match
    • Trained on disagreement set — queries where RAG and GraphRAG produce different correctness outcomes
    • Output: complexity score s(q) ∈ (0, 1)

    3. Score-Driven Routing

    • High complexity (s(q) ≥ τH): route to graph-based retrieval
    • Low complexity (s(q) ≤ τL): route to dense retrieval
    • Borderline (τL < s(q) < τH): weighted Reciprocal Rank Fusion combining both result sets, with the complexity score weighting graph retrieval more heavily for higher-complexity queries

    Graph-Based Retrieval Pipeline¶

    1. Construct heterogeneous graph: entity nodes + passage nodes; edges from OpenIE triples, occurrence links, synonymy
    2. Compute query-fact similarity
    3. LLM-based reranking of top-k candidates
    4. Entity weighting normalized by passage occurrence frequency
    5. Personalized PageRank with selected seed entities
    6. PPR diffusion through relation/synonymy edges to passage nodes

    Results¶

    QA Performance (Mixed benchmark — 4,000 queries across NQ, PopQA, HotpotQA, 2WikiMultihopQA):

    System Accuracy GPT-Accuracy
    ColBERTv2 (dense) 63.2% 68.4%
    HippoRAG2 (graph) 68.5% 73.6%
    EA-GraphRAG 71.6% 76.9%

    Latency:

    Path Latency (s/query)
    Dense retrieval only 0.08
    Graph retrieval only 3.23
    EA-GraphRAG (full system) 2.19
    EA-GraphRAG (without fusion) 1.14

    Key: EA-GraphRAG achieves state-of-the-art accuracy on mixed-complexity benchmarks while reducing latency by ~96% vs. pure GraphRAG by routing simple queries to dense retrieval. The adaptive routing pattern — not any single retrieval method — is the architectural insight.

    Graph RAG Implementation Patterns¶

    Pattern Comparison¶

    Pattern How It Works Where It Wins Where It Loses
    Offline KG + query-time subgraph hydration Extract entities/relations; store graph; retrieve ego-net/community reports Multi-hop reasoning; entity-centric analytics; provenance High ingestion cost; entity resolution; schema drift
    Community summaries (global search) Cluster graph; pre-summarize communities; answer "themes" via composition Corpus-level questions; investigative sensemaking Expensive indexing; summaries can be generic/stale
    Graph traversal to enrich vector results Retrieve seed passages then expand neighbours/claims/timelines Connecting retrieved snippets; relationship questions Over-expansion can flood context; needs budget controls
    Adaptive routing (EA-GraphRAG) Score query complexity; route to dense, graph, or fusion Mixed-complexity workloads; production systems Requires training a routing model; added complexity
    Temporal KG memory Persist evolving facts as time-stamped nodes/edges Long-lived assistants; business data changes Harder ops; requires change detection/invalidation

    Implementation Checklist¶

    Key -- Graph RAG Checklist:

    • Define entity/edge schema (node types, relationship types, required properties)
    • Extraction evals on representative corpus (measure NER/RE precision)
    • Hybrid retrieve: graph paths + text chunks
    • Evaluate whether adaptive routing is needed (analyze query complexity distribution)
    • Good/Better/Best: simple entity linking → typed relations and path constraints → adaptive routing with complexity scoring + feedback loops

    GraphRAG as Hybrid Reasoning Engine¶

    Modern GraphRAG stacks are evolving beyond retrieval into execution and reasoning substrates. The pattern is no longer limited to "retrieve subgraph, stuff into prompt" — instead, the graph itself becomes a space where reasoning operations execute:

    • Subgraph retrieval + path reasoning — retrieve relevant subgraphs, then run reasoning over graph paths (shortest path, constraint propagation, causal chain extraction) before converting results to text for the LLM
    • Graph → text → LLM pipelines — convert structured graph outputs into natural language summaries as an intermediate representation, enabling LLMs to reason over graph-derived insights without needing native graph understanding
    • Graph as execution space — the graph is no longer just a retrieval index but a computation layer where path finding, subgraph extraction, and constraint propagation produce intermediate results that feed generation

    This represents a convergence of GraphRAG with graph ML and reasoning systems — the graph participates in both retrieval and inference, not just context assembly. The practical implication is that GraphRAG pipelines are becoming multi-stage: retrieve subgraph → execute graph operations → optionally convert to text → generate. Teams building GraphRAG systems should evaluate whether their queries benefit from graph-native reasoning operations rather than treating the graph purely as a retrieval source (arXiv, 2025–2026).

    Streaming and Incremental GraphRAG¶

    A critical infrastructure gap in traditional GraphRAG is that graph construction is a batch operation — extract entities, build the graph, detect communities, generate summaries, then query. For domains where data changes continuously (news, financial data, observability systems), this batch model introduces staleness that undermines the value of graph-augmented retrieval.

    Emerging infrastructure now supports incremental GraphRAG: continuous entity extraction from streaming data, dynamic graph updates that add nodes and edges without full reconstruction, and partial re-indexing that updates only the affected communities and summaries. This means the knowledge graph stays current with the data rather than reflecting the state at last indexing time.

    The practical requirements are: change detection at the document level, incremental entity extraction that can process individual documents without reprocessing the corpus, graph update operations that maintain community structure without full re-clustering, and selective summary regeneration for communities that changed. This is harder than incremental vector indexing because graph structure creates dependencies — adding a node can change community membership for its neighbors (arXiv, 2025–2026; GraphRAG research repos).

    Graph Sparsification¶

    Counter-intuitively, making graphs smaller often improves both retrieval quality and latency. Graph sparsification applies targeted pruning to reduce graph complexity without losing the structural signals that make graph retrieval valuable:

    • Edge pruning — remove low-confidence or redundant edges that add noise without improving retrieval paths. Entity extraction produces many spurious relations; aggressive filtering of low-confidence extractions improves precision
    • Community compression — merge small or highly similar communities to reduce the number of community summaries the system must search over, cutting both indexing cost and query-time latency

    The insight is that larger graphs are not automatically better graphs. Over-extracted entities and relations create noisy traversal paths that mislead retrieval and inflate latency. Sparsification targets the noise while preserving the high-value structural relationships that justify using a graph in the first place (arXiv, 2025–2026).

    Key: Before scaling up graph indexing, try scaling down. Pruning low-confidence edges and compressing communities often produces a faster, more precise graph that outperforms the unsparsified version.

    Signals Worth Watching¶

    • Adaptive RAG routing (EA-GraphRAG) may become the standard architecture — dynamically selecting between dense, sparse, graph, and hybrid retrieval based on query complexity
    • Temporal and domain-aware GraphRAG frameworks are emerging for dynamic knowledge domains where facts change over time
    • Graph-centric retrieval frameworks (NodeRAG, RGL) are improving scalability and engineering ergonomics
    • Personalized PageRank as a graph traversal primitive is gaining traction for seed-entity-based retrieval in production systems
    • GraphRAG merging with graph ML + reasoning systems — graphs are evolving from retrieval indexes to execution spaces where reasoning operations (path finding, constraint propagation) run natively before generation
    • GraphRAG + constraint solvers (symbolic AI convergence) — an emerging hybrid pattern blends KG traversal with SAT solvers and constraint programming for solution-space pruning. The graph retrieval stage identifies candidate entities and relationships; the symbolic constraint layer enforces logical rules, regulatory requirements, or domain invariants to prune the solution space before LLM synthesis. This is particularly valuable for compliance, planning, and scientific reasoning domains where answers must satisfy hard constraints, not just be semantically plausible. GraphRAG is quietly merging with symbolic AI again — not as a replacement for neural retrieval but as a post-retrieval verification and pruning layer (arXiv, 2025–2026)
    • GraphRAG evolving toward query planning systems — instead of treating graph retrieval as a fixed traversal pattern, emerging architectures translate questions into graph query plans (analogous to database query optimization), execute multi-hop traversals according to the plan, and optionally synthesize via LLM. This is closer to database query optimization than information retrieval, and it opens the door to cost-based query planning where the system estimates traversal cost before execution (arXiv, 2025–2026)
    • Streaming / incremental GraphRAG — continuous entity extraction and dynamic graph updates are making GraphRAG viable for domains with fast-changing data, eliminating the batch-only bottleneck
    • Graph sparsification as a quality lever — pruning low-confidence edges and compressing communities often improves both retrieval precision and latency, counter to the "bigger graph = better graph" assumption
    • GraphRAG → typed reasoning systems — graphs are evolving beyond untyped entity-relation stores toward strict schemas, typed relations, and validation constraints. Entity nodes carry type annotations (person, organization, concept), edges enforce typed relation contracts (e.g., authored_by must connect Paper → Person), and validation layers reject malformed triples before they enter the graph. This reduces hallucination via type checking at the graph level — the LLM cannot synthesize answers that violate the graph's type system, and retrieval traversals are constrained to type-valid paths. The pattern borrows from database schema enforcement and static type systems in programming languages, applied to knowledge graphs as a hallucination reduction mechanism (arXiv, 2025–2026)
