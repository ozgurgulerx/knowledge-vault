    Graph Data Models for AI & RAG Systems¶

    Reference guide covering graph data models, graph databases, query languages, and integration patterns for knowledge-intensive AI systems.

    Opening Briefing¶

    The default assumption in most RAG architectures is that retrieval is a similarity problem — embed the query, find the nearest vectors, stuff them into context. This framing is incomplete to the point of being misleading. Similarity answers "what looks like this?" but the questions that actually break RAG systems are relational: "who approved this fund's mandate change, and what downstream holdings were affected?" Those queries demand traversal across typed, directed edges — a fundamentally different computational primitive than approximate nearest neighbor search. Graphs are not an enhancement to vector retrieval; they are a distinct retrieval modality that operates on connectivity rather than proximity.

    The technical specifics bear this out in ways that matter for system design. The GraphRAG pattern, as formalized by Microsoft's open-source implementation, introduces an index-time step with no vector-search equivalent: Leiden community detection partitions the entity graph into hierarchical clusters, and an LLM generates summaries at each level of that hierarchy. This is what enables "global" queries — questions about themes, trends, or aggregate properties across an entire corpus — because the community summaries act as pre-computed abstractions over graph structure. Vector stores have no mechanism for this; they retrieve individual chunks, not structural summaries. Meanwhile, property graphs and RDF triple stores represent a genuine schema-design fork: property graphs (Neo4j, FalkorDB) optimize for fast traversal with flexible key-value properties on both nodes and edges, while RDF's URI-based subject-predicate-object triples buy you semantic interoperability and federated querying at the cost of verbosity and traversal speed. Choosing wrong here locks you into workarounds that compound over time.

    The second-order consequence is that production knowledge-intensive systems increasingly require three retrieval stages operating in sequence: vector similarity to find seed entities or passages, graph traversal to expand along relationships and multi-hop paths, and structured filtering to enforce metadata constraints. Each stage answers a different class of question, and the combination produces context that is both semantically relevant and structurally grounded. Graph-grounded generation — injecting traversed subgraph facts as structured context — is what converts retrieval from pattern-matching into something closer to reasoning, because every fact carries explicit provenance back through named edges to source nodes.

    This document maps the full design space: data models and their trade-offs, database and query-language choices, schema patterns, embedding methods for graph-native semantic search, and the specific integration patterns that connect graph infrastructure to LLM pipelines. The operating claim is that graphs are the connective tissue that turns isolated retrieved fragments into a coherent evidence structure — and that understanding when and how to deploy them is now a core RAG engineering skill, not an optional enrichment.

    Core Concepts¶

    Property Graphs vs RDF/Triple Stores¶

    Aspect Property Graph RDF / Triple Store
    Data model Nodes + relationships, both with key-value properties Subject-predicate-object triples (SPO)
    Schema Schema-optional (labels + constraints) Schema via ontologies (RDFS, OWL)
    Identity Internal node/edge IDs URIs for all resources
    Query language Cypher, Gremlin, GQL SPARQL
    Strengths Intuitive modeling, fast traversals, flexible properties Semantic interoperability, standards-based, federated queries
    Weaknesses No built-in semantic reasoning; vendor-specific dialects Verbose; harder to learn; slower for deep traversals
    Best for Application-centric graphs, RAG, recommendation, fraud detection Linked data, ontology-driven domains, cross-org data integration

    Labeled Property Graph Model¶

    • Nodes: entities with zero or more labels (e.g., :Person, :Company)
    • Relationships: directed, typed connections between nodes (e.g., -[:WORKS_AT]->)
    • Properties: key-value pairs on both nodes and relationships
    • Labels: group nodes into sets; enable indexing and schema constraints

    RDF Model¶

    • Triple: <subject> <predicate> <object> -- the atomic unit
    • URIs: globally unique identifiers for subjects, predicates, and object resources
    • Literals: typed values (strings, integers, dates) as objects
    • Named graphs: group triples into contexts for provenance or access control
    • Ontologies: RDFS/OWL define classes, properties, and inference rules

    Schema Approaches¶

    Approach Description Trade-off
    Schema-less No constraints; any node can have any property Maximum flexibility; hard to maintain at scale
    Schema-optional Define constraints/indexes but allow extension Good balance for evolving domains
    Schema-enforced Strict ontology or constraints required Data quality guarantee; slower iteration

    Syntax Comparison: "Find Friends of Friends"¶

    -- Cypher
MATCH (p:Person {name: "Alice"})-[:FRIEND]->()-[:FRIEND]->(fof)
RETURN DISTINCT fof.name

-- SPARQL
SELECT DISTINCT ?fofName WHERE {
  :Alice :friend/:friend ?fof .
  ?fof :name ?fofName .
}

-- Gremlin
g.V().has('Person','name','Alice')
 .out('FRIEND').out('FRIEND')
 .dedup().values('name')

    Graph Data Models for AI & RAG¶

    Knowledge Graphs as Retrieval Layer¶

    • Entity-Relation-Entity triples provide structured facts for grounding LLM responses
    • Graph traversal retrieves multi-hop evidence that vector search misses
    • Explicit provenance: every fact traces back to source nodes/edges

    GraphRAG Pattern¶

    Graphs earn their place when relationships matter more than raw text — compliance chains, research lineage, multi-hop questions where the answer lives in connections, not passages.

    Pipeline stages:

    1. Entity extraction: LLM or NER/RE extracts entities and relations from source text → triples
    2. Graph construction: store extracted triples in a graph database
    3. Community detection: partition graph using Leiden algorithm; generate hierarchical community summaries
    4. Graph-enhanced retrieval: local search (entity ego-net) or global search (community summaries)
    5. Compose & evaluate: assemble graph-grounded context into prompt; run evals against expected paths

    Pitfalls to watch:

    • Noisy extraction → brittle paths: extraction errors compound across hops — a single mis-typed entity or hallucinated relation breaks downstream traversals, producing confidently wrong context. Extraction quality is the single highest-leverage investment in the pipeline.
    • Over-indexing without query policies: building a rich graph is wasted effort if the retrieval layer has no discipline about which paths to follow. Without clear query policies (depth limits, edge-type filters, relevance thresholds), retrieval degrades into unbounded graph walks that surface noise rather than signal.

    Implementation checklist:

    • Define an explicit entity/edge schema before extraction begins — ad-hoc schemas drift fast
    • Run extraction evals on a representative corpus; measure entity recall, relation precision, and triple consistency before trusting the graph for retrieval
    • Wire hybrid retrieval: graph paths + text chunks — graph paths supply structure, text chunks supply nuance

    Extraction eval example:

    def path_coverage(query, graph_paths):
    """Minimal check: do retrieved paths contain the edges the query requires?"""
    return any(required_edge in p for p in graph_paths)

    GraphRAG Maturity Model (Good-Better-Best)¶

    Level Approach What You Get
    Good Simple entity linking — extract named entities and link them in the graph without typed relations Basic entity co-occurrence; enables single-hop lookups but no real traversal reasoning
    Better Typed relations and path constraints — schema-defined edge types with query-time depth/type filters Multi-hop retrieval with controlled precision; queries follow meaningful semantic paths
    Best Learned retrieval policies with feedback loops — model selects traversal strategies based on query type; eval metrics feed back into extraction and retrieval tuning Adaptive, self-improving graph RAG; extraction quality and retrieval relevance improve over time

    Most teams should target "Better" before attempting "Best" — typed relations with path constraints deliver the majority of graph RAG's value without the engineering overhead of learned policies.

    Graph Embeddings for Semantic Search¶

    Method Approach Use Case
    node2vec Random-walk + skip-gram Node similarity, link prediction
    TransE Translational distance in embedding space Knowledge graph completion
    GraphSAGE Inductive node embeddings via neighbor aggregation Large evolving graphs; generalization to unseen nodes
    GNN-based Graph neural networks (GCN, GAT) Classification, clustering, relation prediction

    Hybrid Retrieval: Vector + Graph¶

    • Step 1: Vector similarity retrieves seed entities or passages
    • Step 2: Graph traversal expands to neighbors, relationships, and claims
    • Step 3: Combined context assembled into prompt with budget controls
    • Outperforms pure vector search on multi-hop and relationship-heavy queries

    Schema Design Patterns¶

    Pattern Structure Best For
    Hub-and-spoke Central entity with radiating relationships Customer 360, product catalogs, entity-centric RAG
    Event sourcing Temporal edges with timestamps; immutable event nodes Audit trails, change tracking, temporal reasoning
    Hierarchical taxonomy IS_A / PART_OF directed edges forming trees/DAGs Ontologies, category systems, organizational structures
    Multi-tenant isolation Tenant label/property on all nodes; query-time filtering SaaS applications, shared graph infrastructure
    Bipartite Two node types connected only to each other Recommendations (user-item), document-entity linking

    Graph + LLM Integration Patterns¶

    Pattern How It Works Key Consideration
    Text-to-Cypher / Text-to-SPARQL LLM translates natural language to graph query; execute against DB Requires schema awareness in prompt; validate generated queries
    LLM entity & relation extraction LLM extracts (entity, relation, entity) triples from text Prompt engineering for consistency; needs entity resolution
    Graph-grounded generation Retrieved subgraph facts injected as structured context Reduces hallucination; facts are traceable and auditable
    Agentic graph exploration LLM agent iteratively queries graph, decides next traversal step Handles complex multi-hop questions; higher latency/cost
    Graph-aware reranking Rerank retrieved passages using graph proximity/centrality signals Improves relevance for relationship-heavy queries

    When to Use: Graphs vs Vectors vs Relational¶

    Criterion Graph DB Vector DB Relational DB
    Query type Relationship traversal, multi-hop, path queries Semantic similarity, fuzzy matching Structured filters, joins, aggregations
    Data structure Highly connected, heterogeneous Unstructured/semi-structured embeddings Tabular, normalized
    Explainability High -- paths and relationships are explicit Low -- similarity scores only Medium -- SQL is auditable
    Schema flexibility High (schema-optional) Schema-free Rigid (schema-enforced)
    Best for RAG Entity-centric QA, multi-hop reasoning, provenance Passage retrieval, semantic search Metadata filtering, structured data QA
    Scalability pattern Traversal depth matters more than data volume Scales with embedding count (ANN indexes) Scales with proper indexing and partitioning
    ACID compliance Neo4j: full ACID; others vary Generally eventual consistency Full ACID
    Hybrid with Vector DB for semantic seed + graph expansion Graph DB for structured expansion pgvector for embedded vector search

    Ontology and Vocabulary Discovery¶

    A persistent gap in knowledge graph construction is discovering existing ontologies and vocabularies before building from scratch. AI can generate taxonomies from scratch about any domain, but it would produce better results — or eliminate the need entirely — if it first searched for existing, well-maintained vocabularies in the same domain. As generation becomes effortless, coordination and discovery become more important than creation.

    Open Knowledge Graphs (OKG) addresses this gap directly. Built on Wikidata and refreshed daily via SPARQL queries, OKG indexes 1,803 ontologies/vocabularies, 165 semantic web software tools, and 660 indexed pages as of March 2026. Resources are sorted by quality signals (description completeness, official webpage, license, recency of updates) and categorized by topic using LLM classification. The project provides an API with semantic search (query "movies" → returns Film Club Knowledge Graph), downloadable TTL and JSON datasets, and an MCP server for direct agent integration — enabling agents to ask "find an ontology about biodiversity with an open license" and automatically retrieve one (Steve Hedden, Mar 2026).

    Key: The gap in knowledge graph construction is not generation — it's discovery. Agents should search for existing ontologies before generating from scratch. OKG (openknowledgegraphs.com) + its API and MCP server make this possible programmatically.
