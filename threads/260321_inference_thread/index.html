    Thread: Inference Bottleneck¶

    Date: 2026-03-21 | Archetype: Reframing | Pillar: Inference & model-serving | Status: draft

    1/ Your LLM inference bottleneck isn't the GPU. It's the memory system beneath it.

    An H100 delivers 3,958 TFLOPS. A single decode step for a 70B model reads 140 GB through 3.35 TB/s of HBM and waits.

    The GPU is idle. The memory bus is the constraint.

    2/ This isn't a tuning tip. It's the structural reality of autoregressive decoding.

    Benchmarks confirm >70% of end-to-end inference time is spent in the decode phase. Decode is sequential and memory-bound. Prefill is parallel and compute-bound.

    Two completely different optimization targets sharing one GPU.

    3/ The three highest-impact decode interventions — KV cache locality, token-level parallelism, and speculative decoding — deliver 2-4x throughput improvement.

    Without adding a single FLOP.

    This is a memory-system and scheduling problem disguised as a deep learning problem.

    4/ PagedAttention proved it first. vLLM applied OS virtual memory primitives — page tables, copy-on-write, demand paging — directly to the KV cache.

    Result: memory waste dropped from 60-80% to under 4%. Up to 24x throughput gain.

    The insight wasn't about attention. It was about memory management.

    5/ The OS layer beneath your serving runtime matters more than most teams realize.

    Your choice of memory allocator alone introduces 10-18 GB of RSS variance on identical workloads. That's thousands of KV cache pages you're silently losing to glibc malloc arena fragmentation.

    6/ Transparent Huge Pages in default mode inject 10-100ms compaction stalls into tail latency. NUMA misalignment adds microseconds per DMA transfer that compound across millions of decode steps.

    These aren't exotic optimizations. They're baseline correctness for production inference.

    7/ Speculative decoding — the most hyped decode optimization — is hitting a ceiling.

    Gains plateau at ~2-3x. Constrained by misprediction rates and KV cache duplication overhead.

    The next step isn't better draft models. It's hybrid approaches: speculative + KV-sharing + partial verification.

    8/ Meanwhile, the cheapest optimization is often software scheduling.

    Topology-aware GPU placement yields 20-40% throughput gains with zero hardware changes. Minimize cross-rack attention traffic instead of buying faster GPUs.

    HBM3E delivers 5-8 TB/s theoretical. Real workloads hit 30-55% utilization. Fixing access patterns > adding bandwidth.

    9/ FlashAttention 4 on Blackwell tells the same story from the kernel level.

    Blackwell doubled tensor-core throughput. But shared-memory bandwidth and non-matmul units didn't scale proportionally.

    The optimization frontier is now kernel scheduling and algorithm-kernel co-design. Not raw FLOPS.

    10/ The evidence is unambiguous: inference performance in 2026 is dominated by software — schedulers, memory orchestration, and kernel fusion — not by hardware generation.

    If you're waiting for the next GPU to solve your latency problem, you're optimizing the wrong variable.

    Alt Hooks¶

    1. (data-led) An H100 has 3,958 TFLOPS. During LLM decode, most of them sit idle waiting on memory. Your inference stack is solving the wrong problem.
    2. (contrarian) Everyone is buying faster GPUs for inference. The teams getting 2-4x gains aren't. They're fixing memory access patterns, schedulers, and OS-level fragmentation.
    3. (curiosity) Your memory allocator choice silently wastes 10-18 GB per inference server. That's thousands of KV cache pages — gone before the model even loads.
    4. (reframe) Inference engineering isn't a GPU problem, a model problem, or a framework problem. It's an operating systems problem. Here's why.
    5. (builder-cred) After profiling production inference stacks, the pattern is clear: the biggest gains come from the layers nobody talks about — OS tuning, memory layout, scheduler topology.

    Alt Endings¶

    1. (implication) The next "GPU generation" that matters for inference might not be a GPU at all. Dedicated decode silicon — SRAM-heavy, minimal HBM — is coming. The memory wall is becoming a product category.
    2. (action-item) Three things to check on your inference stack today: (1) Is THP set to madvise instead of always? (2) Are your TP groups on NVLink-connected GPUs? (3) What's your actual HBM utilization vs theoretical? Start there before buying hardware.
    3. (open-question) If software scheduling improvements match the impact of hardware generation upgrades, what does that mean for how we budget AI infrastructure?

    Reply Prompts¶

    1. One caveat: prefill-heavy workloads (long RAG contexts, document ingestion) are still compute-bound. The memory-wall thesis applies most strongly to decode-dominated workloads — which is most production serving.
    2. Curious what others are seeing: has anyone measured their actual HBM utilization vs theoretical bandwidth? The 30-55% ceiling keeps showing up in profiling but I rarely see teams track it as a KPI.
    3. Related: Manus reports a 100:1 input-to-output token ratio in their agent loops. At that ratio, KV cache efficiency and decode latency dominate everything.

    Teaser¶

    LLM inference is a memory-system problem disguised as a deep-learning problem. The GPU is waiting. The memory bus is the constraint. Wrote a thread on what actually drives throughput in 2026.

    Repurpose Blurb¶

    LLM inference performance is dominated by memory systems and software scheduling, not GPU compute. The decode phase accounts for >70% of inference time and is memory-bandwidth bound, meaning optimizations like KV cache locality, topology-aware scheduling, and OS-level memory management deliver 2-4x gains without additional hardware. Teams still treating inference as a GPU selection problem are optimizing the wrong variable.
