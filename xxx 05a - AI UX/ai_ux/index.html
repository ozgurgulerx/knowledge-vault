    AI UX¶

    Opening Briefing¶

    AI UX is not traditional UX with a model bolted on. It is a distinct design discipline whose core problem — designing for systems whose outputs are probabilistic, non-deterministic, and capability-shifting — invalidates the foundational assumptions of conventional interface design. In traditional software, the designer specifies behavior exhaustively: every state, every transition, every edge case. In AI-driven software, the designer specifies constraints on emergent behavior — guardrails, confidence thresholds, escalation policies, identity contracts — and then iterates against live model outputs that no mockup can predict.

    This distinction has three structural consequences that define AI UX as a field.

    First, the interaction surface is the prompt architecture, not the visual interface. The system prompt, context assembly strategy, output formatting constraints, and identity specification (the "soul file") collectively determine how the product feels to use. A designer who does not shape these artifacts is designing a shell around behavior they cannot control. Prompt engineering is a UX discipline — possibly the UX discipline for AI products — because it is where personality, constraints, safety rails, and relational identity are authored.

    Second, the reversibility-risk gradient replaces user preference research as the primary pattern-selection heuristic. Ghost-text autocompletion works for low-risk suggestions because the cost of a bad accept is one backspace. An agent deploying code or sending emails demands explicit confirmation gates, audit trails, and rollback capabilities. The interaction pattern is not chosen by aesthetic preference or user testing alone — it is indexed to the cost of failure. This gradient governs the entire design pattern catalogue: conversational, inline, canvas, command palette, ambient, and agent dashboard are positions on a risk axis, not a style menu.

    Third, the transition from assistive to agentive AI is not a spectrum but a phase transition. When a system moves from "user delegates discrete tasks" to "user delegates goals, agent plans autonomously," every UX assumption changes simultaneously: error recovery moves from "offer regeneration" to "rollback a multi-step plan," transparency moves from citing a source to exposing a full reasoning trace, feedback loops must capture not just output quality but plan quality. Teams that treat this as a gradual slide discover in production that their entire interaction model breaks at the boundary.

    A fourth dimension compounds these challenges: users do not merely want competence from AI. They want software that feels aligned, legible, and relationally coherent. The social-emotional surface — personality, rapport, trust calibration — is not cosmetic. It changes retention, trust calibration, and willingness to delegate high-stakes tasks. Teams that treat personality and relational design as afterthoughts build agents that are technically capable but experientially flat.

    AI UX therefore operates at the intersection of four concerns that traditional UX keeps separate: interaction design (patterns, flows, discoverability), prompt architecture (system prompt, context assembly, output formatting, identity), trust engineering (transparency, explainability, confidence calibration, error recovery), and behavioral economics (risk-indexed pattern selection, feedback loop design, incentive alignment). This section maps the territory across all four.

    Core Frameworks¶

    The Reversibility-Risk Framework¶

    The single most important decision heuristic in AI UX. Every interaction pattern maps to a position on the risk axis:

    Risk Level Pattern Example UX Requirement
    Low (easily reversible) Auto-complete, ghost text, suggestions Gmail Smart Compose Accept/dismiss; no confirmation needed
    Medium (reversible with effort) Content generation, summarization, editing assistance Notion AI, ChatGPT Canvas Preview before apply; undo available
    High (hard to reverse) Data modification, email sending, code deployment, financial transactions AI agents, workflow automation Explicit confirmation; human-in-the-loop; audit trail; rollback

    Design rule: Match interaction pattern to reversibility risk. Never use a low-risk pattern for a high-risk action. When uncertain, err toward more confirmation.

    The Discovery Matrix¶

    Crossing user intent against system initiative resolves the discoverability problem that most AI products handle with a sparkle icon and hope:

    Low system initiative (waits) High system initiative (proactive)
    High user intent (seeking) Strong affordances, clear naming, easy entry points Lean into acceleration — user is active and system is confident
    Low user intent (not seeking) Gentle awareness, discoverable but not pushy Show up helpfully with timing, confidence thresholds, and clear exit paths

    The high-initiative / low-intent quadrant is where most AI features fail: the system surfaces suggestions the user didn't ask for, without sufficient confidence or timing discipline, training users to ignore everything.

    Assistive vs. Agentive: The Phase Transition¶

    Dimension Assistive AI Agentive AI
    Delegation model User delegates discrete tasks User delegates goals; agent plans autonomously
    Error recovery Offer regeneration Rollback multi-step plans
    Transparency Cite sources Expose full reasoning traces, tool usage, decision points
    Feedback loops Output quality (thumbs up/down) Plan quality, step-by-step evaluation
    Trust model "Did it answer correctly?" "Is its plan safe? Will it escalate appropriately?"
    Control model Edit/accept/reject output Approve/modify plans; set boundaries; interrupt execution

    This is not a spectrum. It is a phase transition that changes every UX assumption simultaneously.

    Stateful Collaboration Systems¶

    The chat paradigm is degrading into just one view over a deeper task state machine. New work focuses on persistent interaction state — goals, constraints, intermediate artifacts — rather than stateless prompt/response loops. Interfaces increasingly expose task graphs, memory slots, and evolving plans as first-class UI primitives. The implication: the underlying data model is no longer a conversation transcript but a structured state object that multiple interface views (chat, canvas, dashboard, timeline) can render differently. Products that treat chat as the primary abstraction rather than a projection of richer state will hit scaling walls as agent capabilities grow.

    The downstream consequence is a shift from prompting to state addressing. Users increasingly interact by referencing objects, steps, and prior outputs within the system graph — "update step 3 with X," "rerun using dataset v2" — rather than re-describing context from scratch. Interaction becomes querying and mutating a persistent state graph, not composing natural language instructions. This reframes the UX challenge: the interface must expose addressable nodes (tasks, artifacts, parameters, outputs) and support direct manipulation of graph state, not just free-text input (arXiv, agent systems, 2025–2026).

    Three related patterns are crystallizing from this shift:

    Plan-first interfaces — systems that expose explicit plans before execution, with editable step graphs and user approval checkpoints. The plan becomes a first-class UI object: users review, modify, and approve the plan before the agent acts, reducing silent failure propagation and misaligned long-horizon execution. This is distinct from simple confirmation dialogs — the plan is a rich, interactive artifact that the user co-authors with the agent (arXiv, human-AI collaboration, 2025–2026).

    Artifact-centric interaction — interaction increasingly revolves around documents, code, data tables, and UI components rather than conversational turns. Conversation becomes a secondary control layer for navigating and refining artifacts. The emerging pattern: artifact ↔ agent ↔ refinement loop, where the artifact is the primary locus of collaboration and the chat channel is used for steering, not consuming. The analogy crystallizing in practice: chat = CLI, generated UI = GUI, agents = runtime. Chat acts as a command layer and query interface over system state; actual work happens in generated UIs, artifacts, and agent workflows. This accelerates the degradation of chat-as-primary-interface toward chat-as-control-plane (arXiv, agent UX, 2025–2026; emerging agent platform patterns from OpenAI, Anthropic, Microsoft).

    State addressing as interaction primitive — rather than conversational re-prompting, users point at specific nodes in the system's state graph and issue mutations directly. This implies interfaces need stable, user-visible identifiers for steps, artifacts, and parameters — analogous to cell references in spreadsheets but applied to agent workflows. The pattern collapses the distinction between "talking to the AI" and "editing the system": every user action is either a query against state or a mutation of it (arXiv, agent systems, 2025–2026).

    Intent locking — an emerging primitive that complements state addressing. After initial clarification, systems freeze core intent variables — the user's goal, success criteria, and key constraints — preventing silent mutation during execution. Users can explicitly unlock and modify locked intent, but the system cannot drift from the original goal without surfacing the divergence. This eliminates mid-process goal corruption, a common failure mode in agentic systems where intermediate steps subtly rewrite the objective the user originally specified. The lock/unlock mechanism gives users version-control-like semantics over their intent: the system operates against a pinned intent snapshot, and any proposed change requires explicit user approval (arXiv, agent UX, 2025–2026).

    AI UX as Socio-Technical System¶

    A growing body of HCI research argues that AI UX should no longer be treated as a frontend usability problem but as a system-level interaction across models, infrastructure, governance, and human workflows — what one paper calls "Society-in-the-Loop" design (arXiv, "Beyond the Interface: Redefining UX for Society-in-the-Loop AI Systems," 2026). The implication: interfaces should expose operational signals and decision provenance, not just responses.

    Four evaluation metrics proposed for this framing:

    Metric What it measures
    Accuracy (FPR/FNR) Impact of false positives/negatives on downstream decision-making
    Operational latency Time from model output to human action
    Adaptation time How quickly systems can be tuned or redeployed
    Trust calibration Human reliance vs. oversight balance

    Interface Modality Selection Framework¶

    A research framework proposes designing AI interfaces along three dimensions that together determine the best interface modality (arXiv, "Interface Framework for Human-AI Collaboration within Intelligent User Interface Ecosystems," 2026):

    1. Workflow complexity — how many steps and dependencies the task involves
    2. AI autonomy — how much independent action the system takes
    3. Reasoning depth — how much chain-of-thought or multi-step reasoning is required

    These dimensions map to a modality spectrum: prompt bar → chat workspace → split-screen collaboration → fully autonomous agent UI. The key design insight is fluid transitions between modes rather than fixed UI patterns — future apps may dynamically switch between chat, tool UI, and autonomous agent modes as task demands shift within a single session.

    Dual-Speed Interfaces¶

    An emerging pattern addresses the fundamental tension that one interface cannot serve both novice and expert usage. Dual-speed design provides two interaction modes within the same product:

    • Fast path — minimal UI, instant answers, zero friction. Optimized for speed and flow state. Example: tab-complete in dev copilots, one-click suggestions, ambient auto-actions.
    • Deep path — full control surface: plan editing, tool visibility, step inspection, reasoning traces. Optimized for understanding and steering. Example: opening the agent panel in a coding assistant to see and modify the execution plan.

    The trigger for mode switching is user intent or detected uncertainty — when the system is confident and the task is routine, it stays in fast mode; when it detects ambiguity, high stakes, or explicit user demand for control, it surfaces the deep path. The design challenge is making mode transitions fluid rather than jarring — the deep path should feel like zooming in on the fast path, not switching to a different product. This pattern complements the reversibility-risk framework: low-risk actions default to fast path, high-risk actions surface the deep path automatically (synthesized from copilot and enterprise AI UX teardown reports, 2025–2026).

    Technology-Driven Design Process¶

    AI capabilities evolve faster than designers can study them, while HCI experts routinely join AI projects after the interaction model has already calcified. The co-development process counters this:

    Stage Purpose
    Characterize capabilities Understand what the AI system can and cannot do before designing interactions
    Identify activities Map activities the technology could support
    Understand users Deep-dive into user needs, workflows, and contexts
    Co-develop Iteratively develop technology and UX together — design and engineering in phase

    Key facilitators: WoZ/iML prototyping tools, AI technical education for designers, and bidirectional design-code tools (e.g., Figma MCP for design-to-code-to-canvas loops).

    Prompt Architecture as UX Design¶

    The prompt architecture is where the product's personality, constraints, and behavior are authored. It is the primary UX artifact:

    Layer Function UX Impact
    System prompt Product personality, constraints, behavior rules Defines tone, boundaries, refusal behavior, communication style
    Context assembly What information the model sees (retrieved docs, user history, tool outputs) Determines relevance, grounding, personalization
    Output formatting Structured outputs (JSON mode, XML tags) for reliable UI rendering Enables consistent, parseable, renderable responses
    Identity design ("Soul.md") Durable agent constitution — personality spec defining what the agent is, how it relates to humans, its mission, refusal conditions Creates relational coherence; users "feel something" when AI has identity vs. sterile task completion

    The winning stack for consumer and prosumer agents: competence → trust → memory → identity.

    Personality as product surface: Agents that talk naturally, sustain character, and exhibit social texture feel fundamentally different from sterile task-completion interfaces. Identity design makes personality a first-class product artifact: the system prompt sets behavioral rails, the soul file sets relational identity, and together they define how the agent feels to use.

    Trust & Transparency Engineering¶

    Explainability → Inspectability¶

    The field is shifting from explainability (narratives about why the system did something) through inspectability (direct visibility into what exactly happened) toward manipulability (the ability to change what happens next). Users increasingly want not just debuggable systems but steerable ones — where they can edit intermediate reasoning, modify decision branches at the step level, and re-run from any point. The progression: less "here's why" → less "here's what" → more "change this and re-run" (Google PAIR research on controllability, 2025–2026).

    Technique User-Facing Developer-Facing
    Citations "Based on [source]..." Retrieval scores, source IDs
    Reasoning traces "I'm thinking about..." Full reasoning chain in logs
    Confidence signals "I'm not sure about..." Probability scores, uncertainty metrics
    Tool use visibility "I searched for..." / "I calculated..." Tool call logs, execution traces
    Limitations disclosure "I can't access real-time data" Model card, system prompt documentation
    State inspection "Here's what changed..." (diff views) Decision tree logs, branch-point replay

    The implication for agent UX: the right transparency primitive is not a chat explanation but an inspection panel — something closer to browser DevTools than a conversation turn.

    Oversight-by-Design¶

    An emerging design pattern for high-risk AI systems treats human supervision as an interface primitive rather than a governance layer bolted on after deployment (arXiv, "Human Oversight-by-Design for Accessible Generative IUIs," 2026). Key mechanisms:

    • UI risk signals — uncertainty indicators surfaced inline, not buried in developer logs
    • Escalation policies — automated routing to human review when confidence drops below threshold
    • Mandatory review thresholds — hard gates on high-stakes actions that cannot be bypassed
    • Audit logs tied to interface actions — every AI-driven decision linked to the UI event that triggered it

    The distinction from standard HITL patterns: oversight-by-design embeds supervision into the interface architecture from the start, supporting both human-on-the-loop (monitoring with override capability) and human-in-the-loop (active approval required) controls as first-class interaction primitives.

    Error Recovery Protocols¶

    Error recovery is not a secondary concern — it is a core retention driver. Users forgive bad outputs far more readily than they forgive bad recovery. The quality of failure detection, recovery options, and adaptive behavior after errors determines whether users persist with or abandon a product. The key metric: % of failed tasks successfully recovered. Systems that offer explicit recovery UX — "retry with different strategy," "switch approach," "rollback to last good state" — retain users through failure in ways that single-shot regeneration cannot. Design error recovery as a first-class product surface, not an edge-case handler (synthesized from copilot and enterprise AI UX teardown reports, 2025–2026).

    Error Type UX Response
    Hallucination detected Flag output, offer regeneration, show alternative sources
    Refusal Explain why; suggest rephrasing; offer human escalation
    Tool failure Graceful degradation; retry with fallback; inform user
    Timeout/latency Progress indicator; partial results; cancel option
    Out of scope "I can't help with that. Here's what I can do..."
    Plan failure (agentive) Show failed step in plan; offer rollback; allow user to modify plan and retry
    Context drift Goals subtly mutate across turns; constraints get dropped; system remains locally coherent but globally wrong. Mitigate with goal-anchoring UI, periodic state summarization + user verification, and diff views between intended vs current plan
    Latent misalignment drift More subtle than hallucination: the model follows instructions correctly but the underlying objective slowly diverges from user intent — e.g., user goal is "optimize for clarity" but the system gradually optimizes for brevity instead. Mitigate with constraint pinning (re-anchoring to original objectives), periodic goal reification (surfacing "here is what I think you want" for user confirmation), and "why this step?" inline prompts that force the system to justify its optimization direction (arXiv, human-AI collaboration, 2025–2026)
    Specification collapse When user intent is underspecified, the system fills gaps with plausible but incorrect assumptions, and errors compound across steps. Different from hallucination: outputs are plausible and follow instructions, but violate unstated constraints the user assumed were obvious. Mitigate with upfront constraint elicitation (asking clarifying questions before acting), progressive spec refinement UIs (showing the system's interpretation for user correction), and "assumption surfacing" panels that make the system's inferred constraints explicit and editable (arXiv, human-AI collaboration, 2025–2026)
    Invisible state divergence System state evolves silently through memory updates, tool side-effects, and accumulated context changes while the user's mental model of system state lags behind. The user believes the system is in one state; it is actually in another. Mitigate with state diffs (showing what changed between turns), timeline views (visual history of state evolution), and "what changed?" summaries that proactively surface state mutations the user may not have noticed (arXiv, agent UX, 2025–2026)
    Goal laundering Distinct from context drift: user gives a vague goal, the system refines it internally, and the refined goal diverges subtly but permanently from original intent — becoming the invisible baseline for all subsequent actions. Unlike drift (which is gradual and ongoing), goal laundering happens early and compounds silently because neither user nor system recognizes the divergence. Mitigate with "goal snapshot" UI (freezing the original intent as an explicit artifact), diff views between original intent and current operating goal, and re-approval checkpoints that periodically surface the refined goal for user verification (arXiv, agent systems, 2025–2026)
    Interaction dead-ends The user reaches a state where the system cannot proceed and the user doesn't know how to recover — caused by hidden constraints the system cannot surface or invalid intermediate states that block all forward paths. Unlike other failure modes, dead-ends are bilateral: both sides are stuck. Mitigate with always-present recovery affordances: "recover options" (contextual suggestions for unblocking), "rollback / branch" (return to a known-good state or fork an alternative path), and "suggest next actions" (system proposes moves even when it cannot execute them autonomously). These must be persistent UI elements, not just error-state responses (arXiv, agent systems, 2025–2026)

    Feedback Loops & Measurement¶

    Signal Collection¶

    Signal Collection Method Use
    Explicit feedback Thumbs up/down, ratings, corrections Fine-tuning data, eval dataset expansion
    Implicit feedback Acceptance rate, copy/paste, regeneration rate, session length Quality proxy; A/B test metrics
    Error reports Flag/report button Safety monitoring, edge case discovery
    Task completion Funnel analytics End-to-end success measurement
    Plan feedback (agentive) Step approval/rejection, plan modification Plan quality improvement

    Implicit signals outperform explicit feedback. The emerging hierarchy of signal quality, ranked by reliability: (1) reuse/export — the user took the output and used it externally, the strongest endorsement; (2) edit distance — how much the user modified the output before using it, directly measuring quality gaps; (3) follow-up prompts — refinement requests indicate partial value; (4) thumbs up/down — the weakest signal, noisy and inconsistent. The core insight: behavior is truth, stated preference is noise. Tracking output → edited? → reused? → abandoned? produces higher-quality training data than any explicit rating mechanism. This reframes feedback UX design: instead of optimizing the rating widget, optimize the observability of what users do with outputs (emerging production patterns, 2025–2026).

    Key UX Metrics for AI Products¶

    Metric What It Measures
    First-attempt success rate How often the AI gets it right without regeneration
    Regeneration rate How often users reject and retry — high rate = quality problem
    Acceptance rate For suggestions/completions — proxy for relevance
    Time-to-value How quickly users get a useful result
    Escalation rate How often users abandon AI and seek human help
    Trust calibration Do users appropriately trust/distrust outputs? (over-trust and under-trust are both failures)
    Override rate For agent actions — how often users modify or reject proposed plans

    Generative UI¶

    Generative UI removes the assumption that a human designer authors every screen. Interfaces are assembled at runtime by models within disciplined constraints.

    The Generation Spectrum¶

    Level How It Works Trade-off
    Static (slot filling) Model fills copy, labels, hints within fixed layouts Safest; limited flexibility
    Declarative (component assembly) Model selects from registered component library via typed schema Best balance of flexibility and reliability
    Fully generated Model emits raw HTML/CSS/code Maximum flexibility; hardest to govern

    Contracts Before Intelligence¶

    Five contracts must be in place before any model touches interface generation:

    1. UI schema (DSL): Typed JSON/YAML describing pages, layouts, components, bindings. Versioned and validated.
    2. Design system primitives: Tokens, layout primitives, stable component library with accessibility guarantees.
    3. Capability map: What the app can do. The model composes only from declared capabilities.
    4. Policy and safety: Allowlists, prop constraints, data scopes, redaction rules. Invalid schemas rejected, never rendered.
    5. Observability: Structured logs feeding evaluation loops.

    Runtime software synthesis is the logical endpoint: users should not settle for generic software if an AI can generate a UI tailored to their workflow and preferences. The contracts-first architecture makes this tractable — DSL, tokens, capability map, and policy provide guardrails within which synthesis operates safely.

    The emerging direction is constraint-based UI synthesis — a disciplined evolution beyond free-form generative UI. Instead of models emitting arbitrary HTML/CSS, systems generate interfaces from schema constraints, capability graphs, and safety rules. This yields verifiable UI behavior and composability with backend systems. The synthesis pipeline: intent → structured spec → UI synthesis → interaction loop. This is the contracts-first approach taken to its logical conclusion: the constraints are the generative medium, not just guardrails around it.

    This reframing is solidifying into a broader pattern: generative UI as constraint solving. The shift is from "generate a UI" to "solve for a UI that satisfies all constraints simultaneously" — where the input set includes user intent, device and runtime limits, and safety/policy rules. The model acts as a layout and workflow solver, not a generator in the creative sense. The output is the interface that satisfies the constraint system, not the interface the model "wants" to produce. This makes generative UI tractable for production: the solution space is bounded, verifiable, and auditable because the constraints are explicit (arXiv, generative UI and agent systems, 2025–2026).

    The Paradigm Shift: Answer → Interface → Workflow¶

    Generative UI is collapsing the boundary between assistant and application. The emerging interaction pattern replaces "Prompt → Text" with a three-stage pipeline: conversational input triggers model reasoning, which generates interactive UI components — charts, dashboards, forms, or workflows — as the output artifact. The UI itself becomes an AI output, not a static container for AI responses (Emerge Haus, AI Atlas Report, Q2 2025).

    Google Research formalized this with a generative UI architecture where LLMs produce entire interactive interfaces — tools, dashboards, simulations, buttons, charts, and forms — in response to a prompt rather than returning text (Google Research, "Generative UI: LLMs are Effective UI Generators," 2026). Early deployments are appearing inside Gemini AI Mode and dynamic view interfaces, marking the transition from research concept to shipped product. The implication: interfaces become runtime artifacts generated by models, not designed screens.

    This is part of a broader convergence of three interaction paradigms: (1) generative interfaces where AI creates UI dynamically, (2) agent workspaces where users supervise multiple AI agents, and (3) adaptive modality where the interface mode changes based on task complexity. Together these point toward what some researchers call AI-native operating environments — not applications but environments where the interface is continuously synthesised, the agents are persistent, and the modality adapts fluidly.

    Self-Adapting Interfaces¶

    A growing trend in AI UX is interfaces that reconfigure themselves based on user behavior and context — reordering menus, modifying workflows, and generating components dynamically. This goes beyond static personalization: the interface itself becomes adaptive, adjusting layout, feature prominence, and interaction patterns based on observed usage, expertise level, and task context (Medium, "AI-Driven Trends in UI/UX Design 2025–2026").

    The next evolution is capability-aware adaptation — interfaces that adapt not just to the user but to the model's current state: available tools, context window capacity, confidence levels, and latency constraints. The UI dynamically shows or hides tool affordances, simplifies flows under uncertainty, and escalates to human control when model confidence drops. Combined with generative UI, this points toward a future where no two users see the same application surface, and the surface itself reshapes in real time as model capabilities shift mid-session.

    A specific manifestation is progressive disclosure engines — interfaces that dynamically hide complexity initially and reveal controls as user intent stabilizes. Driven by confidence thresholds, task maturity, and user behavior signals, these systems avoid both cognitive overload (showing everything) and underpowering (hiding too much). The disclosure curve adapts in real time: a novice user exploring a topic sees a simplified surface, while the same interface surfaces advanced controls as the user's queries signal domain expertise and specific intent (arXiv, human-AI collaboration, 2025–2026).

    A further evolution is uncertainty-aware adaptation — interfaces that adapt based on the model's own confidence, the ambiguity level of the current task, and the risk profile of proposed actions. High uncertainty triggers expanded UI: show alternatives, surface controls, present options for user steering. Low uncertainty compresses the interface and may auto-execute. This makes the interface a live reflection of model state, not a static layout — the amount of UI the user sees is proportional to how much the system needs human guidance at that moment (arXiv, human-AI collaboration, 2025–2026).

    A critical counter-pattern is emerging: stability over optimization. Systems that adapt too aggressively erode user trust — users lose spatial memory, develop learned helplessness about where controls live, and begin to distrust the interface itself. The response is deliberate adaptation dampening: cooldown periods between UI changes, hysteresis thresholds that prevent oscillation (the interface must cross a higher confidence bar to change than to stay), and explicit penalization of excessive layout mutations. The insight: predictability is more valuable than optimal layout. A slightly suboptimal but stable interface outperforms a theoretically superior one that keeps shifting. This directly constrains the progressive disclosure and uncertainty-aware adaptation patterns above — they must be governed by stability budgets, not just optimization targets (arXiv, human-AI collaboration, 2025–2026).

    The patterns above describe how interfaces adapt to model state and user behavior, but a parallel track is emerging: user-model co-evolution. Systems maintain evolving user models — inferred preferences, risk tolerance, expertise level, interaction style — and the UI adapts based on this model. Critically, corrections flow in both directions: the system updates its user model based on user behavior, and the user's behavior shifts in response to the adapted interface. The risk is model drift — the system's representation of the user diverges from reality through compounding inference errors, producing increasingly misaligned adaptations. The emerging mitigation is editable user model panels — interfaces that expose the system's inferred model of the user (what it thinks the user prefers, how it rates the user's expertise, what risk tolerance it assumes) and let the user directly correct it. This transforms user modeling from an opaque backend process into a transparent, negotiable contract between user and system (arXiv, agent UX, 2025–2026).

    Discoverability Anti-Patterns¶

    Common failure modes in AI feature discovery:

    Anti-Pattern Symptom Fix
    Sparkle-and-pray Single sparkle icon for all AI features Differentiate AI capabilities with specific, descriptive entry points
    Unsolicited interruption Proactive suggestions without confidence threshold Gate proactive suggestions on confidence score; respect dismissal
    Hidden power Powerful AI features buried in menus Surface contextually when the user's task matches the capability
    Capability ambiguity Users don't know what the AI can do Onboarding that demonstrates 2-3 core capabilities; contextual hints
    Over-promising UI implies perfection; no uncertainty signals Calibrate expectations; show confidence; disclose limitations

    Design Practice in the AI Era¶

    LLM-Generated Personas for UX Research¶

    A new UX research method uses LLM-driven "interactive virtual personas" — designers can interview simulated users, test product ideas, and run rapid feedback loops without recruiting real participants (arXiv, "Augmenting Design with Interactive Virtual Personas," 2025). Promising for early design iteration cycles, but with observed limitations: overly optimistic feedback, bias amplification, and lack of real-world nuance. Best treated as a pre-screening tool that accelerates hypothesis generation, not a replacement for real user research.

    The Structural Shift¶

    The classic design process (Research → Discovery → Mockups → Prototype → Iterate → Ship) is collapsing. AI products require:

    • Build-first discovery — prototype with real model outputs, not static mocks
    • Implementation literacy — designers edit CSS, front-end code, polish features directly in codebase
    • Shrinking vision horizon — 10-year visions → 3-month experiments (AI capabilities change weekly)
    • Trust through iteration speed — users trust products that improve weekly

    Time Allocation Shift¶

    Activity Traditional AI Era
    Mockups / prototyping 60-70% 30-40%
    Engineer pairing 20% 30-40%
    Implementation — ~20%
    Coordination 10% ~10%

    Designer Archetypes for AI Teams¶

    1. Strong Generalists — block-shaped skillset across design, product thinking, engineering, UX, strategy (each ~80th percentile)
    2. Deep Specialists — T-shaped in visual design, technical UX, interaction systems, or AI interface design
    3. Builder New Grads — high curiosity, fast learners, low process baggage; the field changes so fast that experience can become inertia

    Agent UX Architecture¶

    Terminal UX as Agent Interface¶

    A research paper argues that the terminal interface is an ideal model for human-AI agent collaboration, offering properties that chat-based interfaces struggle to match (arXiv, "Terminal Is All You Need: Design Properties for Human-AI Agent Collaboration," 2026):

    • Full transparency — every agent action is visible as an executable command
    • Minimal abstraction — no UI layer hiding what the agent is doing
    • Easy intervention — users can interrupt, modify, or redirect at any point

    Many modern coding agents (Claude Code, Codex CLI, Aider) adopt terminal-like interfaces precisely for these properties. The implication: agent UX may converge around observable execution environments rather than chat windows, especially for technical and high-stakes workflows where action auditability matters more than visual polish.

    Single-Agent Design Principles¶

    • Appear when needed, invisible when not — the defining UX goal
    • Sense-think-do loop visible to user at appropriate granularity
    • Progressive disclosure of reasoning — summary first, full trace on demand
    • Interrupt and redirect — user can always stop, modify, or redirect the agent. Interruptibility is emerging as a core UX primitive, not just a safety feature: systems now explicitly model pause/resume, step override, and mid-execution edits. The pattern: long-running agent → user injects correction → system re-plans locally without restarting. Interruptibility increasingly matters more than autonomy for real-world usability — the ability to course-correct mid-flight is what makes users willing to delegate in the first place (arXiv, agent UX, 2025–2026)
    • Graceful degradation — when agent fails, fall back to manual with context preserved

    Multi-Agent UX Considerations¶

    When multiple agents coordinate, UX must surface:

    • Which agent is acting and its role/authority
    • Shared state — what the agents collectively know and have done
    • Coordination status — who is waiting for whom, what's blocked
    • Delegation chain — how a high-level goal decomposed into agent-assigned tasks
    • Consolidated controls — human-in-the-loop gates at agent boundaries, not just within agents

    Dual-Channel Interfaces¶

    The tension between transparency and cognitive overload is resolving into a specific architectural pattern: dual-channel interfaces with two parallel layers running simultaneously. The execution layer handles agent task execution (tool calls, data fetching, workflow progression), while the explanation layer provides selective visibility into what happened and why. Users toggle between minimal mode (execution only — clean, fast, low cognitive load) and inspect mode (explanation layer revealed — traces, reasoning, decision points). This solves the transparency-overload tradeoff that plagues single-layer interfaces: users who want to trust-and-go can stay in minimal mode; users who need to verify, debug, or learn can drop into inspect mode without the system's behavior changing. The dual-channel pattern is emerging as the structural implementation of the "inspect mode / debug view" concept described elsewhere — not just a feature toggle but an architectural commitment to maintaining two parallel representations of every agent action (arXiv, agent systems, 2025–2026).

    Invisible Orchestration and Zero-Interface Layers¶

    An emerging pattern where AI handles tool routing, data fetching, UI generation, and workflow management behind a seamless, minimal interface — the user sees no explicit system boundaries. This "Truman-style" UX maximizes flow but carries a fundamental risk: loss of user mental model. When the orchestration is invisible, users cannot diagnose failures, predict behavior, or build accurate expectations. The counter-pattern is a "peek behind the curtain" mode — an inspectability layer (see Explainability → Inspectability and Dual-Channel Interfaces above) that users can invoke on demand without breaking the primary flow.

    Early systems are pushing this further toward zero-interface layers — minimizing visible UI entirely through proactive actions, ambient adaptation, and implicit workflow completion. The user interacts via interruptions, not commands: the system acts autonomously and the human intervenes only when something needs correction. The emerging architecture: event bus + agent listeners + UI reflection layer — agents subscribe to environment signals (calendar changes, document edits, file system events, communication triggers) and act without explicit prompts. The UI reflection layer surfaces what happened and what changed, but only after the fact. The risk spike is significant: loss of situational awareness and invisible failures where the user doesn't know something went wrong because they never saw it happen. This represents the extreme end of the autonomy spectrum and requires correspondingly robust safety mechanisms — forced re-engagement points, anomaly surfacing, and "nothing happened silently" guarantees (arXiv, agent UX, 2025–2026).

    A related pattern is continuous partial execution — instead of completing full tasks atomically, the system executes fragments continuously in the background (drafting → refining → validating), surfacing intermediate outputs as they stabilize. The risk: users encounter mid-state outputs and mistake them for final results. The mitigation is stability indicators — explicit output maturity signals ("draft," "refining," "validated") that communicate where each artifact sits on the completion spectrum. Without these indicators, continuous execution degrades trust because users cannot distinguish a work-in-progress from a finished output (arXiv, agent UX, 2025–2026).

    Over-Delegation Collapse (Interaction Collapse Under Autonomy)¶

    A failure mode cluster where users offload too much to AI: they stop verifying outputs, lose task understanding, and cannot recover when the system fails. This is distinct from automation complacency — it involves active loss of competence through disuse, not just passive inattention. The observed pattern follows a predictable loop: system works → trust builds → oversight drops → failure occurs → user is lost — unable to diagnose, recover, or even recognize the failure because they disengaged from the process. As agent autonomy increases, user engagement decreases non-linearly, and recovery becomes impossible at the point where it matters most.

    Design responses include enforced checkpoints (the system pauses and requires user verification), "explain back" interactions (the user must demonstrate understanding before the agent proceeds), partial manual steps deliberately inserted to maintain engagement, and "confirm critical assumptions" gates where the agent surfaces its key assumptions for user validation before proceeding with high-stakes execution (arXiv, human-AI collaboration, 2025–2026).

    Constraint Shadowing¶

    A distinct failure mode from over-delegation: early constraints get overridden or ignored by later execution steps without the user's knowledge. A user specifies "keep it under budget" or "don't modify the production database," and intermediate agent steps silently deprioritize or reinterpret these constraints as new sub-goals emerge. The constraint is never explicitly violated — it is shadowed by downstream logic that treats it as lower priority than more recent objectives.

    The mitigation is constraint lineage tracking — maintaining a visible chain from each active constraint back to its origin (which user instruction, which step, which policy) and surfacing this lineage in the UI. The key interface element: "which constraint influenced this?" — a per-output or per-step query that shows which constraints were active, which were satisfied, and which were deprioritized or overridden. This makes constraint enforcement auditable and gives users a mechanism to detect and correct shadowing before it propagates (arXiv, agent UX, 2025–2026).

    Agent Observability Stacks¶

    Internal tooling for agent systems is converging toward patterns borrowed from distributed systems: traces (reasoning steps, following a request across agent handoffs), spans (tool calls with timing and parameters), state snapshots (capturing agent state at decision points), and replayable sessions for debugging. Replay and diff are becoming core UX tools — not just for developers but for end users who need to understand what happened and why. This is becoming core to AI UX, not just infrastructure — product teams need the same observability that SRE teams demand.

    Agent debugging UIs are an emerging tooling category, bridging the gap between developer-facing traces and user-facing inspectability. Critically, observability is shifting from a developer-only concern to end-user UX: users are getting trace views, step inspection, and replay controls as standard interface elements. The emerging standard: every AI action should be inspectable and reversible by the end user, not just by the engineering team. The strong prediction: "AI DevTools" will converge toward something resembling Chrome DevTools + Figma + Jupyter merged — combining execution tracing, visual inspection of generated artifacts, and interactive exploration of agent state in a single environment (arXiv, agent UX, 2025–2026).

    The next evolution beyond linear traces is causal graph visualization — showing dependencies between steps, tools, and data as a structured graph rather than a sequential log. Users can see "why this happened" structurally: which upstream tool call produced the data that fed the downstream decision, which constraint triggered which fallback, which earlier step's output is load-bearing for the current state. This moves observability from temporal (what happened in order) to causal (what caused what), making root-cause analysis and "what if I change this?" reasoning accessible to end users, not just developers inspecting traces (arXiv, agent systems, 2025–2026).

    A further shift is from observability-as-history to intervention points mapping — systems that surface not just what happened but where the user can intervene to change outcomes. Instead of presenting a flat trace, the interface highlights leverage points (steps where a small change would significantly alter the result) and high-impact edits (parameters or decisions that are load-bearing for downstream outputs). This reframes observability from a passive audit tool to an active steering interface: the user sees the system's execution graph annotated with actionable intervention opportunities, not just a log of past events (arXiv, agent UX, 2025–2026).

    Communication Between Agents (UX-Relevant)¶

    Agent messages should be structured with: intent, inputs, preconditions, expected effects, and confidence — making inter-agent coordination parseable, auditable, and surfaceable to users who need to understand what happened.

    Microsoft HAX Toolkit¶

    The Microsoft HAX Toolkit is one of the most widely used design frameworks for AI UX, designed to help teams prototype expected AI failures during product design rather than after deployment (Microsoft Research, HAX Toolkit):

    • Guidelines for Human-AI Interaction — 18 design guidelines for AI-powered features
    • HAX Workbook — structured design planning for AI product teams
    • HAX Design Library — reusable patterns for common AI interaction problems
    • HAX Playbook — failure scenario testing to surface edge cases before shipping

    Teams are operationalizing HAX into failure-first design pipelines: (1) enumerate failure modes, (2) simulate interaction breakdowns, (3) bind each failure to a UI mitigation pattern, (4) track in telemetry. An emerging extension is "failure budgets" for AI UX — analogous to SRE error budgets — where products define acceptable failure rates per interaction class, and the interface dynamically adjusts confirmation gates and fallback behavior as the budget is consumed.

    The latest evolution is interaction contracts — teams formalizing HAX guidelines into explicit AI behavior contracts with defined failure expectations and UI commitments for recovery. Example: "If confidence < X → must show alternatives + sources." This shifts HAX from design guidance to enforceable UX specs — testable assertions about what the interface must do under specific conditions, bridging the gap between design intent and runtime behavior (Microsoft HAX Toolkit applied design materials, 2025–2026).

    The broader HAX trajectory is shifting from explainability to negotiability. Early AI UX focused on the system explaining its decisions — "here's why I did X." The emerging pattern inverts this: the user negotiates decisions rather than passively receiving explanations. Concrete UI patterns include tradeoff sliders (letting users adjust the balance between competing objectives — speed vs. thoroughness, creativity vs. accuracy), constraint toggles (explicit on/off controls for rules the system follows), and alternative proposals (the system presents 2–3 options with visible tradeoff surfaces rather than a single recommendation). This moves transparency from a read-only property to a read-write interaction: the user doesn't just see what the system decided but actively shapes the decision space (Microsoft HAX Toolkit, applied evolution patterns, 2025–2026).

    Underlying this is the convergence toward standardized failure taxonomies — teams are consolidating AI interaction failures into shared buckets: misunderstanding intent, overconfidence, inconsistency across turns, and harmful completion. Each bucket maps to specific detection signals (telemetry patterns that indicate the failure is occurring) and UI mitigation patterns (interface responses that address it). The result: reusable failure→UX pattern libraries that can be applied across products, analogous to how design systems standardize visual components but applied to AI behavior failures (Microsoft HAX Toolkit applied design workflows, 2025–2026).

    The Three-Layer Model¶

    AI UX is converging on a three-layer architecture that recurs across products, research, and tooling:

    1. Intent layer — natural language, goals, user preferences
    2. Orchestration layer — agents, tools, plans, state machines
    3. Interface layer — generated/adaptive UI, rendered artifacts

    Most current innovation is concentrated on making layer 2 visible without overwhelming users — the orchestration layer is where the complexity lives, and the central UX challenge is surfacing enough of it for trust and control without collapsing the user into an infrastructure dashboard. Products that nail this layer's visibility design will define the next generation of AI UX.

    Key: The meta shift underway is from interaction design → system behavior design. Four primitives are standardizing as the core objects of AI UX: Spec (intent + constraints), Plan (execution graph), State (memory + artifacts), and Trace (what happened). UX is becoming the system that lets users see, edit, and reconcile these four layers — not buttons or screens. The interface is a projection of system behavior, and UX quality is determined by how well the system's behavior is made legible, controllable, and trustworthy through that projection.

    A complementary framing is stabilizing around five control primitives that cut across all three layers: intent (locked or unlocked — see §Stateful Collaboration Systems), graph (the execution structure the system is following), constraints (tracked and visible — see §Constraint Shadowing), user model (editable — see §Self-Adapting Interfaces), and intervention points (explicit — see §Agent Observability Stacks). Together these define UX as a control system over an evolving computation graph — the user's job is not to operate an interface but to monitor and steer a running computation through these five levers (arXiv, agent UX, 2025–2026).

    Signals Worth Watching¶

    • UI protocols for LLM-generated interfaces — standardization of how models describe and render interactive UI
    • Agent debugging UIs — Chrome DevTools-style inspection for AI agent behavior
    • Persistent memory UX primitives — how interfaces expose and let users manage what the AI remembers
    • Interaction diffing — visualizing how AI state changed over time across turns
    • Hybrid human/AI workflow editors — tools where humans and agents co-author execution plans (plan-editing interfaces combining graph + natural language)
    • Constraint programming for UX — expressing user intent as formal specs that bound agent behavior, making constraints a design medium
    • Agent trace visualization standards — convergence toward shared schemas for how agent reasoning and actions are displayed
    • Adaptive disclosure algorithms — principled approaches to progressive complexity revelation based on user signals and task maturity
    • Interaction-level safety patterns — safety mechanisms designed at the UX layer (not the model layer), addressing failure modes that emerge from how humans interact with agents rather than from model outputs alone
    • State diff + timeline UX — visual history of system state evolution with "what changed?" summaries, making invisible state mutations visible
    • Assumption/constraint visualization — panels that surface the system's inferred constraints and assumptions for user verification and editing
    • Interruptible agent architectures — systems that model pause/resume/step-override as first-class primitives, enabling mid-execution correction without restart
    • End-user trace tooling — observability surfaces designed for non-technical users, making every AI action inspectable and reversible
    • Causal graph visualization — moving beyond linear traces to dependency graphs showing why each step/decision happened structurally
    • Pending-intent management UIs — "inbox" interfaces for system-inferred tasks awaiting user approval or implicit confirmation
    • Adaptation stability budgets — hysteresis and cooldown mechanisms that prevent self-adapting interfaces from changing too aggressively
    • Goal snapshot and diff UX — freezing original user intent and surfacing divergence from refined operating goals over time
    • Intent version control systems — applying VCS semantics (branch, diff, merge, revert) to user intent, enabling users to manage goal evolution with the same rigor as code changes
    • User-model editing interfaces — panels that expose and let users directly correct the system's inferred model of their preferences, expertise, and risk tolerance
    • Intervention-point discovery systems — algorithms that identify and surface high-leverage points in execution graphs where small user edits would most significantly alter outcomes
