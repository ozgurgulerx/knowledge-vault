    UX & Agent Design¶

    Opening Briefing¶

    The conventional framing of AI UX treats interface design and model behavior as separate concerns — designers draw screens, engineers tune prompts, and the two meet at an API boundary. This separation is the root cause of most AI product failures. In practice, the prompt architecture — system prompt, context assembly strategy, and output formatting constraints — is the interaction design. A designer who does not shape prompt architecture is designing a shell around behavior they cannot control, which is why the document that follows treats prompt engineering as a UX discipline rather than an engineering detail.

    Three structural observations make this concrete. First, the reversibility-risk gradient governs which interaction pattern is appropriate far more reliably than user preference research or aesthetic judgment. Ghost-text autocompletion works for low-risk suggestions precisely because the cost of a bad accept is one backspace; an AI agent sending emails or deploying code demands explicit confirmation gates and audit trails because reversal costs are measured in hours or reputational damage, not keystrokes. The pattern catalogue here — conversational, inline, canvas, command palette, ambient, agent dashboard — is not a menu of stylistic options but a risk-indexed decision tree. Second, the discovery matrix crossing user intent against system initiative resolves a problem most AI products handle with a sparkle icon and hope. High-intent, high-initiative interactions can accelerate aggressively; low-intent, high-initiative interactions must clear a confidence threshold before surfacing or they train users to ignore every suggestion the system offers. Third, AI capabilities mutate faster than any design team can study them, yet HCI experts routinely join AI projects only after the interaction model has already calcified around engineering defaults. The co-development loop — characterize capabilities, identify activities, understand users, iterate jointly — is not a process nicety but the only known countermeasure to this timing mismatch.

    Together these observations expose a second-order consequence: the gap between assistive AI (user delegates discrete tasks) and agentive AI (user delegates goals, agent plans autonomously) is not a spectrum teams slide along smoothly. It is a phase transition that changes every UX assumption simultaneously — error recovery moves from "offer regeneration" to "rollback a multi-step plan," transparency moves from citing a source to exposing a full reasoning trace, and feedback loops must capture not just output quality but plan quality. Most teams discover this discontinuity in production, after shipping an assistant and wondering why adding tool-use made the entire experience feel unsafe.

    The platform competition for agent UX is intensifying. Microsoft Copilot Cowork integrates Claude Cowork technology directly into Microsoft 365 Copilot with enterprise controls, security, and pricing under the existing M365 Copilot umbrella. The distribution advantage is formidable — Word, Excel, PowerPoint, Outlook, and Teams are already where office work happens. But distribution alone may not be decisive: OpenAI and Anthropic have been "sharper at making people actually want to use the thing" (Louie Peters, Towards AI, Mar 2026). The tension between distribution incumbency and product craft is becoming the central competitive axis for agent UX in enterprise settings.

    A parallel shift compounds the challenge: users do not merely want competence from AI-driven software. They want software that feels aligned, legible, maybe even companion-like. Old software optimized for clicks and screens; new software may need to optimize for rapport, trust, and coherence of personality (OpenClaw founder interview, 2026). This social-emotional surface is not a cosmetic layer — it changes retention, trust calibration, and willingness to delegate high-stakes tasks. Teams that treat personality and relational design as afterthoughts will find their agents technically capable but experientially flat.

    This document maps the territory from that vantage point. It sequences fundamentals (prompting, RAG, feedback) through agent architectures and multi-agent coordination, anchoring each layer to the reversibility-risk framework and the co-development process that keeps design and capability evolution in phase. The pattern tables, study plans, and design checklists that follow are meant to be used as engineering specifications, not inspirational references.

    Predictive UX as Runtime Infrastructure¶

    UX research is shifting from a pre-launch phase to continuous runtime infrastructure. AI-powered UX research tools now simulate users, predict friction pre-launch, and run continuously in production — detecting hesitation, edits, and abandonment patterns to identify design problems before they compound. Synthetic users are used for edge-case discovery and early validation loops, filling the sparse data regions that real-user testing struggles to cover (DesignRush, Akraya, 2026). The implication: UX research becomes an always-on system observing and predicting interaction quality, not a periodic study conducted before shipping.

    Interaction-Level Failure Modes¶

    The dominant failure mode in AI systems is shifting from output-level failures (hallucination, incorrect answers) to interaction-level failures that are systemic rather than per-response. The emerging taxonomy of interaction failures:

    • Mental model mismatch — the user's understanding of what the system can do diverges from actual capability, leading to misplaced trust or underuse
    • Invisible system state — the user cannot tell what the agent knows, what it has done, or what it plans to do next
    • Over-automation loops — the system takes too many autonomous actions without pause points, eroding user control and creating cascading errors
    • Weak recovery UX — when something goes wrong, the system offers no clear path to undo, roll back, or redirect

    These failures are harder to detect than hallucinations (they don't show up in output quality metrics) and harder to fix (they require architectural changes to how the system communicates state and accepts intervention, not just better model outputs). The shift toward agent-based systems amplifies all four failure modes because the gap between what the system is doing and what the user can observe grows with each step of autonomous execution (2025–2026 UX research, industry reports).

    6-Week Study Plan¶

    Weeks 1-3: LLM UX Foundations¶

    Week 1 -- Foundations of LLMs & AI UX

    • Theme: LLM Basics & Human-Centered Design
    • Read People + AI Guidebook (Google)
    • Take ChatGPT Prompt Engineering for Developers (DeepLearning.AI)
    • Mini-Project: "Hello LLM & UX" -- simple command-line chatbot calling OpenAI API for FAQ answering. Note 2-3 observations about model behavior and how to accommodate them in UI (e.g., "thinking..." indicator for long responses).

    Week 2 -- Core Tools and Frameworks

    • Theme: Building with APIs, LangChain, and LlamaIndex
    • Work through LangChain for LLM Application Development (DeepLearning.AI). Read LangChain docs and OpenAI Cookbook examples.
    • Mini-Project: Build a Chatbot MVP -- minimal chat interface (terminal or web) using LangChain for prompt management and memory. Support at least one advanced feature (tool use or conversation memory).

    Week 3 -- Retrieval-Augmented Generation (RAG)

    • Theme: LLMs + Your Data (Knowledge Integration)
    • Follow Activeloop's GenAI course or OpenAI Cookbook on RAG. Use LlamaIndex or LangChain's Retrieval API. Read the Emerging Architectures blog on in-context learning.
    • Create embedding index (Chroma or Faiss) with 5-10 docs. Practice prompt tuning for RAG (cite sources, say "I don't know" when unsure).
    • Mini-Project: Custom Document Q&A Bot -- e.g., "PolicyBot" answering company policy questions with source citation. Test graceful handling of out-of-scope questions.

    Weeks 4-6: Agent UX Advanced¶

    Week 4 -- Multi-Modal Agent Interfaces & UX Design

    • Theme: Agent Architectures, Multi-Modal Interfaces & UX
    • Study agent architectures (sense-think-do loops, goal-oriented behavior). Understand assistive vs. agentive UX (K. Agrawal's guide).
    • Integrate speech or web chat UI. Apply UX principles: agent "appears when needed, invisible when not." Design for transparency and control (show user what tools/data the agent uses).
    • Use Prompt Engineering Guide for Chain-of-Thought and ReAct patterns. Study OpenAI's function calling and Assistants API.
    • Mini-Project: Multi-Step AI Agent -- e.g., "Travel Planner" that looks up flight prices (mock API) and summarizes best option. Agent uses at least two tools in sequence with ReAct-style prompting. Include prototype UI with UX design rationale.

    Week 5 -- Multi-Agent Systems & Personalization

    • Theme: Multi-Agent Collaboration, Feedback & Personalization
    • Use CrewAI for multi-agent collaboration (e.g., "Planner" + "Executor" agents). Study Stanford's "Generative Agents" concept. Deploy AI Town starter kit.
    • Go through Vercel AI SDK Academy (or Chainlit for Python). Implement personalization techniques (fine-tuning guide, People+AI Guidebook's Feedback + Control chapter).
    • Mini-Project: Deployable Chat App with Multi-Agent Backend -- full-stack web chat with: (a) Streaming UX, (b) Feedback capture (rate/correct AI answers), (c) Personalization (bot greets user by name, uses stored preferences), (d) demo of 2+ agents solving a task together.

    Week 6 -- Evaluation, Deployment & Production Readiness

    • Theme: Making It Robust and Ready for Production
    • Use W&B's "LLM Apps: Evaluation" course and OpenAI's Eval framework. Read Guardrails AI documentation.
    • Production considerations: persistent threads via Assistants API, observability (LangSmith to trace decision steps), reliability (guardrails, finite-state control for critical steps), security/privacy, cost optimization (caching, cheaper models for simple tasks). Truesight MCP (MIT licensed, March 2026) makes AI evaluation feel like unit testing — evaluations are created, managed, and run from any MCP-supporting client (editor, chat, or CLI), with "agent skills" to guide correct evaluation workflows.
    • Agent reliability & adversarial testing tools: Greywall (open source, March 2026) is a CLI sandbox that monitors and blocks agent network access in real time, enforcing runtime safety boundaries. Arksim (open source, March 2026) generates synthetic users to automatically test agents through adversarial conversations, enabling systematic agent failure discovery before production.
    • Design evaluation set (5-10 example queries with expected answers). Identify failure modes. Implement at least one guardrail (mandatory citation, moderation check).
    • Mini-Project: Final Capstone -- Refine and Deploy -- take Week 5 app and make it production-ready: add safety features (Guardrails to filter outputs), logging of conversations, simple evaluation script, deploy to cloud or package in Docker. Outcome: architecture report + deployed agent with runbook for handling failures, monitoring, updates.

    Critical: Weeks 1-3 build LLM UX fundamentals (prompting, RAG, feedback). Weeks 4-6 advance into agent design, multi-agent systems, and production deployment. Each week produces a working deliverable.

    AI UX/UI Design Patterns¶

    Human-AI Interaction Design Challenges & Technology-Driven Process¶

    Designing for AI introduces unique challenges that don't exist in traditional software UX. A technology-driven design process addresses these by moving through four stages, each surfacing specific challenges and requiring specific facilitators.

    Technology-driven design process (4 stages):

    Stage Purpose
    Characterize tech capabilities Understand what the AI system can/cannot do before designing interactions
    Identify user activities Map activities the technology could support
    Understand user activities Deep-dive into user needs, workflows, and contexts
    Tech-UX co-development Iteratively develop technology and UX together

    Human-AI interaction design challenges (surfacing across the stages):

    • Difficult to frame what counts as AI
    • Difficult to articulate what AI can/cannot do
    • Difficult to find skilled AI technical collaborators
    • Difficult to understand a working AI system's design potential
    • Cannot envision AI uses that do not exist yet
    • Do not know how to bring a human-centered view to AI
    • HCI/design experts often join AI teams late in the design/dev process
    • Do not know how HCI/design and AI experts should collaborate

    Technology-driven design facilitators:

    • WoZ/iML tools for exploring AI interactions (Wizard-of-Oz prototyping, interactive machine learning)
    • AI technical education for designers — bridging the knowledge gap so design teams can participate meaningfully from the earliest stages
    • Bidirectional design-code tools — Figma MCP server became bidirectional (March 2026): GitHub Copilot users can pull design context into code AND push working UI back to Figma canvas, tightening the "design → code → canvas → feedback" loop and enabling true co-development between designers and AI-assisted engineers

    Key: The core tension: AI capabilities evolve faster than designers can study them, while designers join AI projects too late to shape the interaction model. The fix is co-development from stage one, supported by prototyping tools (WoZ/iML) and technical literacy programmes for design teams.

    Discoverability & Initialization¶

    AI feature discovery must be educational, intentional, well-timed, and mapped to intent. The sparkle emoji has become the de facto signifier for AI features — recognizable but overloaded, since the variety of AI capabilities far exceeds what one icon can communicate.

    Common negative discovery responses:

    • "There's too much going on, and I don't know what I'm supposed to pay attention to."
    • "I didn't ask for that."
    • "I keep discovering things by accident."
    • "It's cool, but I don't know how to use it."
    • "This doesn't feel like it's for me."
    • "I don't know what it can do."

    Discovery design framework (User Intent x System Initiative):

    Low system initiative (waits to be prompted) High system initiative (surfaces proactively)
    High user intent (user knows they want this) User leads the way — provide strong affordances, clear naming, easy entry points Lean into acceleration — user is active and system is confident, assist without friction
    Low user intent (user isn't looking for this) Tread lightly — gentle awareness, avoid interruption, discoverable but not pushy Show up helpfully — system has a strong hypothesis, surface with timing, confidence thresholds, and clear exit paths

    Design checklist:

    1. "Does the user already know they want this?" — High intent: clear entry points. Low intent: gentle awareness.
    2. "Will the tool surface proactively or wait?" — Low initiative: strong affordances + naming. High initiative: consider timing, confidence level, and exit paths.

    Interaction Patterns by Reversibility Risk¶

    Risk Level Pattern Example UX Requirement
    Low (easily reversible) Auto-complete, suggestions Gmail Smart Compose, ghost text suggestions Accept/dismiss; no confirmation needed
    Medium (reversible with effort) Content generation, summarization Notion AI, ChatGPT Canvas Preview before apply; undo available
    High (hard to reverse) Data modification, email sending, code deployment AI agents, workflow automation Explicit confirmation; human-in-the-loop; audit trail

    Prompt Engineering as UX¶

    • System prompt = product personality, constraints, behavior rules
    • Context assembly = what information the model sees (retrieved docs, user history, tool outputs)
    • Output formatting = structured outputs (JSON mode, XML tags) for reliable UI rendering
    • Identity design ("Soul.md") = a durable agent constitution that goes beyond the system prompt. Most agent frameworks obsess over tools, memory, or planning, but a fourth layer matters: identity. A "Soul.md" is an explicit, persistent identity interface for the model — a personality spec defining what the agent is, how it relates to humans, its mission, and when it should refuse misuse. Early user testing showed strong reactions: users "felt something" when the AI had a soul file, suggesting durable agent constitutions alongside system prompts may become a repeatable design pattern (OpenClaw founder interview, 2026). The winning stack for consumer and prosumer agents appears to be: competence → trust → memory → identity (OpenClaw founder interview, 2026).
    • The PM/designer shapes UX by designing the prompt architecture, not just the visual interface

    Personality as product surface: Agents that talk naturally, sustain character, and exhibit humor feel fundamentally different from sterile task-completion interfaces. An agent joking about its week or roleplaying convincingly is not a trivial demo — it signals that usability is moving from pure task completion toward a hybrid of competence + social texture (OpenClaw founder interview, 2026). Identity design makes personality a first-class product artifact: the system prompt sets behavioral rails, the soul file sets relational identity, and together they define how the agent feels to use.

    Explainability as Operational Transparency¶

    Technique User-Facing Developer-Facing
    Citations "Based on [source]..." Retrieval scores, source IDs
    Reasoning traces "I'm thinking about..." (chain-of-thought) Full reasoning chain in logs
    Confidence signals "I'm not sure about..." Probability scores, uncertainty metrics
    Tool use visibility "I searched for..." / "I calculated..." Tool call logs, execution traces
    Limitations disclosure "I can't access real-time data" Model card, system prompt documentation

    Feedback Loops & Metrics¶

    Signal Collection Method Use
    Explicit feedback Thumbs up/down, ratings, corrections Fine-tuning data, eval dataset expansion
    Implicit feedback Acceptance rate, copy/paste, regeneration rate, session length Quality proxy; A/B test metrics
    Error reports Flag/report button Safety monitoring, edge case discovery
    Task completion Funnel analytics End-to-end success measurement

    Error Recovery Protocols¶

    Error Type UX Response
    Hallucination detected Flag output, offer regeneration, show alternative sources
    Refusal Explain why; suggest rephrasing; offer human escalation
    Tool failure Graceful degradation; retry with fallback; inform user
    Timeout/latency Progress indicator; partial results; cancel option
    Out of scope "I can't help with that. Here's what I can do..."

    Design Pattern Catalogue¶

    Pattern Description Best For
    Conversational (chat) Turn-based dialogue; memory across turns Open-ended exploration, Q&A, support
    Inline/contextual AI embedded in existing workflow (editor, spreadsheet) Productivity tools, code editors
    Canvas/workspace Spatial editing with AI; iterate on artifacts Document drafting, code generation, design
    Command palette Slash commands or keyboard shortcuts invoke AI Power users, quick actions
    Ambient/proactive AI surfaces suggestions without being asked Notifications, smart defaults, anomaly alerts
    Agent dashboard Shows agent plan, progress, tool usage in real-time Complex multi-step tasks, automation monitoring

    Critical: Match interaction pattern to reversibility risk. Low-risk = auto-apply (ghost text). High-risk = confirm-before-execute (agent dashboard with approval gates). The distinction between assistive AI (user delegates tasks) and agentive AI (user delegates goals, agent plans and executes) is the central UX design challenge. Agents should be "helpful but not annoying -- appearing when needed, invisible when not."

    The Human-Agent-UI Triangle: Why Terminal-Based Agent Tools Work¶

    The convergence of agentic tools — Claude Code, OpenAI Codex, Cursor's agent mode — on terminal-based interaction is not coincidental. The Human-Agent-UI triangle framework provides formal HCI grounding for this convergence by identifying three design properties central to effective human-AI-UI collaboration (Alexandre De Masi, University of Geneva, arXiv:2603.10664, CHI 2026).

    Three design properties of the Human-Agent-UI triangle:

    1. Representational compatibility — alignment between the agent's native format (text) and the interface format. Terminal interfaces have direct structural mapping: tool invocations = shell commands, parameters = arguments, output = text streams. No perception or translation layer is needed. GUI agents, by contrast, must solve a perception problem (interpreting pixels, computing coordinates) before they can act — this translation layer is the primary bottleneck. Evidence: a carefully designed text-based Agent-Computer Interface (ACI) outperformed agents using a default Linux shell by 10.7 percentage points on SWE-bench. Using executable Python code as agent action space yields up to 20% higher success rates than JSON-based function calling because code is a more expressive text representation.

    2. Transparency — whether the interaction medium makes agent actions, reasoning, and history visible and inspectable. In terminals, the text stream simultaneously serves as communication channel, explanation surface, chronological record, and approval mechanism. Key distinction: explanations are integrated into the interaction flow rather than requiring separate interfaces. This property directly addresses the interaction-level failure modes documented above — invisible system state, over-automation loops, and weak recovery UX are structurally mitigated when the full action history is the interface itself.

    3. Low barriers to human participation — natural language input collapses the Gulf of Execution: users specify what they want, agents determine how. The historical CLI limitation (command recall, syntax memorization) is eliminated by LLM translation. This inverts the traditional terminal accessibility problem.

    Empirical evidence motivating the framework:

    • GUI agent performance gap: Best model achieves 12.24% task success on OSWorld vs 72.36% for humans; frontier web agents show up to 59% lower success rates on realistic tasks than simpler benchmarks — the bottleneck is representational compatibility, not raw model capability
    • Terminal-based tool adoption: By late 2024, AI-generated code accounted for ~30% of new Python functions on GitHub; a study of 129,000+ GitHub projects found coding agent adoption rates of 15-23%, with traces of 50+ distinct agentic tools
    • Transparency matters for performance: Experienced open-source developers using AI assistants were measured as 19% slower than without AI, despite perceiving themselves as faster — directly motivating the transparency property as a design requirement, not a nice-to-have
    • Competitive convergence: Claude Code, OpenAI Codex, and Cursor's agent mode all converge on the text-based sequential pattern despite being built by competing organizations, suggesting the design properties are structural rather than stylistic

    Mixed-initiative interaction in terminals:

    The CLI prompt provides an unambiguous turn boundary — the human holds initiative by default. This maps directly to the reversibility-risk framework: configurable permission modes range from suggestion-only (all actions require approval) to fully autonomous (agent executes without pausing), with intermediate modes gating on risk level. The turn boundary is architecturally explicit, unlike GUI agents where initiative transfer is often ambiguous.

    The framework's core argument: The primary bottleneck for GUI agents is not perceptual capability — it is the absence of representational compatibility, transparency, and low barriers to human participation. The terminal serves as a design exemplar whose properties any agent-facing modality must replicate to achieve comparable effectiveness.

    Key: The Human-Agent-UI triangle reframes the "terminal vs. GUI" debate from an aesthetic preference into a structural analysis. Any agent interface — graphical or otherwise — must solve for representational compatibility, transparency, and low participation barriers. Interfaces that lack these properties will underperform regardless of the underlying model's capability.

    Generative UI: From Static Screens to Adaptive Systems¶

    The patterns above assume a human designer authors every screen. Generative UI removes that assumption: interfaces whose structure and behavior are assembled at runtime by models, not hard-coded in advance. The shift is from interface-first to outcome-first — designers define goals, constraints, and allowlists; the system renders the right interface for the moment.

    The generation spectrum:

    Level How it works Trade-off
    Static (slot filling) Model fills copy, labels, hints, or validation messages within a fixed, pre-approved layout Safest and most predictable; limited flexibility
    Declarative (component assembly) Model selects and composes from a registered component library via a typed schema (JSON/YAML DSL) Best balance of flexibility and reliability; recommended default
    Fully generated Model emits raw HTML/CSS/code Maximum flexibility but hardest to govern; trust, accessibility, and consistency risks escalate

    Declarative generation is the practical sweet spot. The model operates against a UI schema (DSL) — a typed JSON or YAML contract describing pages, layouts, components, and data bindings — that serves as the API between generators and renderers. This contract-first approach means the renderer is deterministic and debuggable even when the generator is probabilistic.

    Contracts before intelligence — the foundational layer:

    Before any model touches interface generation, five contracts must be in place:

    1. UI schema (DSL): Typed JSON/YAML describing pages, layouts, components, and bindings. Versioned and validated (JSON Schema + runtime checks). This is the API between generators and renderers.
    2. Design system primitives: Tokens, layout primitives, and a stable component library with clear props and accessibility guarantees. Tokens are hard constraints, not suggestions.
    3. Capability map: What the app can do (search, create, export). The model composes only from declared capabilities — it never invents new ones.
    4. Policy and safety: Allowlists, prop constraints, data access scopes, redaction rules, and rate limits. Invalid schemas are rejected or sanitized, never rendered.
    5. Observability: Structured logs of inputs, chosen variants, user events, and outcomes, feeding evaluation loops that improve selection over time.

    Proven generation patterns:

    • Server-driven UI (schema-first): Backend returns a UI schema; client renders deterministically. Debuggable and cache-friendly.
    • Slot filling: Model fills copy, labels, hints, or validation messages within an approved layout — the simplest and safest entry point.
    • Mixed-initiative flows: The assistant proposes a UI change; the user approves, edits, or rejects. No silent mutations.

    Context signals for adaptation:

    Generative UI adapts using front-end behavioral signals — a lightweight mini-CDP that requires no user identity:

    • Behavioral events: Page views, clicks, dwell time, scroll depth, search terms, feature usage frequency.
    • Derived traits: Inferred preferences ("likes FX," "prefers dark mode," "prefers compact layout").
    • Recency and frequency: Last visited paths, top actions, recently accessed sections.
    • Explicit preferences: User-opted favorites, density toggles, locale choices.

    These signals drive concrete quick wins: remembered navigation paths, reordered quick actions based on frequency, contextual nudges suppressed after repeated dismissal, reading-mode preferences persisting across sessions, and search intelligence that pre-expands frequently queried widgets.

    Guardrails and UX quality:

    Generative UI inherits the reversibility-risk framework from the pattern catalogue above, with additional constraints specific to runtime generation:

    • Determinism boundaries: Models select from allowlisted components and props — never raw code or untyped HTML.
    • Accessibility by default: Components remain accessible regardless of whether a human or model selects them; roles, labels, and focus order are enforced at the renderer level.
    • Latency budgets: Cache schemas, stream renderable chunks, precompute common variants. Degrade gracefully to cached templates when models are slow or offline — never block critical paths on generation.
    • Consistency and theming: Generation stays within tokenized design primitives. Tokens are constraints, not suggestions.
    • Data hygiene: Validate bindings, throttle queries, sanitize outputs. Models never emit executable code or unsafe URLs.

    Engineering checklist for generative UI:

    • Define the DSL with types, versioning, and validation (JSON Schema + runtime checks)
    • Build a deterministic renderer: schema-to-component mapping with exhaustive prop validation and safe defaults
    • Write policy: allowlists, prop ranges, PII controls, auth scopes; reject on breach with actionable errors
    • Design offline-first: cached templates and non-model fallbacks for critical paths
    • Stand up an evaluation harness: golden tasks, screenshot diffs, accessibility tests, latency/error SLOs, canary rollouts
    • Wire telemetry and feedback capture: edits, aborts, success metrics, and model rationales to improve selection over time

    Runtime software synthesis — the frontier beyond copilots:

    Generative UI's logical endpoint is not just adaptive layouts but runtime software synthesis: users should not settle for generic software if an AI can generate a UI tailored to their taste, workflow, and preferences. This pushes beyond copilots (AI assisting within fixed apps) into a regime where the AI shapes the app surface itself — composing views, controls, and workflows that may never have been designed by a human (OpenClaw founder interview, 2026). The contracts-first architecture described above is what makes this tractable: the DSL, design tokens, capability map, and policy layer provide the guardrails within which synthesis can operate safely, while observability and feedback loops let the system learn which generated surfaces actually serve users well.

    Key: Generative UI is not "let the model draw screens." It is a disciplined architecture where contracts, design tokens, and policy guardrails come first, and the model operates within those boundaries to assemble interfaces that adapt to user context. The shift is from designing screens to designing the parameters and constraints within which screens are generated.

    Multi-Agent Coordination Architecture¶

    The study plan (Week 5) introduces multi-agent collaboration through frameworks like CrewAI. But moving from a demo to a production multi-agent system requires understanding that most so-called multi-agent systems are linear toolchains with new names. True multi-agency requires concurrent actors negotiating over a shared objective with explicit state, communication protocols, and guardrails.

    Core ingredients of a real multi-agent system:

    Ingredient Purpose
    Roles and typed capabilities Each agent (planner, critic, executor, tool-caller) exposes a typed capability set — not free-form prompts. Roles define authority boundaries.
    Shared state (blackboard/graph) A task graph plus facts plus artifacts that all agents read and write. Updates are atomic and observable.
    Coordination policy Explicit rules for who can act when, on what. Turn-taking, parallelism, and arbitration are declared, not emergent.
    Sandboxed environments Isolated I/O for tools, data, and effects. Reproducible simulations for learning and testing.
    Evaluation hooks Continuous tracing, critique, and scoring of plans, actions, and outcomes — not just final output quality.

    Coordination patterns:

    Pattern How it works Best for
    Supervisor to workers A planner decomposes goals into tasks; workers execute; a critic verifies results; the loop repeats until the objective is met Well-defined decomposable tasks with clear success criteria
    Peer consensus (debate to resolution) Multiple planners independently produce plans; a judge agent selects or merges the best elements Problems benefiting from diverse reasoning strategies; reducing single-point-of-failure bias
    Market/auction Tasks are bid out to specialized agents; cost and utility scores drive assignment Heterogeneous agent pools with varying specializations and resource costs
    Hierarchical control High-level goals decompose into subgoals, then into executable steps, with feedback flowing back up at each level Complex multi-layered objectives requiring different abstraction levels

    Communication and memory:

    Agents do not communicate through unstructured chat. Messages are structured with explicit fields: intent, inputs, preconditions, expected effects, and confidence. This structure makes inter-agent communication parseable, auditable, and debuggable.

    Memory is layered across three tiers:

    • Short-term (episode): Current task context, recent actions, and working state.
    • Long-term (project): Accumulated knowledge, learned preferences, and historical outcomes persisting across sessions.
    • External (vector/graph indices): Retrieval-augmented memory for domain knowledge, documentation, and artifacts too large for context windows.

    Every state transition is attributed — tagged with the acting agent and its rationale — making the full decision history auditable.

    Safety and governance:

    Multi-agent systems amplify the reversibility-risk framework because errors compound across agent boundaries. The governance layer adds three mechanisms beyond single-agent safety:

    • Policy first: Allowlists, redaction rules, rate limits, and authority boundaries are defined per role. An executor agent cannot escalate its own permissions.
    • Counterfactual checks: High-risk actions are simulated in a shadow environment before execution. Results require explicit approval before promotion to production state.
    • Human-in-the-loop gates: Sensitive scopes trigger elevation to a human reviewer. Rollbacks are first-class operations, not afterthoughts.

    Engineering checklist for multi-agent systems:

    • Define agent roles and their typed capabilities (interfaces + schemas)
    • Stand up a shared blackboard/graph with optimistic concurrency and versioned snapshots
    • Implement a coordinator that schedules turns, arbitrates conflicts, and enforces policy
    • Add a critic/evaluator agent with golden tasks and outcome metrics (precision, latency, cost, SLA adherence)
    • Build a replayable environment (simulation + fixtures) and wire tracing for every message and action
    • Ship canaries; measure deltas; promote policies by evidence, not intuition

    Key: The north star for multi-agent design is multiple specialized agents cooperating over a shared state to deliver a measurable outcome — reliably, safely, and faster than a single generalist. The phase transition from single-agent to multi-agent changes coordination, error recovery, and governance simultaneously, just as the transition from assistive to agentive AI changes every UX assumption.
