    Recent Methods for Building Chatbots with Context Engineering, Agentic Retrieval, Memory, and Graph Context¶

    Opening Briefing¶

    The defining bottleneck in production chatbot systems is not the language model — it is the 128k-token window that the model conditions on and the engineering required to fill it correctly. Most teams treat retrieval as a solved preprocessing step: chunk documents, embed them, fetch the top-k nearest neighbors, and concatenate. That mental model is roughly where web search was before link analysis. The shift documented here is from passive retrieval to retrieval as a learned, multi-step policy — one where the model itself participates in deciding whether to retrieve, what granularity to operate at, and when to stop. Self-RAG introduces reflection tokens that let the generator critique its own grounding mid-sequence; A-RAG exposes retrieval interfaces at four granularities (document, summary, passage, chunk) and delegates strategy selection to an agent planner. The trade-off is sharp: on benchmarks requiring multi-hop reasoning, agentic retrieval dominates, but for high-volume single-hop lookups, hybrid dense-plus-sparse search with a cross-encoder reranker remains cheaper by an order of magnitude in latency and token spend.

    Memory systems reveal a parallel architectural insight. Long-term memory is not storage — it is context precomputation. Every memory architecture in this space, from Letta's OS-style tiered cache to Zep's temporal knowledge graph to A-MEM's Zettelkasten-inspired note network, answers the same question: given a future prompt whose content is unknown today, what derived artifacts should be materialized now so that the right 4k–8k tokens can be hydrated into a 128k window at query time? The engineering consequence is that memory design is inseparable from retrieval policy design. Compaction (moving raw data to external storage and keeping handles) is reversible and should be the default; summarization is irreversible and should be applied only when signal-to-noise is the binding constraint, not token count alone. Getting this ordering wrong is the single most common cause of what practitioners call context rot — the gradual burial of true constraints under accumulated low-value tokens.

    Graph-based augmentation, particularly GraphRAG's community-summary architecture, addresses a real gap: corpus-level sensemaking and multi-hop questions that no single chunk can answer. But the critical evaluation literature — notably "GraphRAG under Fire" (2025) — demonstrates that graph indexing adds substantial cost and latency without accuracy gains when the query distribution is already well-served by chunk retrieval. The decision boundary is structural: if queries require relationship traversal, temporal reasoning, or thematic synthesis across hundreds of documents, graph indexing amortizes. If they do not, it is overhead.

    The operating claim of this document is that production-grade context assembly is a compiler problem, not a search problem. The system must parse heterogeneous sources, optimize token allocation under budget constraints, route queries through the cheapest policy that meets a reliability target, and persist derived artifacts for future reuse. The sections that follow lay out the components of that compiler — from compression and routing primitives through memory tiering to graph indexing — with concrete architecture patterns, framework mappings, and the failure modes that distinguish paper designs from deployed systems.

    Executive Summary¶

    Surveys practical approaches (2023-2026) for building production chatbots that stay grounded, handle long horizons, and scale across four pillars: context engineering, agentic retrieval, memory systems, and graph-based context / knowledge graphs.

    The headline shift: from "big prompt + top-k vector search" toward explicit, controllable pipelines that assemble, compress, route, and persist context -- often with the model participating in decisions (agentic retrieval, agentic memory) rather than passively consuming retrieved text.

    Two other major shifts:

    • Graph-first augmentations for "connect-the-dots" questions and corpus-level sensemaking (GraphRAG: LLM-extracted entity graphs, hierarchical community detection, pre-generated community summaries). Indexing is expensive; only amortises when the corpus is reused heavily.
    • Structured memory layers: OS-inspired tiering (MemGPT/Letta), temporal knowledge-graph memory (Zep/Graphiti), agentic memory evolution (A-MEM). These treat context window as a scarce cache with machinery for what to remember, how to update it, how to retrieve it fast.

    Key: The open-source ecosystem now reflects these patterns: frameworks emphasise explicit orchestration graphs (LangGraph), agent workflow primitives (OpenAI Agents SDK, CrewAI, smolagents), strong retrieval abstractions (Haystack, LangChain, LlamaIndex), and specialised storage layers (Qdrant, Milvus, Weaviate, Chroma, pgvector; Neo4j for graphs). Model Context Protocol (MCP) has emerged as a standardised "context/tool bus" but expands the attack surface and needs careful sandboxing.

    Context Engineering and Orchestration Foundations¶

    What Context Actually Is¶

    The model can only condition on tokens in its current context window — formally, it computes p(next tokens | context). "Context" is not just the prompt; it is the union of four categories of information fed to the LLM at inference time:

    1. Instructions — the system prompt and any task-specific directives (prompt engineering lives here)
    2. Retrieved facts — documents, SQL results, knowledge-graph triples, API responses (RAG lives here)
    3. Conversation history — prior turns, scratchpad, evolving state
    4. Tool outputs — function-call results, code execution traces, agent sub-task returns

    Context engineering is the discipline of optimising all four categories together. Where prompt engineering focuses on crafting instruction text, context engineering architects the entire information flow — data, tools, memory, ranking, and budgets. It is a strict superset: prompt engineering and RAG are both sub-problems of context engineering.

    Minimal Effective Context¶

    The core design principle is not "how do I stuff more in?" but rather:

    Given this step, what is the smallest context the model needs to take the correct next action?

    If the context is too short, the model is blind — missing key facts or instructions. If too long or noisy, important bits get diluted, cost explodes, and behaviour becomes unstable. The goal is the minimal effective context at every step.

    This principle is especially acute in the enterprise, where giant context windows create the illusion that retrieval is solved. In practice, a knowledge worker may have millions of documents nominally available, yet the model's useful token budget for any single task remains tiny. The bottleneck is not window size — it is context engineering: the quality of search, the discipline of ranking, the rigor of retrieval filtering, and the judgment of when to stop searching versus keep exploring. Messy, permissioned, sprawling enterprise data remains messy even as models grow smarter; the context window does not clean the data for you (Aaron Levie, Box, Mar 2026).

    Key: The winning companies may not be the ones with the most data — they may be the ones that can produce the smallest, cleanest, highest-authority context slice per task (Aaron Levie, Box, Mar 2026).

    Architectural Trends¶

    Everything else must be selected, shaped, and injected. Modern chatbot quality is a function of a context assembly pipeline: ingestion -> indexing -> retrieval/routing -> compression/structuring -> prompt composition -> generation -> logging/evaluation.

    Key architectural trends:

    • Moving from implicit prompt concatenation to explicit state machines or graphs. LangGraph models applications as graphs with state (short-term memory) checkpointed per thread -- enabling replay, time-travel, and HITL patterns.
    • Haystack's modular pipelines: retrievers, routers, memory layers, tools, evaluators, generators -- each stage individually testable and replaceable. Debugging production assistants requires inspecting intermediate artefacts (retrieved passages, routing decisions, tool calls), not just final answers.

    Context Compression¶

    Compression is a top-leverage technique because token budgets dominate both failure modes (irrelevant context causing hallucinations) and cost/latency.

    Compression Type How It Works Best For Risk
    Query-aware contextual compression (post-retrieval) Retrieve broadly, then compress/filter retrieved docs conditioned on query and conversation state (LangChain DocumentCompressor/ContextualCompressionRetriever) Token-budgeted prompts; noisy corpora Extra LLM call; may "compress away" the critical sentence
    Prompt compression (pre-generation, model-driven) LLMLingua / LongLLMLingua -- compress prompts to fit budgets while keeping salient tokens Large fixed scaffolding (policies, product manuals, user profiles) May drop "small" constraints governing correctness (date ranges, safety constraints, edge cases)
    Contextual compression with guarantees (emerging) Compression models optimized for bounded information loss and answer-preservation guarantees (probabilistic) — the compressed context provably retains the information needed to produce the correct answer above a target probability threshold Production systems needing aggressive context pruning with safety bounds Still early; guarantees are probabilistic, not absolute; calibration required per domain

    Key: The emergence of compression with formal guarantees changes the risk calculus for aggressive pruning in production. Previously, any compression risked silently dropping the critical sentence. Bounded-loss compression models make it possible to set an explicit information retention target (e.g., 95% answer preservation probability) and prune everything below that threshold, making aggressive context reduction safer and auditable (arXiv, 2025–2026).

    Tool and Context Interoperability: MCP¶

    Model Context Protocol (MCP) by Anthropic standardises how applications expose tools, data sources, and context to LLM hosts/clients. MCP externalises tool schemas and data connectors into "servers," letting agents reuse a growing ecosystem of integrations.

    Key: MCP-style connectivity introduces security risk if file paths, shell tools, or git operations are exposed too broadly. Production designs should treat tool layers as untrusted and enforce boundaries via sandboxing/ACLs rather than hoping the model will self-restrict.

    Retrieval-Augmented Generation and Agentic Retrieval¶

    Dedicated document: RAG Guide — full coverage of RAG pipelines, retrieval strategies, agentic retrieval, Azure AI Search, Graph RAG, vector databases, and the open-source ecosystem. See also RAG Evals & Production Engineering for the three-layer evaluation framework.

    RAG Pipeline Checklist¶

    Use when domain knowledge is too large or dynamic to fit in context windows and correctness matters.

    Key -- RAG 2.0 Architecture Sketch:

    Ingest -> Chunk -> Enrich (entities, tables) -> Index
               ↓                      ↑
           Policies <- Query -> Retrieve -> Compose -> Evals

    Key -- RAG 2.0 Pipeline Checklist:

    • Ground-truth set covering key intents
    • Chunking with structure awareness (headings, tables)
    • Enrichment: entities, citations, table extraction
    • Retrieval policies + diversity (filters, recency)
    • Compose with citations and abstain behavior
    • Good/Better/Best: naive vector search -> hybrid retrieval + citations + abstain -> structured enrichments, policies, evaluators per intent

    Common pitfalls:

    • Over-chunking without semantic boundaries (headings, paragraph breaks) destroys coherence
    • Unenriched tables and figures lead to hallucinated facts — always extract and annotate them during ingestion
    • Missing retrieval policies (filters, recency, diversity) cause the system to surface stale or redundant passages

    Key -- Citations Eval Snippet:

    def evaluate(query, answer, gold):
    return int(citation_present(answer) and contains(gold, answer))

    Hybrid Retrieval Routing Criteria¶

    Key -- Hybrid RAG Routing Checklist:

    • Define routing criteria by query intent (keyword, dense, graph)
    • Instrument retrieval choices and outcomes
    • Add evals per route (e.g., factuality, coverage)
    • Pitfall: unclear selection policies lead to inconsistent results; over-fetching drives up latency and cost

    Embeddings and Vector Index Selection¶

    Key -- Embeddings & Vector Databases:

    • Index selection: HNSW (fast approximate, high memory), IVF (lower memory, needs tuning), flat (exact, small datasets only)
    • Metadata filtering: combine vector similarity with structured filters (date, source, entity type) to improve precision
    • Embedding drift: monitor embedding model changes; re-index when switching models or after significant corpus shifts
    • Choose domain-specific embedding models when general-purpose models underperform on jargon-heavy corpora

    MUVERA (March 2026): Compresses multi-vector retrieval (late interaction) into fixed-dimensional encodings, reporting ~70% memory reduction and much smaller HNSW graphs at some recall/query-throughput cost. Reinforces a key finding: single-vector retrieval degrades significantly on harder out-of-distribution settings, and late-interaction methods remain stronger there — MUVERA offers a practical middle ground by approximating late-interaction quality in a single-vector-compatible index format (victorialslocum, lateinteraction, Mar 2026).

    Knowledge Lifecycle¶

    Key -- Knowledge Freshness & Contracts:

    • Define freshness SLAs per knowledge source (e.g., financial data: daily; policy docs: on-change)
    • Establish knowledge contracts: required evidence types, provenance metadata, versioning policy
    • Implement entity resolution and canonicalization to prevent duplicate/conflicting knowledge entries

    Where Baseline RAG Breaks¶

    Baseline RAG (chunk + embed + top-k vector similarity -> stuff into prompt) has two structural limitations:

    1. Multi-hop / "connect-the-dots" questions: required evidence distributed across documents; no single chunk is semantically similar enough
    2. Global sensemaking questions: corpus-level themes, structure, or narratives; retrieving a few chunks cannot represent "the dataset"

    A third limitation surfaces in agentic contexts: static RAG goes stale, and even dynamic RAG that refreshes data still struggles with semantic ambiguity and operational context. For example, "Apple" in a Slack corpus could mean the company or a literal apple — similarity retrieval alone cannot reliably disambiguate for enterprise reasoning (Cognee demo, 2026). The fix is not better RAG but a memory layer above RAG: structured, evolving, graph-assisted memory that disambiguates through ontology and relational context rather than embedding distance alone. See Agent Memory Systems for the full architecture spectrum, including Cognee's graph-memory approach and domain-scoped agent memory patterns.

    GraphRAG is explicitly motivated by these failure modes, contrasting baseline RAG with graph-based indexing and community summaries for both local entity reasoning and global summarisation.

    Retrieval Strategies Comparison¶

    Strategy What It Does Best For Latency & Cost Common Failure Modes
    Dense top-k vector search Retrieve semantically similar chunks Narrow questions; factual lookup Low (1 query + top-k fetch) Misses multi-hop evidence; retrieves "nearby but wrong" snippets
    Hybrid (dense + sparse) + fusion Combine lexical matching (BM25) and dense similarity; fuse rankings (RRF) High-precision QA; jargon and exact terms Moderate (two retrievals + fusion) Redundant/near-duplicate passages; needs reranking/filtering
    Query rewriting / "multi-query" retrieval Generate multiple paraphrases/sub-questions; retrieve per query and merge Recall-heavy domains; ambiguous queries Higher (multiple retrieval calls) Drifts into off-topic queries; increases noise without reranking
    Reranking (cross-encoder / LLM-as-reranker) Re-score candidate passages using a stronger model Reducing hallucinations; improving grounding Moderate-high (additional inference) Overfits to superficial cues; adds cost and tail latency
    Contextual compression Compress/filter retrieved docs using query context Token-budgeted prompts; noisy corpora Moderate (extra compression pass) Drops the key sentence; compresses away provenance
    Hierarchical retrieval (RAPTOR) Build tree of clustered summaries; retrieve both local chunks and higher-level summaries Long documents; "what's the gist + details" queries Higher at indexing time; query-time moderate Summary drift accumulates; indexing complexity; tuning needed
    Self-reflective adaptive RAG (Self-RAG) Model decides when to retrieve and critiques/improves its answer using retrieved evidence High-stakes QA; reducing unsupported claims High (iterative loops) Loop instability; extra tokens and calls; requires careful stopping criteria
    Tool-based agentic retrieval (A-RAG) Provide retrieval tools at multiple granularities; agent plans retrieval strategy Complex tasks requiring targeted evidence navigation High (planning + multiple tool calls) Planning errors and tool misuse; expensive for simple queries
    GraphRAG local search Start from relevant entities; fan out to neighbours/claims/text units Entity-centric questions, relationship queries Moderate (graph traversal + context assembly) Entity extraction/linking errors; graph maintenance overhead
    GraphRAG global search Use community summaries to answer corpus-level "themes" Dataset summarisation; exploratory sensemaking Moderate at query time (many partial answers + synthesis) High indexing cost; summaries can be stale or overly generic

    Agentic Retrieval as "RAG with a Decision-Maker"¶

    Two newer directions encode a shared design principle: retrieval is not a single step -- it is a policy.

    • Self-RAG: model-driven mechanism to decide whether to retrieve and self-critique answers with retrieval evidence. Dynamically invokes retrieval and reflection when needed. In production: implement strict budgets and stopping rules.
    • A-RAG: frames agentic retrieval as a toolkit of retrieval interfaces across granularities (whole documents, summaries, passages, raw chunks) plus agent planning. Strong performance on agentic QA benchmarks but inherently trades throughput for reasoning depth.

    A frequently underrated dimension of agentic retrieval is knowing when to stop searching. Enterprise retrieval is fundamentally an explore/exploit judgment problem, not merely a retrieval problem. The model must decide whether to keep digging through additional sources, retry queries with different formulations, or admit that the answer may not exist in the available corpus. Systems that lack explicit stopping criteria and retrieval budgets tend to either give up too early — missing evidence that one more hop would have surfaced — or spiral into redundant searches that burn tokens without improving answer quality (Aaron Levie, Box, Mar 2026).

    Key: If you expect high query volume with mostly simple lookup, baseline/hybrid RAG plus reranking typically dominates on cost. If you expect lower volume with complex multi-step investigations, agentic retrieval policies can be worth it -- especially if you cache intermediate artefacts across sessions. In either regime, design explicit stopping policies — the model needs a disciplined signal for when further retrieval is unlikely to improve the answer (Aaron Levie, Box, Mar 2026).

    Azure AI Search: Agentic Retrieval as a Managed Service¶

    Azure AI Search ships agentic retrieval (public preview, 2025-11-01-preview API) — implementing the agentic retrieval pattern described above as a fully managed, three-layer pipeline on top of existing search indexes.

    Architecture — 3 layers:

    1. Knowledge Source — a thin wrapper around a search index (or blob storage, OneLake, SharePoint, web) that sets retrieval defaults: which fields to search, filters, reranking config.
    2. Knowledge Base — the orchestrator. Connects one or more knowledge sources to an LLM deployment. Drives query planning, subquery execution, and result synthesis.
    3. LLM (Azure OpenAI) — decomposes complex/multi-hop queries into focused subqueries, corrects spelling, incorporates chat history. Supported models: gpt-4o, gpt-4o-mini, gpt-4.1 family, gpt-5 family.

    Workflow:

    App/Agent → Knowledge Base (retrieve) → LLM query planning
                                             ↓
                                       N subqueries (parallel)
                                             ↓
                                 Hybrid search + semantic reranking per subquery
                                             ↓
                                       Merged 3-part response:
                                         1. Grounding data (merged content)
                                         2. Source references (citations)
                                         3. Activity plan (execution details)

    Output modes and reasoning effort:

    Setting Options Trade-off
    Output mode AnswerSynthesis (LLM formulates answer with citations) · ExtractedData (raw results for downstream processing) Synthesis adds latency + tokens but gives ready-to-use answers
    Retrieval reasoning effort minimal (no LLM, intents only) · low (default — LLM query planning + synthesis) · medium (aggressive expansion, iterative search) Higher effort = better multi-hop recall, higher cost/latency

    Prerequisites: semantic ranker enabled on the search service, an Azure OpenAI deployment with a supported model, RBAC roles (Search Service Contributor to manage, Search Index Data Reader to query, Cognitive Services User on the OpenAI resource for the search service's managed identity).

    Agent integration via MCP: A knowledge base exposes an MCP endpoint at {search-endpoint}/knowledgebases/{kb-name}/mcp?api-version=2025-11-01-preview. Agents connect to it as a RemoteTool project connection and use MCPTool with allowed_tools=["knowledge_base_retrieve"] — the agent automatically calls the KB tool when user queries match.

    Cost model: Token-based billing for agentic reasoning tokens (50M free tokens/month on Free tier) plus standard Azure OpenAI pay-as-you-go for query planning and answer synthesis. Example: 2,000 retrievals × 3 subqueries avg ≈ $4.32 total.

    Key: Agentic retrieval is a good fit when you already have Azure AI Search indexes and want multi-hop, spelling-tolerant, chat-history-aware retrieval without building the orchestration yourself. The main trade-off is added latency from the LLM query planning layer. For high-throughput simple lookups, stick with direct hybrid search + semantic reranking. For complex investigative queries at moderate volume, the managed agentic pipeline saves significant engineering effort.

    Memory Systems for Chatbots and Agents¶

    Dedicated document: Agent Memory Systems — full coverage of memory architectures (9 patterns compared), update edges, forgetting, compaction vs summarization, stateful agent platforms (Letta, Zep, Supermemory), evaluation dimensions, and design checklist.

    Memory is the complement to retrieval: where retrieval finds relevant external context at query time, memory precomputes and materializes derived artifacts (profiles, timelines, entity graphs) so the right tokens are ready before the query arrives. The key engineering insight is that long-term memory is context precomputation, not storage. See the dedicated document for architecture patterns, the compaction-vs-summarization ordering rule, and the emerging structured-evolving-state paradigm.

    A memory-layered RAG architecture is solidifying as the standard unified memory stack across agents and RAG systems, formalizing the tiering that frameworks like Letta and Zep implement into four explicit layers:

    Layer Name Function Latency Persistence
    L1 Cache (exact + semantic) Semantic dedup of repeated/similar queries; serves cached answers and retrieval sets Sub-ms Session or TTL-based
    L2 Short-term session memory Conversation history, scratchpad, evolving task state Low Per-session
    L3 Vector retrieval Dense/sparse/hybrid search over indexed corpora Moderate Persistent
    L4 Graph / structured sources Knowledge graphs, relational DBs, typed entity stores Variable Persistent

    Each layer acts as a cache miss fallback for the layer above: L1 misses promote to L2, L2 misses trigger L3 retrieval, and L3 gaps escalate to L4 graph traversal or structured queries. The architecture unifies what were previously separate concerns (caching, conversation management, retrieval, knowledge graphs) into a single coherent memory hierarchy with explicit promotion/demotion policies (arXiv, 2025–2026).

    Graph-Based Context and Knowledge Graph Integration¶

    Graph-based context preserves structure that pure embeddings erase: entities, relations, communities, timelines, and provenance.

    Graph RAG Implementation Checklist¶

    Key -- Graph RAG Checklist:

    • Define entity/edge schema (node types, relationship types, required properties)
    • Extraction evals on representative corpus (measure NER/RE precision)
    • Hybrid retrieve: graph paths + text chunks
    • Good/Better/Best: simple entity linking -> typed relations and path constraints -> learned policies + feedback loops
    • Architecture: Text -> NER/RE -> Triples -> Graph DB; Query (entities/paths) -> Retrieve -> Compose -> Evals

    Key -- Graph Path Coverage Eval:

    def path_coverage(query, graph_paths):
    return any(required_edge in p for p in graph_paths)

    GraphRAG as a Reference Design¶

    GraphRAG (From Local to Global): builds entity graph from source documents -> partitions into communities (hierarchical clustering) -> generates bottom-up community summaries -> answers questions via (i) global search over community summaries or (ii) local search around query-relevant entities and neighbours. A "DRIFT" mode combines local search with community context.

    Key: Indexing can be expensive. GraphRAG behaves like an offline compilation step plus a query-time "decoding" step. Defaults may underperform on your domain without tuning. The upstream repo explicitly warns about indexing cost.

    Neo4j-Centric GraphRAG Patterns¶

    • Neo4j GraphRAG package for Python: knowledge graph creation from unstructured text, retrievers spanning graph search, vector search, and hybrid retrieval patterns
    • Neo4j LLM Knowledge Graph Builder (open source): transform PDFs/docs/web pages into a Neo4j knowledge graph using LLM extraction, facilitating graph queries and graph-enhanced RAG
    • Neo4j Labs "agent memory": stores short-term conversation context, entity-extracted persistent knowledge, and reasoning traces -- essentially "memory as a context graph"

    Graph Integration Patterns¶

    Pattern How It Works Where It Wins Where It Loses
    Offline KG + query-time subgraph hydration Extract entities/relations; store graph; retrieve ego-net/community reports and attach as context Multi-hop reasoning; entity-centric analytics; provenance High ingestion cost; entity resolution; schema drift
    Community summaries (GraphRAG global search) Cluster graph; pre-summarise communities; answer "themes" via summary composition Corpus-level questions; investigative sensemaking Expensive indexing; summaries can be generic/stale
    Graph traversal to enrich vector results Retrieve seed passages/entities then expand neighbours/claims/timelines Connecting retrieved snippets; relationship questions Over-expansion can flood context; needs strong budget controls
    Temporal KG memory Persist evolving facts as time-stamped nodes/edges; retrieve "what was true when" Long-lived assistants; business data changes; temporal reasoning Harder ops; requires change detection/invalidation policy
    Graph extraction on-demand Build/update small local graph per session/task; discard afterwards Ad-hoc investigations; privacy constraints Repeated build cost; inconsistent linking across sessions

    Key: Graph augmentation is not automatically better than high-quality hybrid retrieval + reranking. "GraphRAG under Fire" (2025) is a critical evaluation showing the graph can add cost/latency without accuracy gains if the task is already well-served by chunk retrieval. Use graphs when queries need structure (relations, temporal constraints, corpus-level themes), not as a default.

    Context Engineering Deep Dive¶

    Compaction vs Summarization¶

    These are the two primary tools for fighting context rot — when appended history, partial summaries, and stale instructions accumulate so much junk that the true constraints and goals are buried, and the model starts following accidental patterns instead of the intended specification. Context rot has a particularly insidious variant in agentic systems: agents can keep repeating known-bad paths because old mistakes remain in-context. If a retrieval attempt returned irrelevant results or a tool call failed, those traces linger in the window and can cause the model to revisit the same dead ends. Actively pruning bad context — removing or demoting failed retrieval results, superseded plans, and error traces — is as important as adding good context. This is a practical reason why memory management matters even within a single session, not only across sessions (Aaron Levie, Box, Mar 2026).

    Aspect Context Compaction Context Summarization
    Info source Raw history, code, docs Same
    What you keep in prompt Handles / IDs / small structs Short textual / JSON summary
    Reversibility Yes (via tools / DB) No (you lose detail)
    Where full info lives Outside model (FS, DB, tools, vector store) Nowhere accessible unless you also store raw data
    Goal Reduce prompt size, keep exact info available when needed Improve signal-to-noise, keep only what matters conceptually
    Typical operations "Save file", "store message", "index doc" then reference "Summarize last N turns/docs into K tokens and drop raw text"

    Compaction in practice means replacing large blobs with references (file://, doc_id, memory_key) that the model can resolve via tools. Example: instead of stuffing 2k lines of code into every turn, keep a one-line note and expose a read_file tool. Summarization in practice means rewriting 10k tokens into 300 tokens of distilled meaning — a bullet list of key facts, or a state JSON like { goals: [...], decisions: [...], open_questions: [...] }. The original detail is lost unless you also store the raw data separately.

    Key -- Practical Heuristic:

    1. Apply compaction first (default): move code, long docs, old turns to external storage; keep short references + tools to fetch on demand
    2. Apply summarization when: you only care about state not wording, you're hitting context rot even with compaction, or you want a stable small "world state" object
    3. Design-wise: compaction = design of your state & storage layer; summarization = design of your state update function

    A useful abstraction is a ContextManager with two methods: compact(state, raw_events) -> state, external_refs and summarize(state, history) -> state_summary. This separates the two concerns cleanly and can be dropped into any agent harness.

    Share Context by Communicating¶

    A corollary of minimal effective context: you are the compiler, not the model. Do not outsource the job of deciding relevance by throwing a 100-page PDF into the prompt and hoping the model figures out what matters. Instead, pre-process the raw material, extract constraints and goals, and narrate the relevant slice explicitly.

    In agent setups this means tools should return structured summaries and highlights, not raw full text. Prompts should feed those summaries plus a clear instruction: "Given these 3 bullet summaries, decide the next action." The principle: share context by communicating (tell the model what matters about the artefacts) rather than communicate by sharing context (dump everything and hope).

    Context Processing by Data Type¶

    When assembling context from heterogeneous sources, the data type determines the processing strategy. A counterintuitive but important asymmetry underlies all of this work: reading enterprise data correctly is harder than writing new content. Generation is relatively straightforward once the model has good context, but retrieval requires finding the right facts inside huge, messy, permissioned corpora — navigating access controls, resolving conflicting versions, and distinguishing authoritative sources from stale duplicates. Teams that invest heavily in generation quality while underinvesting in retrieval quality have the equation backwards (Aaron Levie, Box, Mar 2026).

    • Unstructured data (video, audio, long-form text): summarise aggressively to avoid flooding the window, but preserve full detail when correctness demands it (e.g., legal documents). Even with expanding context windows, costs remain per-token.
    • Semi-structured data (JSON, XML): strip keys and values the model does not need. Messy JSON with irrelevant fields increases hallucination risk and wastes budget.
    • Structured data (SQL tables, CSVs): never inject raw rows. Use aggregate queries with WHERE clauses to surface only what the model needs. Balancing relevance and completeness across these data types is the central challenge.

    Keep the Toolset Small¶

    Every tool exposed to an agent is extra surface area for failure, extra tokens (tool descriptions consume context), and extra branching entropy — the model must decide among N options, and large tool menus cause decision paralysis and erratic tool selection. Tools are context too; they live in the prompt and in the model's decision space.

    The corollary: do not give one agent 20 tools "just in case." Instead, compose systems: a top-level router agent with 2-4 broad capabilities, each of which may internally orchestrate more tools, but the LLM interface stays small per step.

    Agent-as-Tool Pattern¶

    The natural extension of "fewer tools is better" is to make agents themselves callable as tools with typed schemas.

    Key -- Agent-as-Tool Pattern: Define sub-agents with narrow responsibilities and expose each as a single tool with a clean typed schema:

    • research_agent: { query: string, depth: "shallow" | "deep" } -> { findings: Finding[], confidence: number }
    • planner_agent: { goal: string, constraints: Constraint[] } -> { steps: Step[], risks: Risk[] }

    Benefits: top-level prompt only needs one-line descriptions; internal complexity lives inside the tool's sub-calls; you're factoring context (global = small capabilities + task state; local = big and specialized per agent-tool).

    Hierarchical Agent Design and State Management¶

    Production agent systems benefit from hierarchical composition: a top-level agent owns 3-5 tools, each of which may itself be an agent with its own micro-tools. This keeps context small at every level while allowing deep specialization internally.

    Supporting practices:

    • Explicit state objects: maintain conversation_state, project_state, memory_state as first-class structures rather than relying on the model to reverse-engineer state from prose.
    • Scheduled compaction: after N turns or N tokens, rewrite history into summary. Do not wait for the window to overflow.
    • Schemas everywhere: JSON tool responses, typed fields, small enums. Avoid free-text where structured values are expected.
    • Separate user-visible text from machine-visible state: the LLM should condition on a clean state = {...} object, not a soup of conversation prose.

    Context Engineering Checklist¶

    Key -- Actionable Checklist:

    1. Stop auto-appending everything. Maintain a state object and periodically summarize.
    2. Design "next-step context" as a function: what does the model minimally need to decide the next action?
    3. Shrink tools, deepen systems. Fewer tools per agent; more layering/composition between agents.
    4. Promote good sub-agents to first-class tools with strict schemas.
    5. Narrate relevance to the model. Don't just share documents -- tell the model what matters for this step.

    Context Engineering as Product Category¶

    Context engineering as successor to prompt engineering (March 2026): LlamaIndex explicitly frames context engineering as the successor to prompt engineering, with structured parsing/extraction as a core lever — the quality of what goes into the context window matters more than how you phrase the instruction around it. Hugging Face now serves Markdown paper views to agents and has a Paper Pages skill for searching and reading papers more token-efficiently, reflecting a broader ecosystem shift: tools are being redesigned around the assumption that agents, not humans, are the primary consumers of technical content (Clement Delangue, Niels Rogge, AINews, Mar 2026).

    Prompt Engineering Techniques¶

    Key -- Advanced Prompt Techniques:

    • Meta-prompting: use an LLM to generate or refine prompts for another LLM call; enables self-improving prompt pipelines
    • Prompt compression: techniques like LLMLingua / LongLLMLingua to compress prompts while preserving salient tokens; useful for large fixed scaffolding (policies, product manuals)
    • System prompt architecture, few-shot exemplar selection, chain-of-thought prompting, structured output schemas, prompt templating and versioning

    Recommended Architectures¶

    Three archetypes from lightweight to heavy-duty. Guiding principle: choose minimum complexity that achieves your reliability target under realistic latency/cost constraints.

    1. Lightweight Chatbot with Short-Term Context¶

    Purpose. Conversational UX, small workflows, low latency. Avoid heavy retrieval unless needed.

    Key patterns. Short-term state in an orchestrator; bounded conversation window; (optional) incremental summaries.

    flowchart TD
  U[User message] --> G[Guardrails / validation]
  G --> S[Session state: last N turns]
  S --> P[Prompt composer]
  P --> LLM[LLM call]
  LLM --> R[Response]
  R --> S
  R --> Log[Tracing + metrics]

    Implementation notes. If you adopt an execution-graph orchestrator, persist short-term state as thread checkpoints for debug and replay. LangGraph explicitly models short-term memory as thread-scoped state via checkpoints, enabling HITL and fault tolerance.

    Suggested stacks. Python: LangGraph or Haystack pipelines; TypeScript/JS: LangChain.js or MCP clients if you need tool integrations.

    2. RAG-Based Assistant with Persistent Memory¶

    Purpose. "Ask my documents" + personalisation across sessions. Medium complexity, production value.

    Key patterns. Hybrid retrieval + reranking; query-aware contextual compression; explicit separation of immutable logs vs derived memory artefacts; evaluation harness (RAGAS) as part of CI.

    flowchart TD
  U[User message] --> C[Classifier / router]
  C -->|needs knowledge| Q[Query rewriting / expansion]
  Q --> R1[Retriever: hybrid dense+sparse]
  R1 --> RR[Reranker]
  RR --> CC[Contextual compression]
  CC --> PC[Prompt composer]
  PC --> LLM[LLM]
  LLM --> A[Answer + citations]
  A --> MLog[Append to event log]
  MLog --> MDer[Async memory distillation]
  MDer --> VDB[Vector store / document store]
  MDer --> Prof[Structured user/profile memory]
  A --> Eval[Offline eval / monitoring]

    Implementation notes. Two persistence layers minimum:

    1. Document knowledge store (vector DB or pgvector) for RAG grounding
    2. Memory store for user-specific facts/preferences and summaries. LangGraph explicitly distinguishes short-term checkpoint state from long-term store namespaces; Letta similarly persists all messages and supports pinned memory blocks.

    Repo mappings. Framework: LangChain / LlamaIndex / Haystack. Retrieval store: Qdrant / Milvus / Weaviate / Chroma / pgvector. Evaluation: RAGAS. Memory: Letta (OS-style) or LangGraph store.

    3. Multi-Agent System with Graph Context¶

    Purpose. Complex investigations, multi-step workflows, evolving enterprise knowledge, strong provenance. Highest complexity, highest upside.

    Key patterns. Multi-agent orchestration (handoffs or workflow graphs); graph-based indexing (GraphRAG) or graph database (Neo4j GraphRAG); temporal/relational memory when facts change; strict budgets and sandboxing.

    flowchart TD
  U[User goal] --> Orchestrator[Workflow graph / agent router]
  Orchestrator --> Planner[Planner / coordinator agent]
  Planner -->|subtask| Spec1[Specialist agent: retrieval]
  Planner -->|subtask| Spec2[Specialist agent: reasoning]
  Planner -->|subtask| Spec3[Specialist agent: tools]
  Spec1 --> KG[Graph index / Neo4j]
  Spec1 --> VDB[Vector DB]
  KG --> SubG[Subgraph + community reports]
  VDB --> Chunks[Relevant chunks]
  SubG --> Context[Context builder]
  Chunks --> Context
  Context --> Synth[Final synthesis agent]
  Synth --> Answer[Answer + provenance]
  Answer --> Memory[Update memory graph + logs]
  Answer --> HITL[Optional human review]

    Implementation notes. GraphRAG's official process: entity/relationship extraction -> community hierarchy (Leiden clustering) -> bottom-up summaries -> query modes (global/local/DRIFT). Treat indexing as an offline batch job and amortise across many queries; the upstream repo warns about indexing cost.

    For graph database-backed approaches, Neo4j's GraphRAG package offers first-party retrievers for graph + vector patterns, and Neo4j Labs shows how "context graphs" can encode short-term, long-term, and reasoning memory.

    For agent orchestration, OpenAI Agents SDK provides a small set of multi-agent primitives.

    Agent Coordination Patterns¶

    Pattern Pros Cons Best For
    Single agent + tools (ReAct style) Simple; fewer moving parts Harder to modularise; brittle for long tasks Tool-using chatbots, short workflows
    Planner-executor Better decomposition and controllability More calls; coordinator errors Medium complexity workflows
    Multi-agent with handoffs Clear ownership; parallel work Coordination overhead; consistency issues Research, large tasks, specialist roles
    Graph-based workflow orchestration Deterministic control, checkpointing, HITL Upfront engineering; learning curve Production systems needing reliability
