    Agent Memory Systems¶

    See also: RAG, Knowledge & Context Engineering | LLM Agentic Systems | AI Engineering Practices

    Opening Briefing¶

    The conventional framing of agent memory is "store the chat history and retrieve relevant parts later." That framing is wrong in a way that matters architecturally. Long-term memory is not storage — it is context precomputation. Every memory system in the current landscape, from Letta's OS-style tiered cache to Zep's temporal knowledge graph to Supermemory's update-edge model, answers the same question: given a future prompt whose content is unknown today, what derived artifacts should be materialized now so that the right 4k–8k tokens can be hydrated into a 128k window at query time? The engineering consequence is that memory design is inseparable from retrieval policy design — and getting the ordering wrong between compaction (reversible, should be default) and summarization (irreversible, only when signal-to-noise is the binding constraint) is the single most common cause of what practitioners call context rot: the gradual burial of true constraints under accumulated low-value tokens.

    The strongest emerging thesis pushes further: models are getting good at acting but remain bad at remembering. Supermemory's Dhravya Shah frames persistent agent intelligence as primarily a memory systems problem, not a model problem. The key insight is not that "memory is useful" — everyone says that — but that the data model of memory determines agent quality. Memory as structured evolving state with explicit update edges, selective forgetting, and cache-aware injection outperforms memory as flat vector retrieval or appended chat logs. The models converge across providers; the memory layer does not. This makes memory architecture the durable differentiator for agent systems that must maintain coherent behavior across sessions, users, and time.

    A sharper restatement: agent failure in production is mostly a memory and state problem, not an intelligence problem (Cognee demo, 2026). Classic RAG fetches context but does not give agents durable, structured, evolving memory across sessions or systems. Agentic systems can act but are often stateless — restart them weeks later and they have forgotten what happened, what worked, and what the system state was. The fix is not better retrieval but a memory layer above RAG — closer to an operating system for agent memory than a normal RAG framework. The novelty is not "graph + vector" (that pattern exists) but the productization: treating memory as a data architecture problem rather than "stuff more text into the prompt." A contrarian nuance applies, however: many companies do not have a "memory problem" first — they have an eventing, schema, and source-of-truth problem. If billing and entitlements are poorly modeled, no amount of graph memory saves them. Graph memory helps most after the operational backbone is sane. The deepest value is not "agents that remember like humans" but "agents operating over structured, persistent, scoped state."

    This document covers the representation, storage, retrieval, updating, and evaluation of agent memory — from ephemeral scratchpads through tiered caching to temporal knowledge graphs — with concrete architecture patterns, framework comparisons, and the failure modes that separate demos from deployed systems.

    Core Concepts¶

    "Memory" is no longer synonymous with "include the chat transcript." Recent surveys characterize memory as a dedicated module with five concerns: representation, storage, retrieval, updating, and evaluation, distinguishing episodic (what happened), semantic (what is true), and procedural (how to do things) memory.

    Most modern systems combine three layers:

    1. Raw event storage — immutable logs of messages, tool results, and observations
    2. Derived memory artifacts — summaries, entity profiles, timelines, preference models
    3. Retrieval policies — when to recall what, at what granularity, with what freshness requirements

    Key — Agent Memory Architecture:

    Input -> Scratchpad (ephemeral) -> Tools
      -> Profile (long-term) -> Ledger (task)
    • Define memory types and retention windows
    • Source-of-truth + PII handling
    • Summarization with confidence and citations
    • Good/Better/Best: ephemeral scratchpad → task ledger with rollups → governed profile with consent and expiry

    Memory as Structured Evolving State¶

    The strongest design principles from Supermemory (Dhravya Shah, March 2026):

    Update edges as a first-class primitive: Old facts are not simply overwritten or deleted — the system tracks that one fact supersedes another via explicit update edges connecting old and new versions. This preserves provenance and supports temporal reasoning ("what did we believe before?") while keeping the active memory current. Memory as a versioned graph, not a flat store.

    Forgetting as a product feature: A good memory system must decide what to remember, what to ignore, and how to invalidate stale facts. Forgetting is active curation that prevents context rot. Without it, memory systems accumulate noise that eventually overwhelms signal.

    Hybrid memory + raw context fallback: If no distilled memory exists for a query, the system surfaces relevant raw context via retrieval. This avoids cold-start failure — the system gracefully degrades to standard RAG until enough interactions accumulate to synthesize durable memories.

    Prompt-cache-aware memory injection: Static profile and memory sits high in the prompt and changes rarely, exploiting cache discounts (Anthropic 90%, OpenAI 50%). Only the dynamic tail (recent conversation, task-specific context) changes per request. Structuring memory return order to maximize cache hit rates reduces cost and latency simultaneously.

    Memory as Reasoning¶

    A fundamentally different approach reframes memory not as a storage problem but as a trained reasoning task. Where all other architectures above start from "what facts should we store and how do we retrieve them?", reasoning-based memory starts from "what conclusions can we derive from observed data, and how do we scaffold those conclusions into a predictive model of the user or agent?"

    The thesis, articulated by Plastic Labs/Honcho, draws on predictive processing from cognitive science: biological memory is not high-fidelity storage — it is a prediction system that constructs internal models from sparse data, checks predictions against new observations (surprisal), and updates the model at the margins. Human social cognition works the same way — we build mental models of other people through prediction and error correction, not by storing facts about them. The argument is that LLMs can replicate and exceed this process because they lack the compute constraints, cognitive biases, belief resistance, and neural inertia that limit human reasoning.

    The approach trains specialized reasoning models to perform formal logical inference — deductive (certain conclusions from stated premises), inductive (generalizations from observed patterns), and abductive (best explanations for observed behavior) — over user and agent interaction data. The output is not stored facts but atomic, composable conclusions, each supported by premises and qualified with natural-language certainty. These conclusions scaffold on one another into a reasoning tree that constitutes a working model of personal identity — preferences, patterns, psychology, and predicted behavior.

    Key architectural properties that distinguish this from storage-based approaches:

    • Composability — conclusions are atomic units that can be dynamically recombined and scaffolded to answer any query, not pre-structured for specific retrieval patterns
    • Contradiction handling via reasoning — instead of overwrite rules or update edges, the system reasons through contradictions using formal logic, producing updated conclusions with explicit justification
    • Inference from sparse data — logical reasoning extracts latent information that static extraction misses, because the model derives implications and best-explanation hypotheses rather than just recording what was explicitly stated
    • Traceable predictions — every conclusion carries its reasoning trace (premises → inference → conclusion), making the memory system auditable and debuggable in ways that embedding-based retrieval cannot match
    • Asynchronous improvement — the reasoning tree can be computed over at any time to derive new conclusions from existing ones, improving the representation without new input data

    Key: The critical distinction is between memory as data (extract facts, embed, store, retrieve) and memory as model (reason over observations, derive conclusions, scaffold predictions, synthesize context at inference time). Storage-based memory requires the retrieval query to align with how information was stored; reasoning-based memory can answer questions that were never anticipated at storage time because the reasoning tree can be traversed from any entry point (Courtland Leer & Vince Trost, Plastic Labs, "Memory as Reasoning," Aug 2025).

    Memory Evaluation¶

    Key — Memory Recall Eval Snippet:

    def recall_rate(prompts, memory):
    return sum(int(intent in memory) for intent in prompts) / len(prompts)

    Evaluation dimensions (what separates good memory from bad):

    • Knowledge extraction quality — did the system correctly identify what matters?
    • Temporal reasoning — does it know what changed and when?
    • Multi-session reasoning — can it connect facts across separate conversations?
    • Preference understanding — has it learned user patterns and tastes?
    • User action tracking — does it remember what the user actually did (not just said)?
    • Assistant output tracking — does it remember what the agent itself said and recommended?
    • Write-back effectiveness — do feedback loops (where agents record what they learned about retrieval strategies) actually improve future investigation quality? This is the evaluation analog of Cognee-style write-back memory: after an investigation, the agent writes back what it learned about how future searches should be done, and the metric is whether subsequent searches improve as a result (Cognee demo, 2026)

    Memory Benchmark Landscape (2024-2026)¶

    Seven major benchmarks now define the evaluation surface. The cross-benchmark consensus: temporal reasoning is consistently the hardest capability, showing up to 73% performance gaps between systems and humans.

    LongMemEval (Wu et al., ICLR 2025) has emerged as the gold standard — testing five abilities (information extraction, multi-session reasoning, temporal reasoning, knowledge updates, abstention) across 500 curated questions in conversations scaling from ~115K tokens (LongMemEval_S) to 1.5M tokens (LongMemEval_M). Three-stage framework: Indexing → Retrieval → Reading with LLM-as-judge scoring. Commercial chat assistants show 30-60% accuracy drop on sustained interactions; full-context GPT-4o achieves only 60-64% (arXiv, OpenReview).

    LoCoMo (ACL 2024, Snap Research/UNC Chapel Hill) tests 10 conversations of ~300 turns each across single-hop QA, multi-hop reasoning, temporal reasoning, and adversarial questions. Widely adopted but has significant limitations: short conversations (~9K tokens), data quality concerns, and vendor disputes — Mem0 and Zep have publicly contradicted each other's reported scores, making LoCoMo rankings unreliable for cross-vendor comparison (arXiv, ACL 2024).

    Other benchmarks: MemBench (ACL 2025 Findings) distinguishes factual vs reflective memory. MemoryBench (Tsinghua, 2025) pioneers continual learning evaluation across 11 datasets, 3 domains, 2 languages. MemoryAgentBench (ICLR 2026) tests four competencies — accurate retrieval, test-time learning, long-range understanding, conflict resolution — revealing no existing method excels at all four. EverMemBench (Feb 2026) targets multi-party group conversations. Letta Leaderboard evaluates autonomous memory management through tool calls.

    Five Architectural Patterns That Separate Winners¶

    Pattern 1: Multi-strategy retrieval is the single biggest differentiator. Hindsight (4 strategies: semantic, BM25, graph traversal, temporal → 91.4%) > Zep (3 strategies: cosine, BM25, BFS → 71.2%) > Mem0 (1-2 strategies: vector, optional graph → 49%). The correlation is nearly linear: different query types demand different retrieval approaches. BM25 catches exact mentions embeddings miss; graph traversal finds multi-hop connections invisible to flat similarity; temporal filtering prevents returning outdated facts (Vectorize benchmark analysis, 2025-2026).

    Pattern 2: Graph structure is essential for complex reasoning but vector search remains important for breadth. The 22-point gap between Zep (71.2%, graph-native) and Mem0 (49%, vector-primary) on LongMemEval directly reflects the limitation of pure vector approaches for multi-hop, temporal, and relational queries. But graph-only retrieval misses semantically similar content that lacks explicit edges — every top system uses hybrid storage. The specific graph implementation matters less than having one.

    Pattern 3: Temporal modeling correlates with the largest performance gains. Systems with explicit temporal modeling — Hindsight's dual timestamps, Zep's bi-temporal model, Cognee's temporal search — score 20-60 points higher on temporal queries than systems treating time as metadata. Hindsight improved from 31.6% baseline to 91.0% on temporal queries specifically, a nearly 60-point gain.

    Pattern 4: Active memory consolidation prevents degradation at scale. Systems that merely accumulate memories without consolidation suffer from noise. Hindsight's reflect operation updates beliefs on new evidence. Zep invalidates contradicted facts (preserving history while preventing stale retrieval). Cognee's memify pipeline prunes stale nodes and strengthens frequent connections. Letta's sleep-time compute enables background refinement.

    Pattern 5: Agent-controlled memory can outperform specialized infrastructure. Letta's demonstration that a simple filesystem approach (agent + file tools) achieves 74.0% on LoCoMo — outperforming Mem0's specialized infrastructure at 68.5% — suggests that giving an LLM iterative search/read/organize capability can matter more than storage sophistication. However, this consumes tokens for memory operations and depends on model instruction-following quality.

    Benchmark and CI/CD Tooling¶

    A concrete measurement layer for agent memory is emerging — moving memory evaluation from qualitative assessment to quantifiable, automatable metrics integrated into engineering pipelines.

    MIRIX (arXiv:2507.07957): a multi-layer agent memory system that explicitly separates episodic, semantic, and procedural memory into distinct modules — each with its own storage format, retrieval policy, and update mechanism. Rather than treating all memory as a single vector store, MIRIX routes incoming information to the appropriate memory type at write time and selects the right memory module at query time based on the nature of the request (event recall vs. factual lookup vs. strategy retrieval). The system reports large gains over RAG baselines, validating the thesis that typed memory architecture outperforms undifferentiated retrieval. MIRIX's significance is less in its specific implementation than in what it proves: memory type separation is a performance lever, not just an organizational convenience. Systems that treat episodic, semantic, and procedural memory as interchangeable retrieval targets leave performance on the table.

    Vectorize Agent Memory Benchmark (AMB) (Mar 2026): an open, runnable evaluation harness consisting of a CLI, datasets, and judge prompts. AMB records four core metrics — accuracy, ingestion time, retrieval time, and token cost — across two modes: single-query (isolated recall) and agentic (multi-query, tool-driven workflows). The agentic mode explicitly surfaces tradeoffs — whether a multi-step workflow improves answer quality at the cost of latency and tokens — making it possible to quantify retention and recall over time rather than eyeballing accuracy on static benchmarks. The harness is designed to grow to cover stress datasets, multilingual cases, and community contributions (Vectorize, Mar 2026).

    Microsoft ai-agent-evals / Foundry GitHub Action: automates agent evaluations in CI/CD with statistical tests. Evaluator datasets feed into CI pipelines, collecting latency, token cost, and accuracy data across builds. Releases can be gated on memory regression thresholds — treating memory performance as a first-class metric in delivery pipelines, not an afterthought. This closes the loop between memory evaluation and deployment: memory degradation blocks the release rather than surfacing as a production incident (Microsoft, 2026).

    Key: The combination of AMB-style benchmarks + CI/CD gating means memory systems can now be evaluated with the same rigor as retrieval pipelines: measurable metrics, automated regression detection, and release gates. The missing piece — connecting benchmarks to production-like memory backends — is addressed by MCP-based memory providers (see Mem0 under Stateful Agent Platforms).

    Compaction vs Summarization¶

    Two operations reduce stored context. They are not interchangeable:

    Compaction Summarization
    What it does Moves raw data to external storage; keeps handles/references in active memory Condenses content into shorter representation; discards source
    Reversibility Fully reversible — original data retrievable on demand Irreversible — detail lost permanently
    When to use Default strategy. Token count is the binding constraint Only when signal-to-noise is the binding constraint, not token count
    Risk Retrieval latency for compacted data Context rot from accumulated lossy compressions

    Key: Compaction should be the default. Summarization should be applied only when signal-to-noise ratio justifies permanent information loss. Getting this ordering wrong is the #1 cause of context rot.

    Stateful Agent Platforms¶

    Hindsight (Vectorize, Dec 2025, MIT license): current SOTA on LongMemEval (91.4%) and LoCoMo (89.61%). Separates memory into four epistemic networks — world facts, agent experiences, entity observations, and evolving opinions/beliefs — structurally distinguishing evidence from inference rather than treating all memories uniformly. Retrieval runs four concurrent strategies: cosine semantic similarity, BM25 keyword matching, graph traversal across a shared memory graph, and temporal reasoning, fused via cross-encoder reranking. Stores dual timestamps (occurrence time and mention time), enabling both "what happened when" and "what did I learn when" queries. On temporal queries specifically, improved from 31.6% baseline to 91.0% — a nearly 60-point gain (arXiv, VentureBeat, Vectorize, Dec 2025).

    Letta (formerly MemGPT, UC Berkeley, ICML 2024, Apache 2.0, ~20.9K GitHub stars): the LLM manages its own memory like an OS managing virtual memory — context window is "RAM," external databases are "disk," agent pages data in/out through function calls. Three memory tiers: core memory (size-limited read-write text blocks pinned in-context, ~2K chars each — "human" block for user facts, "persona" block for agent self-concept), recall memory (complete uncompressed message history as searchable database), and archival memory (PostgreSQL + pgvector with HNSW indexing). Agent controls memory via explicit function calls: core_memory_append, core_memory_replace, memory_rethink, archival_memory_search, archival_memory_insert. Memory pressure warnings at ~70% context capacity; forced eviction with recursive summarization at ~100%. Sleep-time compute (Apr 2025) addresses user-facing latency: background agents process information during idle periods using stronger/slower models, writing refined "learned context" to shared memory blocks. Demonstrated 74.0% on LoCoMo with a simple filesystem approach (agent + file tools, GPT-4o-mini), outperforming Mem0's 68.5% — evidence that agent capability matters more than specialized memory infrastructure. Uses PostgreSQL with 42+ tables and Alembic migrations; full agent state serializable to open Agent File (.af) format (arXiv, ICML 2024; Letta docs).

    Zep/Graphiti (Apache 2.0, 24K+ GitHub stars): core engine builds a formally defined graph G = (N, E, phi) in three hierarchical tiers — episode subgraph (raw conversation turns, non-lossy), semantic entity subgraph (extracted entities and relationships as persistent facts), and community subgraph (label propagation clusters with high-level summaries) — mirroring the psychological distinction between episodic and semantic memory. The key innovation is a bi-temporal data model: every entity edge tracks four timestamps — valid_at (when fact became true), invalid_at (when superseded), created_at (when ingested), expired_at (when logically replaced) — enabling point-in-time queries ("What did we know about X on date Y?"), historical reasoning, and enterprise compliance audit trails. Contradicting facts are invalidated rather than deleted, preserving the complete temporal record. Retrieval pipeline f(alpha) = chi(rho(phi(alpha))) runs three concurrent strategies: cosine similarity, BM25, and breadth-first graph traversal — critically, no LLM calls during retrieval (everything pre-computed via vector, BM25, and graph indexes), achieving sub-200ms to sub-second latency (P95 ~300ms in Zep Cloud). Reranking options include reciprocal rank fusion, MMR, cross-encoder scoring, node distance, and episode-mentions frequency. Supports Neo4j (primary), FalkorDB, Kuzu (embedded), and Amazon Neptune backends. Main tradeoff: thorough graph construction is expensive — ingestion for large corpora can take hours due to multiple LLM calls for entity extraction, resolution, and relationship inference (arXiv; Graphiti docs; Zep Cloud).

    Supermemory: memory-as-a-service layer that decides what to learn, tracks changes via update edges, supports forgetting, and returns memory in prompt-cache-friendly order. Integrated Composio for broad tool access (~45 min PR, merged in ~1 hour). Dual product: consumer "memory wallet" + API for companies. Thesis: models converge; memory is the differentiating component.

    Cognee (Topoteretes, Berlin, $7.5M seed Feb 2026, ~12K GitHub stars): three-store architecture — graph (Kuzu), vector (LanceDB), and relational (SQLite) — all file-based by default for zero-infrastructure local development, swappable to production databases (Neo4j, Qdrant, PostgreSQL). Core abstraction is the DataPoint (Pydantic model carrying content + metadata). The cognify() pipeline runs six stages: classify → check permissions → extract chunks → extract graph (via Instructor for structured LLM output) → summarize → embed and persist. Optional ontology validation uses RDF/OWL ontologies to canonicalize entities — fuzzy matching via difflib.get_close_matches() resolves "car manufacturer," "automobile maker," and "vehicle producer" to a single canonical node, reducing graph fragmentation. Offers 14 retrieval modes from basic RAG to graph-completion with chain-of-thought, natural language to Cypher, temporal search, and auto-select. Default GRAPH_COMPLETION mode uses vector search as a hint to find relevant graph triplets, then traverses the graph — fundamentally different from top-k cosine similarity. The memify() post-processing pipeline is inspired by cognitive science: prunes stale nodes, strengthens frequent connections, adds derived facts, optimizes embeddings. Domain-scoped partitioning (billing agents see billing memory, support agents see support memory, supervisor sees all) serves as both security and relevance pattern. On HotPotQA, chain-of-thought graph traversal improved exact match by 1,618% over base configuration. Benchmarks are primarily self-reported; independent third-party validation is limited (Cognee docs; Skills Marketplace; Cognee evaluations, 2026).

    Mem0 (Y Combinator, $24M raised Oct 2025, ~48K GitHub stars): the most pragmatic approach — a two-phase extraction-update pipeline converting conversations into discrete natural-language facts in a vector database with optional graph enhancement. Extraction combines three context sources (conversation summary, last 10 messages, new message pair) and uses an LLM to extract candidate facts. Update phase retrieves top 10 similar existing memories and the LLM decides one of four operations: ADD, UPDATE, DELETE, or NOOP — conflict resolution is entirely LLM-delegated (flexible but opaque). Optional graph variant (Mem0g) stores entities in directed labeled graph G=(V,E,L) with dual retrieval: entity-centric search (identify entities → traverse neighbors) and semantic triplet search. Supports 24+ vector stores (default: Qdrant), 5+ graph stores (default: Neo4j). Now available as MCP server (mem0-mcp, Mar 2026). Achieves excellent latency (1.40s P95 vs 17.12s full-context, 60s LangMem) but scores only ~49% on LongMemEval — revealing that single/dual-strategy semantic retrieval struggles with diverse query types at scale. Graph variant adds ~3 points on temporal reasoning but doesn't close the gap with graph-native systems. Key weaknesses: no bi-temporal modeling, no fact/opinion separation, no BM25/keyword search in base variant, no confidence scores, no built-in forgetting/decay mechanism (Mem0 docs; arXiv; Vectorize benchmark comparison, 2025-2026).

    Honcho (Plastic Labs): personal identity platform that treats memory as a trained reasoning task rather than storage. Specialized models perform deductive, inductive, and abductive inference over user/agent interaction data, producing composable conclusion trees that serve as working identity models. The system derives latent insights from sparse data via formal logic and synthesizes optimal context at inference time from the reasoning tree rather than retrieving pre-stored facts. API-based (Courtland Leer & Vince Trost, Plastic Labs, "Memory as Reasoning," Aug 2025).

    Claude Code agent memory (v2.1.33, Feb 2026): memory frontmatter field on subagents with three scopes — user (cross-project, ~/.claude/agent-memory/), project (version-controlled, .claude/agent-memory/), local (git-ignored). First 200 lines of MEMORY.md injected into agent system prompt at startup. Agent reads/writes its own memory freely. Skills provide static knowledge at startup; memory provides dynamic knowledge built over time.

    Design Checklist¶

    1. Classify memory types — episodic (events), semantic (facts), procedural (how-to). Each has different retention, retrieval, and update patterns
    2. Default to compaction — move raw data to external storage before summarizing. Keep handles retrievable
    3. Implement update edges — track fact supersession explicitly rather than overwriting or appending
    4. Design for forgetting — define invalidation rules, staleness thresholds, and confidence decay
    5. Structure for prompt caching — place stable memory high in the prompt; vary only the dynamic tail
    6. Handle cold start — fall back to raw context retrieval when no distilled memory exists
    7. Evaluate continuously — measure recall rate, temporal accuracy, multi-session coherence, and preference fidelity
    8. Separate memory scopes — user-level (cross-project), project-level (team-shared), local (personal). Mirror the settings hierarchy. In multi-agent systems, also consider domain-scoped memory where each agent sees only its domain partition (e.g., billing sees billing, support sees support) — this is both a security pattern (least-privilege) and a relevance pattern (less noise per agent) (Cognee demo, 2026)
    9. Respect PII — define consent, expiry, and source-of-truth policies for personal data in memory
    10. Monitor context rot — track whether memory injection improves or degrades task completion over time
    11. Implement write-back feedback loops — after investigations, agents should record what retrieval strategies worked and what to try differently, so future searches improve over time. Measure whether write-back actually improves downstream task quality (Cognee demo, 2026)
    12. Fix operational foundations first — graph memory helps most after the operational backbone (eventing, schemas, source-of-truth) is sane. If upstream data models are broken, memory architecture cannot compensate
