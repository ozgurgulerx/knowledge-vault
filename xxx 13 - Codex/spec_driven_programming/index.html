    Spec-Driven Programming for Agentic Coding¶

    Opening Briefing¶

    The fundamental mistake in agentic coding is not insufficient prompting — it is the absence of a verification boundary between human intent and machine output. Most teams adopting Claude Code or Codex treat the conversation itself as the control surface: they prompt carefully, review chat output, and hope the agent understood. This inverts the correct relationship. The conversation is ephemeral and lossy; context windows erode over long sessions, and natural language instructions degrade through paraphrase and reinterpretation. What persists — and what actually governs correctness — is the testable specification that exists outside the chat, in version-controlled files with machine-checkable acceptance criteria.

    The architecture that makes this work operates on three distinct layers of precision, each mapped to a different verification mechanism. Behavioural contracts (inputs, outputs, error cases, invariants) become unit and property-based tests. Architectural intent (module boundaries, API shape, dependency constraints) becomes contract tests and schema validation against OpenAPI or JSON Schema definitions. Implementation freedom (naming, folder layout, optimization) is left deliberately unspecified, giving the agent room to operate without generating false constraint violations. The critical insight is that RFC 2119 keywords — MUST, MUST NOT, SHOULD, MAY — are not documentation conventions here but compilation targets: every MUST that lacks a corresponding test, schema check, or CI gate is a specification that will silently drift from reality. The document's north-star metric, percentage of acceptance criteria with automated evidence in CI, directly measures this mapping's completeness.

    What emerges from this layered approach is a second-order consequence that most teams miss: spec-driven programming does not slow agentic coding down — it accelerates it by making agent output disposable. When the spec and its verification harness are the source of truth, you can re-run an agent session from scratch, swap between Claude Code and Codex on the same repository, or parallelise multiple agent threads against different acceptance criteria, because correctness is defined externally rather than embedded in a single conversation's history. The agent becomes a fungible implementation engine rather than a brittle co-author whose context you must carefully preserve.

    This document codifies the spec-driven control system for agentic coding: layered specification templates, tool-specific instruction file conventions, a Plan-Patch-Prove workflow, and a testing strategy that encodes each spec layer into the appropriate verification mechanism. It is organized as a practitioner's reference — templates, checklists, and repo structures — rather than theory, because the gap between teams that ship reliably with agents and those that do not is almost never conceptual understanding but operational discipline in how specifications are written, verified, and enforced through CI.

    Executive Summary¶

    • Vibe-coding is the interaction style (fast, conversational, intent-first)
    • Spec-driven is the control system (contracts, automated verification, CI gates)
    • Put long-lived rules in CLAUDE.md / AGENTS.md; put feature-scoped intent in SPEC.md
    • Every MUST becomes either a test, a schema validation, or a CI gate — if it's only prose, it will drift
    • Track work as diffs + commits, not chat output; if it's not in git, it didn't happen

    Spec Granularity¶

    Three layers for agent-ready specs:

    • Behavioural contract (precise): Inputs/outputs, error cases, edge cases, invariants, acceptance criteria
    • Architectural intent (semi-precise): Module boundaries, data ownership, API shape, constraints ("no new deps," "must be backwards compatible")
    • Implementation freedom (flexible): Internal names, folder structure, optimisation choices

    Use RFC 2119 semantics: MUST / MUST NOT / SHOULD / MAY.

    Templates¶

    Template A: SPEC.md (feature work)¶

    # <Feature name>

## Goal

- What user outcome should exist?

## Non-goals

- Explicitly out of scope.

## Context

- Links, existing modules, constraints, migration notes.

## Functional requirements (normative)

- MUST:
  - ...
- MUST NOT:
  - ...
- SHOULD:
  - ...
- MAY:
  - ...

## Acceptance criteria (executable)

- [ ] Given ..., when ..., then ...
- [ ] API returns <status> with body matching <schema>
- [ ] Negative cases (must fail):
  - ...

## Examples

- Input / output examples (JSON, CLI transcripts)
- UX expectations (if relevant): screenshot links / text layout notes

## Observability

- Logs/metrics/traces required?

## Security / privacy

- Threat assumptions, secrets, auth model

## Release and rollout

- Feature flag? Backwards compatibility? Migration steps?

    Template B: AGENTS.md / CLAUDE.md (repo constitution)¶

    # AGENTS.md / CLAUDE.md

## Setup commands

- Install deps: ...
- Run tests: ...
- Lint/format: ...

## Repository map

- src/: ...
- docs/: ...
- scripts/: ...

## Engineering rules

- No new deps without approval
- Keep PRs small; prefer incremental commits
- Do not change public API without updating OpenAPI spec + contract tests

## Tooling

- Test runner: ...
- Coverage threshold: ...
- CI: GitHub Actions

    Template C: API Contracts as Specs¶

    • OpenAPI for HTTP API interface definitions
    • JSON Schema (draft 2020-12) for structured data validation
    • Codex can constrain outputs to match a JSON Schema via --output-schema

    Core Workflow¶

    1. Load repo rules (CLAUDE.md / AGENTS.md)
    2. Read SPEC.md
    3. Produce a plan (read-only)
    4. Implement in small diffs
    5. Verify (tests, lint, contract validation)
    6. Summarise diff + remaining risks
    7. Commit + PR
    8. CI gates + staging deploy
    9. Production deploy

    Prompting Patterns¶

    Plan, Patch, Prove (PPP)

    • Plan: restate spec, list files to touch, list tests to write/run
    • Patch: implement minimal diff
    • Prove: run test suite, map each acceptance criterion to evidence

    Spec as checklist with stop conditions

    • "Implement only that change, and stop. Do not refactor unrelated files."

    Diff-first review

    • Review diffs before submitting; highlight risks before PRs

    Testing Strategy¶

    Test type Spec layer encoded Best at catching Example tooling
    Unit Local behaviour contracts Logic bugs, regressions Jest; pytest
    Integration Cross-module IO contracts Wiring issues, misconfigs Jest + testcontainers; pytest
    Property-based Invariants ("for all inputs...") Edge cases, weird combos fast-check; Hypothesis
    Contract Producer/consumer API contracts Breaking API changes, version skew Pact

    Key tools: Property-based testing (Hypothesis for Python, fast-check for JS/TS) and consumer-driven contract testing (Pact) are the two highest-leverage additions to a standard test pyramid for spec-driven agent work.

    Example Repo Structure (General Pattern)¶

    <project>/
  AGENTS.md          # or CLAUDE.md — repo-level agent instructions
  SPEC.md            # feature spec with acceptance criteria
  <manifest>         # package.json / pyproject.toml
  src/               # or app/
    api.ts|py        # routes / endpoints
    domain/          # core logic (pure functions, validators)
    schemas/         # JSON Schema / OpenAPI definitions
  tests/
    test_*.unit.*    # unit tests for core logic
    test_*.property.*  # property-based tests (fast-check / Hypothesis)
    test_*.integration.*  # integration tests
  schemas/
    openapi.yaml     # or *.schema.json — machine-checkable contracts
  .github/
    workflows/
      ci.yml         # lint + test on PR; deploy on main
  Dockerfile         # (if container deployment)

    Checklists¶

    Scoping¶

    • MUST/MUST NOT/SHOULD requirements with explicit pass/fail conditions
    • Every MUST has a planned test (unit/integration/property/contract)
    • Non-goals are explicit (prevents agent scope creep)
    • At least one realistic example input/output per interface

    Execution (agent sessions)¶

    • Start with plan-only mode for multi-file changes
    • Require the agent to map acceptance criteria to evidence (tests, outputs)
    • Keep persistent rules in CLAUDE.md / AGENTS.md, not in conversation
    • Prefer small diffs; review diffs before merge

    Testing¶

    • Unit tests for core transformations
    • Property tests for invariants and input fuzzing
    • Contract tests for APIs (OpenAPI + Pact or similar)
    • CI runs at least lint + unit on every PR push

    Staging¶

    • Use preview deployments for fast behavioural validation
    • Keep config in environment variables, not in git
    • Smoke tests against preview/staging before main merge

    Commit¶

    • Commit after each acceptance criterion / test gate is satisfied
    • Use structured commit messages (e.g., Conventional Commits)
    • Never merge an agent PR without reading the diff and test outputs

    Deployment¶

    • Pick one: Git-based preview deploy (Vercel) or container deploy (Fly/Docker)
    • Ensure CI is green on main, then deploy
    • Document rollback procedure

    Risks and Limitations¶

    • Underspecification — "build a login page" forces the agent to invent dozens of decisions; spec-first eliminates this
    • Spec drift / context erosion — long sessions lose early constraints; put persistent rules in instruction files, not conversation history
    • Tool and web-input trust — treat web results as untrusted; use cached search where possible
    • Over-automation in CI — use danger-full-access only in controlled environments; enforce sandboxing, drop sudo, never rely on read-only alone to protect secrets
    • Hooks need governance — Claude Code hooks and CI bots can write commits; require least privilege and auditability
    • Spec and review debt — when agents are cheap and parallel, teams can produce code faster than they can validate architecture, duplication, abstraction quality, and long-term maintainability. The symptom: duplication creeps in and requires explicit review expeditions to detect. The fix: treat review capacity as a throughput constraint, not just agent capacity (Sam Breed, Anthropic, Mar 2026)
    • Permissive sandboxing in regulated contexts — "skip all permission prompts" and YOLO execution modes may suit fast-moving internal teams, but are inappropriate defaults for enterprise environments with secrets, deployment blast radius, or regulatory requirements (banking, healthcare, large monorepos). The operating model must be stricter than the tooling's most permissive setting

    Best Practices¶

    • Treat SPEC.md as the PR's source of truth; require acceptance criteria mapped to evidence
    • Encode invariants as property tests for input spaces humans won't enumerate
    • Encode interface boundaries as contracts (OpenAPI / JSON Schema / Pact)
    • Use hooks (Claude Code) or CI sandboxing (Codex) to enforce policy: "tests must pass," "no destructive ops," "format on write"
    • Prefer preview deployments to keep iteration fast while verifying in realistic environments
    • Keep agent instruction files short, concrete, and layered

    North Star Metric¶

    % of acceptance criteria that have automated evidence in CI (tests, schema validation, lint gates, deployment smoke checks). This single metric captures spec-driven maturity: if your criteria aren't verified automatically, they will drift.
