    Engineering Practices¶

    Opening Briefing¶

    The defining engineering challenge of 2024-2026 is not building AI features — it is surviving the hundred-fold cost gradient that separates a naive deployment from a viable one. Input token pricing spans from $0.15 per million tokens on a mid-tier model like Gemini Flash to $15 per million on a frontier model like Claude 3.5 Sonnet, a spread so wide that model routing — dynamically dispatching queries to cheap models for simple tasks and frontier models for hard ones — has become an architectural primitive rather than a post-launch optimization. Teams that treat model selection as a one-time decision at design time will find their unit economics collapse the moment usage scales, because the cost variance formula is multiplicative: average tokens times price times request volume, with no natural ceiling on any term.

    This cost pressure intersects a second structural force: the fine-tuning decision hierarchy that the industry has converged on through hard experience. The sequence — prompting first, then RAG, then supervised fine-tuning, then distillation — is not a suggestion but a risk-ordered escalation path. Each step up the ladder increases data dependency, staleness risk, and iteration cycle time. RAG retrieval adds 200-500 milliseconds of latency per query but preserves traceability through citations; fine-tuning eliminates that latency overhead but locks in a static knowledge snapshot that begins decaying immediately. The teams that skip to fine-tuning out of ambition rather than necessity accumulate technical debt that compounds silently until a domain shift exposes it.

    What makes this moment distinct is that all three frontier labs — OpenAI, Anthropic, and Google DeepMind — have independently arrived at capability-triggered safety frameworks that function as a de facto industry standard. Whether called Preparedness Levels, AI Safety Levels, or Critical Capability Levels, the mechanism is identical: measured capability thresholds unlock mandatory evaluation and containment requirements. This convergence matters because it means that engineering teams building on these models inherit a layered safety contract — pre-deployment red-teaming, input classifiers, output filters, runtime monitoring — that must be wired into the system architecture from the start, not bolted on before launch.

    The operating claim of this document is that production AI engineering is systems engineering, not model engineering. The ten-step governance-aware lifecycle laid out here — from problem framing through compliance mapping — reflects a discipline where the model is one component in a composition that includes retrieval pipelines, tool-use guardrails, content classifiers, cost controls, and audit trails. What follows is the full technical reference for building within that reality.

    Fine-Tuning & Alignment¶

    Technique When to Use Trade-offs
    SFT (Supervised Fine-Tuning) Consistent style/format on domain data Risk of overfitting; data goes stale
    DPO (Direct Preference Optimization) Align outputs to human preferences without reward model Simpler than RLHF; less flexible
    PEFT/LoRA Lightweight adaptation; resource-constrained Fewer parameters updated; faster/cheaper; may underperform full fine-tune on complex domains
    Distillation Transfer frontier model capability to smaller model Cost reduction at inference; quality ceiling limited by teacher model
    RL + Synthetic Data (e.g., Databricks KARL, March 2026) Task-specialized models via iterative synthetic data generation and large-batch off-policy RL (OAPL) Beats Claude 4.6 and GPT-5.2 on enterprise knowledge tasks at ~33% lower cost and ~47% lower latency; RL learns to search more efficiently (stop earlier, fewer wasted queries)
    Hypernetwork-generated LoRA (e.g., Sakana AI Doc-to-LoRA, 2026) Hypernetwork generates LoRA adapters from documents or task descriptions in one forward pass at runtime Enables memory/skill updates without full finetuning; continual learning without catastrophic forgetting; no gradient-based training at adaptation time

    Critical: Fine-tuning decision hierarchy: Start with prompting -> Add RAG -> Fine-tune only if prompting+RAG insufficient -> Distill for cost optimization.

    Note: Replaying generic pretraining data during finetuning reduces catastrophic forgetting and improves finetuning-domain performance when finetuning data is scarce (Kotha & Liang, March 2026).

    RAG & Grounding¶

    Robust RAG Pipeline (2026 Standard)¶

    1. Document ingestion -- multi-format (PDF, HTML, DOCX), layout-aware parsing, table extraction
    2. Chunking -- semantic chunking (not fixed-size); hierarchical (document -> section -> paragraph)
    3. Embedding -- domain-tuned embedding models; hybrid search (dense + sparse/BM25)
    4. Retrieval -- top-k retrieval + reranking (cross-encoder reranker); query expansion/decomposition
    5. Generation -- retrieved context injected into prompt; model generates with citations/attributions
    6. Evaluation -- RAG triad: Retrievability (did we find the right docs?), Answer accuracy (is the answer correct?), Groundedness (is the answer supported by retrieved docs?)

    Grounding as API Primitive¶

    • Google Vertex AI: grounding API connects Gemini to Google Search or enterprise data stores
    • OpenAI: function calling + retrieval tools in Assistants API
    • Anthropic: tool use with structured outputs

    RAG Attack Surface¶

    Threat Mitigation
    Prompt injection (direct/indirect) Input sanitization, instruction hierarchy, canary tokens
    Data poisoning (corrupted knowledge base) Source validation, provenance tracking, anomaly detection
    Context manipulation Retrieval filtering, access controls on data sources

    RAG vs. Fine-Tune Decision Hierarchy¶

    Criterion Choose RAG Choose Fine-Tune
    Knowledge freshness Data changes frequently Stable domain knowledge
    Traceability Need citations/sources Style/format consistency matters more
    Data volume Large corpus, growing Curated dataset, fixed
    Cost profile Per-query retrieval cost Upfront training cost, lower inference
    Latency Adds retrieval latency (~200-500ms) No retrieval overhead

    Tool Use & Agents¶

    Pattern Description Risk
    Single tool call Model calls one function (e.g., search, calculator) Low risk; deterministic fallback
    Sequential tool chain Model plans multi-step sequence (search -> extract -> summarize) Medium risk; error propagation
    Autonomous agent Model loops: plan -> act -> observe -> replan High risk; runaway loops, unsafe actions, cost explosion

    Agent guardrails: max iterations, budget caps, allowlisted tools only, human-in-the-loop for irreversible actions, deterministic checkpoints. For multi-hour autonomous sessions — such as Codex's overnight runs where agents work through queued tasks without human supervision — three additional patterns become load-bearing: task contracts with explicit exit criteria (the agent knows when it is done, not just what to do), compaction for context management (long-running sessions exceed any context window; periodic summarization of completed work keeps the active context bounded), and Firecracker microVM isolation (each task runs in a disposable VM so failures, hangs, or resource leaks cannot cascade across the queue). These patterns convert the autonomous agent from a high-risk runaway loop into a supervised batch system with per-task blast radius.

    Production Workflow Orchestration¶

    Most agent demos are linear prompt chains with fragile state management. Production systems require typed workflow graphs — declarative definitions of agents, edges, fan-out/fan-in points, sub-workflows, and decision gates — where every node has typed inputs and outputs enforced via Pydantic schemas. The runtime validates contracts and rejects invalid transitions, turning "prompt chain with logging" into a rigorous orchestration layer.

    Core Workflow Primitives¶

    Primitive What It Does Production Value
    Typed workflow graph Agents, edges, fan-out/fan-in, decision gates declared as a graph with Pydantic-typed I/O Runtime enforces contracts; rejects invalid transitions early; errors attributed to specific agents/tools
    Fan-out/fan-in execution Launch parallel agent tasks (e.g., KYC, fraud check, income verification) and synchronize results Configurable policies: fail-fast vs. best-effort; handles partial failures; manages concurrent execution
    Checkpointing & resume Persist workflow state at named checkpoints; resume on failure, replay, or A/B testing Checkpoints are versioned with full shared state + conversation memory snapshots; enables state diffing
    HITL gates Explicit pause/resume points for human decisions — first-class workflow nodes, not hacks Emit structured requests, wait for approval/rejection/adjustment, inject response into shared state with full attribution
    Shared state & memory Agents communicate via shared state dictionary and thread-scoped conversation memory State updates are atomic and observable; memory is queryable for replay and debugging

    Event-Driven API Pattern¶

    Production agent workflows expose an event-driven API rather than request/response:

    • POST /runs — start workflow, returns run_id immediately
    • GET /runs/{run_id}/events — SSE stream (long-lived connection) delivering typed JSON payloads for every workflow event
    • POST /runs/{run_id}/hitl — fulfill HITL request
    • POST /runs/{run_id}/resume — resume from checkpoint
    • GET /runs/{run_id}/state — snapshot shared state + memory

    Every SSE event includes timestamp, event type (progress, waiting, checkpoint.saved, hitl.resolved), phase identifier, status, overall + step progress ratios, and trace/span IDs for correlation with tracing backends.

    OpenTelemetry Instrumentation¶

    Telemetry is a first-class concern, not an afterthought. Every workflow run, agent invocation, tool call, fan-out boundary, checkpoint, and HITL gate emits structured OpenTelemetry spans with trace and span IDs. FastAPI auto-instrumentation captures HTTP boundaries; custom spans cover workflow internals. GenAI-specific span attributes — genai.agent, genai.model, genai.tokens.prompt, genai.tokens.completion, genai.latency_ms, genai.cache_hit — enable cost analysis and latency dashboards.

    A ProgressTracker provides weighted progress calculation across workflow stages. Each phase contributes a normalized weight to overall progress (e.g., document intake 6%, parallel fan-out 32%, risk ensemble 22%), with real-time SSE streams exposing granular progress plus trace IDs to front-ends.

    The observability stack runs locally via Docker Compose (backend + OTEL Collector + Jaeger) and is Azure Monitor-ready by pointing OTLP_ENDPOINT to Azure Monitor OTLP ingestion. GenAI attributes map to Azure Monitor custom metrics for cost/latency dashboards.

    Workflow Visualization¶

    GraphViz export generates SVG workflow diagrams with color-coded node types: agents (boxes), decision points (diamonds), fan-out/fan-in (octagons), HITL gates (hexagons), sub-workflows (double octagons), and start/end (ovals). Edges show dependencies. The diagram is queryable via API (GET /workflow/graph.svg) for documentation or real-time UI rendering.

    Jaeger trace timelines show full execution — parallel agent fan-out, synchronization barriers, checkpoint saves, HITL pauses — with spans nested to reflect orchestration hierarchy (workflow → stage → agent → tool).

    Graceful Degradation & Policy-First Design¶

    Production workflows tolerate infrastructure absence: missing OTEL collector falls back to console export, missing Graphviz returns a fallback SVG, missing checkpoints replay from start. Fan-out policies (fail-fast vs. best-effort), HITL timeout policies, and checkpoint retention policies are configurable via environment and enforced at runtime, not post-hoc.

    Engineering Checklist for Agent Workflows¶

    1. Define workflow graph with typed nodes (Pydantic schemas for inputs/outputs)
    2. Implement RunContext with emit/checkpoint/HITL primitives
    3. Add fan-out/fan-in executors with configurable policies
    4. Instrument all workflow boundaries with OTEL spans (workflow → stage → agent → tool)
    5. Stand up OTEL Collector + Jaeger (local Docker Compose or Azure Monitor)
    6. Build SSE streaming API with trace/span IDs in every event
    7. Implement weighted progress tracker with per-stage contributions
    8. Add GraphViz export for workflow visualization
    9. Write smoke tests that exercise normal/borderline/failure paths
    10. Ship canaries; measure latency/error rates; promote by evidence

    Reference implementation: Credit Desk Lite — a multi-agent credit underwriting workflow with 8 stages, 6 agents, fan-out/fan-in, sub-workflows, full OTEL instrumentation, SSE streaming, HITL gates, checkpoint/resume, and GraphViz export. Tech stack: FastAPI, Pydantic, OpenTelemetry, Jaeger, GraphViz, SQLite checkpoints, SSE streaming. North star: production agent systems are workflow orchestrators with typed contracts, comprehensive telemetry, and human-in-the-loop gates.

    Latency & Streaming¶

    • Time to first token (TTFT): critical for perceived responsiveness; target <500ms
    • Streaming: essential for chat UX; send tokens as generated
    • Latency budget: model inference + retrieval + tool calls + safety checks; each adds 100-500ms

    Cost Variance Formula¶

    Monthly cost = (avg_input_tokens x input_price + avg_output_tokens x output_price) x monthly_requests

    Margin levers: prompt caching (OpenAI, Anthropic offer cached context discounts), model routing (cheap model for easy queries, frontier for hard), batching, shorter prompts, output length limits.

    Failure-Aware Routing (Eval → Route → Specialize)¶

    Model routing is evolving from a static cost lever into a dynamic, eval-driven specialization loop. Instead of routing solely on query difficulty, production teams now route on classified failure type: hallucination → RAG-heavy path, reasoning failure → chain-of-thought or tool-use path, ambiguity → clarification agent. The pattern replaces monolithic "one model + one prompt" architectures with eval → classify failure → route to specialized sub-system, where a lightweight classifier or small LLM acts as the router. The result is higher reliability without retraining and lower cost via smaller models per path — each sub-system is optimized for the failure mode it handles rather than attempting to be generally capable. The router itself becomes core product logic, not infrastructure detail: "which system handles this?" is an architectural decision on par with model selection (emerging production patterns, Arize AI, 2025–2026).

    Code Structure for Agent Consumption¶

    Code written for agent consumption differs structurally from code written for human consumption. OpenAI's Codex — a 90%+ self-generated codebase serving 1M+ weekly active users — has converged on patterns that maximize agent success rates: explicit type annotations everywhere (agents rely on type signatures as navigational anchors more than humans do), comprehensive test suites as the primary verification mechanism (agents validate their own output by running tests, not by reading code), small focused files over large monoliths (bounded context windows make single-responsibility files an architectural requirement, not just a style preference), and AGENTS.md as the entry point for agent context (a machine-readable project manifest that replaces the human-oriented README as the first file an agent reads). These patterns also improve human readability, but their primary design driver is agent effectiveness — a codebase optimized for agents is one where the fine-tuning decision hierarchy (prompting -> RAG -> fine-tune -> distill) can operate over well-typed, well-tested, well-partitioned modules rather than ambiguous monoliths. The shift extends beyond codebases into open-source contribution itself: when a project receives thousands of PRs and issues in days, PRs increasingly function as "prompt requests" — not finished solutions, but signals about user pain points. In an agent era, contribution workflows shift from code submission to problem articulation, synthesis, and curation, subtly redefining what "contributing to open source" means (OpenClaw founder interview, 2026).

    The Engineer as Orchestrator¶

    The structural implication of agent-optimized codebases is broader than formatting conventions — it redefines the engineering role itself. Coding is being commoditized faster than engineering is (AI Engineering Conference, Mar 2026). The emerging stack is: planning, context and tooling, orchestration, verification and evals, durability and security, and product judgment. The hard part shifts from "I write code" to "I design, steer, verify, recover, and choose what matters." What accelerates this is the collapse of the learning tax: every engineer becomes a "mini R&D department" — a frontend person can push into recommender systems, an ML person can ship React — because implementation is no longer the bottleneck to cross-domain work (AI Engineering Conference, Mar 2026).

    This maps directly to where bottlenecks have migrated. Old engineering optimized typing speed, boilerplate elimination, and implementation velocity. The new scarce resources sit higher in the stack: planning quality, trust calibration (knowing when to accept vs. reject agent output), verification design, CI/infra throughput, ownership structure, product taste and prioritization, and failure recovery (AI Engineering Conference, Mar 2026). The cost variance formula and model routing strategies described above are examples of decisions that require engineering judgment no agent can automate — they demand understanding of business context, risk tolerance, and system-level trade-offs.

    Compressed-Context Reasoning: Privacy-Preserving Use of Reasoning Models¶

    The Model Selection Matrix above highlights data privacy as a key dimension, and the reasoning models row in the capabilities table shows that models like o1, o3, and DeepSeek-R1 excel at complex multi-step reasoning. These two concerns intersect in a powerful pattern: compressed-context reasoning, where privacy-preserving feature vectors replace raw PII in prompts, and reasoning models operate over those safe abstractions rather than sensitive personal data.

    Teams often default to "on-prem LLM with full PII context," maximizing raw detail but increasing privacy exposure, friction, and cost — while rarely improving real decision quality. The alternative is to compress user and business context into privacy-preserving representations, then apply a reasoning model that integrates signals, optimizes under constraints, and explains outcomes.

    Why compressed context wins over PII-heavy prompts:

    Advantage How It Works
    Cross-domain context integration Fuse transactional, behavioral, conversational, and content signals into compact features: cohort/segment IDs, derived intents, stability metrics, trust scores, eligibility flags. These abstractions travel safely and are easier to audit than raw PII.
    Constraint-driven optimization Real systems are multi-objective: user utility, cost, risk, compliance, SLAs. Reasoning models weigh trade-offs explicitly (e.g., preference satisfaction vs. risk budget) and produce actions that satisfy hard constraints while maximizing soft ones.
    Temporal reasoning Compressed features (event cadence, recency, dwell change, churn risk, lifecycle stage) let the model reason about what-if outcomes and next best actions without exposing raw timelines or identifiers.
    Conversational explanation Explanations reference segments, policies, and constraints rather than PII fields. Users hear why an action happened in plain language; auditors see policy-aligned traces.

    Compressed context vs. PII-heavy on-prem LLMs:

    • Privacy & governance: Move from raw fields to derived traits; minimize data-in-motion and storage of sensitive attributes.
    • Generalization: Reason over stable abstractions (segments, intents) instead of idiosyncratic identifiers; reduces overfitting to personal detail.
    • Latency & cost: Smaller prompts and fewer redaction passes; easier caching because features are normalized.
    • Robustness: Feature drift is measurable; policies encode constraints explicitly; outputs are reproducible.

    What to compress into the feature layer:

    • Segments and cohorts (behavioral, value-based, risk, lifecycle)
    • Derived preferences (format, channel, tone), intents, and tasks
    • Policy/eligibility flags and risk tiers
    • Constraint budgets (cost, latency, compliance, fairness thresholds)
    • Temporal features (recency, frequency, stability, trend, seasonality)

    Implementation path:

    1. Build a privacy-preserving feature layer: segmentation, trait extraction, eligibility rules, constraint budgets
    2. Define explicit policies and hard/soft constraints; expose them to the model as structured inputs
    3. Use a reasoning-capable model (small local or hosted) to generate actions and natural-language rationales
    4. Log features + constraints + decisions (no raw PII) for replay, audits, and A/B tests
    5. Monitor drift in features and policies; retrain segmentation and trait extractors on schedule

    When to use each approach: Use compressed-context reasoning when you need cross-domain fusion, policy compliance, explainability, and scale under strict privacy constraints. Use PII-rich on-prem LLMs only when raw identifiers materially change outcomes and you have strong legal basis, storage controls, and audit coverage.

    Critical: Compress context into safe, auditable features and let the model reason under constraints. You gain privacy, robustness, and better decisions — without hauling raw PII into every prompt.

    Data Flywheels as Control Systems (MAPE Loops)¶

    The traditional data flywheel pattern — collect user feedback, retrain globally, redeploy — is giving way to continuous closed-loop control modeled on MAPE (Monitor → Analyze → Plan → Execute) loops from control systems engineering. The shift: production systems now embed live feedback signals into runtime (implicit signals like user edits and retries, explicit signals like ratings and preferences, operational signals like latency and routing failures) rather than accumulating offline datasets for periodic retraining.

    The concrete pattern, demonstrated in NVIDIA-style adaptive agent systems: detect failure modes in specific components (routing, query rewriting), isolate the failing component, fine-tune only that component, and redeploy — resulting in a 10× smaller model with +70% latency improvement compared to global retraining (arXiv, "Adaptive Data Flywheel: Applying MAPE Control Loops to AI Agent Improvement", 2025). The key architectural upgrade is recognizing the flywheel as a multi-layer system: a UX loop (user corrections feeding back), a model loop (targeted fine-tuning and eval), and a system loop (routing and tool selection optimization). The builder pattern is interaction → structured feedback → failure classification → targeted fix → redeploy → repeat, not logs → retrain everything.

    A more aggressive variant is Meta's CharacterFlywheel, which runs the loop on live user traffic rather than offline failure analysis. Over 15 iterative model generations, the system cycles through user interactions → reward modeling → SFT/RL → A/B test → deploy, producing +19.4% engagement depth and instruction-following improvement from 59% to 84.8%. The key difference from MAPE-style failure isolation: the CharacterFlywheel uses reward models as the flywheel core — each product KPI (engagement, instruction adherence, safety) gets its own reward model that directly drives the training loop, making the flywheel metric-optimized rather than failure-type-specific. The practical takeaway: build a reward model per product KPI, not generic evals (arXiv, "CharacterFlywheel: Scaling Iterative Improvement of Engaging and Steerable LLMs in Production", Meta, 2026).

    Tiered Code Review for AI-Generated Code¶

    The defence-in-depth principle applies not only to model safety but to code quality in AI-native codebases. OpenAI's Codex — whose codebase is 90%+ self-generated — runs a three-tier review system that operationalizes this: (1) automated CI checks (lint, type-checking, test suites) gate every commit, (2) AI-powered review by a separate model instance inspects diffs for security vulnerabilities, style violations, and logic errors, catching ~60% of issues before a human sees them, and (3) human review remains mandatory for merges to protected branches. This is the production implementation of defence-in-depth applied to code quality rather than model safety — each layer catches a different class of defect, and no single layer is trusted alone.

    Red-Teaming Protocol¶

    1. Scope -- define attack categories (prompt injection, jailbreaks, bias elicitation, harmful content, PII extraction)
    2. Internal red team -- dedicated team with adversarial prompt expertise
    3. External red team -- third-party security firms, bug bounty programs
    4. Automated red-teaming -- LLM-generated adversarial prompts at scale
    5. Reporting -- findings logged in risk register; mitigations tracked to closure

    Content filtering Input/output classifiers (toxicity, PII, CSAM)
    Audit logging All model inputs/outputs logged (with PII redaction) for compliance
    Kill switch Ability to disable AI features instantly without full deployment
    A/B rollback Automated revert if quality metrics drop below threshold

    PM-Engineering Collaboration Models¶

    Model Companies How It Works
    Research-driven OpenAI, Anthropic, DeepMind Researchers lead capability development; PMs package for users. PM influence grows post-research.
    PM-led with eng partnership Notion, Canva, Adobe PMs own problem definition and prioritization; eng owns implementation. Traditional product development with AI components.
    Platform/infra-led Databricks Platform teams build AI capabilities; product PMs integrate into surface areas. Requires strong cross-team coordination.

    A more radical model is emerging alongside these: single-threaded ownership with minimal collaboration overhead. High-performing teams increasingly optimize for one engineer per feature, less coordination by default, faster iteration, and deeper trust in agents (Kilo Code, AI Engineering Conference, Mar 2026). The progression follows a trust ladder: autocomplete, then chat, then single-agent delegation, then full orchestration. Under this model, bottlenecks are process, review load, CI saturation, and product direction — not raw implementation capacity. The anti-collaboration thesis is not "never talk" but "most collaboration is latency and comfort theater" — in agentic workflows, handoffs between humans are more expensive relative to solo ownership than they were in manual coding (Kilo Code, AI Engineering Conference, Mar 2026). The more likely end state is fewer human-human handoffs and more human-agent-human review loops. Important caveat: this works best in high-taste, high-speed, low-compliance environments with exceptional talent density. It breaks in regulated domains, messy legacy estates, and teams with uneven judgment — precisely the contexts where the governance-aware lifecycle and defence-in-depth layers described elsewhere in this document remain essential.

    Gaps & Opportunities¶

    Gap Opportunity
    Evaluation tooling is immature Standardized eval frameworks for production LLM apps (beyond research benchmarks). One emerging pattern treats evals as a control system, not a one-time gate: dataset, task, scorer, experiment loop, production logging, then feeding real user traces back into the eval dataset — a closed loop that continuously improves coverage (BrainTrust, AI Engineering Conference, Mar 2026). A concrete finding from this approach: agentic search vs. vector search for bug-fixing tasks — agentic search (where the model navigates the codebase step by step) generally performed better or equally well while being much cheaper, because vector retrieval returned local chunks without enough connective tissue for reasoning across a codebase. Caveat: this was tested on small datasets with non-determinism and a basic vector implementation; hybrid approaches are likely needed for production, and the researchers were transparent about these limitations, which made the result more credible (BrainTrust, AI Engineering Conference, Mar 2026).
    Cost optimization is ad hoc Better tooling for token cost tracking, caching strategies, model routing (cheap model for easy queries, expensive for hard)
    Personalization is shallow Deep user modeling -- AI that learns individual preferences over time (beyond basic context)
    Multi-agent coordination Production-grade orchestration for multi-agent workflows (planning, delegation, error recovery)
    AI UX patterns are still evolving No established design system for AI interactions; opportunity for standardization
    Enterprise governance Unified platforms for model risk management, audit trails, compliance across multiple AI vendors
    Vertical AI products Horizontal platforms dominate; vertical-specific AI (legal, healthcare, finance) remains underbuilt
    Offline/edge AI Most products require cloud; on-device AI for privacy-sensitive or latency-critical use cases

    Assistive vs. Automation GTM¶

    Dimension Assistive (human-in-the-loop) Automation (AI-driven)
    User trust High (user confirms) Must be earned over time
    Error tolerance User catches errors Errors have direct impact
    Adoption curve Faster (augments existing workflow) Slower (requires process change)
    Value proposition "Work faster" "Work happens without you"
    GTM motion Bottom-up (individual users adopt) Top-down (org-level decision)

    Critical: Most successful 2024-2026 products start as assistive AI and graduate to automation as trust builds and error rates decrease.
