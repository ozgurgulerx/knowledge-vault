    Frontend Design with Coding Agents¶

    See also: Generative UI | Codex Expert Guide | Claude Code Expert Guide | AI Engineering Practices

    Opening Briefing¶

    The defining gap in AI-generated frontends is not capability but taste. Coding agents can produce functional UIs, but when prompts are underspecified, models fall back to high-frequency patterns from training data — generic structure, weak visual hierarchy, default typography stacks (Inter, Roboto, Arial), flat single-color backgrounds, card-heavy layouts, and purple-on-white color schemes. The result is plausible but unmemorable. The fix is not a better model — it is better steering: explicit design constraints, visual references, narrative structure, and design-system adherence that guide the agent toward the specific design you envision.

    GPT-5.4 represents a step change in frontend generation capability, with three practical gains over predecessors: stronger image understanding throughout the design process (native image search and generation tools for mood boards and asset selection), more functionally complete apps (games and complex UX that previously required multiple iterations now work in one or two turns), and computer use for verification (Playwright integration for inspecting rendered pages, testing viewports, and validating behavior — the first mainline model trained for computer use) (OpenAI, "Designing Delightful Frontends with GPT-5.4", Brian Fioca, Alistair Gillespie, Kevin Leneway, Robert Tinn, Mar 2026).

    The broader pattern applies beyond GPT-5.4: the quality ceiling for AI-generated frontends is set by the prompt's design constraints, not the model's generation capacity. Every technique here works across coding agents — Claude Code, Codex, Cursor — because the bottleneck is specification, not generation.

    Hard Rules for Frontend Generation¶

    These constraints prevent the most common AI-generated frontend anti-patterns. Include them in system prompts, CLAUDE.md files, or agent instructions.

    Layout and Composition¶

    • One composition per viewport — the first viewport must read as a single cohesive composition, not a dashboard (unless it is a dashboard)
    • Full-bleed hero only — on landing pages, the hero image should be a dominant edge-to-edge visual plane or background by default. Do not use inset hero images, side-panel layouts, rounded media cards, tiled collages, or floating image blocks unless the existing design system requires it
    • Hero budget — the first viewport should contain only: the brand, one headline, one short supporting sentence, one CTA group, and one dominant image. Do not place stats, schedules, event listings, address blocks, promos, or secondary marketing content in the first viewport
    • No hero overlays — do not place detached labels, floating badges, promo stickers, info chips, or callout boxes on top of hero media
    • One job per section — each section should have one purpose, one headline, and usually one short supporting sentence

    Cards, Clutter, and Chrome¶

    • Default: no cards — never use cards in the hero. Cards are allowed only when they are the container for a user interaction. If removing a border, shadow, background, or radius does not hurt interaction or understanding, it should not be a card
    • Reduce clutter — avoid pill clusters, stat strips, icon rows, boxed promos, schedule snippets, and multiple competing text blocks

    Typography and Color¶

    • Expressive fonts — use purposeful fonts and avoid default stacks (Inter, Roboto, Arial, system-ui). Typography is a primary design lever
    • No flat backgrounds — do not rely on flat single-color backgrounds; use gradients, images, or subtle patterns to build atmosphere
    • Choose a clear visual direction — define CSS variables for the palette; avoid purple-on-white defaults and dark mode bias
    • Two typefaces maximum — one for display/headlines, one for body

    Brand and Identity¶

    • Brand first — on branded pages, the brand or product name must be a hero-level signal, not just nav text or an eyebrow. No headline should overpower the brand
    • Brand test — if the first viewport could belong to another brand after removing the nav, the branding is too weak

    Motion and Interaction¶

    • Use motion for presence and hierarchy, not noise — ship at least 2-3 intentional motions for visually-led work
    • Keep fixed/floating UI elements from overlapping text, buttons, or key content across screen sizes. Place them in safe areas with sufficient spacing

    Responsive and Technical¶

    • Ensure the page loads properly on both desktop and mobile
    • For React code, prefer modern patterns (useEffectEvent, startTransition, useDeferredValue) when appropriate. Do not add useMemo/useCallback by default unless already used in the codebase
    • Exception: when working within an existing design system, preserve the established patterns, structure, and visual language

    Techniques for Steering Design Quality¶

    1. Start with Design Principles¶

    Define constraints upfront rather than hoping the model infers them:

    • One H1 headline
    • No more than six sections
    • Two typefaces maximum
    • One accent color
    • One primary CTA above the fold

    These constraints prevent the model from defaulting to busy, over-structured layouts.

    2. Provide Visual References¶

    Reference screenshots or mood boards help the model infer layout rhythm, typography scale, spacing systems, and imagery treatment. Instruct the model to generate a mood board first — several visual options for the user to review before proceeding. Describe the attributes the images should capture: style, color palette, composition, and mood.

    Prompt pattern: "Default to using any uploaded/pre-generated images. Otherwise use the image generation tool to create visually stunning image artifacts. Do not reference or link to web images unless explicitly asked."

    3. Structure the Page as a Narrative¶

    The most effective marketing pages follow a narrative arc:

    1. Hero — establish identity and promise
    2. Supporting imagery — show context or environment
    3. Product detail — explain the offering
    4. Social proof — establish credibility
    5. Final CTA — convert interest into action

    Providing this structure prevents the model from creating formless pages with competing sections.

    4. Define the Design System Early¶

    Establish core design tokens before generation:

    • Colors: background, surface, primary text, muted text, accent
    • Typography roles: display, headline, body, caption
    • Spacing scale and border radius conventions

    React + Tailwind is the stack where GPT-5.4 (and most coding agents) performs strongest for rapid iteration to polished results.

    5. Ground in Real Content¶

    Providing real copy, product context, or a clear project goal is one of the simplest improvements. Real context helps the model choose the right site structure, shape clearer section narratives, and write believable messaging instead of falling back to generic placeholder text.

    6. Dial Back the Reasoning¶

    For simpler websites, more reasoning is not always better. Low and medium reasoning levels often lead to stronger frontend results — the model stays fast, focused, and less prone to overthinking. Reserve higher reasoning for complex interactive experiences or ambitious designs.

    7. Use Computer Use for Verification¶

    Playwright integration allows the model to:

    • Inspect rendered pages visually
    • Test multiple viewport sizes
    • Navigate application flows and detect state/navigation issues
    • Compare output against a reference UI screenshot

    This creates a build → inspect → refine loop that significantly improves the likelihood of polished, functionally complete interfaces.

    Common AI Frontend Anti-Patterns¶

    These are the recurring failure modes when prompts lack design constraints:

    Anti-Pattern What happens Fix
    Card soup Every piece of content wrapped in bordered, shadowed cards Default to no cards; use cards only for interactive containers
    Purple-on-white Default color scheme with no visual identity Define palette as CSS variables upfront
    Dashboard-as-landing-page First viewport crammed with stats, grids, and competing sections Hero budget: brand + headline + CTA + one image
    Generic hero Inset image, rounded corners, decorative gradient instead of real visual Full-bleed hero with product/place/atmosphere imagery
    Typography neglect Inter or system fonts everywhere, uniform sizing Choose expressive display + body font pair; define scale
    No motion Static page with no transitions or interactions Require 2-3 intentional motions for visual presence
    Placeholder overload "Lorem ipsum" and stock descriptions filling every section Provide real copy or clear content strategy upfront
    Overcrowded viewport First viewport has stats, schedules, promos, and metadata One job per section; hero budget constraint

    Agent-Specific Notes¶

    Codex / GPT-5.4¶

    GPT-5.4 was specifically trained with improved UI capabilities and native image tool use. The frontend-skill is installable via $skill-installer frontend-skill in Codex, providing structure, taste, and interaction pattern guidance. GPT-5.4 is the first mainline model trained for computer use, enabling Playwright-based visual verification natively (OpenAI, Mar 2026).

    Claude Code¶

    Claude Code's frontend-design skill (superpowers plugin) provides similar steering. The key difference: Claude Code's skill system loads instructions as conversation context rather than tool-level integration, and verification relies on the user's local browser rather than built-in computer use. The hard rules and design techniques above work directly as CLAUDE.md instructions.

    Cursor / Windsurf¶

    These IDE-integrated agents benefit from the same constraint set added to project-level instruction files (.cursorrules, workspace settings). The main gap: no native visual verification — the developer serves as the visual feedback loop.

    Key: The quality ceiling for AI-generated frontends is determined by specification quality, not model capability. A well-constrained prompt on a mid-tier model produces better frontends than an unconstrained prompt on a frontier model. Invest time in the design brief, not in model selection.
