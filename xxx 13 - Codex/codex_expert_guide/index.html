    OpenAI Codex — Architecture, Best Practices, and Deployment Playbook¶

    Opening Briefing¶

    Codex is OpenAI's agentic coding platform — a command centre for multi-agent coding workflows that reads your codebase, executes code in sandboxed environments, and iterates autonomously toward task completion. The core insight from the highest-leverage Codex users: treat the agent as a powerful but fallible contributor and push quality guarantees into the harness — explicit repo instructions, hermetic execution, deterministic checks, and automated evaluation loops — rather than relying on "better prompting" alone.

    Codex works best when treated less like a one-off assistant and more like a teammate you configure and improve over time. The mental model: start with the right task context, use AGENTS.md for durable guidance, configure Codex to match your workflow, connect external systems with MCP, turn repeated work into skills, and automate stable workflows. The ROI is a direct function of harness quality, not prompt sophistication (OpenAI Codex Best Practices, Mar 2026).

    As of March 2026, Codex has 1M+ weekly active users (5x growth since January 2026), with 90%+ of Codex's own codebase written by Codex itself — the strongest possible dogfooding signal (Gergely Orosz, Pragmatic Engineer, "How Codex is Built", Mar 2026).

    Architecture & How Codex Is Built¶

    Codex is written in Rust by a ~30-engineer team, chosen early for performance and memory safety in the sandbox runtime. The agent loop is a 5-step state machine implementing the ReAct pattern, production-hardened in a compiled language:

    1. Gather context from conversation + environment
    2. Call the model (GPT-5.3-Codex)
    3. Parse response for tool calls
    4. Execute tool calls in a Firecracker microVM sandbox
    5. Loop or return final response

    GPT-5.3-Codex is a coding-specialized variant of GPT-5.3, fine-tuned specifically for Codex's agentic workflows — not a generic model, but one optimized for the agent loop's structured tool-call patterns.

    Sandboxing: Every code execution runs in a Firecracker microVM — isolated filesystem (ephemeral, destroyed after session), network restricted to allowlist, per-agent resource limits. This is the production answer to "agent running arbitrary code."

    Parallelism: 4-8 concurrent agents per user session, each in its own isolated microVM sandbox. Agents cannot interfere with each other.

    Three-tier code review (Codex's production pattern):

    1. Automated CI checks — lint, type, test
    2. AI-powered review by a separate model instance checking security, style, and logic (~60% of issues caught before human review)
    3. Human review for merges to protected branches

    (Gergely Orosz, Pragmatic Engineer, "How Codex is Built", Mar 2026)

    Prompting & Task Context¶

    Codex is already strong enough to be useful even when prompts aren't perfect. Clear prompting isn't required to get value, but it makes results more reliable — especially in larger codebases or higher-stakes tasks.

    A good default includes four elements in every prompt:

    • Goal: What are you trying to change or build?
    • Context: Which files, folders, docs, examples, or errors matter? Use @ mentions to reference specific files
    • Constraints: What standards, architecture, safety requirements, or conventions should Codex follow?
    • Done when: What should be true before the task is complete — tests passing, behavior changing, a bug no longer reproducing?

    This helps Codex stay scoped, make fewer assumptions, and produce work easier to review.

    Reasoning levels — choose based on task difficulty:

    • Low for faster, well-scoped tasks
    • Medium or High for complex changes or debugging
    • Extra High for long, agentic, reasoning-heavy tasks

    Key: Speech dictation inside the Codex app provides faster context capture than typing — especially useful for initial brainstorms and requirement capture.

    (OpenAI Codex Best Practices, Mar 2026)

    Planning for Complex Tasks¶

    If the task is complex, ambiguous, or hard to describe well, ask Codex to plan before coding.

    Three approaches that work well:

    Plan mode — the easiest and most effective option for most users. Lets Codex gather context, ask clarifying questions, and build a stronger plan before implementation. Toggle with /plan or Shift+Tab.

    Interview mode — ask Codex to question you first when you have a rough idea but aren't sure how to describe it. Tell it to challenge your assumptions and turn the fuzzy idea into something concrete before writing code.

    PLANS.md template — for advanced workflows, configure Codex to follow a persistent execution-plan template for longer-running or multi-step work. Plan files survive across sessions and give agents stable context for multi-step work — whereas plan mode context disappears when the session ends.

    Key: Planning is not optional for complex tasks — it prevents expensive agent drift. Persistent plan files beat ephemeral plan mode for anything requiring cross-session continuity.

    (OpenAI Codex Best Practices, Mar 2026)

    AGENTS.md — The Repo Constitution¶

    AGENTS.md is an open-format README for agents. It loads into context automatically and is the best place to encode how you and your team want Codex to work in a repository. Codex popularized this as the repo-level instruction standard, and the Feb 2026 arXiv research on AGENTS.md effects was conducted primarily on Codex repos.

    A good AGENTS.md covers:

    • Repo layout and important directories
    • How to run the project
    • Build, test, and lint commands
    • Engineering conventions and PR expectations
    • Constraints and "do-not" rules
    • What "done" means and how to verify work

    Hierarchy: Global AGENTS.md in ~/.codex for personal defaults, repo-level file for shared standards, subdirectory files for local rules. More specific files closer to the current directory win.

    Scaffolding: The /init slash command scaffolds a starter AGENTS.md — edit the result to match how your team actually builds, tests, reviews, and ships code.

    Sizing discipline: Keep it practical. A short, accurate AGENTS.md is more useful than a long file full of vague rules. Start with basics, add rules only after you notice repeated mistakes. If AGENTS.md grows too large, keep the main file concise and reference task-specific markdown files for planning, code review, or architecture.

    Retrospective loop: When Codex makes the same mistake twice, ask it for a retrospective and update AGENTS.md. Guidance stays practical and based on real friction.

    High-Signal AGENTS.md Template¶

    # AGENTS.md

## Contract
- If you change code, run fastest relevant checks and report results.
- Prefer small, reviewable diffs; split large work into staged PRs.
- Never introduce new dependencies without updating lockfiles.

## How to verify
- Unit tests: `...`
- Lint/format: `...`
- Typecheck: `...`
- Integration tests (only when touching boundaries): `...`

## Repo invariants
- Public API compatibility rules
- Security: never log secrets; never broaden network egress; never disable auth checks
- Performance: no new N+1 queries; no unbounded loops in hot paths

## Code style (only what CI can enforce)
- Formatter/linter rules that matter
- Naming conventions that break tooling if violated

## Where to look
- Architecture: `docs/architecture.md`
- Key modules: `src/...`, `services/...`
- Sharp edges: `docs/gotchas.md`

    Key: AGENTS.md should encode the minimum runnable contract for changing code safely — what checks to run, what constraints matter, where sharp edges are. Let discovery happen through tools/tests.

    AGENTS.md Research Findings¶

    Feb 2026 arXiv papers disagree on AGENTS.md effects. Reconciling hypothesis: AGENTS.md helps when it removes ambiguity and accelerates correct verification, but hurts when it adds irrelevant constraints.

    • arXiv 2602.11988 (Feb 12): AGENTS-like context can decrease success rates + increase cost
    • arXiv 2601.20404 (Jan 28): Finds runtime and output-token reductions with AGENTS.md

    (OpenAI Codex Best Practices, Mar 2026; arXiv, Feb 2026)

    Configuration & Consistency¶

    Configuration makes Codex behave consistently across sessions and surfaces — model choice, reasoning effort, sandbox mode, approval policy, profiles, and MCP setup.

    Configuration layers:

    • Personal defaults in ~/.codex/config.toml (Settings > Configuration > Open config.toml from the Codex app)
    • Repo-specific behavior in .codex/config.toml
    • Command-line overrides for one-off situations (CLI only)

    config.toml defines durable preferences: MCP servers, profiles, multi-agent setup, experimental features. Edit directly or ask Codex to update it.

    Two key control knobs:

    • Approval mode — when Codex asks for permission to run a command
    • Sandbox mode — whether Codex can read/write in the directory and which files the agent can access

    The CLI, IDE, and Codex app all share the same configuration layers.

    Key: Configure Codex for your real environment early. Many quality issues are really setup issues — wrong working directory, missing write access, wrong model defaults, or missing tools and connectors. Start with tight permissions, then loosen only for trusted repos or specific workflows once the need is clear.

    (OpenAI Codex Best Practices, Mar 2026)

    Testing, Review & Quality Gates¶

    Don't stop at asking Codex to make a change. Ask it to create tests, run checks, confirm the result, and review the work before you accept it. Codex can do this loop — but only if it knows what "good" looks like. That guidance comes from either the prompt or AGENTS.md.

    The verification loop should include:

    • Writing or updating tests for the change
    • Running the right test suites
    • Checking lint, formatting, or type checks
    • Confirming the final behavior matches the request
    • Reviewing the diff for bugs, regressions, or risky patterns

    Diff panel: Toggle in the Codex app to directly review changes locally. Click on a specific row to provide feedback fed as context to the next turn.

    /review slash command provides multiple review modes:

    • Review against a base branch (PR-style)
    • Review uncommitted changes
    • Review a specific commit
    • Use custom review instructions

    If your team has a code_review.md file referenced from AGENTS.md, Codex follows that guidance during review — a strong pattern for consistency across repositories and contributors.

    GitHub Cloud integration: Set up Codex to run code reviews on PRs automatically. At OpenAI, Codex reviews 100% of PRs. Enable automatic reviews or have Codex reactively review when you @Codex.

    Harness Control Pipeline¶

    Task intake -> Plan step (constraints + verification contract)
  -> Choose execution mode (single agent or worktree fork)
    -> Apply patch -> Run minimal checks (lint/type/unit)
      -> Pass? -> Generate summary + artefacts -> Human review -> Merge
      -> Fail? -> Iterate: diagnose -> patch -> re-run
        -> Post-merge: add eval case if failure was novel
    Primitive What to Do
    Forbid Unsafe actions by default; require explicit approvals for exceptions
    Require Run AGENTS.md checks at minimum; treat as contract, not suggestion
    Record Command logs, diffs, structured JSON outputs for fast human review

    (OpenAI Codex Best Practices, Mar 2026)

    MCP for External Context¶

    Use MCP when the context Codex needs lives outside the repo. Model Context Protocol is an open standard connecting Codex to external tools and systems — replacing copy-paste of live information into prompts with repeatable integrations.

    Use MCP when:

    • The needed context lives outside the repo
    • The data changes frequently
    • You want Codex to use a tool rather than rely on pasted instructions
    • You need a repeatable integration across users or projects

    Codex supports both STDIO and Streamable HTTP servers with OAuth. In the Codex App, head to Settings > MCP servers for custom and recommended servers. The CLI uses codex mcp add with a name, URL, and configuration details.

    Key: Add tools only when they unlock a real workflow. Start with one or two tools that clearly remove a manual loop you do often, then expand from there. Don't wire in every tool you use upfront.

    (OpenAI Codex Best Practices, Mar 2026)

    Skills Ecosystem¶

    Once a workflow becomes repeatable, package it as a Skill (SKILL.md file) with instructions, context, and supporting logic Codex should apply consistently. Skills work across the CLI, IDE extension, and Codex app.

    Design principles:

    • Keep each skill scoped to one job
    • Start with 2-3 concrete use cases
    • Define clear inputs and outputs
    • Write the description so it says what the skill does and when to use it — include trigger phrases a user would actually say
    • Start with one representative task, get it working well, then turn it into a skill

    Good candidates for skills:

    • Log triage
    • Release note drafting
    • PR review against a checklist
    • Migration planning
    • Telemetry or incident summaries
    • Standard debugging flows

    Skills architecture: Skills are folders anchored by SKILL.md with YAML frontmatter for discovery/routing. Full instructions load only when invoked. Framed as enablement for repeatable workflows, scripts/templates, and sandboxed execution.

    Scale: As of March 2026, Codex maintains 100+ internal skills covering common workflows (PR creation, bug triage, dependency updates, migration scripts). SkillsBench counted 47,000+ unique skills across 6,300+ repositories — though almost none have eval harnesses. Most are AI-generated, vibe-checked with a handful of manual runs, then shipped.

    Storage: Personal skills in $HOME/.agents/skills, shared team skills in .agents/skills inside a repository — especially helpful for onboarding new teammates.

    Tooling: The $skill-creator skill scaffolds the first version; $skill-installer installs locally. The skill description is the most critical piece — a vague description means unreliable triggering. A description rewrite alone fixed 5 of 7 failures in one case study (Gemini Interactions API skill, 66.7% → 100% pass rate).

    Cross-tool portability: Vercel's skills.sh targets multiple tools, making skills a portable unit across agent surfaces — suggesting "agent capability packaging" may standardize faster than any one vendor's plugin system.

    Testing Skills¶

    Key: Don't ship skills without evals. The skill description is the trigger mechanism — if it's vague, the skill won't trigger reliably.

    Grade outcomes, not paths — three dimensions:

    1. Outcome — Does it produce a usable result? Code compiles, API returns valid response, document renders
    2. Style & instructions — Does the output follow conventions and directives? Right SDK, correct model IDs, naming conventions
    3. Efficiency — How much time, tokens, effort? No unnecessary retries, reasonable token count, no command thrashing

    Lightweight eval harness (4 steps):

    1. Create a prompt set (10-20 prompts). Include negative tests — prompts where the skill should NOT trigger
    2. Run the agent and capture output through the CLI, not a mock
    3. Write deterministic checks — small functions (typically regex) returning booleans
    4. Add LLM-as-judge (optional) for subjective assessment using structured output schemas

    Best practices: Use directives not information ("Always use X" > "X is recommended"). Isolate each run. Run 3-5 trials per prompt. Test across harnesses. Graduate passing evals into regression suites. Detect skill retirement by running evals with the skill unloaded.

    (OpenAI Codex Best Practices, Mar 2026)

    Automations & Scheduled Work¶

    Once a workflow is stable, schedule Codex to run it in the background. In the Codex app, automations let you choose the project, prompt, cadence, and execution environment.

    Good candidates:

    • Summarizing recent commits
    • Scanning for likely bugs
    • Drafting release notes
    • Checking CI failures
    • Producing standup summaries
    • Running repeatable analysis workflows on a schedule

    Execution environments: Choose between a dedicated git worktree (isolated) or your local environment.

    Key: Skills define the method, automations define the schedule. If a workflow still needs a lot of steering, turn it into a skill first. Once predictable, automation becomes a force multiplier. Use automations for reflection and maintenance too — review recent sessions, summarize repeated friction, improve prompts and workflow setup over time.

    (OpenAI Codex Best Practices, Mar 2026)

    Session Management¶

    Codex sessions are working threads that accumulate context, decisions, and actions over time. Managing them well has a big impact on quality.

    Key slash commands:

    • /experimental — toggle experimental features and add to config.toml
    • /resume — resume a saved conversation
    • /fork — create a new thread preserving the original transcript
    • /compact — summarize earlier context (Codex also auto-compacts)
    • /agent — switch between active parallel agent threads
    • /theme — choose syntax highlighting theme
    • /apps — use ChatGPT apps directly in Codex
    • /status — inspect current session state

    Thread discipline: Keep one thread per coherent unit of work. If the work is still part of the same problem, staying in the same thread preserves the reasoning trail. Fork only when the work truly branches.

    Multi-agent offloading: Use subagents for bounded work — exploration, tests, triage — while keeping the main agent focused on the core problem.

    Compaction: When conversations exceed context limits, Codex summarizes prior context into a condensed representation — preserving task state, file changes, and test results while discarding conversational filler. Both Codex and Claude Code converge on this pattern as essential for extended agentic sessions.

    (OpenAI Codex Best Practices, Mar 2026)

    Memory and State Management¶

    Key: OpenAI's Jan 2026 cookbook treats memory as a high-value attack surface and recommends guardrails at distillation, consolidation, and injection stages.

    State-based memory store pattern:

    • Structured profile fields + curated memory notes
    • Explicit memory distillation during runs
    • End-of-run consolidation (dedupe/conflict resolution)
    • Deterministic injection as YAML frontmatter + markdown lists
    • Precedence: latest user input > session overrides > global defaults

    Memory commands: /m_update, /m_drop for explicit memory management; expanded memory-read/metrics pipelines.

    Memory guardrails: Never store sensitive data; reject instruction-shaped memories; enforce "no invention" during consolidation; wrap in explicit delimiters; treat as advisory, not authoritative.

    (OpenAI Cookbook, Jan 2026)

    Parallel Worktrees & Multi-Agent Workflows¶

    Power users cite "do more in parallel" using isolated workspaces as the repeated advantage over "better prompts."

    Codex parallelism: 4-8 concurrent agents per user session, each in its own Firecracker microVM sandbox. Agents cannot interfere with each other.

    Zack Proser's two-tier workflow: Queue multiple Codex tasks for maintenance/SDLC grunt work, then spend human focus on hard architectural work using other tools.

    Harness patterns at scale (1M+ WAU):

    • Session continuity — resume-from-PR/branch, session forking
    • Instruction layering — global vs repo instruction files; override behaviors
    • Resource stability under parallelism — OOM pressure, memory leaks under multiple sessions
    • Structured privileges — permissions history, approvals, read-only shapes, network approvals

    Agent HQ inside GitHub — two quality-positive workflows:

    • PR review + remediation loops: @codex review → apply fixes in follow-up agent sessions
    • Issue-to-PR delegation: Agent produces patch under normal branch protections, humans review

    Key: The lesson is not that one tool "wins," but that you batch the cheap work and reserve expert attention for the parts the agent still struggles with.

    (Zack Proser; Gergely Orosz, Pragmatic Engineer, Mar 2026)

    Common Mistakes¶

    • Overloading prompts with durable rules instead of moving them into AGENTS.md or a skill
    • Not letting the agent see its work by omitting build and test command details
    • Skipping planning on multi-step and complex tasks
    • Giving Codex full permissions before understanding the workflow
    • Running live threads on the same files without using git worktrees
    • Turning a recurring task into an automation before it's reliable manually
    • Treating Codex as something to watch step by step instead of using it in parallel with your own work
    • Using one thread per project instead of one thread per task — bloated context, worse results over time

    (OpenAI Codex Best Practices, Mar 2026)

    Skills storage $HOME/.agents/skills (personal), .agents/skills (repo) ~/.claude/skills/ (personal), .claude/skills/ (project)
    Dogfooding 90%+ of Codex's own codebase written by Codex itself Internal teams report 3x faster incident debugging
