    Become an Expert on Claude Code — Capability Map, Benchmarks, and Deployment Playbooks¶

    Opening Briefing¶

    The defining mistake teams make when adopting agentic coding tools is treating them as faster autocomplete — a smarter tab-completion that writes more lines per keystroke. Claude Code is architecturally the opposite: it is a closed-loop executor that reads your codebase, proposes multi-file patches, runs your test suite, interprets failures, and iterates autonomously. That closed loop is the capability discontinuity. It means the bottleneck is no longer how fast the model can generate code, but how well the surrounding harness — repo instructions, permission boundaries, deterministic checks, and context discipline — constrains and verifies the agent's output.

    The evidence converges on a counterintuitive finding: context reduction outperforms context enrichment. Top practitioners report that bloating CLAUDE.md with exhaustive documentation degrades agent performance, while treating it as a minimal logical router — a thin if-else directory pointing to narrowly scoped rule and skill files — preserves the agent's reasoning fidelity across long sessions. This maps directly onto the token economics: a single 1M-token Sonnet invocation can cost roughly $20, meaning undisciplined context accumulation is both a quality problem and a budget problem. The practitioners who get 2-10x speedups (3-minute multi-file refactors, 5-minute test suites reaching 95% coverage) are the same ones who enforce strict session scoping, separate research from implementation in distinct context windows, and define exit criteria through passing tests rather than subjective completeness. The February 2026 arXiv findings on AGENTS.md crystallize this: repo-level instructions help when they remove ambiguity and accelerate verification, but hurt when they add irrelevant constraints — a result that two independent papers reached from opposite directions.

    The second-order consequence is that agentic coding inverts the traditional skill hierarchy. The scarce capability is no longer writing code but engineering the harness — designing the permission boundaries, hooks, quality gates, and contract files that make autonomous execution reliable. Teams that treat Claude Code as a junior developer who needs mentorship through repo structure rather than through prompting are the ones reporting order-of-magnitude productivity gains with no increase in defect rates.

    This document operates on a single claim: the ROI of agentic coding tools is a direct function of harness quality, not prompt sophistication. What follows is the full capability map, deployment architecture, benchmarking data, and failure-mode catalog needed to build that harness correctly — from first install through team-wide adoption.

    Executive Summary¶

    Key: Claude Code is an agentic CLI coding assistant (not an IDE plugin). It lives in your terminal, directly edits files, runs shell commands, and makes git commits. Think of it as a powerful junior developer at superhuman speed that still requires mentorship.

    • What it does: Whole-codebase reasoning (cross-file insights), multi-file patches, targeted bug-fixes, tedious task automation (linting, deps, merge conflicts), /security-review scanning
    • Integration surfaces: VS Code, JetBrains (diff viewers, context sharing), GitHub Actions (@claude on issues/PRs), Model Context Protocol (MCP) for external tools (Jira, Notion, DBs, Slack, Figma)
    • Limitations: Works best when scope is well-defined; large monorepos can dilute focus; CLI-only (macOS/Linux; Windows needs WSL); permission prompts for risky actions
    • ROI: Anthropic internal teams report 3x faster incident debugging; complex features done in ~15 min vs hours; order-of-magnitude speedup for test writing and boilerplate
    • Models: Claude Opus 4.1 (200k context, top reasoning) vs Claude Sonnet 4 (1M context, cost-effective). Opus for precision; Sonnet for whole-repo analysis
    • Privacy: Anthropic does not use your code for model training by default; zero-retention mode available

    Agentic Engineering Principles¶

    Key: Agentic engineering is the discipline of designing repos, tools, memory, and feedback loops so AI agents can execute useful work repeatedly, safely, and with compounding performance. The future moat is not prompting skill — it is environment design for agents.

    The shift is from "AI helps me code" to "how do I engineer an environment where agents can reliably operate?" The unit of optimization moves from developer productivity to agent loop quality — shaping environment, context, and feedback so an agent can keep executing with less human intervention.

    This is distinct from casual prompt-and-copy-paste "vibe coding." Production-grade agentic workflows are closer to a fusion of developer platform engineering, knowledge engineering, eval/validation engineering, workflow automation, and human-in-the-loop systems design.

    The Five Pillars¶

    1. Context Engineering — Give agents the right amount of context, not the maximum amount. Large context windows do not remove the need for curation.

    • Context bloat is the #1 performance killer — too many plugins, memory systems, or poorly-named skills overwhelm the agent with irrelevant information. Context is best served fresh and condensed.
    • After compaction: Include a rule in CLAUDE.md that the agent reads first — re-read the task plan and relevant files before continuing. Agents are atrocious at "filling in the gaps" post-compaction. Trigger manual /compact at ~50% context fill — waiting for auto-compaction loses more information.
    • High-effort reasoning: Use the keyword "ultrathink" in prompts to trigger maximum reasoning effort from Claude.
    • Separate research from implementation. Vague prompts ("Build an auth system") force context pollution. Precise prompts ("Implement JWT with bcrypt-12, refresh token rotation, 7-day expiry") focus the agent. When you don't know the details, run a separate research session first.

    2. Agentic Validation — Agents need engineered self-check loops, not just unit tests.

    • Tests as milestones: "Unless these X tests pass, your task is NOT complete; you are NOT allowed to edit the tests." Deterministic, verifiable exit criteria.
    • Screenshots + verification: After tests pass, get the agent to screenshot and verify design/behaviour — enables iterative refinement toward a target design.
    • Task contracts: Create {TASK}_CONTRACT.md specifying tests, screenshots, and verification required before the agent can terminate the session.
    • Validation is the real moat — anyone can wire a model into a code editor. Fewer teams can build strong self-check loops, domain-specific validators, and recovery logic. This is closer to autonomous systems engineering than traditional app dev.

    3. Tooling to Remove Friction — Every time an agent gets blocked, that blockage is an opportunity to build a tool, CLI, skill, or interface.

    • Search, deep research, multimodality, and task systems are examples at the product layer; CLI wrappers and custom skills are examples at the workflow layer. Humans should stop being the bottleneck for recurring execution steps.
    • External dependencies lock you into solutions for problems that may not exist in the next model generation. Frontier companies absorb the best community patterns into the base product — skills, memory, subagents, planning all started as community solutions. Just update your CLI tool periodically and read what's new.

    4. Agent-Friendly Codebases — You are no longer writing only for the next engineer; you are writing for the next agent.

    • Most brownfield repos are hostile to agents: dead code, inconsistent patterns, half-finished migrations, weak structure, undocumented domain decisions. This "poisons" the agent loop.
    • File structure, docs, logs, conventions, and domain notes are no longer passive artifacts — they are active control surfaces for machine workers. Make repo structure, documentation, logging, and conventions explicitly agent-friendly.
    • Externalized tacit knowledge is a competitive advantage. "If domain knowledge isn't in the codebase, it doesn't exist for the agent." Business rules, product decisions, specs, architecture choices — anything that lives in Slack, meetings, or senior engineers' heads becomes economically damaging in an agentic environment when left undocumented.

    5. Compound Team Workflows — Once context, validation, tooling, and codebase improvements are shared across a team, each improvement builds on the previous ones.

    • A new CLI, MCP server, skill, validation routine, or repo convention becomes reusable infrastructure. Winning teams converge on shared agentic workflows rather than each engineer improvising locally.
    • The advantage compounds when the team standardizes — not on prompting techniques, but on environment design.

    Tactical Patterns¶

    Exploit sycophancy — don't fight it. Agents are designed to please. If you ask "find me a bug," it will find one — even if it has to invent one.

    • Use neutral prompts: Instead of "Find me a bug in the database," say "Search through the database, follow along with the logic of each component, and report back all findings."
    • Adversarial agent pattern for high-fidelity bug hunting:
    • Bug-finder agent: Scored +1/+5/+10 by impact severity — finds everything (superset, including false positives)
    • Adversarial agent: Gets the score of each bug it disproves, but -2x penalty if wrong — aggressively disproves but with caution
    • Referee agent: Told it's being checked against ground truth — scores both agents. Result is near-flawless fidelity.

    One session per contract. 24-hour sessions cause context bloat by mixing unrelated work. Better: one new session per contract, with an orchestration layer spawning fresh sessions. Stop-hooks can prevent termination until a contract is fulfilled.

    Emerging craft practices from practitioners (AI Engineering Conference, Mar 2026):

    • Voice for spec capture: Dictate requirements verbally and let the agent structure them into formal specs — faster than typing for initial brainstorms and requirement capture
    • Layered memory: Organize memory across three tiers — session (ephemeral, current task), project (CLAUDE.md / plan files, persists across sessions), and global (~/.claude, personal preferences across all projects). Each layer has different persistence and scope, preventing context pollution while maintaining continuity

    CLAUDE.md as a Logical Router¶

    Key: Treat CLAUDE.md as a minimal if-else directory pointing to context, not as a document dump. It should contain routing logic, not content.

    • Structure: "If coding, read coding-rules.md. If writing tests, read coding-test-rules.md. If tests are failing, read coding-test-failing-rules.md."
    • Rules encode preferences (what NOT to do). Skills encode recipes (HOW to do something specific).
    • Size discipline: Keep each CLAUDE.md under 200 lines; 60 lines is the recommended target for reliable adherence. For larger instruction sets, split into .claude/rules/ — modular rule files that are loaded conditionally without bloating the root file (shanraisshan/claude-code-best-practice, 12.2k stars, March 2026).
    • Conditional and nested rules work well — agents follow complex branching logic reliably now.
    • Iterative refinement: Start barebones, add rules when you see the agent doing something you disapprove of. Over time, rules and skills will accumulate and eventually contradict or cause context bloat — periodically consolidate and remove contradictions.

    Key: The cycle is: start simple -> add rules/skills -> magic -> performance degrades -> consolidate/clean up -> magic again. Repeat.

    Formatting for Signal Strength¶

    Size discipline is the ceiling, but structure is the signal. A 20-line prose paragraph gets ignored just as easily as a 200-line one — the variable isn't word count but formatting. Structural elements — headers, code fences, bullet lists — create anchor points that agents latch onto; prose paragraphs don't. The same instruction reformatted from a prose sentence into a headed, code-fenced bullet reliably flips agent compliance from ignore to follow (Gábor Mészáros, "CLAUDE.md Best Practices: 7 Formatting Rules for the Machine," dev.to, Mar 2026).

    Seven structural rules that determine whether instructions survive from file to agent behavior:

    1. Include rationale on every prohibition. "Never force push — rewrites shared history, unrecoverable for collaborators" is an instruction the agent weighs. The bare "never force push" is an instruction it skips. Rationale lets the agent generalize: understanding why force push is forbidden, it will also avoid git reset --hard origin/main without being told. Every prohibition should carry its reason — this is the most undervalued formatting choice.

    2. Keep heading hierarchy shallow (3 levels max). h1 for file title, h2 for sections, h3 for subsections. Deep nesting (h4, h5) dilutes attention — the hierarchy creates ambiguity about which level governs. If you need an h4, you probably need a separate file.

    3. Name files descriptively. docs/api-authentication.md tells the agent whether the file is relevant before opening it. docs/guide.md forces a read-then-decide round trip. Descriptive names save the agent a context-consuming file read in projects with dozens of docs.

    4. Use headers as attention resets. One topic per header. The agent navigates to the right section instead of parsing the whole paragraph. Without headers, every instruction competes with every other instruction for attention.

    5. Put commands in code blocks. Commands in prose get read as descriptions. Commands in backticks get treated as executable. This is the single highest-impact change — pytest in a code fence is a command; "run pytest" in a sentence is a suggestion.

    6. Use standard section names. ## Testing gets recognized instantly. ## Quality Assurance Verification Process doesn't. Agents are trained on millions of READMEs — they know what ## Testing, ## Commands, ## Structure, and ## Conventions mean. Familiar names carry built-in context; creative names are noise.

    7. Make every instruction immediately actionable. The test: could the agent execute this instruction right now without asking a clarifying question? "Follow best practices" fails. "Format with ruff format before committing" passes.

    The rules are multiplicative: headers create sections, sections hold code blocks, code blocks contain actionable commands, rationale explains why, descriptive file names route attention to the right file, and shallow hierarchy keeps everything findable.

    Key: The framing that connects routing (what to include) and formatting (how to write it) is attention budget. The agent has a limited context window. What matters isn't just what's in it — it's how the agent decides what's relevant at each step. Structure is what makes your instructions win that competition. Orientation without compliance means the agent knows your project but ignores your rules. Compliance without orientation means the agent follows instructions but works in the wrong place. You need both.

    Own the Outcome¶

    No agent today is perfect. Hand coding is not dead — it is being pushed up the abstraction stack. Humans will still write critical logic, define invariants, design validation layers, decide architectural boundaries, and repair failures in ambiguous zones. What dies first is low-leverage manual implementation labor. Relegate design and implementation to agents, but you own the outcome — review, verify, and remain the engineer of record.

    The "Universal Operator" Thesis¶

    A broader framing is emerging: Claude Code is not merely a coding copilot but a universal operator that collapses no-code automation, traditional coding, orchestration, and productization into a single builder workflow. Instead of using separate tools for automation (n8n, Zapier), IDEs for code, deployment platforms for shipping, and consultants for sales framing, a single agentic CLI session can wire together all four — from prototype through client-facing artifact (Nate Herk, "Build & Sell with Claude Code," Mar 2026).

    The implication is that the bottleneck has shifted from coding ability to operational taste — context control, system decomposition, integration wiring, and packaging output into something a client or end-user will actually buy. The practitioners capturing the most value are not the best model researchers; they are the ones who can reliably turn agentic workflows into deployed, client-visible systems and price them. This reframes the scarce skill from "can you write code?" to "can you design the harness, compose the agent stack, and ship something durable?" — a shift that favours breadth of integration knowledge over depth in any single tool.

    Key: Fast prototype throughput is not durable delivery capability. Browser automation, agent teams, and MCPs often look cleaner in tutorials than in production. Client delivery depends on reliability, security, maintenance, and scope control — not just build speed.

    System Anatomy (How Claude Code Works)¶

    Component Role
    Local CLI Client npm install -g @anthropic-ai/claude-code. Scans project, loads CLAUDE.md, presents REPL prompt
    Context Gathering Reads project tree, entry points, open IDE files, live diagnostics (compiler/linter errors)
    Claude LLM Backend Anthropic API or Bedrock/Vertex. TLS-encrypted. Returns text or Actions
    Action Execution File editing (diff/patch), shell commands (npm test), git operations, MCP calls
    Long-Term Memory CLAUDE.md files = project-specific persistent memory (style rules, arch notes). /compact condenses session history
    Security & Sandboxing Permission system: risky actions default to "ask". Allow/deny lists configurable. Transcripts logged locally 30 days

    Claude Code workflow: You describe task -> CLI sends prompt+context to Claude -> Claude proposes code/actions -> CLI applies (with your oversight) -> you iterate.

    CLI vs SDK system prompts: The CLI uses a modular system prompt architecture: ~269 base tokens plus 110+ conditionally-loaded components assembled at runtime. The SDK uses a minimal default prompt — to match CLI behavior, use the claude_code preset combined with settingSources: ["project"]. There is no determinism guarantee even with temperature=0, due to MoE routing (±8-14% variance proven), hardware routing, batching, and floating-point arithmetic (ref: shanraisshan/claude-code-best-practice; known issue github.com/anthropics/claude-code/issues/3370).

    For Codex's architecture (Rust, Firecracker microVMs, 5-step ReAct state machine), see codex_expert_guide.md.

    Capability Map & Command Catalog¶

    Core Capabilities¶

    • Repo Comprehension: Semantic understanding of entire codebase. New engineers onboard in minutes, not days
    • Code Editing & Patching: Implement features, refactor (rename across files, split classes), apply small fixes — all via natural language
    • Automated Bug Diagnosis: Closed-loop detect -> fix -> test -> refine cycle. Provide stack trace, Claude locates cause, patches, runs tests
    • Test Generation: "Write unit tests for invoice.py" -> ~10 tests in ~5 min, catches real bugs, follows project style from CLAUDE.md
    • Code Review & PR Prep: /review critiques diffs for bugs/style/security; generates PR descriptions; @claude on GitHub reviews PRs automatically
    • Security Analysis: /security-review scans for SQL injection, XSS, path traversal, weak crypto, hardcoded secrets. Found DNS rebinding RCE and SSRF vulns in Anthropic's own code pre-release
    • DevOps Automation: Dependency bumps, release notes from git log, unused import cleanup, DB query optimization

    Advanced Tool Use Patterns (API-Level, GA Feb 2026)¶

    These are API-level features (GA since February 2026) that affect how Claude Code orchestrates tools internally. Source: shanraisshan/claude-code-best-practice (12.2k stars, March 2026).

    • Programmatic Tool Calling (PTC): Claude writes Python that orchestrates tools in a sandbox. Only stdout enters context — tool results from programmatic calls are NOT added to Claude's context window. 3 tools = 1 inference pass instead of 3, yielding ~37% token reduction. Config: allowed_callers: ["code_execution_20250825"]. Container lifetime ~4.5 minutes. Not available on Bedrock/Vertex. Not for MCP tools.
    • Dynamic Filtering for Web Search/Fetch: Claude writes and executes Python to filter web results before they enter context, achieving ~24% fewer input tokens. BrowseComp: Opus 4.6 improved from 45.3% to 61.6%. DeepSearchQA F1: Opus 4.6 from 69.8% to 77.3%.
    • Tool Search Tool: Mark infrequently-used tools with defer_loading: true for ~85% reduction in tool definition tokens (77K to 8.7K). Claude Code has this built-in as MCPSearch auto mode since v2.1.7 — triggers automatically when MCP tool descriptions exceed 10% of context.
    • Tool Use Examples: Add input_examples to tool definitions. Improves accuracy from 72% to 90% on complex parameter handling.

    Integration Capabilities¶

    • IDE (VS Code, JetBrains): Interactive diff viewing, selection context, file reference shortcuts (Cmd+Option+K), live diagnostics feed, quick launch (Ctrl+Esc / Cmd+Esc)
    • GitHub Actions & @claude Bot: @claude implement on issue -> Claude creates branch, codes, tests, opens PR (~15 min). @claude review this on PR -> AI code review comments. @claude fix -> pushes fix commit
    • MCP Extensibility: Connect Jira, Confluence, Notion, PostgreSQL, Sentry, Figma, iOS Simulator. Register via claude mcp add .... Anthropic calls MCP "USB-C for AI"
    • Channels (research preview, Mar 2026): Claude Code now exposes channels so developers can interact via messaging apps (starting with Slack), enabling persistent developer workflows and ambient agent access — the agent is reachable wherever the developer already works, not just in the terminal or IDE. This is part of a broader push beyond "model API" toward continuous, multi-surface developer presence (@anthropic, Latent Space AINews, Mar 2026)

    Long-Context Workflows¶

    • Whole-Repo Analysis: Sonnet 1M tokens = ~750k lines of code in memory. "Scan entire repo for deprecated library usage"
    • Multi-Document Synthesis: Ingest specs + RFCs + code simultaneously. "Find discrepancies between API design docs and implementation"
    • Extended Agentic Sessions: Multi-day autonomous agents. 1M context unlocks "multi-day sessions on real-world codebases"
    • Local Scheduled Tasks: Claude Code desktop added local scheduled tasks that run while the computer is awake (March 2026), enabling background automation without requiring active user interaction

    Key: Use 1M context only when you need holistic reasoning or massive input. Default to 100-200k for cost/latency. Sonnet 1M pricing roughly doubles beyond 200k.

    Spec-Driven Programming & the "Repo Constitution" Pattern¶

    Key: The strongest pattern across top practitioners is the shift from "prompting" to institutionalizing context inside the repo. For Claude Code this is CLAUDE.md; for Codex, AGENTS.md. Treat it as the agent's constitution — keep it short, curated, and oriented around what the agent gets wrong.

    Why Spec-Driven Beats Ad-Hoc Prompting¶

    • Shrivu Shankar frames CLAUDE.md as the agent's constitution — curated guardrails, not a docs dump
    • Mukesh Murugan includes dedicated setup tactics for preventing unwanted refactors
    • Sabrina Ramonov uses project memory files and skill scaffolding
    • Creators use these files as an organizational forcing function — if running tests or deploys is too verbose, they create wrappers and document them, nudging repos into being more automation-friendly

    Plan-First, Chunked Execution¶

    • Planning is not optional — it prevents expensive agent drift
    • Plan files over ephemeral plan mode: Anthropic's Sid argued that plan mode and plan files are among the most important force multipliers. The recommendation: write persistent markdown plan files rather than relying on ephemeral plan mode alone. Plan files survive across sessions and give agents stable context for multi-step work — whereas plan mode context disappears when the session ends. Let agents critique and revise plans recursively before executing (Sid, Anthropic, AI Engineering Conference, Mar 2026)
    • Addy Osmani's workflow doctrine: specs-before-code, break work into small iterative chunks (clear goal, bounded scope, strong feedback loop)
    • Boris Cherny reinforces: consistent emphasis on experimentation plus structure (parallelism, worktrees, habits) rather than one-shot prompts
    • Baseline prompt-run-review loop: The tightest iteration cycle is (1) describe intent and constraints clearly — inputs, outputs, expected tests; (2) ask for minimal code that passes the tests, run it, paste failures back; (3) iterate until green, then ask for refactors backed by benchmarks. Keeping the first pass minimal avoids over-engineering and keeps context lean; deferring refactors until correctness is established prevents wasted work on code that may not survive the next iteration (see Advanced Context Engineering for Agents)

    Hooks & Quality Gates¶

    • Agentic coding only becomes reliable when the environment makes it hard to ship broken states
    • Claude Code's hooks mechanism (/hooks) runs custom code at lifecycle events — the primary interactive way to set up notifications and automation
    • Shrivu's enterprise pattern: enforce tests at commit time using "block-at-submit" hooks; avoid blocking at write time; treat deterministic checks as the complement to softer guidance in CLAUDE.md
    • Third-party writeups (GitButler, DataCamp) reinforce hooks as workflow automation primitives
    • Emerging hook patterns from practitioners: use hooks to force lint, tests, and documentation updates automatically on every agent action — removing the human bottleneck for routine quality checks. Build screenshot-based release review workflows where the agent captures visual state and verifies it against design targets before marking a task complete (AI Engineering Conference, Mar 2026)

    Skills Ecosystem¶

    • Anthropic skills: shareable extensions (SKILL.md bundles) invokable when relevant or via slash commands. Skills have become one of the most used extension points in Claude Code, with hundreds in active use at Anthropic (Anthropic, "Lessons from Building Claude Code: How We Use Skills", Mar 2026)
    • Vercel's skills.sh targets multiple tools, making skills a portable unit across agent surfaces — suggests "agent capability packaging" may standardize faster than any one vendor's plugin system
    • Ooi Yee Fei: skills as "executable expertise" that impose discipline and checkpoints
    • Customization primitives are simpler than expected: The most powerful customization primitives are surprisingly simple — skills, MCP servers, and personal memory systems — not giant custom harnesses. Lightweight, composable primitives beat monolithic agent frameworks. This explains why the Claude Code ecosystem converges on a small number of extension points (skills, MCP, CLAUDE.md, hooks) rather than requiring teams to build elaborate orchestration layers (Sid, Anthropic, AI Engineering Conference, Mar 2026)
    • Scale: SkillsBench counted 47,000+ unique skills across 6,300+ repositories as of March 2026. Almost nobody is testing them — most are AI-generated, vibe-checked with a handful of manual runs, then shipped

    Skills discovery in monorepos: Unlike CLAUDE.md (which walks up the directory tree), skills use nested discovery — .claude/skills/ directories are discovered on-demand only when working with files in those directories. Skill descriptions are always in context (up to a 15,000 character budget, configurable via SLASH_COMMAND_TOOL_CHAR_BUDGET); full skill content loads only when invoked. For subagents with preloaded skills, full content IS injected at startup. Priority order: Enterprise > Personal (~/.claude/skills/) > Project (.claude/skills/). Prefer commands over subagents for simple workflows (shanraisshan/claude-code-best-practice, 12.2k stars, March 2026).

    Two skill categories that matter for testing:

    • Capability skills — help the agent do something the base model can't do consistently. These may become unnecessary as models improve; evals tell you when to retire them
    • Preference skills — document specific workflows. Durable, but only as valuable as their fidelity to your actual workflow; evals verify that fidelity

    Skill Design Patterns (Anthropic Internal Practices)¶

    The following patterns come from Anthropic's internal experience building and operating hundreds of skills (Anthropic, "Lessons from Building Claude Code: How We Use Skills", Mar 2026):

    The description field is for the model, not for humans. When a session starts, Claude Code builds a listing of every available skill with its description. This listing is what Claude scans to decide "is there a skill for this request?" — meaning the description is a trigger specification, not a summary. Write it as a precise description of when the skill should fire, not what it does abstractly.

    Memory and data persistence. Skills can include a form of memory by storing data — anything from an append-only text log or JSON file to a SQLite database. A standup-post skill might keep a standups.log with every post it has written, so the next invocation reads its own history and reports what changed since yesterday. Data stored in the skill directory may be deleted on upgrade; use ${CLAUDE_PLUGIN_DATA} (a stable per-plugin folder) for anything that must persist across upgrades.

    Bundled scripts for composition. One of the most powerful things you can give Claude is code. Giving Claude helper scripts and libraries lets it spend its turns on composition — deciding what to do next — rather than reconstructing boilerplate from scratch. A data science skill might bundle functions to fetch data from an event source; Claude then generates scripts on the fly to compose those functions for prompts like "What happened on Tuesday?" This shifts the agent from a code generator to a code composer.

    On-demand hooks. Skills can include hooks that activate only when the skill is called, lasting for the duration of the session. This enables opinionated safety or workflow constraints that would be too restrictive to run all the time:

    • /careful — blocks rm -rf, DROP TABLE, force-push, kubectl delete via PreToolUse matcher on Bash. Only activated when working near production
    • /freeze — blocks any Edit/Write that is not in a specific directory. Useful when debugging: prevents accidentally "fixing" unrelated files while adding logs

    Structured user interaction. If a skill needs to collect information from the user, it can instruct Claude to use the AskUserQuestion tool to present structured, multiple-choice questions rather than free-form conversation.

    Composing skills. Skills can depend on each other — for example, a CSV generation skill that calls a file upload skill. Dependency management is not natively built into marketplaces or skills yet, but you can reference other skills by name and the model will invoke them if installed.

    Measuring skill usage. Anthropic uses a PreToolUse hook to log skill usage company-wide. This reveals which skills are popular and which are under-triggering compared to expectations — enabling data-driven curation rather than guesswork.

    Distribution and Marketplace Management¶

    Two distribution paths for skills:

    • Repo-level — check skills into .claude/skills/ in your repository. Works well for smaller teams across relatively few repos, but every checked-in skill adds to the model's context budget
    • Plugin marketplace — a Claude Code Plugin marketplace where users upload and install plugins. Better for scale, as it lets each team member choose which skills to install rather than loading all skills for everyone

    Organic curation model (Anthropic's approach): No centralized team decides which skills go into the marketplace. Instead, skills surface organically — authors upload to a sandbox folder in GitHub and share via Slack or other forums. Once a skill has gotten traction (determined by the skill owner), they submit a PR to move it into the marketplace. A curation step before release is important because it is easy to create bad or redundant skills (Anthropic, "Lessons from Building Claude Code: How We Use Skills", Mar 2026).

    Key: Most skills at Anthropic began as a few lines addressing a single gotcha, then improved iteratively as Claude hit new edge cases. Start small, ship early, refine based on real usage data from PreToolUse logging.

    Evaluating & Testing Skills¶

    Key: You wouldn't ship code without tests. Don't ship skills without evals. The skill description is the most important piece — if it's vague, the skill won't trigger reliably. A description rewrite alone fixed 5 of 7 failures in one case study (Gemini Interactions API skill, 66.7% → 100% pass rate).

    Define success before writing the skill — grade outcomes, not paths:

    1. Outcome — Did the skill produce a usable result? Code compiles, API returns valid response, document renders. If the output doesn't work, nothing else matters
    2. Style & instructions — Does the output follow your conventions and the skill's directives? Right SDK, correct model IDs, naming conventions, specified formatting
    3. Efficiency — How much time, tokens, and effort? No unnecessary retries, reasonable token count, no command thrashing. Two runs can produce identical correct output, but one burned 3x the tokens. This is the most undervalued dimension — regressions here are real costs that compound

    Lightweight eval harness (4 steps):

    1. Create a prompt set (10-20 prompts to start). Each prompt tests a specific scenario and declares its own success criteria via expected_checks. Include negative tests — prompts where the skill should NOT trigger. A skill with too-broad keywords will fire on every request. Example structure:
    {
  "id": "py_basic_generation",
  "prompt": "Write a Python script that sends a text prompt to Gemini...",
  "should_trigger": true,
  "expected_checks": [
    "correct_sdk",
    "no_old_sdk",
    "current_model",
    "interactions_api"
  ]
}

    1. Run the agent and capture output — test the skill the same way the agent experiences it (through the CLI, not a mock). Capture the full response including stats and exit code

    2. Write deterministic checks — each check is a small function (typically regex against extracted code) returning a boolean. Register all checks in a dispatch registry keyed by check_id from the prompt set. Deterministic checks are fast, cheap, and reproducible

    3. Add LLM-as-judge for qualitative checks (optional) — for skills requiring subjective assessment (design quality, code structure, naming conventions). Use structured output (Pydantic schemas) to constrain the judge's response into parseable, trackable results. Use selectively — LLM grading adds cost and latency

    Best practices:

    • Start with the skill description — the name and YAML frontmatter are the trigger mechanism. Vague description = unreliable triggering
    • Use directives, not information — "Always use interactions.create()" works; "The Interactions API is the recommended approach" doesn't. Models follow instructions better than they infer implications
    • Isolate each run — clean environment per test case. Accumulated context bleeds between cases and masks real failures
    • Run multiple trials — agent behavior is nondeterministic. Run 3-5 trials per prompt and look at the distribution, not a single pass/fail
    • Test across harnesses — the same skill behaves differently depending on the agent framework. If your skill is used across tools, eval it in each
    • Graduate your evals — capability evals start at low pass rates and give you a hill to climb. Once they hit ~100%, they graduate into regression evals that protect against backsliding
    • Detect skill retirement — run evals with the skill unloaded. If they still pass, the model has absorbed the skill's value. Retire it

    Parallel Worktrees — The Real Multiplier¶

    • Power users cite "do more in parallel" using isolated workspaces as the repeated advantage over "better prompts"
    • Both Claude Code and Codex emphasize multi-agent workflows and worktree/branch isolation
    • Zack Proser's workflow: queue multiple Codex tasks (maintenance/SDLC grunt work), then spend human focus on hard architectural work using other tools

    Key: The lesson is not that one tool "wins," but that you batch the cheap work and reserve expert attention for the parts the agent still struggles with.

    Adversarial PR Review with Confidence Filtering¶

    Anthropic uses Claude internally for PR review with adversarial-style review loops and confidence filtering. The pattern: the AI reviewer runs multiple passes, scores its own confidence on each finding, and surfaces only high-confidence issues to the human reviewer. The result is that humans spend more time on taste and product alignment than line-by-line bug hunting — separating signal from noise in code review. This extends the adversarial agent pattern (see Agentic Engineering Principles) into the PR workflow specifically (Sid, Anthropic, AI Engineering Conference, Mar 2026).

    Prompt Caching (Auto-Caching)¶

    Every Claude API call runs two phases: prefill (processing the entire prompt — the expensive phase) and decode (generating the response token by token). If a request shares an exact prefix with a previous request, the prefill computation is cached, hashed, and reused. Cache hits cost 10% of standard input token pricing (Joe Njenga, "Anthropic Automatic Prompt Caching," Feb 2026).

    Manual caching required placing a cache_control: { type: "ephemeral" } breakpoint on specific message blocks and moving it forward each turn as the conversation grew. Auto-caching replaces this with a single top-level parameter:

    {
  "cache_control": { "type": "ephemeral" },
  "messages": [ ... ]
}

    The API automatically identifies the longest matching prefix, moves the cache breakpoint to the last cacheable block, and reuses it on every subsequent turn. Manual block-level cache_control still works for granular control (e.g., caching system prompt independently from per-user project context) — auto-caching handles everything else on top.

    Token math example: A code review agent with 15,000 tokens of static context (system prompt + tools + project context) running 40 turns: without caching, 600,000 input tokens billed at full price; with caching, turn 1 at full price (cache write) + turns 2–40 at 10% = 73,500 total — an 88% reduction on static token cost alone.

    Five production rules from the Claude Code team (sourced from Thariq, Anthropic, shared Feb 2026):

    1. Order prompts static-to-dynamic. Caching uses exact prefix matching via cryptographic hash — one character difference anywhere in the prefix produces a different hash and a full-price bill. The Claude Code harness structures every request: base system instructions → tool definitions → CLAUDE.md/project memory → session state → conversation messages. Timestamps in system prompts, non-deterministic tool loading order, or parameters that change between sessions all silently break the prefix.

    2. Never change tools mid-session. Adding or removing a tool changes the cached prefix and forces a full rebuild. The Claude Code team uses EnterPlanMode and ExitPlanMode as tools themselves rather than swapping tool definitions — the tool list stays identical, and mode changes flow through system messages.

    3. Use system messages, not prompt edits. When state changes mid-session (file updates, time changes, user preferences), editing the system prompt breaks the hash. Instead, pass updated information as a <system-reminder> tag inside the next user message or tool result — the model reads the update while the cached prefix stays intact.

    4. Don't switch models mid-conversation. Prompt caches are per-model. Switching from Opus to Haiku 100,000 tokens deep means paying full price to rebuild Haiku's cache from scratch — the "cheaper" model costs more. Use subagents for subtasks requiring a different model: the parent prepares a focused handoff with only relevant context, and the main session cache stays intact.

    5. Cache-safe compaction. When hitting the context window limit, naive compaction (separate API call with different system prompt and no tools) kills the cache. The fix: use the exact same system prompt, tools, and context as the parent conversation, prepend the full conversation history, and append the compaction prompt as the final user message. The API sees a request nearly identical to the last turn — cache hits, and only the compaction prompt itself bills at full price.

    Key: The Claude Code team monitors cache hit rate with the same urgency as uptime — alerts fire when it drops. For any agent running more than a handful of turns, prompt caching is the difference between a viable product and a cost spiral. Auto-caching removes the implementation burden, but the five ordering and stability rules above determine whether you actually get cache hits in production.

    Failure Modes & Mitigations¶

    Symptom Cause Fix
    Hallucinated edits (unwanted code changes) Vague prompt, model over-generalization Constrain prompt: "Only modify parseData(), do not alter other logic." Add ground truth to CLAUDE.md
    Partial refactor (broken references) Context window limits, stopped early Break into smaller chunks. Run tests after each step. Use /review to catch misses
    Flaky/incorrect tests No runtime knowledge, guessed outputs Review & run all generated tests. Seed random generators. Add "All tests must be deterministic" to CLAUDE.md
    Tool-call dead ends (stuck after test failure) Ambiguous output, permission denial Intervene: "The test failure indicates a null pointer — fix that in utils.js"
    Stylistic deviations Missing CLAUDE.md style rules Add explicit style preferences. Run linter/formatter after Claude's changes
    Context poisoning (confused, irrelevant responses) Stale context in long session Use /compact or start fresh. "Forget previous discussion, focus only on X now"
    Destructive infra commands (unintended resource deletion) Agent executes Terraform/IaC commands without guardrails Deny destructive infra CLIs (terraform destroy, kubectl delete) in permissions. Incident: Claude Code accidentally ran a Terraform command that deleted DataTalksClub's production database and snapshots, wiping 2.5 years of course data
    Performance slowdown Large context, rate limiting Use /clear, start fresh session. Scope prompts narrowly
    Refusal / non-answer Safety filter triggered, unclear prompt Rephrase with legitimate intent. Provide more context. Check for sensitive content in project files

    Key: Use fail-safe prompts: "Refactor this function, and ensure all references are updated (don't leave broken references)." Articulating pitfalls makes Claude more likely to self-check.

    When NOT to Use Claude Code¶

    • Tight inline autocompletion: Use IntelliJ AI or inline completion tools instead
    • Trivial 5-line scripts: Faster to write yourself
    • Obscure DSLs / niche domain languages: Claude may hallucinate syntax
    • Massive monorepos (millions of lines): Use code search tools to narrow scope first, then point Claude at subsets
    • Performance-critical / memory-constrained code: AI may introduce suboptimal patterns. Heavy human review needed
    • Safety-critical software (medical, aerospace, crypto): AI output must be expert-validated with formal methods
    • Windows-only shops without WSL: Native Windows support not yet available
    • Teams not onboard: Forced adoption backfires. Encourage, don't mandate
    • Competitor CLI agents (Aider, Cline) may be better for: self-hosting, open-source models, real-time cost display, autonomous "thinking mode"
    • When cloud-hosted persistent agents suffice: Cursor Automations (March 2026) and T3 Code offer always-on agent workflows that may fit teams preferring GUI-first or multi-model orchestration
