    LLM Quantization, Distillation & Deployment¶

    See also: LLM Landscape & Trends | LLM Architectures | Inference Engineering | High-Performance LLM Serving | GPU & Datacenter Infrastructure

    Opening Briefing¶

    The industry spent years treating quantization as a concession — a quality tax you paid to squeeze a model onto cheaper hardware. That framing is now obsolete. The gap between FP16 and INT4 quality has collapsed to less than two percent on most benchmarks while cutting memory consumption by four times, and purpose-built formats like MXFP4 can fit a 120-billion-parameter model on a single 80GB GPU. Quantization is not a quality compromise; it is an architectural decision that determines which hardware can run which models, how many users a single node can serve, and whether a model ships at all.

    Three developments have driven this shift. First, quantization-aware training and calibration-based methods such as imatrix have closed the accuracy gap that once made post-training quantization risky. Unsloth's UD-Q4_K_XL format, for example, achieves a 51% reduction in Maximum KLD compared to naive round-to-nearest at only 8% larger file size — a trade-off that would have seemed implausible two years ago. Second, hardware vendors have baked low-precision arithmetic directly into silicon: NVIDIA's Hopper and Blackwell architectures include native FP8 tensor cores, and the MXFP4 microscaling format extends this to four-bit operations with per-block scaling factors that preserve dynamic range. Third, the rise of Mixture-of-Experts architectures has made quantization not merely helpful but mandatory for practical deployment, since MoE models carry enormous total parameter counts even though only a fraction activate per token.

    The second-order effect is subtler and more consequential. When quantization formats become reliable enough to treat as first-class deployment targets, the entire model development pipeline reorganizes around them. Teams now train at BF16 and ship at FP8 or INT4 as a default workflow, not a special case. Llama 4 ships its Scout variant with on-the-fly INT4 quantization and its Maverick variant with FP8 weights — the precision format is a design parameter, not an afterthought. Distillation, speculative decoding, and MoE offloading strategies feed into the same optimization surface, turning deployment into a multi-dimensional search over quality, latency, throughput, and hardware cost.

    The thesis of this document is that quantization, distillation, and deployment are a unified engineering discipline, not three separate topics. The real question practitioners face is no longer "should I quantize" but "which format for which deployment target, validated against which task distribution." The sections that follow map that decision space — from precision fundamentals through server-side and local deployment patterns to the speculative decoding and MoE offloading techniques that complete the modern inference stack.

    Quantization Fundamentals¶

    Quantization reduces the numerical precision of model weights (and optionally activations) from their training format — typically FP32 or BF16 — to lower-bit representations. The technique works because neural network weight distributions are approximately Gaussian with low effective rank: most values cluster near zero, and the information content per parameter is far less than 16 or 32 bits.

    Precision Formats¶

    Format Bits Range / Properties Typical Use
    FP32 32 8-bit exponent, 23-bit mantissa; full IEEE 754 Training reference, legacy inference
    FP16 16 5-bit exponent, 10-bit mantissa; limited dynamic range Training (with loss scaling), inference
    BF16 16 8-bit exponent, 7-bit mantissa; same range as FP32 Modern training default, inference baseline
    FP8 (E4M3) 8 4-bit exponent, 3-bit mantissa Datacenter inference (Hopper/Blackwell)
    FP8 (E5M2) 8 5-bit exponent, 2-bit mantissa; wider range, less precision Gradient communication, some inference
    INT8 8 256 discrete levels, symmetric or asymmetric Server inference, activation quantization
    INT4 4 16 discrete levels, typically group-quantized Single-GPU inference, local deployment
    MXFP4 4 Microscaling: per-block shared exponent + 4-bit elements Very large model fitting (e.g., 120B on 80GB)
    NF4 4 Normal Float: 4-bit quantile quantization (QLoRA) Fine-tuning, edge/mobile deployment

    Key Concepts¶

    • Dynamic range matters as much as bit width. BF16 preserves FP32's exponent range while halving mantissa bits — a trade-off that works well for neural networks where relative magnitude matters more than absolute precision.
    • Group quantization divides weight tensors into small groups (typically 32-128 elements), each with its own scale factor. This captures local statistics and dramatically improves INT4/NF4 quality.
    • Per-block scaling (as in MXFP4) extends this idea to hardware-native formats, allowing 4-bit arithmetic without catastrophic outlier clipping.
    • Activation quantization is harder than weight quantization because activation distributions change with input data. Most practical systems quantize weights statically and leave activations at higher precision or quantize them dynamically.

    Quantization Methods¶

    Post-Training Quantization (PTQ)¶

    PTQ applies quantization after training is complete. The model is trained normally at full precision, then weights are converted to a lower-bit format. PTQ methods range from simple to sophisticated:

    • Round-to-Nearest (RTN): The simplest approach — round each weight to its nearest quantized value. Works acceptably for INT8 but degrades significantly at INT4.
    • GPTQ (Generative Pre-Trained Transformer Quantization): A one-shot, layer-wise method based on Optimal Brain Quantization. Uses a small calibration dataset (typically 128-256 samples) to minimize the layer-wise reconstruction error. Produces high-quality INT4 models and remains widely used.
    • AWQ (Activation-Aware Weight Quantization): Identifies salient weight channels by analyzing activation magnitudes rather than weight magnitudes alone. Protects important channels with higher effective precision through per-channel scaling. Often outperforms GPTQ on instruction-following tasks.
    • Calibration-based methods: Use representative data to compute optimal scale factors, zero points, and group boundaries. Quality depends heavily on calibration data matching deployment distribution.

    Quantization-Aware Training (QAT)¶

    QAT simulates quantization during training through straight-through estimators, allowing the model to learn weight distributions that are robust to low-precision representation. QAT consistently outperforms PTQ — EmbeddingGemma, for instance, uses QAT to keep RAM under 200MB while preserving embedding quality. The cost is a more complex training pipeline and the need to commit to a target precision format before training completes.

    iMatrix Calibration¶

    Importance matrix (imatrix) calibration measures the sensitivity of model outputs to perturbations in each weight group, then allocates quantization precision accordingly. Unsloth's imatrix calibration dataset is purpose-built for chat, coding, long-context, and tool-calling distributions, producing GGUF files that preserve quality on these tasks specifically. This represents a shift from generic calibration toward task-aware quantization.

    GGUF & Local Deployment¶

    GGUF (GPT-Generated Unified Format) is the standard file format for the llama.cpp ecosystem and the dominant format for local model deployment via tools like LM Studio, Ollama, and koboldcpp.

    Unsloth GGUF Variants¶

    Unsloth has extended the standard GGUF quantization types with optimized variants:

    Variant Description Trade-off
    Q4_K_M 4-bit with medium group size Good balance of size and quality; community default
    Q4_K_XL 4-bit with extra-large calibration 8% larger than Q4_K_M but 51% lower Maximum KLD
    Q5_K_M 5-bit with medium group size Noticeably better quality; ~25% larger than Q4_K_M
    Q6_K 6-bit Near-FP16 quality; useful when VRAM allows
    Q8_0 8-bit Baseline quality reference for GGUF
    UD variants Unsloth Dynamic Variable bit allocation across layers based on sensitivity

    KLD as a Quality Metric¶

    Kullback-Leibler Divergence (KLD) between the quantized model's output distribution and the full-precision reference measures how much information quantization destroys. Maximum KLD captures worst-case divergence — the tokens where quantization most distorts predictions. This is a more meaningful metric than average perplexity for detecting catastrophic quantization failures on specific input patterns.

    Qwen3.5-9B: Quantization Provider Matters as Much as Quant Level¶

    A detailed GGUF quantization comparison of Qwen3.5-9B using KLD and perplexity as metrics revealed that at the 4-bit level, the quantization provider matters as much as the quant level itself (r/LocalLlama, Mar 2026):

    Provider Quant KLD Relative Quality
    bartowski Q4_K_M 0.0087 Baseline
    unsloth Q4_K_M 0.0222 2.5x worse
    lmstudio Q4_K_M 0.0353 4x worse

    For VRAM-limited scenarios where dropping below Q4 is unacceptable, bartowski's IQ4_XS (4.93 GiB, KLD 0.0127) was identified as the optimal trade-off. The community consensus reinforced that KLD is more informative than perplexity for evaluating quantization quality — perplexity captures average performance, but KLD reveals "catastrophic failure" cases where the model remains fluent but makes systematically wrong decisions. The core implication is that calibration data choice is more critical than the quantization engine itself at the 4-bit level (r/LocalLlama, Mar 2026).

    Unsloth Studio¶

    Unsloth Studio is an open-source web UI for training and running LLMs locally across Mac, Windows, and Linux. It claims 2x training speed with 70% less VRAM across 500+ supported models, lowering the hardware bar for fine-tuning significantly. The tool supports GGUF, vision, audio, and embedding models, and can auto-create datasets from PDF, CSV, and DOCX files — removing a major friction point for users who have domain data but lack the expertise to format it for training. Additional features include code execution, side-by-side model comparison, and export to GGUF and Safetensors formats. Unsloth Studio represents a broader trend toward making fine-tuning accessible to practitioners who are not ML engineers, consolidating what previously required multiple CLI tools and scripts into a single local interface (AINews / r/LocalLlama, Mar 2026).

    Practical Guidance for Local Deployment¶

    • For models under 14B parameters: Q5_K_M or Q6_K if VRAM allows; Q4_K_M as the floor.
    • For models 14B-70B: Q4_K_M or Q4_K_XL is typically the practical choice on consumer GPUs.
    • For models over 70B: Q4_K_M with partial CPU offloading, or MXFP4 on datacenter GPUs.
    • Always validate on your specific tasks. Generic benchmark preservation does not guarantee preservation on your workload.

    Gemma 4: A Case Study in Day-0 Ecosystem Readiness¶

    Gemma 4 received day-0 local inference support across every major framework — a milestone illustrating how mature the local deployment ecosystem has become. llama.cpp shipped support on release day, with ggerganov demonstrating Gemma 4 26B A4B Q8_0 on an M2 Ultra at 300 t/s (with the caveat that prompt-recitation and speculative decoding inflated the number) and promoting brew install + llama-server as the canonical one-liner. Ollama (0.20+), vLLM (GPU and TPU), and LM Studio all had working support on launch day. Browser-local inference was demonstrated via transformers.js running Gemma 4 on WebGPU (xenovacom, ClementDelangue). Modular/MAX announced production inference support "in days" (clattner_llvm), and RTX 4090 long-context throughput benchmarks with TurboQuant KV quantization appeared almost immediately (basecampbernie).

    The broader point: as recently as a year ago, new model architectures routinely took weeks to gain support across llama.cpp, Ollama, vLLM, and LM Studio. Gemma 4 — a new architecture, not a Llama variant — receiving same-day coverage across all frameworks signals that the local inference ecosystem has crossed a maturity threshold. New model families can now be evaluated locally on release day rather than waiting for community ports (AINews, ggerganov, Apr 2026).

    Server-Side Quantization¶

    Datacenter deployment has different constraints from local deployment: throughput and cost-per-token matter more than fitting on a single card, and multi-GPU setups are the norm.

    FP8 for Datacenter GPUs¶

    FP8 is the emerging standard for datacenter inference on NVIDIA Hopper (H100) and Blackwell (B200) GPUs:

    • Native FP8 tensor core support means no software overhead for dequantization.
    • 2x throughput improvement over BF16 with minimal quality loss (typically <0.5% on benchmarks).
    • Llama 4 Maverick ships with FP8 weights as the intended deployment format.
    • FP8 works well for both weights and activations, simplifying the quantization pipeline.

    MXFP4 for Large Models¶

    The MXFP4 (Microscaling FP4) format uses per-block shared exponents to maintain dynamic range at 4-bit precision:

    • Enables fitting models like gpt-oss-120B on a single 80GB GPU.
    • Block size (typically 32 elements) determines the granularity of the shared exponent.
    • Quality is better than naive INT4 because the floating-point format preserves relative magnitude within each block.
    • Requires hardware or library support for efficient inference (emerging in TensorRT-LLM and vLLM).

    Inference Frameworks¶

    • vLLM: Supports FP8, INT8, INT4, AWQ, GPTQ, and Marlin kernels. PagedAttention reduces KV-cache memory waste. Active development on MXFP4 and speculative decoding integration.
    • TensorRT-LLM: NVIDIA's optimized inference library with deep integration of FP8 and INT4 quantization, custom kernels for each GPU generation, and support for in-flight batching.
    • SGLang: Emerging framework with strong quantization support and RadixAttention for prefix caching.
    • llama.cpp (serving platform expansion): Beyond GGUF inference, llama.cpp has expanded into a complete local serving platform. The built-in WebUI and MCP (Model Context Protocol) server integration mean that llama-server now provides a self-contained local inference endpoint with a browser interface and tool-calling support — capabilities that previously required separate frontends or proxy layers (ggerganov, Apr 2026).
    • Krasis LLM Runtime: A new runtime designed to run very large models on a single GPU by streaming expert weights through the GPU rather than holding them all in VRAM simultaneously. Krasis optimizes separately for prefill and decode phases, managing the flow of data between system RAM and VRAM to keep the GPU fed without requiring the full model to be resident. It has demonstrated running Qwen3-235B at usable speeds on consumer-grade GPUs such as the RTX 5080, making hundred-billion-parameter MoE models accessible outside datacenter environments (AINews / r/LocalLlama, Mar 2026).

    Knowledge Distillation¶

    Knowledge distillation transfers capabilities from a large "teacher" model to a smaller "student" model by training the student to match the teacher's output distribution rather than just the hard labels.

    How Distillation Works¶

    1. The teacher model generates soft probability distributions (logits) over the vocabulary for each token.
    2. The student model is trained to minimize a combination of the standard cross-entropy loss (against ground truth) and a KL divergence loss (against the teacher's soft distribution).
    3. The temperature parameter controls the softness of the distributions — higher temperatures reveal more of the teacher's uncertainty structure.

    When Distillation Beats Direct Training¶

    • When the student architecture is too small to learn certain capabilities from raw data alone but can learn them from the teacher's structured output distribution.
    • When labeled data is limited but the teacher can generate high-quality synthetic training data.
    • When the goal is to transfer a specific capability (e.g., reasoning, instruction following) rather than general language modeling.
    • DeepSeek-R1-Distill models demonstrated that reasoning capabilities can transfer effectively from a large reasoning-trained teacher to much smaller students.

    Relationship to Post-Training¶

    Distillation is increasingly integrated with post-training pipelines. The boundary between "distillation" and "training on synthetic data generated by a stronger model" is blurred — in practice, much of RLHF and instruction tuning involves forms of implicit distillation where a stronger model's outputs shape the training signal.

    Speculative Decoding¶

    Speculative decoding accelerates autoregressive generation by using a small, fast "draft" model to propose multiple tokens, then verifying them in parallel with the full target model.

    Draft-Verify Mechanism¶

    1. The draft model generates K candidate tokens autoregressively (K is typically 3-8).
    2. The target model processes all K tokens in a single forward pass (which is nearly as fast as processing one token due to GPU parallelism).
    3. Tokens are accepted or rejected based on a modified rejection sampling scheme that guarantees the output distribution matches the target model exactly.
    4. On rejection, the target model's distribution is used to sample the correct token, and the process restarts from that point.

    Performance Characteristics¶

    • Typical speedup: 1.5-2.5x depending on the acceptance rate, which depends on how well the draft model approximates the target model.
    • No quality loss: The rejection sampling scheme is mathematically exact — the output distribution is identical to the target model's.
    • Best for: High-latency scenarios where time-to-first-token is less important than tokens-per-second for long generations.
    • Draft model selection: The draft model should share the tokenizer and approximate the target model's distribution. Smaller models from the same family work well.

    Extensions¶

    • Medusa: Adds multiple prediction heads to the target model itself, eliminating the need for a separate draft model. Each head predicts a different future token position, and a tree-based verification scheme checks multiple candidate continuations simultaneously.
    • vLLM Speculators: A library pushing speculative decoding toward production readiness with optimized draft model integration, dynamic speculation length, and batch-aware scheduling.
    • Self-speculative decoding: Uses early exit from the target model's own layers as the draft, avoiding the need to maintain a separate model entirely.

    MoE-Specific Deployment¶

    Mixture-of-Experts models present unique deployment challenges because their total parameter count far exceeds their active parameter count. A model with 400B total parameters but 17B active parameters per token needs enough memory to hold all experts but only enough compute for the active subset.

    MoE Offloading Strategies¶

    • CPU offloading: Keep inactive experts in CPU RAM and load them to GPU on demand. Effective when the token routing pattern is predictable enough to prefetch experts.
    • Disk offloading: For models that exceed CPU RAM, experts can be paged from SSD. NVMe SSDs make this viable for interactive use at reduced throughput.
    • LM Studio MoE offload parameter: Enables running large MoE models on consumer GPUs by configuring which layers to offload. For example, Qwen-3.5-35B at Q4_K_M with 262K context runs on a 4070Ti with appropriate offload settings.

    Expert Parallelism¶

    In multi-GPU deployments, expert parallelism distributes different experts across different GPUs. Each GPU holds a subset of experts, and an all-to-all communication step routes tokens to the appropriate GPU. This is distinct from tensor parallelism (which splits individual layers) and pipeline parallelism (which assigns different layers to different GPUs).

    Quantization Interactions¶

    MoE models benefit disproportionately from quantization because the total parameter count — not the active count — determines memory requirements. INT4 quantization of a 400B-total MoE model reduces memory from ~800GB (BF16) to ~200GB, making it feasible on a single 8xH100 node rather than requiring multiple nodes.

    Notable MoE Releases¶

    • NVIDIA Nemotron 3 Super: A 120B-parameter MoE model with 12B active parameters, designed for agentic reasoning. Fully open-source — weights, datasets, and recipes are all published. The data pipeline spans 10 trillion curated tokens for pretraining and 40 million samples for post-training, with RL training across 21 environments generating 1.2 million rollouts. Nemotron 3 Super supports Quantization Aware Training (QAT) with NVFP4 precision, making it a reference case for hardware-vendor-aligned quantization. GGUFs require 64GB+ memory; initial benchmarks show it scoring below Qwen3.5 in LM Arena with style-control off, suggesting that raw scale does not automatically translate to user-preference wins (Latent.Space / r/LocalLlama, Mar 2026).

    Deployment Decision Guide¶

    Format Selection by Target¶

    Deployment Target Recommended Format Rationale
    Datacenter GPU (H100/B200) FP8 Native tensor core support, minimal quality loss, 2x BF16 throughput
    Single server GPU (A100/4090) INT4 (AWQ or GPTQ) Fits larger models on one card; AWQ preferred for instruction tasks
    Consumer GPU (local) GGUF Q4_K_M / Q4_K_XL llama.cpp ecosystem, CPU+GPU split, broad hardware support
    Edge / Mobile INT4 / NF4 Minimum memory footprint; QAT recommended for quality
    Very large MoE (100B+) MXFP4 or FP8 + expert offload Balance between fitting in memory and maintaining quality
    Fine-tuning on consumer HW NF4 (QLoRA) 4-bit base model with LoRA adapters in BF16

    Validation Practices¶

    1. Benchmark on your tasks, not generic leaderboards. A model that preserves MMLU scores under quantization may still degrade on your specific code generation or domain QA tasks.
    2. Measure Maximum KLD, not just average perplexity. Worst-case divergence reveals failure modes that averages hide.
    3. Test edge cases explicitly. Long-context performance, structured output generation, and tool calling are often the first capabilities to degrade under aggressive quantization.
    4. Compare against the full-precision model on a held-out set from your actual deployment distribution before committing to a quantization format.
    5. Re-validate when updating models. A quantization format that worked well for one model version may not work for the next — architecture changes affect quantization robustness.
