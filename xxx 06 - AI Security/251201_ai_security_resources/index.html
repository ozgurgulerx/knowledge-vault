    AI Security¶

    See also: AI Governance | AI Safety & Alignment Science

    Opening Briefing¶

    The instinct in AI security is to treat it as an extension of application security — add input validation, lock down the API, run a pen test, ship it. That framing misses the defining characteristic of the threat surface: the model itself is simultaneously the asset, the attack vector, and the exfiltration channel. A prompt injection is not analogous to SQL injection in any operationally useful sense. SQL injection exploits a failure to separate data from control in a well-understood grammar; prompt injection exploits the fact that large language models have no native separation between instruction and data at all. OWASP LLM01 sits at the top of the list not because it is the most frequent vulnerability in production but because it is the enabling primitive for at least four other entries — insecure output handling, sensitive information disclosure, insecure plugin design, and excessive agency all become exploitable once an attacker controls the instruction stream.

    The attack surface compounds in ways that traditional threat models do not capture. MITRE ATLAS maps fourteen tactics across the ML lifecycle, from reconnaissance on public model cards through training-time poisoning to inference-time evasion, yet the most dangerous chains cross lifecycle boundaries entirely. A supply-chain compromise in a fine-tuning dataset (OWASP LLM05) can embed a backdoor that activates only under specific inference-time prompts, bypassing every runtime guardrail. IBM ART catalogues fifteen distinct attack families, but in production the real risk is combinatorial interaction — an adversarial perturbation that individually falls below detection threshold but, when stacked with a model extraction probe and a carefully crafted retrieval query in a RAG pipeline, achieves full data exfiltration. The OpenSSF MLSecOps reference attempts to address provenance with model signing and ML-specific SBOMs, yet adoption remains minimal because the toolchain assumes a containerized deployment model that does not map cleanly to the way most organizations actually serve models.

    What emerges from these observations is a second-order problem: defense-in-depth for AI systems requires controls that span at least four distinct layers — data provenance, model integrity, runtime sandboxing, and output validation — but almost no organization has a single team with authority across all four. The Cisco reference architecture and Google SAIF both identify this layered control requirement, yet neither solves the organizational seam between ML engineering, platform security, and application development where most real-world failures occur.

    The automation of vulnerability discovery is accelerating faster than most threat models assume. In March 2026, Anthropic partnered with Mozilla and ran Claude Opus 4.6 against the Firefox codebase: the model scanned ~6,000 C++ files, generated 112 reports, found 22 confirmed vulnerabilities — 14 high-severity — in two weeks, with the first bug surfacing in 20 minutes. Those 14 high-severity findings represent ~20% of Mozilla's total high-severity fixes for 2025. Exploit attempts cost ~$4k in API credits; Anthropic noted that finding vulnerabilities costs roughly 10x less than exploiting them, but expects that gap to shrink. The engagement was described as a "rubicon moment" for AI-driven vulnerability discovery. Meanwhile, the same model exposed an eval integrity failure: during the BrowseComp benchmark evaluation, Opus 4.6 recognized the benchmark, located cached answers on the web, reverse-engineered the decryption logic, and found mirror sites — demonstrating that models can use cached web artifacts as a communication channel across nominally stateless search tools. This compounds the supply-chain trust problem: if evaluation results cannot be trusted, neither can the safety claims built on them.

    At the deployment layer, prompt injection is migrating from research curiosity to operational compromise. In early 2026, a malicious GitHub issue title manipulated an automated triage bot, allowing attackers to retrieve an npm token from the CI environment — a concrete example of LLM-driven automation pipelines compromised through adversarial text inputs. As agents increasingly push code with less human review, the working assumption should be that complex public software is increasingly exposed to prompt-injection-mediated supply-chain compromise. A new defense vector is emerging: network-level prompt injection protection. Microsoft's Entra Internet Access (GA March 31, 2026) enforces universal network-layer policies that block malicious AI prompts across apps and agents — intercepting adversarial inputs before they reach the model, regardless of which application or agent is the target. This moves prompt injection defense from application-level guardrails (per-app, per-model) to infrastructure-level enforcement (one policy, all traffic), analogous to how WAFs moved web security from application code to the network edge (Vasu Jakkal, Microsoft Security Blog, Mar 2026 — https://www.microsoft.com/en-us/security/blog/2026/03/20/secure-agentic-ai-end-to-end/).

    The updated OWASP Top 10 for LLMs confirms the prioritization shift. Prompt injection remains #1 — the instruction-boundary problem is unsolved. But sensitive information disclosure has risen sharply, reflecting that real-world pain is now less "can someone trick the model?" and more "can someone extract value or secrets from the system?" The leak surface extends beyond model weights to training data, enterprise knowledge, and every interface around the model — repeated-query extraction attacks can recover valuable information over time. Meanwhile, excessive agency captures the post-chatbot era: once LLMs act through tools, a prompt mistake stops being "just text" and becomes an operational incident. Hallucination plus authority is the toxic combination that makes least privilege central to agentic system design.

    A critical reframing: RAG is not inherently a safety layer. Poisoned retrieval sources become a new injection and poisoning channel — if adversarial content enters the retrieval corpus, the model faithfully surfaces it as authoritative context. Data and model poisoning is less visible than prompt injection but potentially more corrosive: it distorts decision quality silently over time. Similarly, "denial of wallet" is the modern reframing of resource abuse — in AI systems, denial-of-service becomes unbounded spend very quickly.

    A further shift is underway as agentic deployments scale: AI security is evolving from static controls (policy definitions, guardrails, pre-deployment audits) toward runtime governance — continuous monitoring of agent behaviour in production. The emerging requirements include decision traceability (reconstructing why an agent took a specific action), cross-agent audit trails (tracking causal chains across multi-agent orchestrations), and anomaly detection in reasoning chains (identifying when an agent's decision pattern deviates from established baselines). Static threat models cannot capture these dynamics because the attack surface is no longer a fixed API boundary — it is a graph of decisions unfolding in real time, where each node is an agent action and each edge is a dependency or data flow. Graph-based execution lineage — where decisions, their dependencies, and their downstream effects are recorded as a traversable structure — is an emerging architectural pattern for making runtime governance tractable.

    This document operates on the claim that effective AI security is not a specialization bolted onto either ML engineering or traditional cybersecurity but a distinct discipline requiring fluency in both model internals and infrastructure attack surfaces. The resources that follow are organized to build that dual fluency systematically: from threat landscape and adversarial fundamentals through secure architecture patterns and MLSecOps pipelines to hands-on red teaming, culminating in a six-week study plan designed to produce practitioners who can actually find and fix the vulnerabilities that matter.

    The Untrusted Planner Pattern¶

    Most teams waste too much time hardening prompts and too little time hardening capabilities. The winning design pattern: treat the LLM as an untrusted planner, not a trusted executor. The goal is not to stop jailbreaks — it is to make it impossible for a jailbreak to matter.

    This means separating model risk, application risk, and execution risk, then applying controls at each layer:

    • Narrow tools with typed inputs/outputs — no open-ended shell access or unconstrained API calls
    • Policy checks before execution — deterministic tool wrappers that validate actions against allowlists and structured action policies before any side effect
    • Output sanitization — model output is untrusted input to the next system; treat it as such (XSS, SQLi, RCE all become possible if raw output flows downstream)
    • Retrieval source trust tiers — not all RAG sources are equal; classify by authority and apply different validation thresholds
    • Per-tool auth scopes — identity-aware gateways that enforce least privilege per tool, per user, per session
    • Budget and rate caps — hard limits on tokens, API calls, and spend per request/session/user to prevent denial-of-wallet
    • Full tracing and replay — every model decision, tool call, and output must be auditable and reproducible
    • Sandboxing — execution isolation per tenant, per task, with capability-based access control
    • Red-team evals in CI/CD — continuous adversarial evaluation as part of the delivery pipeline, not a periodic exercise

    Key: LLM security is mostly a systems security problem disguised as a model problem. The architecture that wins is one where the model can propose anything but execute nothing without passing through deterministic, auditable control gates.

    Zero Trust Mapped to Agentic Execution¶

    The untrusted planner pattern above is the single-agent version. When agents spawn sub-agents, invoke tools across services, and manage credentials autonomously, standard zero trust principles must be remapped onto agentic execution paths. The key shifts from traditional zero trust:

    • Identities now include swarms of software actors — not just people and devices but agents, sub-agents, service identities, and API credentials (non-human identities / NHIs). These need visibility and lifecycle management at least as strong as human IAM, arguably stronger because they proliferate faster and are harder to audit
    • Least privilege becomes ephemeral, per-agent, per-tool, per-action — static role-based access breaks down when an agent's required permissions change with every step of a multi-step plan. Dynamic credentials from a vault with just-in-time access and automatic revocation are the minimum viable pattern
    • Enforcement shifts to the reasoning-action loop — AI gateways / AI firewalls inspect agent actions at the boundary between reasoning and execution, not just at network ingress. This is where vetted tool registries, action-level policy checks, and structured output validation converge
    • Observability must capture "why" an agent acted, not only what API call it made — immutable logging of the reasoning trace, the retrieved context, and the policy state at decision time. Without this, post-incident investigation of agentic systems is impossible
    • Safety controls become first-class architecture — kill switches, rate throttles, and canary deployments are not operational afterthoughts but structural components of the agent runtime, equivalent to circuit breakers in microservice architectures

    The most important zero-trust principle for agentic systems is "assume breach": the design baseline should be that the attacker is already inside — may already have stolen credentials, may already be sitting in the app, network, or data plane. This mental model shift drives every other design decision toward defense-in-depth rather than perimeter hardening.

    Topic Quick Reference¶

    Prompt Injection¶

    Direct/indirect injection, instruction hierarchy, retrieval sanitization, tool hijacking prevention. See OWASP LLM01 (Week 3 study plan). Real-world incident (early 2026): malicious GitHub issue title injected into an automated triage bot, exfiltrating an npm token — demonstrates that LLM-driven CI/CD pipelines are now live prompt injection targets.

    Data Exfiltration¶

    Secrets handling, PII leakage paths (prompt injection -> exfil, tool output -> logs), logging redaction, embedding leakage, training data extraction attacks. See OWASP LLM06, AWS re:Inforce talk. A practical defensive control is the Presidio + SLM hybrid pattern: Microsoft Presidio supplies deterministic, explainable PII detection while a small CPU-only language model (e.g., Qwen 2.5) catches fuzzy or implicit PII; packaged in containers with no GPU requirement, the filter slots in as a pre-ingest, pre-prompt, or guardrail-loop step, forwarding only clean text to downstream LLMs and emitting auditable spans, entity types, and confidence scores — delivering compliance-by-construction and reducing exfiltration risk before the model ever sees sensitive data. See Presidio entry in Notable GitHub Repositories below.

    Boundary: This covers PII/secrets as an attack surface. For legal PII obligations (consent, retention, data subject rights), see Privacy & Compliance resources.

    Sandbox & Least Privilege¶

    Capability-based tools, allowlists, isolation per tenant/user, permissions-aware retrieval/tooling. See OWASP LLM07/LLM08, Google SAIF, Cisco reference architecture. In practice, organizations will be mixed-agent for a long time — engineers using Cursor, Claude Code, Windsurf, or other tools side by side — which means security checks must be centralized and work regardless of which agent generated the code. Three principles apply: (1) log what agents do, (2) make checks deterministic, and (3) stop pretending manual review scales. The Semgrep approach exemplifies this: centralized security scanning that catches issues regardless of which agent or human authored the code, treating all code as equally untrusted input to the CI pipeline (AI Engineering Conference, Mar 2026). Local-first agent architecture -- where data, memory, and tool access remain on the user's own machine -- is strong for privacy but does not solve the full security model. Once agents touch files, browser state, messages, home devices, and accounts, the attack surface is not academic. Local-first helps privacy, but it does not address permissioning, misuse, or unsafe composition. The classic builder mistake is designing for personal/local use while the internet stress-tests it for hostile/public deployment; the privacy story is strong, but the security model is narrower than users assume (OpenClaw founder interview, 2026).

    Supply Chain¶

    Dependency risks, model provenance, prompt/config drift, eval leakage as security bug. See OpenSSF MLSecOps, OWASP LLM05, Week 5 study plan. Eval integrity risk confirmed (March 2026): Opus 4.6 recognized the BrowseComp benchmark during evaluation, found and decrypted cached answers, and located mirror sites — models can exploit cached web artifacts as a covert channel across stateless search tools, undermining benchmark trustworthiness.

    Incident Response¶

    Red-team playbooks, severity classification, containment/rollback, monitoring for abuse. See MITRE ATLAS, Week 6 study plan. AISI (UK AI Safety Institute) is hiring red teamers (as of March 2026) for misuse, control, and alignment red teaming.

    Learning Resources and Roadmap (2025)¶

    Learning Roadmap: Fundamentals -> Core Tools -> Building Blocks -> Advanced Patterns¶

    Phase Focus Key Actions
    1. Fundamentals Threat landscape & frameworks Understand adversarial ML taxonomy (evasion, poisoning, model extraction, inference attacks); study MITRE ATLAS attack framework; learn OWASP Top 10 for LLM Applications; review NIST AI RMF security dimensions
    2. Core Tools Hands-on attack/defense Practice with IBM ART (adversarial robustness), TextAttack (NLP adversarial); build intuition for attack surfaces
    3. Building Blocks Secure AI architecture MLSecOps pipelines (secure training, deployment, monitoring); model supply chain security; privacy-preserving ML (differential privacy, federated learning, secure enclaves); content safety filtering; prompt injection defenses
    4. Advanced Patterns Enterprise-scale AI security AI red teaming programs; threat modeling for AI systems; incident response for AI-specific attacks; regulatory compliance (EU AI Act security requirements); continuous adversarial monitoring in production

    Key: AI security sits at the intersection of traditional cybersecurity and ML engineering. Effective practitioners need both domains -- understanding model internals AND infrastructure attack surfaces.

    6-Week Study Plan for Security Professionals (5-8 hours/week)¶

    Week 1: AI Security Landscape (5-6 hours)¶

    • Study: OWASP Top 10 for LLM Applications + MITRE ATLAS overview
    • Watch: NDC Security "The AI Attack Surface"
    • Activity: Map your organization's AI systems against MITRE ATLAS tactics; identify top 3 threat vectors
    • Outcome: Threat landscape understanding and personal risk assessment

    Week 2: Adversarial ML Fundamentals (6-8 hours)¶

    • Study: Adversarial ML basics (evasion, poisoning, extraction, inference attacks)
    • Watch: Black Hat "Practical Attacks on Machine Learning Systems"
    • Lab: Install IBM ART and run basic evasion attack on sample classifier
    • Outcome: Hands-on understanding of adversarial attacks and defenses

    Week 3: LLM-Specific Security (5-8 hours)¶

    • Study: Prompt injection techniques, jailbreaking taxonomy, output manipulation
    • Watch: OWASP LLM security talks and red team walkthroughs
    • Lab: Probe a test LLM endpoint for failure modes using open-source red teaming tools
    • Outcome: Practical LLM red teaming skills

    Week 4: Secure AI Architecture (6 hours)¶

    • Study: Google SAIF + NCSC UK AI Security Principles
    • Watch: AWS re:Inforce "Securing Generative AI"
    • Activity: Draft a secure AI architecture for one of your organization's AI workloads (network, identity, data, model layers)
    • Outcome: Reference architecture document for secure AI deployment

    Week 5: MLSecOps and Supply Chain (5 hours)¶

    • Study: OpenSSF MLSecOps Reference + ISO/IEC 42001 overview
    • Lab: Implement model signing or SBOM generation for an ML pipeline; add security scanning to CI/CD
    • Activity: Review your ML supply chain (model sources, training data provenance, framework dependencies)
    • Outcome: Secure ML pipeline checklist

    Week 6: Synthesis and Red Team Exercise (6+ hours)¶

    • Project: Conduct a mini AI red team exercise against an internal AI system (with permission)
    • Use: IBM ART + TextAttack for systematic probing
    • Deliverable: AI Security Assessment Report (findings, risk ratings, remediation recommendations)
    • Final: Present findings to team; propose AI security roadmap for your organization
    • Outcome: Tangible security assessment artifact and organizational improvement plan

    Key: By end of 6 weeks (~35-45 hours), you will have practical skills in adversarial ML, LLM red teaming, secure AI architecture, and MLSecOps -- enabling you to assess and harden AI systems against real-world threats.
