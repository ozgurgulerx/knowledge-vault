    The Part of Your AI Agent That Actually Matters Isn't the Model — It's the Harness¶

    And on Azure, the harness story is finally getting interesting.¶

    I've spent the last few months building agent systems on Azure, and one thing keeps smacking me in the face: we're all obsessing over models when the real engineering happens in the harness.

    Let me back up. An agent harness is every piece of code, config, and execution logic that isn't the model itself. System prompts, tool registries, sandbox infrastructure, orchestration logic, session state, approval gates, tracing — all harness. The cleanest framing I've seen comes from LangChain's anatomy paper: Agent = Model + Harness. If you're not the model, you're the harness.

    Why does this matter? Because LangChain proved that changing ONLY the harness — same model, same tools, same task set — improved Terminal-Bench 2.0 scores by 13.7 points. That's not a rounding error. That's the difference between a demo and something you'd put in front of a customer.

    Here's how to think about harness engineering on Azure, and why 2026 is the year it becomes a real discipline.

    The Six Layers Every Agent Harness Needs¶

    Before touching Azure services, internalize this mental model. A production harness breaks into six layers:

    1. Entry/control plane — API gateway, chat UI, or event trigger
    2. Router/orchestrator — what handles each request and how
    3. Execution layer — one agent or many, in sequence, parallel, or handoff patterns
    4. Tool layer — OpenAPI endpoints, functions, MCP tools, databases, retrieval
    5. State + policy layer — session memory, approval gates, retry limits, budgets, content policy
    6. Evidence layer — traces, evals, run logs, quality metrics

    Think of this as a diagnostic tool, not a deployment checklist. If your system is missing a layer, you have a gap. But not every layer needs to be elaborate. A thin policy layer with hard timeout caps is often enough. A thin evidence layer with structured logging beats nothing.

    The 15-module inventory that sits underneath these layers includes things like agent loops with doom-loop detection, prompt composers with per-tool instruction injection, tool routers with lazy schema loading, context managers with compaction triggers, sandbox substrates, tracing with OpenTelemetry, and evaluation harnesses. Not every system needs all 15. But if you can't point to where each concern is handled — even if the answer is "we accept the risk" — you have an unexamined gap.

    Azure's Two-Speed Architecture¶

    Here's where Azure gets interesting. Microsoft has quietly set up a two-speed architecture that maps cleanly to the "demo vs. production" divide most teams face.

    Path A — the 30-minute proof. Foundry Agent Service plus a hosted agent plus the playground. You deploy a containerized agent via azd up, validate in the Foundry playground, and you're done. Managed hosting, built-in tools, good demo optics. This is the path you show a VP to prove the concept works.

    Path B — the real harness. Agent Framework workflow in code, deployed on Azure Functions Durable or App Service, with Foundry traces and evals wired in. Code-first orchestration. Long-running workflows. Event triggers. Pause and resume. Deterministic flow control. This is the path you take when someone asks "can this be productionised?"

    Microsoft's own documentation frames the tradeoff explicitly: code-first frameworks give you more control and speed locally, while Foundry Agent Service gives you managed integration, playground testing, autoscaling, and built-in guardrails with identity.

    My take: demo Path A, build Path B. Use the playground to validate your agent logic fast, then move the real implementation into Agent Framework workflows where you control every decision point.

    Mapping Azure Services to the Six Layers¶

    Here's how the layers translate to actual Azure services:

    Model + agent runtime maps to your Foundry project or Foundry Agent Service. This is where your model lives and where agent sessions are managed.

    Workflow and orchestration maps to Agent Framework workflows for complex cases, or the Foundry workflow UI for simpler ones. Agent Framework is positioning itself as the successor to Semantic Kernel and AutoGen, bringing session state, telemetry, and workflow control under one roof.

    Tools map to OpenAPI endpoints, Azure Functions, and MCP tools. The MCP integration is worth noting — the app-service-mcp-foundry-agent-python sample shows how to wire MCP servers into a Foundry agent, which means your agent gets access to external tool ecosystems without custom integration code.

    State maps to Foundry's persistent or service-managed conversation history, or your own custom store if you need finer control over session continuity.

    Observability maps to Application Insights plus OpenTelemetry plus Foundry traces. This is one of Azure's genuine strengths — the trace pipeline is well-integrated and you get span-level visibility into LLM calls, tool calls, and agent decisions out of the box.

    Evaluation maps to the Azure AI Evaluation SDK and Foundry evaluators. More on this below, because evaluation is where most teams underinvest.

    A Minimal Reference Architecture¶

    Here's the skeleton I start from when building a harness on Azure:

    User / UI / API
   -> Gateway / FastAPI / Function HTTP trigger
      -> Harness Controller
         -> Intent router
         -> Policy checks
         -> Budget / timeout / retry manager
         -> Session state store
         -> Workflow orchestrator
              -> Retrieval agent
              -> Tool-using action agent
              -> Verifier / checker agent
         -> Response composer
      -> Trace + logs + eval events

    This isn't aspirational architecture. It's the minimum viable harness. The intent router decides which agent handles the request. The policy layer enforces budget and timeout caps. The workflow orchestrator runs agents in the right order, including a verifier that checks the output before it leaves the system. And everything emits trace events so you can debug failures after the fact.

    The verifier agent is the part most teams skip and most teams regret skipping. When an action agent generates an answer, the verifier checks groundedness — did the answer actually come from the retrieved data? — and validates that required fields are present. Without this step, your agent hallucinates confidently and nobody catches it until a customer complains.

    The Five-Screen Demo That Sells Harness Engineering¶

    Stop demoing generic assistants. Demo a narrow but complete harness instead. Microsoft's documentation suggests a five-screen sequence that I've found genuinely effective:

    Screen 1: Architecture slide. One-page diagram showing user, harness controller, agents, tools, checker, logs, and evals. This sets the frame — you're showing a software system, not an AI trick.

    Screen 2: Live run. Submit a real request that requires at least one tool call. Something like "Customer shipment delayed; explain cause and next action." The audience watches the agent classify the request, retrieve shipment facts from a mock API, recommend an action, and get the recommendation verified by a checker agent.

    Screen 3: Trace view. Pull up the execution trace in Foundry or Application Insights. Show spans for each LLM call, tool call, and agent decision. This is where technical audiences lean forward.

    Screen 4: Failure injection. Break one tool on purpose. Kill the shipment API. Show the harness retrying, falling back, and returning a controlled error instead of hallucinating an answer. This is the real harness moment. This is what separates your demo from every other ChatGPT wrapper.

    Screen 5: Eval report. Show a tiny JSONL test set with metrics — groundedness, relevance, tool-call accuracy, task completion — via the Azure AI Evaluation SDK. This proves the system is measurable, not just impressive.

    Once you show this sequence, the audience stops seeing "AI demo" and starts seeing "software system." That shift in perception is worth more than any benchmark number.

    Prompt Caching: The Harness Constraint Nobody Talks About¶

    If you're building long-running agents — and on Azure, most production scenarios involve multi-turn conversations — prompt caching is not an optimization you bolt on later. It's a structural constraint that must inform your harness design from day one.

    The core mechanism is prefix matching. The API caches everything from the start of the request up to each cache breakpoint. Any change anywhere in the prefix invalidates everything after it. This single constraint drives harness design decisions that feel counterintuitive until you understand why.

    Order your prompt: static first, dynamic last. System prompt and tools go first (cached globally). Project-level context like CLAUDE.md or equivalent goes next (cached per project). Session context follows (cached per session). New conversation messages go last (new per turn).

    Never change tools mid-conversation. Adding or removing a tool invalidates the cache for the entire session. The intuitive approach — only expose tools the model needs right now — is an anti-pattern. Keep all tools present and use other mechanisms to control behavior. If you have many tools, send lightweight stubs with deferred loading rather than full schemas.

    Never switch models mid-session. Caches are model-specific. If you're deep into a conversation with one model and want to ask an easy question on a cheaper model, you pay full price to rebuild the entire cache. The right pattern is subagents — hand off a bounded task to a cheaper model with its own fresh cache.

    Use messages for state changes, not prompt mutations. When information becomes stale (timestamps, changed files, new context), inject updates as conversation messages rather than modifying the system prompt. This preserves the cached prefix.

    Anthropic's Claude Code team monitors cache hit rate like uptime and declares incidents when it drops. That level of discipline around caching is what separates production harnesses from prototypes.

    Bounded Autonomy: The Operating Model That Actually Works¶

    Full agent autonomy is a trap. The model that works in practice is bounded autonomy — a repeating cycle where humans establish intent and agents accelerate execution within that frame.

    The cycle looks like this:

    1. Human seeds the work — chooses frameworks, establishes architecture, makes key decisions
    2. Agent plans and executes within a bounded workspace
    3. Verification is explicit — a verifier pass checks output before merge
    4. Scope stays PR-sized — work stops at natural merge points
    5. Context resets — merge, archive the workspace, start fresh for the next unit

    The natural operating unit is one pull request, not one feature or one session. PR-sized scoping reduces stale context, prevents plan invalidation, and makes verification tractable. When a task is larger than one PR, decompose it into independent chunks that can be parallelized.

    This maps directly to Azure: your Agent Framework workflow orchestrates the bounded task, Foundry traces capture the execution, and the evaluation SDK validates the output. The harness enforces the bounds — budget caps, timeout limits, tool access restrictions — so the agent can't wander off into expensive or dangerous territory.

    Evaluation: The Harness Module Everyone Skips¶

    An evaluation harness is distinct from your runtime harness but must be tightly connected to it. It runs agent tasks at scale, records full traces, grades outcomes, and aggregates results. Crucially, when you evaluate an agent, you're evaluating the harness and model together, not the model in isolation.

    On Azure, the evaluation pipeline looks like this:

    change -> build -> eval harness runs -> quality gate -> deploy ->
production trace mining -> regression suite updates -> re-eval

    The Azure AI Evaluation SDK gives you evaluators for groundedness, relevance, and custom metrics. Wire these into your CI pipeline so that prompt changes, tool changes, and config changes trigger automated evaluation before deployment. Harbor-style job configs work well here — define your test cases as JSONL, run them in parallel containers, and gate deployment on passing scores.

    A practical tip from the eval literature: design test cases from production data whenever possible. Production logs are the gold standard because they reflect real user behavior. If you don't have production data yet, synthetic generation via LLM is your next best option. Hand-written test cases are a last resort.

    Use deterministic metrics wherever you can — string match, valid JSON checks, regex format validation, precision/recall. These are cheaper, faster, and 100% reliable. Save LLM-as-a-judge grading for dimensions that actually require it, like helpfulness and tone.

    Context Rot and What Your Harness Should Do About It¶

    Context rot is how agent performance degrades as the context window fills. Models get worse at reasoning as accumulated tool outputs, stale instructions, and conversation history crowd out useful signal. Your harness is fundamentally a delivery mechanism for good context engineering.

    Three harness-level strategies:

    Compaction. When context approaches capacity — roughly 85% — the harness summarizes and offloads the existing window so the agent can continue. The trick is making compaction cache-safe: use the exact same system prompt, tools, and context as the parent conversation so you get cache hits on the shared prefix. Only the compaction instruction itself is uncached.

    Tool-call offloading. Large tool outputs clutter context without adding value. Keep only the head and tail of outputs above a threshold and write the full result to the filesystem for on-demand access.

    Progressive disclosure. Don't load all tool schemas on agent start. Load metadata only — name and one-line description — and bring in full instructions and tool subsets when the agent activates a skill. The model didn't choose to have hundreds of tool schemas in context. Your harness should protect it.

    What's Coming Next¶

    Four directions worth watching:

    Automatic harness synthesis. LLMs iteratively generating the harness code itself — synthesizing policy enforcement, tool routing, and safety constraints as executable code rather than prompt instructions. This moves "harness generation" from a dev-ops task to a performance and safety lever.

    Harness-model co-evolution. Agent products are being post-trained with their harnesses in the loop. Useful primitives get discovered, added to the harness, and used when training the next model generation. The risk: models become brittle when you change the harness they were trained with. The opportunity: harness optimization remains a huge untapped lever independent of model choice.

    Dynamic tool assembly. Just-in-time tool and context loading based on current state will replace fixed tool menus. Retrieval-style tool selection with trace-informed pruning of unused tools becomes standard.

    Eval-training convergence. The same task definitions powering offline evaluation, regression CI, and online training signals. Your evaluation harness doubles as an RL training environment, enabling prompt optimization and fine-tuning of specialized sub-agents on your specific workload.
