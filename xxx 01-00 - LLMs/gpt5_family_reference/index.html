    GPT-5 Family Reference¶

    Opening Briefing¶

    GPT-5.4 is not primarily a smarter language model. It is an agent runtime disguised as a model release. The March 2026 convergence of frontier coding capabilities (from GPT-5.3-Codex) with native computer use, tool search, and a million-token context window signals that OpenAI has stopped optimizing for the "best answer to a question" and started optimizing for "best executor of a multi-step workflow." The benchmark gains confirm this: OSWorld-Verified jumped from 47.3% to 75.0% between GPT-5.2 and GPT-5.4, while GPQA Diamond moved only 0.4 points. The capability frontier has shifted from reasoning about text to operating on environments.

    Two architectural decisions reveal the underlying trade-offs. First, the reasoning.effort parameter creates a hard fork in the model's behavior: at none, you get a conventional LLM with full sampling controls (temperature, top_p, logprobs), but at any higher setting, those controls are disabled entirely and reasoning tokens — invisible via the API — are billed as output tokens at $15 per million. This means every production deployment must treat reasoning effort as a cost-multiplier knob with no intermediate observability. Second, the 1,050,000-token context window carries a pricing discontinuity at 272K tokens that doubles input cost and adds 50% to output cost for the entire session, not just the overage. Combined with documented performance degradation on graph-reasoning tasks in the 256K-1M range, the million-token window is better understood as an agent state buffer with compaction than as a faithful long-context reader.

    These two facts together produce a counterintuitive implication: the most cost-effective and reliable GPT-5.4 deployments will use less context and less reasoning, not more. The optimal pattern is a multi-model cascade — nano for routing and extraction at one twenty-fifth the cost, the full model with targeted RAG retrieval rather than blind context stuffing, and reasoning effort dialed to the minimum that passes evaluation. Prompt caching (90% discount on cached tokens) and the Batch API (50% discount on async jobs) further reward architectures that treat the model as an orchestrated component rather than a monolithic brain.

    This reference consolidates the GPT-5 family's API surface, benchmark data, pricing mechanics, fifteen build patterns, and production runbook into a single operational document. The operating claim throughout is that GPT-5.4 demands systems engineering, not prompt engineering — the returns come from how you compose the model into toolchains, manage its cost envelope, and constrain its agent loops, not from crafting a better system message.

    GPT-5.4 Model Report¶

    Executive Summary¶

    GPT-5.4 (API: gpt-5.4) released 5 March 2026 across ChatGPT, the API, and Codex. Higher-compute variant: GPT-5.4 Pro (gpt-5.4-pro). OpenAI has not disclosed parameter count, exact architecture, training compute, or data mixture. GPT-5.4 (xhigh) returns OpenAI to #1 (tied) on the Artificial Analysis Intelligence Index alongside Gemini 3.1 Pro Preview (score 57, up from 51 for GPT-5.2 xhigh). GPT-5.4-xhigh also claims #1 on LiveBench. The model uses 47% fewer tokens than GPT-5.2 for equivalent tasks.

    Architecture & Training¶

    No architecture paper published. RL-trained reasoning; exact recipe undisclosed. First general GPT-5 model with mitigations for "High capability in Cybersecurity."

    Mental model: GPT-5.4 is designed for agent loops: reason -> call tools -> operate GUIs from screenshots -> compress/maintain long state.

    Vision & Computer Use¶

    Multimodality = vision input tuned for UI control, not general omni-model.

    • high: up to 2,500 patches / 2048px max dimension
    • original: up to 10,000 patches / 6000px (recommended for computer use, OCR, click accuracy)
    • Harness shapes: built-in tool, custom harness, code-execution
    • Requirements: isolation and confirmation

    Key: Use detail: "original" on screenshots for best click accuracy. Run in isolated environment, treat page content as untrusted input.

    GPT-5.4 Mini and Nano¶

    OpenAI launched GPT-5.4 mini and GPT-5.4 nano across API, ChatGPT, and Codex, positioning them as its most capable small models. GPT-5.4 mini is more than 2x faster than GPT-5 mini, targets coding, computer use, multimodal understanding, and subagent workloads, and offers a 400k context window in the API. OpenAI claims mini approaches larger GPT-5.4 performance on SWE-Bench Pro and OSWorld-Verified while using only 30% of GPT-5.4 Codex quota, making it the new default for background coding workflows and subagent fan-out (@OpenAIDevs, Jun 2026).

    Pricing is $0.75/M input and $4.50/M output for mini, with nano priced above prior nano tiers — continuing OpenAI's pattern of better performance at higher per-tier price points (@scaling01, Jun 2026). Third-party evals were mixed: Mercor's APEX-Agents reported 24.5% Pass@1 for mini with xhigh reasoning, while BullshitBench placed the new small models relatively low on resistance to false-premise and jargon traps. Developers immediately highlighted mini's utility for subagents in Codex, computer-use workloads, and external products such as Windsurf.

    Early Feedback¶

    • Mercor: "the best model we've ever tried" -- APEX-Agents benchmark, long-horizon deliverables
    • Harvey: "sets a new bar" for document-heavy legal work; BigLaw Bench 91%
    • Zapier: "outstanding coding assistant" -- fewer iterations, faster completion
    • Mainstay: autonomous coding + improved adherence to project conventions

    Early reporting emphasises workplace tooling and partnerships for financial/workflow contexts -- targeting "knowledge work in situ."

    Arena (Chatbot Arena): GPT-5.4 High entering top 10 with large gains in creative writing and "longer query" categories; math performance roughly flat vs GPT-5.2-High.

    Coding caveat: GPT-5.4 Codex appears weaker for coding than GPT-5.3 Codex per developer reports.

    Cost vs GPT-5.2: ~28% higher benchmark run cost ($2.50/$15 vs $1.75/$14 per 1M input/output tokens). Context window expanded from 400K (GPT-5.2) to ~1.05M tokens.

    Strengths: CritPt (physics reasoning) and TerminalBench Hard (agentic coding/terminal use).

    15 Build Patterns for GPT-5¶

    Core principles: schema-first, safety-first. GPT-5 supports parallel function calls, built-in tools, reasoning_effort, verbosity control, and constrained decoding (100% JSON compliance in strict mode).

    Pattern Codex¶

    # Pattern Use Case Key Features Latency (p95)
    1 Structured JSON API Deterministic data extraction strict=true, JSON Schema, constrained decoding ~300-800ms
    2 Direct Tool Calling (Single) Single external API call function_call, Tools API ~500ms + external
    3 Tool-Using Agent (Multi-step) Complex multi-step, multiple APIs Agents SDK, reasoning_effort high, parallel tools 1-15s
    4 RAG QA over proprietary knowledge Embeddings, long context, optional search tool ~700ms
    5 Streaming Chatbot UX Real-time conversational UI stream=True, SSE/WebSockets ~100-300ms TTFT
    6 Batch Processing Pipeline Offline large-scale jobs (10k+) Batch API (50% savings), gpt-5-nano Up to 24h
    7 Complex Data Transformation Text-to-code, log parsing, SQL gen CFG grammar, high reasoning_effort 1-5s
    8 Multimodal Assistant Image/audio I/O GPT-5 Vision, Whisper, DALL-E ~1-10s
    9 Orchestration via Middleware GPT-5 as pipeline step Functions in workflows, CoT prompting Varies
    10 Evaluation & Moderation Quality/safety checks score function, Moderation API ~500ms added
    11 Multi-tenant SaaS Per-tenant chatbot/analytics Feature store, per-tenant prompts/quotas Base pattern
    12 Multi-model Cascade Cost/latency optimization gpt-5 + mini + nano, reasoning routing 0.3-1.3s
    13 Schema-First API SQL gen, classification (no human loop) JSON mode, zero-shot/few-shot ~400ms
    14 Content Generation + Moderation Blogs, marketing with guardrails System message, verbosity, Moderation API 2-5s
    15 Personalized Assistant (Memory) Long-term user personalization Conversation history, vector store for episodic memory Slightly higher

    Selected Pattern Details¶

    Pattern 1 -- Structured Outputs: Use response_format with json_schema + strict: true. Strict mode = 100% conformity. Always validate with JSON parser as backup. Log valid JSON rate (should be ~100%).

    Pattern 3 -- Multi-Tool Agent: ~500 tokens/step x ~5 steps = ~2500 tokens (~$0.025/session). Guardrails: max step count (5-10), timeout, sentinel prompt to prevent infinite loops. Use mini for intermediate steps.

    Pattern 4 -- RAG: Two variants: (a) orchestrator-driven (app retrieves, stuffs prompt); (b) GPT-driven via search_documents function call. Embedding ~$0.0004/query. RAG more cost-effective than blindly using 272k context.

    Pattern 6 -- Batch: 50% cost reduction on tokens. Break very long jobs into 10k-task batches. Assign IDs for idempotency.

    Pattern 12 -- Multi-model Cascade: Route easy queries to nano, hard queries to full gpt-5. Significant savings if fallback is rare.

    Migration Checklist (GPT-4.x to GPT-5)¶

    Area Action
    Model endpoint Update to gpt-5. Three sizes: gpt-5, gpt-5-mini, gpt-5-nano
    New parameters verbosity (low/medium/high), reasoning_effort (minimal to high)
    Function calling Syntax mostly same. Ensure strict usage. Remove manual JSON hacks.
    Output differences GPT-5 more verbose/expert-level by default. Test and adjust verbosity.
    Structured outputs Switch to response_format with json_schema + strict: true
    Context length 272k tokens (vs GPT-4's 8k/32k). Re-evaluate chunking logic.
    Cost $1.25/1M in ($0.125 cached), $10/1M out. Use mini/nano for heavy users.
    Quality/regression tests Run existing eval suite on GPT-5. Verify tool use behavior.
    Safety Less prone to jailbreaks, more honest. Fewer erroneous refusals.
    Prompt adjustments Highly steerable. Simplify overly complex constructions.
    Parallel calls Handle possible array of function calls if model suggests concurrency.
    Batch API Consider migrating manual batching for 50% savings.
    Client library Upgrade OpenAI SDK to latest (supports OpenAI.Agent etc.)
    Rollout Phased: test -> shadow -> 5% canary -> 25% -> 50% -> 100%. Keep GPT-4 fallback.

    Reliability & Observability Runbook¶

    Rate Limiting & Backoff¶

    • Client-side rate limiting per OpenAI quota. Exponential backoff with jitter on HTTP 429 (1s, then 2s). Max retry 2-3.

    Idempotency¶

    • Hash user request as key. Store request IDs.

    Timeouts¶

    • ~30s for GPT-5 reasoning, shorter for mini. Wrap tool calls with timeouts.

    Circuit Breakers¶

    • External API fails 5x in a row -> stop calling. Switch to degraded mode for OpenAI errors.

    Input/Output Validation¶

    • Enforce max length. Sanitize control characters. Always try/except JSON parsing. Verify categories in expected set. Use Pydantic/type guards.

    Logging & Tracing¶

    • Log every request: timestamp, model, input/output length. Correlation/trace ID per user request. Integrate with OpenTelemetry/Datadog.

    Key Metrics & Alerts¶

    • Latency: p50, p95. Alert if p95 exceeds threshold.
    • Error rates: API errors, tool errors, function call errors. Alert if > X%.
    • Token usage: per request and per day. Spot anomalies.
    • Function call counts: alert if suddenly spikes (model looping).
    • Structured output parse failures: model regression signal.
    • Content filter triggers: monitor moderation flag increase.

    PII & Privacy¶

    • Mask/remove PII in logs. Respect Zero Data Retention mode. Ensure deletion propagates to vector stores.

    Failover¶

    • Route critical requests to a backup provider or smaller local model. Maintain multiple model versions behind config abstraction.

    Guardrails on Tools¶

    • Require confirmation for sensitive actions. Strict scopes per user. Limit repeated calls (e.g., max 2 send_email per session).

    Safety & Known Failure Modes¶

    1. Tool routing errors early in session -- tool selection less reliable with thin context; use explicit prompting
    2. Incomplete execution on long-horizon tasks -- model stops after partial coverage unless completion rules explicit
    3. Prompt injection via untrusted UI content -- design confirmation/consent policies for risky actions
    4. Vision limitations -- approximate counting, no metadata processing, CAPTCHAs blocked
    5. Long-context degradation -- sharp performance drop on some tasks in 256K-1M range

    Mitigation patterns: confirmation at point of risk, explicit output contracts + "definition of done", lowest effective reasoning effort, isolated computer-use environment (sandbox browser/VM).

    Anti-Patterns¶

    1. No schema validation -- relying on model output without JSON parsing/validation
    2. Unbounded agent loops -- no step limit or timeout on multi-tool agents
    3. No fallback plan -- single point of failure on OpenAI API
    4. Ignoring cost -- using full GPT-5 for trivial tasks where nano suffices
    5. Skipping evals -- no regression tests when changing prompts or models
    6. Over-filtering -- overly strict moderation causing legitimate refusals
    7. Blind context stuffing -- sending 272k tokens when RAG with targeted retrieval is more effective
    8. No observability -- no logging, no metrics, no alerts

    90-Day Adoption Plan¶

    Sprint 1: Foundational Integration (Days 1-30)¶

    • Week 1: Identify use cases, get API access, update SDKs, team training
    • Week 1-2: Prototype structured outputs (strict mode), test function calling, benchmark latency vs GPT-4
    • Week 2: Logging/tracing setup, monitoring dashboards, vector store if RAG needed, compliance review
    • Week 3: Inventory all GPT usage, update prompts, config flags for GPT-4/5 toggle
    • Week 4: Internal QA, run eval suite (GPT-5 vs GPT-4), fix regressions

    Sprint 2: Scale-Out & Beta (Days 31-60)¶

    • Week 5: Canary release (5%), monitor dashboards, ensure fallback
    • Week 6: Analyze canary data, implement streaming/mini routing, deploy caching, load test
    • Week 7-8: Increase rollout 25% -> 50% -> 100%, monitor cost and support tickets

    Sprint 3: Hardening (Days 61-90)¶

    • Week 9: Security/compliance audit, moderation log review
    • Week 10: Simulate failures, 2x peak load tests, auto-failover to GPT-4
    • Week 11-12: Pilot multimodal, add new tools, expose verbosity/reasoning_effort to users
    • End: Retrospective, document learnings, plan next 90 days

    Developer Integration Quick Start¶

    Best Defaults¶

    1. Use the Responses API for agentic workflows -- better chain-of-thought handling, reduces reasoning tokens
    2. Choose reasoning.effort by task: none for routing/extraction; low/medium for multi-step reasoning; high/xhigh only when evals show wins
    3. Sampling controls require effort=none -- otherwise control via output contracts

    Prompt Engineering¶

    GPT-5.4 responds best to "contract-style" prompting -- treat as workflow executor.

    • Clamp output length and format via output contracts
    • Force persistence -- require completion until end state verified
    • Tool preambles -- prompt model to explain why it's calling a tool (boosts accuracy)

    SDKs & Operations¶

    • JS/TS, Python, .NET, Java, Go
    • Rate-limit aware retries/backoff
    • Background mode for Pro and tool-heavy workflows
    • Snapshot pinning (gpt-5.4-2026-03-05) for regulated workflows
