    Model Context Protocol (MCP)¶

    See also: Agent Harness Engineering | LLM Agentic Systems | AI Security

    Opening Briefing¶

    The Model Context Protocol (MCP) is an open protocol, originally created by Anthropic (Nov 2024), that standardizes how AI applications provide context, tools, and data sources to LLMs. The analogy everyone uses: MCP is the USB-C port for AI applications — a single, universal connector that replaces the N-times-M problem of custom integrations between every AI client and every external service. Before MCP, every agent framework had its own way of wiring tools; MCP replaces that with one protocol spec that any client or server can implement.

    Since December 2025, MCP is governed under the Linux Foundation's Agentic AI Foundation (AAIF), with founding contributions from Anthropic, OpenAI, and Block. This governance shift signals that MCP is being treated as plumbing for agents rather than a single-vendor experiment. Official sources cite 10,000+ active public servers and 97M+ monthly SDK downloads (Python + TypeScript combined) as of early 2026 (Anthropic, AAIF, Dec 2025). The ecosystem is no longer just "clients + servers" — it is accumulating supporting institutions: a Registry, reverse-DNS naming with verification, packaging/bundling formats, standardized remote auth, security guidance, and managed server offerings from major cloud providers.

    MCP matters for agent harness engineering because it defines the tool layer (Layer 4 in the six-layer harness model) as a first-class protocol concern rather than leaving it to ad-hoc function-calling implementations. The biggest trade-off: MCP standardizes tool/data wiring but does not automatically solve context-window inflation, latency, or trust. It can increase token burn when tool catalogues are large; conversely, it improves context efficiency when servers keep large data out of the prompt and return compact, structured results.

    A notable trend: vendors shipping MCP servers as official gateways to their own ecosystems — turning docs, APIs, and operations surfaces into agent-consumable tools. These are not toy servers; they are authoritative, continuously-updated context sources that compete with brittle scraping and out-of-date training priors.

    Architecture: Client–Server Model¶

    MCP follows a client–server architecture built on JSON-RPC 2.0.

    Roles¶

    Role What it is Examples
    Host The container/coordinator that manages clients, user consent, security policy, and model integration Claude Desktop, VS Code + Copilot, Claude Code CLI
    Client A protocol-level connector inside the host; maintains an isolated stateful session per server; handles negotiation and message routing The SDK's Client class
    Server A lightweight process or service that exposes capabilities (tools, resources, prompts) to clients; can request sampling through client interfaces A filesystem server, a database server, a weather API wrapper

    The key constraint: one client connects to one server. A host that needs multiple servers spins up multiple clients internally — the host is the fan-out point, not the protocol itself.

    Key: A design principle frequently overlooked in casual implementations is server isolation: servers should not read the entire conversation nor "see into" other servers. The host enforces boundaries and chooses what to share. This is a deliberate security constraint, not an accidental limitation.

    Transports¶

    MCP is transport-agnostic but the specification defines two standard transports:

    • Stdio — client launches the server as a subprocess; JSON-RPC messages are newline-delimited on stdin/stdout; stderr is for logging; stdout must be protocol-only. Best for local tools. No network overhead, no auth needed.
    • Streamable HTTP — a single MCP endpoint supports POST/GET; servers can optionally use SSE for streaming; includes explicit guidance on reconnect, resumability, session IDs (Mcp-Session-Id header), and a required MCP-Protocol-Version header. Required for remote/cloud-hosted servers. Supports the MCP authorization framework (OAuth 2.1-based).

    Legacy note: The 2024-11-05 spec defined a separate "HTTP+SSE" transport with two endpoints. The 2025-03-26+ spec replaced it with Streamable HTTP using a single endpoint. OpenAI's Agents SDK labels SSE as deprecated and recommends Streamable HTTP or stdio for new integrations. Prefer Streamable HTTP for new remote deployments; keep SSE only for legacy compatibility.

    The Three Primitives¶

    MCP servers expose capabilities through three core primitives. Each primitive has a distinct control model:

    Primitive Purpose Control Analogy
    Tools Actions the model can invoke Model-controlled (the LLM decides when to call) POST endpoints / function calls
    Resources Data the application can read Application-controlled (the host/client decides what to attach) GET endpoints / file reads
    Prompts Templated interaction patterns User-controlled (the user selects which prompt to use) Slash commands / prompt templates

    Tools¶

    Tools are the most commonly used primitive. A tool is a function with a name, description, and JSON Schema input definition (plus optional output schema) that the LLM can call during a conversation. The server declares available tools; the model decides when and how to call them.

    Key properties:

    • Discovered via tools/list, invoked via tools/call
    • Can represent anything: API calls, database queries, computations, file operations, shell commands
    • Support listChanged notifications so the client knows when the tool set updates dynamically
    • Annotations (added in 2025-03-26): tools can declare metadata like readOnlyHint, destructiveHint, idempotentHint, and openWorldHint to help clients/users make trust decisions without inspecting implementation

    Resources¶

    Resources expose data that the host application can retrieve and inject into the LLM context. Unlike tools, resources are not model-invoked — the application decides which resources to include.

    Key properties:

    • Discovered via resources/list, read via resources/read
    • Identified by URI (e.g., file:///path/to/doc.md, postgres://db/table, screen://screenshot)
    • Support subscriptions: the client can subscribe to a resource URI and receive notifications when the content changes
    • Support templates: URI templates (RFC 6570) that let the server expose parameterized resources (e.g., users://{user_id}/profile)

    Prompts¶

    Prompts are server-defined templates that produce structured message sequences. They are selected by the user (not the model), making them ideal for codified workflows.

    Key properties:

    • Discovered via prompts/list, retrieved via prompts/get
    • Can accept arguments (required or optional) to customize the generated messages
    • Return a list of messages with role and content — the client injects these into the conversation
    • Use case: a "code_review" prompt that takes a language argument and produces a specialized system message

    Connection Lifecycle¶

    Every MCP session follows a three-phase lifecycle:

    1. Initialization¶

    The client sends an initialize request containing:

    • protocolVersion — the latest version the client supports (e.g., "2025-11-25")
    • capabilities — what the client can do (roots, sampling, elicitation)
    • clientInfo — name, version, description

    The server responds with:

    • protocolVersion — the negotiated version (must match the client's or be the server's latest)
    • capabilities — what the server offers (tools, resources, prompts, logging, tasks)
    • serverInfo — name, version
    • instructions — optional natural-language instructions for the LLM on how to use this server

    After receiving the response, the client sends an initialized notification to signal readiness.

    Version negotiation rule: If the server responds with a version the client doesn't support, the client should disconnect. If using HTTP, the client must include MCP-Protocol-Version header on all subsequent requests.

    2. Operation¶

    Normal message exchange. The client can:

    • List and call tools
    • List and read resources (and subscribe to changes)
    • List and get prompts
    • Send completion requests, logging, and progress notifications

    The server can (if the client declared the capability):

    • Sampling: ask the client to perform an LLM generation (model-in-the-loop for nested agent patterns). Tool-enabled sampling is now supported; includeContext modes that automatically leak broader context are soft-deprecated.
    • Elicitation: ask the client to collect information from the user (forms, URLs)
    • Roots: request the list of filesystem roots the client has exposed

    3. Shutdown¶

    Either side can terminate. The client calls close(), or the transport disconnects. Servers should handle abrupt disconnections gracefully.

    Advanced Capabilities¶

    Sampling (Server-Initiated LLM Calls)¶

    Sampling lets a server request that the client perform an LLM completion. This enables agentic behaviors where a tool-providing server can itself reason about intermediate results without needing its own LLM API key. The client maintains full control — it can modify the request, apply safety policies, or require user approval before sending to the model.

    Use case: a code analysis server calls sampling to ask the LLM to summarize findings before returning the final tool result.

    Elicitation (Server-Initiated User Input)¶

    Elicitation lets a server request structured input from the user via the client. Two modes:

    • Form mode: server defines a JSON Schema form, the client renders it and returns the user's answers
    • URL mode: server provides a URL for the user to visit (e.g., an OAuth consent page), and the client notifies the server when the interaction is complete

    Roots (Filesystem Boundaries)¶

    Clients can expose roots — filesystem URIs that define the boundaries where a server may operate. Servers use roots/list to discover which directories they have access to. Includes path traversal considerations. This is how MCP enforces the principle of least privilege for filesystem-aware tools.

    Tasks (Long-Running Operations)¶

    Tasks (added in 2025-11-25) support long-running, asynchronous operations. Servers can report progress, clients can list and cancel tasks. This enables patterns like background code generation, multi-step data pipelines, or deployment workflows that run beyond a single request-response cycle.

    MCP Apps (Interactive UI in Chat)¶

    A major 2025–2026 evolution: UI in chat. MCP Apps is a negotiated extension (io.modelcontextprotocol/ui) enabling servers to deliver interactive UIs via ui:// resources and standard MCP JSON-RPC messaging, with mandatory iframe sandboxing and auditable communication. Multiple hosts already support this extension: Claude, Claude Desktop, VS Code GitHub Copilot, Goose, Postman, MCPJam.

    This pushes MCP beyond tool calling into a standard for interactive human-agent workflows — forms, dashboards, mediated approvals — which may become the primary UX pattern for high-risk enterprise actions.

    Logging¶

    Servers can emit structured log messages at standard severity levels (debug, info, warning, error, critical, alert, emergency). The client can set the minimum log level via logging/setLevel. Log messages are sent as notifications and can include arbitrary JSON data.

    Integration Patterns¶

    Local Toolchain Augmentation (IDE-Centric)¶

    The most common pattern: local stdio servers installed by configuration (or via one-click install flows). IDEs manage starting/stopping servers, discovering tools, and optionally prompting for per-tool approvals. VS Code explicitly warns that local servers can run arbitrary code and adds trust prompts, tool toggles, and optional sandboxing.

    Remote MCP Servers as Shareable Apps (Consumer + Enterprise)¶

    OpenAI documents building remote MCP servers that surface private knowledge sources (e.g., a vector store) into ChatGPT as "data-only apps" (formerly connectors), including for deep research and company knowledge workflows. This pattern turns MCP servers into shareable, authenticated connectors rather than local dev tools.

    Managed Remote Servers by Cloud Vendors (Enterprise Ops)¶

    Google Cloud emphasizes managed remote MCP servers, claiming reduced developer burden vs community-built local servers and extending the concept via Apigee for governed enterprise API exposure. Cloudflare provides "stateless" vs "stateful per-session" reference architectures via Durable Objects per session. Microsoft is productizing Azure integration with 40+ service connectors.

    Tool Brokering and Filtering (Scale Control)¶

    Without tool filtering/search/indexing, "thousands of tools" becomes unmanageable for both latency and context-window reasons. OpenAI's Agents SDK treats MCP servers as tool providers with built-in patterns for caching list_tools(), filtering tool exposure (static allow/block lists or dynamic logic per run), and capturing MCP activity in traces. Anthropic's AAIF donation post explicitly references tool search and programmatic tool calling to optimize production-scale deployments.

    Developer Experience and Tooling¶

    Tooling Ecosystem¶

    • MCP Inspector: a visual testing tool with a browser UI plus a proxy bridging multiple transports (stdio, SSE, Streamable HTTP), with helpers for exporting configuration snippets (~9k GitHub stars)
    • MCP Bundles (.mcpb): package a local server + manifest for one-click installation in desktop apps; targets portability, end-user installation UX (auto-updates, variable configuration, curated directory)
    • MCP Registry: the official registry provides unopinionated metadata (server.json) pointing to code/binaries hosted on package registries; supports namespace management via DNS verification; intended as upstream "source of truth" feeding downstream marketplaces/aggregators. In preview since Sep 2025; warns about breaking changes/data resets pre-GA.

    Operational Friction Points¶

    Versioning and transport churn. The 2025-11-25 transport update (Streamable HTTP replacing HTTP+SSE) introduces real-world compatibility burdens. The spec includes backward-compat guidance and a required MCP-Protocol-Version header; servers may assume a fallback version if no header is provided. SDKs are adapting — e.g., OpenAI's Agents SDK labels SSE as legacy.

    Session management, state, and scaling. Streamable HTTP supports session IDs and resumable streaming. Stateful workflows reduce repeated setup costs but introduce session-hijack risk and operational complexity. Frameworks differ: LangChain's MultiServerMCPClient is stateless by default (fresh session per invocation), which simplifies lifecycle but can amplify latency and repeated discovery unless cached. Cloudflare explicitly separates stateless vs stateful patterns (including per-session Durable Objects).

    Observability and traceability. Production MCP use is distributed tool execution — you need visibility across host decisions, tool calls, tool outputs, and network calls. OpenAI's Agents SDK captures MCP activity in traces and calls out caching and tool-list latency as a first-order issue. VS Code offers server logs, restart controls, and trust resets — practical UX reflecting that MCP servers fail, hang, or misbehave in the wild.

    Empty outputs and null handling. The Python MCP layer in Microsoft's agent-framework now normalizes empty tool outputs to explicit JSON null instead of allowing blank placeholders to propagate into responses — a fix that prevents "no tool output found" errors from corrupting agent runs (GitHub issue #4677, Microsoft agent-framework, Mar 2026). This is a class of subtle failure: the tool executes successfully but returns nothing, and the absence of an explicit null causes downstream Azure 400 errors. Related validation now protects against duplicate tool names between clients and MCP servers, preventing silent tool override when composing tool sets across repositories.

    Lifecycle deadlocks in long-running workflows. Task ownership and lifecycle tweaks in the MCP core reduce deadlocks and timeouts that previously surfaced as provisioning or streaming hangs in long-running agent workflows. On the hosted side, sample builds for hosted agents now include Docker build fixes addressing experimental API warnings, improving CI reliability for isolated Docker sample builds (Microsoft agent-framework, Mar 2026).

    Key: After upgrading to post-Mar 14 SHAs, verify that empty tool outputs appear as null in handlers and that tool registries contain no name collisions. If HostedFileContent corruption persists, continue using REST file uploads as the fallback (issue #4646 remains active).

    Token Economics and Performance¶

    The Core Token Reality¶

    MCP standardizes how tools and context are connected, but the runtime loop still routes information through the model: tool discovery metadata → model decides tool calls → tool results returned → model incorporates results → repeat. The MCP client loads tool definitions into the model's context window, and intermediate results often pass through the model multiple times.

    Concrete example: for a 2-hour sales meeting transcript, copying content through tool calls can mean ~50,000 additional tokens, potentially exceeding context windows and increasing error likelihood from manual copying (Anthropic engineering blog).

    Token Consumption Patterns¶

    Pattern Why it burns tokens Example magnitude
    Tool catalogue inflation Tool definitions injected into model context; JSON Schemas are verbose A medium tool schema = 150–400 tokens; 50 tools can consume 7.5k–20k tokens before any work begins
    Large artifacts routed through model loop Results returned as text force the model to re-read, rewrite, and re-emit +50,000 tokens for a 2-hour transcript echoed into a CRM update (sourced, Anthropic)
    Binary-as-base64 in tool channel Base64 expands payload; tokenizers treat it as many tokens Spec supports image/audio + base64 in sampling/tool content; rarely viable beyond tiny artifacts
    Thinking/reasoning artifacts in tool results Some server outputs include hidden chain tags or verbose reasoning Real servers expose strip_thinking options to remove <think>…</think> tags explicitly to save tokens

    Mitigation Strategies¶

    Two complementary approaches emerging as best practice:

    1. Do more work outside the model loop: present MCP servers as code APIs so an execution environment can process large data and only send compact results back to the model — reducing context pressure and copying errors (Anthropic engineering blog)
    2. Reduce and target tool exposure: tool filtering and tool search prevent "thousands of tools" from becoming a context and latency disaster. OpenAI's Agents SDK bakes in tool filtering and list_tools() caching; Anthropic cites tool search and programmatic tool calling for production optimization

    Performance Bottlenecks¶

    • Tool discovery: repeated tools/list calls are latency hotspots with remote servers; OpenAI explicitly warns that every agent run calls list_tools() and provides a cache_tools_list option with invalidation hooks
    • Remote auth and metadata discovery: OAuth discovery adds extra HTTP fetches and can become a latency and SSRF risk surface if not bounded
    • Statefulness trade-off: stateful servers cut repeated setup but require session management (resumability, expiration, hijack mitigations) and often additional infrastructure

    Code Execution Pattern: MCP Servers as Code APIs¶

    The highest-leverage mitigation for MCP token overhead is presenting MCP servers as code APIs inside a sandboxed execution environment, rather than having the model make direct tool calls with results flowing through context each time. This pattern, documented by Anthropic's engineering team, achieves 98.7% token reduction in representative workflows (from ~150,000 tokens to ~2,000 tokens).

    The two problems this solves:

    1. Tool definition overhead — loading all tool definitions upfront can consume hundreds of thousands of tokens before the agent reads the user request
    2. Intermediate result copying — when agents retrieve data to pass between tools, the full call transcript flows through context twice; a 2-hour meeting transcript attached to a CRM record means ~50,000 additional tokens

    Architecture: file-per-tool with typed interfaces

    servers/
├── google-drive/
│   ├── getDocument.ts
│   └── index.ts
├── salesforce/
│   ├── updateRecord.ts
│   └── index.ts

    Each tool becomes a TypeScript file with typed interfaces and wrapper functions. Instead of sequential tool calls passing data through the model, agents write code:

    // Data stays in execution environment — never enters model context
const transcript = (await gdrive.getDocument({...})).content;
await salesforce.updateRecord({data: {Notes: transcript}});

    Key capabilities unlocked:

    Capability How It Works Impact
    Progressive disclosure Agent navigates filesystem to discover and load only needed tool definitions on demand Avoids upfront loading of entire tool catalogue
    Data filtering Agent writes code to transform large datasets (e.g., filter 10,000-row spreadsheet to 5 relevant rows) before results reach the model Dramatic token reduction for data-heavy workflows
    Control flow in code Loops, conditionals, and error handling execute in code rather than requiring repeated model evaluations Lower latency; fewer LLM round-trips
    Privacy preservation Intermediate results stay in the execution environment; PII can be automatically tokenized before model visibility, then restored for final tool calls Sensitive data never enters model context
    State persistence Agent can persist progress to files for resumption; enables reusable "skills" across sessions Avoids re-computation; builds institutional knowledge

    Trade-offs:

    • Requires a secure execution environment with sandboxing, resource limits, and monitoring
    • Higher implementation complexity than direct tool calls
    • Agent must be capable of writing correct code (increasingly viable with modern models)

    Key: The code execution pattern is not a workaround — it is the emerging production architecture for MCP at scale. Direct tool calls work for small tool surfaces; code execution is required when tool counts, data volumes, or privacy requirements exceed what fits comfortably in the context window. Cloudflare independently validated this approach, coining the term "Code Mode."

    Key: MCP can reduce integration engineering cost (N×M connector sprawl), but may increase runtime cost unless carefully designed. Make token economy an explicit design target, not an afterthought.

    Security, Privacy, and Governance¶

    Threat Model: What MCP Changes¶

    MCP increases the blast radius of an LLM surface by making it easy to wire the agent into file systems, developer platforms, SaaS APIs, and infrastructure. The spec is explicit: MCP enables "arbitrary data access and code execution paths," and implementers must treat tool descriptions/annotations as untrusted unless obtained from trusted servers.

    Five trust boundaries in any MCP deployment:

    1. User ↔ host UX
    2. Host ↔ model provider
    3. Host/client ↔ MCP server
    4. MCP server ↔ upstream APIs/data stores
    5. Software supply chain (server distribution channel)

    Concrete Threats and Mitigations¶

    Threat How it happens Mitigations
    Malicious MCP servers (supply chain) Installing a server package that exfiltrates data or runs arbitrary code. Real incident: malicious postmark-mcp package added a hidden BCC to exfiltrate email contents Treat servers as code execution; use trusted publishers; prefer curated registries; sandbox local servers; continuously scan dependencies
    DNS rebinding against local servers Remote websites interact with a locally-bound MCP server Streamable HTTP spec requires validating Origin headers; bind to localhost for local deployments
    OAuth token confusion / "token passthrough" MCP server accepts a token intended for another audience and forwards it Spec requires Resource Indicators (RFC 8707), token audience validation; explicitly forbids token passthrough
    Confused deputy in proxy servers Proxy uses static client IDs + consent cookies; attacker tricks flow to skip consent Per-client consent registries, strict redirect URI checks, CSRF protections, careful state cookie timing
    SSRF during auth metadata discovery Malicious server supplies internal URLs in metadata endpoints; client fetches them HTTPS-only in production; block private IP ranges (incl. 169.254.169.254); validate redirect targets; use egress proxies
    Session hijacking Stealing Streamable HTTP session IDs or abusing long-lived sessions Secure session ID handling; session expiration; transport-level encryption
    Cryptographic misuse inside MCP servers Developers implement ad-hoc crypto and get it wrong. A 2025 study scanned 9,403 servers: crypto logic found in 720, ~19.7% exhibiting misuses (leaked keys, insecure primitives) (arXiv, 2025) Use established crypto libraries; avoid rolling custom crypto; scan for misuse patterns
    Over-permissioned local execution Local servers get broad filesystem/network access by default VS Code supports sandboxing for stdio servers on macOS/Linux (filesystem/network allowlists); trust prompts and org policy controls
    Prompt injection via tool/results Tool outputs instruct the model to exfiltrate data or escalate actions Treat tool outputs as untrusted; constrain tools to least privilege and narrow schemas; require per-call approval for risky tools; validate outputs in the host

    Security Model Layers¶

    1. Transport-level: Stdio is inherently local (no network exposure). HTTP transports should use TLS and the MCP authorization framework (OAuth 2.1, PKCE, RFC 8707 resource indicators, token audience validation, no token passthrough).
    2. Capability negotiation: clients and servers declare only the capabilities they support — a server that doesn't declare tools cannot receive tool calls.
    3. Roots: clients control which filesystem paths servers can see.
    4. Human-in-the-loop: hosts should prompt users before executing sensitive tool calls. Tool annotations (destructiveHint, readOnlyHint) help UIs surface appropriate confirmation dialogs.
    5. Sampling control: when a server requests sampling, the client can modify, reject, or gate the request behind user approval.

    Key principle: The host application is always the trust boundary. MCP servers are untrusted by default; the host decides what to allow.

    Privacy and Governance¶

    The spec's security principles require explicit user consent before exposing user data to servers and prohibit transmitting resource data elsewhere without consent. In practice, privacy risks arise from:

    • Data flow ambiguity: a tool call can route sensitive data through (a) the LLM provider, (b) MCP server operators, and (c) upstream APIs; logs and traces can unintentionally persist secrets
    • Discovery-layer trust: the Registry is metadata-only and delegates scanning to package registries and downstream aggregators; it uses namespace authentication and DNS verification but does not itself guarantee code safety. Enterprises are explicitly advised to run private registries for private servers.

    Key: Treat MCP adoption as a security programme (publisher allowlists, attestations, scanning, approvals, audit) rather than a pure developer convenience feature.

    Configuration¶

    MCP servers are configured per-client. The standard pattern for desktop clients is a JSON config file:

    {
  "mcpServers": {
    "filesystem": {
      "command": "node",
      "args": ["/path/to/filesystem-server/build/index.js"],
      "env": {
        "ALLOWED_DIRECTORIES": "/Users/username/Documents"
      }
    },
    "database": {
      "command": "python",
      "args": ["/path/to/db-server/main.py"],
      "env": {
        "DATABASE_URL": "postgresql://localhost/mydb"
      }
    }
  }
}

    For Claude Desktop: ~/Library/Application Support/Claude/claude_desktop_config.json (macOS).

    For Claude Code: configured in .claude/settings.json or project-level .mcp.json files.

    MCP vs. Direct Function Calling¶

    Dimension Direct function calling (e.g., OpenAI tools) MCP
    Scope Tools defined inline in API request Tools, resources, and prompts as a protocol
    Discovery Static — defined at request time Dynamic — list + listChanged notifications
    Reusability Per-application Any MCP client can connect to any MCP server
    Data access Tool must fetch its own data Resources provide a separate, application-controlled data channel
    Server-initiated actions Not possible Sampling + elicitation let servers request LLM calls and user input
    Ecosystem Vendor-specific Open spec with growing ecosystem of pre-built servers

    MCP doesn't replace function calling — it builds on top of it. The client translates MCP tools into the underlying model's function-calling format. The value is in the standardized discovery, lifecycle, and multi-primitive model that function calling alone doesn't provide.

    Building MCP Servers¶

    TypeScript SDK¶

    import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import {
  CallToolRequestSchema,
  ListToolsRequestSchema,
} from "@modelcontextprotocol/sdk/types.js";

const server = new Server(
  { name: "my-server", version: "1.0.0" },
  { capabilities: { tools: {} } },
);

server.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [
    {
      name: "get_weather",
      description: "Get current weather for a location",
      inputSchema: {
        type: "object",
        properties: {
          location: { type: "string", description: "City name" },
        },
        required: ["location"],
      },
    },
  ],
}));

server.setRequestHandler(CallToolRequestSchema, async (request) => {
  if (request.params.name === "get_weather") {
    const location = request.params.arguments?.location;
    return {
      content: [{ type: "text", text: `Weather in ${location}: 65F, Sunny` }],
    };
  }
  throw new Error("Tool not found");
});

const transport = new StdioServerTransport();
await server.connect(transport);

    Python SDK¶

    from mcp.server import Server
from mcp.server.stdio import stdio_server
import mcp.types as types

server = Server("my-server")

@server.list_tools()
async def list_tools() -> list[types.Tool]:
    return [
        types.Tool(
            name="get_weather",
            description="Get current weather for a location",
            inputSchema={
                "type": "object",
                "properties": {
                    "location": {"type": "string", "description": "City name"}
                },
                "required": ["location"]
            }
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict) -> list[types.TextContent]:
    if name == "get_weather":
        return [types.TextContent(type="text", text=f"Weather in {arguments['location']}: 65F, Sunny")]
    raise ValueError(f"Tool not found: {name}")

async def main():
    async with stdio_server() as (read_stream, write_stream):
        await server.run(read_stream, write_stream)

    Design Patterns and Best Practices¶

    Server Design Patterns¶

    1. Single-responsibility servers — one server per integration (GitHub server, Postgres server, Slack server). Compose at the host level, not inside a mega-server.
    2. Thin wrappers over existing APIs — MCP servers should be adapters, not reimplementations. Wrap existing SDKs/CLIs.
    3. Use tool annotations — declare readOnlyHint: true for safe tools, destructiveHint: true for dangerous ones. This helps clients build trust UIs.
    4. Resource + tool combos — expose data via resources (for context injection) and actions via tools (for model-driven execution). Don't force everything through tools.
    5. Graceful degradation — handle disconnections, respect timeouts, implement proper error responses with JSON-RPC error codes.

    Adoption Best Practices¶

    These reflect current spec/security guidance and operational realities visible in vendor SDKs and IDE tooling:

    1. Start with strict scope minimization: expose fewer tools than you think you need; prefer read-only resources and narrowly-scoped tools; adopt allowlists and per-run dynamic filters
    2. Treat tool outputs as hostile inputs: validate, constrain schemas, and avoid "instructional" tool output that can override host policy; the spec explicitly warns that tool annotations/descriptions can be untrusted
    3. Make token economy an explicit design target: keep large data out of the model loop; return minimal structured summaries; use execution environments for heavy lifting; avoid base64 blobs in context
    4. Prefer Streamable HTTP for new remote deployments: align with the latest spec and SDK guidance to reduce future migration burden; keep SSE only for legacy
    5. Implement OAuth correctly or not at all: for HTTP transports, follow the authorization spec (OAuth 2.1, Protected Resource Metadata, PKCE, RFC 8707 resource indicators, token audience validation; prohibit token passthrough)
    6. Harden discovery and distribution: use curated registries/marketplaces, publisher verification, dependency scanning, and sandboxing for local servers; assume supply-chain attacks will target MCP servers because of their permissions
    7. Operate MCP like a distributed system: add tracing/logging, cache tool lists when safe, and plan for upgrades (protocol versions, transport changes, extension negotiation)

    MCP Maturity Lifecycle¶

    MCP has moved from hype to infrastructure. The pattern is standard for successful protocols:

    Phase Status (early 2026) Evidence
    1. Launch Complete Nov 2024 public release; spec + SDKs
    2. Hype Past peak Widespread "USB-C for AI" framing; demo-driven excitement
    3. Security/governance headaches Active OAuth 2.1 hardening; auth for remote servers; phishing/token-leakage risks identified; enterprise trust questions
    4. Abstraction into products Underway OpenAI Apps SDK builds on MCP; MCP Apps push conversation toward UI/UX; products and registries sit in front of the protocol
    5. Boring but durable adoption Emerging 10,000+ public servers; ChatGPT, Cursor, Gemini, Copilot, VS Code support; Linux Foundation governance

    Why MCP gets less attention now:

    • Mindshare moved up the stack. Once MCP became plumbing, discourse shifted to the product layer: Apps SDK, agent UX, deployment workflows. People use the capability without naming the protocol.
    • Adjacent standards diluted the spotlight. Google's A2A protocol (agent-to-agent coordination) split the narrative — MCP for tools/context, A2A for agent coordination. Complementary, but they divide attention.
    • Security reality hit the hype. Moving from local demos to remote enterprise use made auth and trust the hard part. The roadmap is now enterprise-hardening (governance, transport scalability, working groups), not novelty.
    • No new spec since Nov 2025. Not stagnation — consolidation. But it reduces headline frequency.

    By March 2026, the "MCP is dead" discourse surfaced on Twitter, but the backlash was about ergonomics, not demand — @pamelafox joked MCP was "pronounced dead after mass exposure to curl," even as usage continued to boom (@pamelafox, Latent Space AINews, Mar 2026). The more substantive debate crystallized around the MCP-vs-skills architectural split: LlamaIndex drew the distinction that MCP tools are strongest when you need deterministic, centrally maintained APIs and rapidly changing ground truth, while skills are lighter-weight local natural-language procedures but more failure-prone (LlamaIndex, Mar 2026). This split is becoming a real decision point for agent builders choosing how to expose capabilities. Meanwhile, Chrome v146 added web MCP support, with a demo showing a LangChain Deep Agent continuously browsing X and compiling daily summaries — extending MCP's reach into the browser runtime (@tadasayy, @bromann, Latent Space AINews, Mar 2026).

    The MCP skepticism sharpened further in mid-March 2026. skirano bluntly declared "MCP was a mistake. Long live CLIs." (skirano, Mar 2026), while denisyarats joked about a "model CLI protocol" — both pointing at the same underlying tension: MCP's protocol overhead may be unnecessary when agents can simply invoke CLIs directly (denisyarats, Mar 2026). This is not a fringe position; it represents a visible counter-narrative that CLI-based tool integration is simpler, more composable, and already battle-tested, while MCP adds abstraction layers whose benefits are unclear for many local-first workflows. The counter-argument remains that CLIs lack standardized discovery, schema negotiation, and auth — exactly the things MCP provides for remote and multi-vendor scenarios. The debate tracks the broader pattern: MCP's value proposition is strongest in remote, multi-tenant, enterprise contexts and weakest in single-developer, local toolchain setups where a shell script suffices.

    Key: "MCP is getting less attention because it is becoming more real." The adoption signal remains strong (10,000+ servers, multi-vendor backing, major platform integration). Less hype should not be confused with decline.

    What MCP does NOT solve: MCP standardizes tool/data connectivity but does not solve evals, memory boundaries, auth end-to-end, observability, orchestration, or agent-to-agent coordination. Once teams realize they still need all of these, the "MCP is the whole answer" excitement naturally drops. That is a sign of maturation, not failure.

    Token-Efficient MCP: Operational Best Practices¶

    The "MCP burns context window" criticism is valid — but the problem is usually naïve client patterns, not the protocol itself. Both OpenAI and Anthropic have published concrete mitigations.

    The two token sinks:

    1. Tool definitions — MCP tools include names, descriptions, and JSON schemas. A medium tool schema costs 150–400 tokens; a server with 50 tools can consume 7.5k–20k tokens before any work begins. Many clients load all definitions up front, overloading the context window.
    2. Intermediate tool results — many clients pass intermediate tool outputs back through the model each step. A long transcript can add 50,000+ tokens. Tool definitions and results can sometimes consume 50,000+ tokens before an agent even reads the user request.

    Is this inherent to MCP? Partly. The MCP spec has mechanisms for selective loading (tools/list supports pagination; resources are separately listed/read). The inefficiency appears when clients choose the simple pattern: "list all tools, inject all schemas, loop all results through the LLM."

    Practical thresholds:

    Scale Approach Token Impact
    1–10 tools, concise schemas Direct loading; usually fine Low overhead
    10–30 tools Filter with allowed_tools; cache stable definitions Manageable with discipline
    50+ tools or large data payloads Deferred loading + tool search + code execution Naïve MCP gets expensive fast without these

    Operational checklist for token-efficient MCP:

    Key -- MCP Token Efficiency Checklist:

    • Split servers by task domain — one server per integration, not one mega-server
    • Keep tool descriptions concise — put extended examples in system prompt, not in tool description fields
    • Use allowed_tools whenever task scope is known — prevents loading irrelevant tool definitions
    • Use deferred loading / tool search for broad tool inventories — load definitions only as needed
    • Cache stable tool definitions — tool schemas rarely change; cache them across runs
    • Do transformation outside the model — fetch/filter/aggregate in code execution, return only distilled results to the model
    • Never pipe large raw artifacts through the model — use resource handles, filtered extracts, or server-side summarization
    • Strip thinking/reasoning artifacts — remove <think>…</think> tags from server outputs to save tokens

    The deeper insight: MCP exposed that raw LLM-mediated tool orchestration is often the wrong abstraction at scale. MCP is fine as a standardized discovery and invocation layer. It becomes ugly when the model itself serves as the router, data pipe, planner, and transformer for every step. The serious pattern is: MCP + harness/runtime discipline — the protocol for connectivity, the runtime for efficiency.

    Real-world adoption of MCP: India's Ministry of Statistics (MoSPI) launched an MCP server to connect AI tools with government statistical data — a concrete example of MCP being used for authoritative, structured data access in production government contexts (Economic Times, 2026).

    Protocol Versioning and Outlook¶

    Versioning¶

    MCP uses date-based versioning (e.g., 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25). Each version is a full spec revision. Version negotiation happens during initialization — the client proposes its latest, the server responds with its latest, and they must agree or disconnect.

    Key version milestones:

    • 2024-11-05: Initial public release. Stdio + HTTP+SSE transports. Tools, resources, prompts, sampling.
    • 2025-03-26: Streamable HTTP transport (replaces HTTP+SSE). Tool annotations. OAuth 2.1 authorization framework.
    • 2025-06-18: Elicitation (form + URL modes). Structured tool output. Audio content type.
    • 2025-11-25: Tasks (long-running operations). Enhanced capability negotiation. Completion and validation improvements.

    Extensions System¶

    MCP now has a formal extensions mechanism with vendor prefixes: official extensions use io.modelcontextprotocol; third parties use reversed domains. Official extensions include OAuth client credentials and enterprise-managed authorization frameworks. The existence of this layered model (small core + optional capabilities) signals convergence toward a sustainable, extensible architecture rather than a monolith.

    Outlook¶

    Grounded trends (strong evidence in 2025–early 2026 releases):

    • Managed MCP servers will expand: Google Cloud, Cloudflare, and Microsoft have already positioned MCP servers as managed infrastructure; first-party doc servers are proliferating
    • Security hardening will continue: Streamable HTTP tightened Origin validation; OAuth requirements now explicitly include PKCE and resource indicators; real incidents and research (cryptographic misuse study, supply-chain attacks) keep pressure on defaults and scanning
    • Tool scalability work is becoming first-class: caching, tool filtering, tool search, and programmatic calling are being treated as necessary for "thousands of tools" scenarios

    Emerging category — headless SaaS / agent-native enterprise apps. ivanburazin describes a new wave of headless SaaS — traditional enterprise software rebuilt as agent-first APIs with no human UI (ivanburazin, Mar 2026). The thesis: if the primary consumer of a SaaS product is an agent rather than a human, the product should ship an API (or MCP server) as the primary interface, not a dashboard. This aligns with concrete product launches: Rippling's AI analyst (agent-driven HR/finance queries), Anthropic's Claude for Excel/PowerPoint (agent-as-office-tool), and the observation that meeting-notes apps are quietly becoming broader AI context/data apps whose real value is structured data extraction for downstream agents (zachtratar, Mar 2026). MCP is a natural delivery mechanism for headless SaaS — the server exposes the product's capabilities as tools and resources, and agents consume them without a browser in the loop. This pattern could accelerate MCP adoption in enterprise contexts where the "server" is not a developer tool but the product itself.

    Speculation (clearly flagged): If MCP continues to attract cloud-vendor managed endpoints, the ecosystem may split into (a) local-first workflows for developer productivity and private data, and (b) governed remote workflows for enterprise automation, where the MCP server becomes a policy-enforcing gateway (auth, rate limits, auditing, PII controls) rather than a thin tool wrapper. This would mirror the evolution of APIs from library calls to API gateways — especially given Google's explicit Apigee positioning.
