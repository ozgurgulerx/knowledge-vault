    Agent Memory Architecture¶

    Opening Briefing¶

    The defining gap in multi-agent systems is not reasoning quality but memory management — how agents store, retrieve, share, and forget information across turns, sessions, and collaborators. Most current frameworks treat memory as a black-box vector store or an ever-growing context window. The more productive framing is memory as a systems architecture problem: cache hierarchies, coherence protocols, bandwidth constraints, and eviction policies — the same concerns that govern CPU memory subsystems, applied to agents that must coordinate over shared knowledge.

    The practical consequence is that memory is becoming the differentiator for agent quality, not model selection. Systems that extract reusable strategies from trajectories, enforce coherence across agents, and tier persistence by access pattern will outperform systems that simply stuff more tokens into the context window.

    Market behaviour in early 2026 confirms this thesis. Integrators building multi-agent orchestration services — agent routing layers, task decomposition engines, cross-agent coordination — are finding that their systems remain mostly prompt-based and weak on shared state. The gap is conspicuous: no strong persistent context layer exists across agents in production. Orchestration frameworks can dispatch and sequence, but the agents they coordinate operate with no durable shared memory, rediscovering context on every invocation and losing inter-agent state between sessions. This makes graph-structured memory — where relationships, decisions, and learned context persist across agents and sessions — a structural wedge for any system that positions itself as the state layer for multi-agent coordination.

    Memory as Computer Architecture — The Hierarchy Model¶

    The most rigorous framing treats multi-agent memory as a direct analogue to CPU cache architecture, with explicit latency tiers, bandwidth constraints, and coherence requirements (Zhongming Yu et al., "Multi-Agent Memory from a Computer Architecture Perspective," Architecture 2.0 Workshop, Mar 2026).

    Three-Tier Hierarchy¶

    • L1 (agent-local) — individual working memory and immediate task context. Fast, volatile, session-bound. Analogous to L1 cache: small, low-latency, private to one agent.
    • L2 (shared inter-agent) — conversation history, interaction artifacts, and coordination state between collaborating agents. Shared but bounded. Analogous to L2/L3 cache: larger, moderate latency, coherence-managed.
    • L3 (global-persistent) — long-term knowledge bases, learned patterns, consolidated insights across all sessions and agents. Slow but durable. Analogous to main memory or disk-backed storage.

    Four Memory Types¶

    Orthogonal to the hierarchy, agent memory divides into functional types:

    • Working memory — short-term context and current task state
    • Episodic memory — timestamped interaction records and decision histories
    • Semantic memory — consolidated knowledge and learned generalisations
    • Procedural memory — reusable patterns, tool-use strategies, and execution recipes

    Access Patterns¶

    Memory retrieval strategies map to three dimensions:

    • Recency-based — temporal proximity (most recent interactions first)
    • Relevance-based — semantic similarity (embedding-driven retrieval)
    • Frequency-based — usage patterns (most-accessed knowledge surfaces first)

    Scope¶

    Memory further segments by scope: individual (private to one agent), shared (between collaborating agents), and system-wide (global knowledge repositories). By persistence: volatile (session-bound), persistent (cross-session), and archived (historical reference, compressed).

    Coherence and Coordination¶

    The hardest unsolved problem in multi-agent memory is coherence — ensuring that when one agent updates shared knowledge, other agents see the update rather than operating on stale cached state. The computer architecture analogy is direct: cache coherence protocols (MESI, MOESI) solve this for CPUs, but no equivalent standard exists for agents yet.

    Architecture Concepts Applied to Agents¶

    CPU Architecture Concept Agent Memory Application
    Cache hierarchy Multi-tier memory (working / shared / persistent)
    Coherence protocols Ensuring agents see consistent, up-to-date knowledge
    Bandwidth limitations Communication overhead between agents sharing memory
    Locality of reference Grouping related agent interactions to reduce memory traffic
    Eviction policies Determining what to forget when memory is full
    False sharing Multiple agents unnecessarily contending for the same memory region
    Write-back vs write-through Deferred vs immediate propagation of memory updates

    Open Problems¶

    1. How to achieve consensus on shared memory updates across asynchronous agents?
    2. What memory capacity is truly necessary for competent long-horizon behaviour?
    3. How does memory architecture choice affect emergent multi-agent behaviours?
    4. Can CPU coherence protocols transfer directly to distributed agent systems, or do they need fundamental redesign?

    Empirical Evidence: Memory Improves Agent Performance¶

    IBM trajectory memory — extracting reusable strategy, recovery, and optimisation tips from agent trajectories improved AppWorld task completion from 69.6% to 73.2% and scenario goals from 50.0% to 64.3%, with the biggest gains on hard tasks. The mechanism: agents that remember what worked (and what failed) in prior runs avoid repeating mistakes and reuse successful strategies (@dair_ai, IBM, Latent Space AINews, Mar 2026).

    Hermes Agent — a self-hostable agent that retains skills and user-specific memory over time, demonstrating the product value of persistent procedural + episodic memory (@abxxai, @Teknium, Latent Space AINews, Mar 2026). By April 2026, Hermes Agent hit a major usage milestone and expanded its memory integrations to multiple providers via a new pluggable memory system, validating the thesis that memory architecture — not model choice — is the differentiating layer for persistent agents (Teknium, AINews Apr 2026).

    Enzyme (local semantic index) — a plugin pitched as solving the "too many workspace files" problem by providing local embedding-based semantic search with 8ms query latency. Enzyme represents the emerging pattern of lightweight, local-first memory layers that give agents fast semantic access to large workspaces without requiring cloud round-trips or heavyweight vector database infrastructure (jphorism, AINews Apr 2026).

    Key: The IBM result is significant because it shows memory as a performance lever independent of model quality — the same model with better memory management scores materially higher, especially on the hardest tasks where accumulated experience matters most.

    Practical Implications for System Design¶

    For agent framework builders:

    • Dedicate infrastructure for inter-agent memory. Shared memory layers require explicit synchronisation protocols — treating shared state as "just another context window" will produce coherence failures at scale.
    • Implement tiered persistence. Hot data (recent interactions) in fast-access layers; cold data (historical context) in slower, compressed storage. Not all memories deserve the same retrieval latency.
    • Design coherence protocols. Agents must invalidate cached knowledge when peers update shared facts. Without this, multi-agent systems silently degrade as agents diverge.
    • Optimise communication patterns. Minimise unnecessary memory traffic through locality-aware scheduling — place frequently communicating agents together.

    For evaluation:

    • Evaluate agents not just on task accuracy but on memory efficiency — operations per solution.
    • Test long-horizon tasks where memory management becomes the bottleneck.
    • Measure multi-agent memory contention and coherence overhead.

    For production deployment:

    • Monitor memory access patterns to predict system bottlenecks before they manifest.
    • Dynamically adjust tier boundaries based on observed agent behaviour.
    • Implement memory compression for agents with different temporal requirements.

    Hierarchical Memory RAG¶

    The convergence of agent memory and retrieval-augmented generation is producing hierarchical memory RAG architectures that tier memory by temporal scope and access pattern, mirroring the L1/L2/L3 hierarchy but mapped to RAG-specific storage layers:

    • Short-term (session context) — the current conversation and working state, held in the context window or a fast volatile store. Equivalent to L1 — immediate, high-bandwidth, session-scoped.
    • Mid-term (vector DB) — recent interactions, retrieved documents, and intermediate reasoning artifacts persisted in a vector store for cross-turn retrieval within a session or across recent sessions. Equivalent to L2 — semantic search over recent knowledge.
    • Long-term (graph / compressed memory) — consolidated knowledge, entity relationships, and distilled insights stored in a knowledge graph or compressed memory format. Equivalent to L3 — slow but comprehensive, spanning the full history of the agent's interactions.

    This hierarchy represents the practical convergence point of agents and RAG: the agent's memory system is its retrieval system, and retrieval quality depends on how well the system manages promotion, eviction, and consolidation across tiers. Short-term context feeds mid-term storage via embedding; mid-term knowledge consolidates into long-term graph structures through periodic extraction and summarization. The key design challenge is the consolidation policy — when and how to promote episodic memories into semantic knowledge and graph structure without losing critical detail (arXiv, 2025–2026 on hierarchical memory RAG).
