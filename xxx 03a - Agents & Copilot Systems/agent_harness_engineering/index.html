    Agent Harness Engineering¶

    See also: LLM Agentic Systems | AI Engineering Practices | Claude Code Expert Guide

    Opening Briefing¶

    An agent harness is the control system around an agent, not the agent itself. The cleanest definition: Agent = Model + Harness. If you're not the model, you're the harness (LangChain, "Anatomy of an Agent Harness", Mar 2026). A harness is every piece of code, configuration, and execution logic that isn't the model itself — system prompts, tools and their descriptions, bundled infrastructure (filesystem, sandbox, browser), orchestration logic (subagent spawning, handoffs, model routing), and hooks/middleware for deterministic execution (compaction, continuation, lint checks). A raw model is not an agent; it becomes one when a harness gives it state, tool execution, feedback loops, and enforceable constraints.

    Most people who say "agent harness" really mean one of three narrower things — a chat assistant with tools, a workflow engine with LLM steps, or a multi-agent orchestration pattern. A real harness is broader: the engineering envelope around all three. The design methodology is to work backwards from desired agent behaviour to harness features: identify what the model cannot do out of the box (maintain durable state, execute code, access real-time knowledge, set up environments) and convert each gap into a harness-level capability.

    Key: The strongest empirical evidence that harness engineering matters more than model selection: LangChain reports a +13.7 point improvement (52.8 → 66.5) on Terminal-Bench 2.0 by changing ONLY the harness, keeping the model fixed (LangChain, early 2026). The improvement came from a disciplined loop: analyse traces → add middleware (build→verify→fix loops, pre-completion checklists) → rerun evals. Terminal-Bench 2.0 itself (Jan 2026) operationalises harness choice as an experimental variable across 89 tasks and 32,155 trials.

    The "Model-Harness Training Loop" thesis is gaining traction as a corollary: open models combined with execution traces and fine-tuning infrastructure create a virtuous cycle where harness improvements generate training signal for better models, which in turn enable more sophisticated harnesses (Vtrivedy10, AINews Apr 2026). LangChain notes that open models are now "good enough" at tool use, retrieval, and file operations to drive harnesses like Deep Agents — meaning the binding constraint has shifted decisively from model capability to harness quality (hwchase17, AINews Apr 2026). Self-healing agent feedback loops — where GTM agents automatically correct based on runtime failures — represent the next evolution of harness-level intelligence, closing the gap between evaluation and remediation within the harness itself (hwchase17, Vtrivedy10, AINews Apr 2026). On the infrastructure side, LangSmith reports that Azure's share of OpenAI traffic rose from 8% to 29% over 10 weeks based on 6.7 billion agent runs, suggesting that enterprise governance and compliance requirements are driving routing decisions at the harness level — further evidence that the harness (including deployment topology and policy enforcement) matters as much as the model (LangChain, AINews Apr 2026).

    This view is now widely shared. The Turing Post's interview with Michael Bolin frames coding agents as a problem of tools, repo legibility, constraints, and feedback loops — what many now call harness engineering — rather than a problem of model capability (Michael Bolin, Turing Post, Mar 2026). dbreunig made a similar point about why teams stick with DSPy: the value is in the harness abstractions, not the underlying model. nickbaumann argued that GPT-5.4 mini matters specifically because cheap, fast subagents change the economics of delegation — when model costs drop, the set of tasks worth delegating to a subagent expands, making harness-level orchestration decisions (what to delegate, how to compose results) the binding constraint rather than model price (nickbaumann, Mar 2026).

    The Six-Layer Harness Model¶

    A production harness decomposes into six distinct layers (Microsoft Learn, Mar 2026):

    1. Entry/control plane — API gateway, chat UI, or event trigger that initiates the workflow
    2. Router/orchestrator — decides which agent, tool, or pattern handles each request
    3. Execution layer — one agent or multiple agents in sequential, concurrent, handoff, or maker-checker patterns
    4. Tool layer — OpenAPI endpoints, functions, MCP tools, databases, retrieval systems
    5. State + policy layer — session memory, approval gates, retry limits, budget/timeouts, content policy
    6. Evidence layer — traces, evals, run logs, quality metrics

    Key: The six layers are a diagnostic tool, not a deployment checklist. If your system is missing a layer, you have a gap — but not every layer needs to be elaborate. A thin policy layer with hard timeout caps and a budget ceiling is often enough; a thin evidence layer with structured logging is better than none.

    Guarded Agents: Four-Stage Execution Pipeline¶

    A more granular pattern is emerging within the execution layer specifically: guarded agents that split execution into a four-stage pipeline with explicit policy enforcement between planning and action:

    1. Planner — the LLM generates an intent or action plan
    2. Validator — constraint validators and tool-call filters check the plan against policy (allowlists, budget caps, safety rules) before any execution occurs
    3. Executor — approved actions are dispatched to tools
    4. Auditor — post-execution verification scores outputs and triggers rollback strategies on policy violations

    This pattern maps onto the six-layer model (the validator draws from layer 5's policy engine; the auditor feeds layer 6's evidence layer) but makes the separation mandatory and sequential rather than advisory. The key benefit is reducing cascading failures — a bad plan is caught at the validator stage before it triggers tool calls, and a bad execution is caught at the auditor stage before results propagate to the next agent step. Teams adopting this pattern report that the validator alone eliminates a significant class of agent failures (hallucinated tool calls, out-of-scope actions, budget-exceeding plans) that previously required post-hoc cleanup (emerging agent architecture patterns, 2026).

    Sandbox Architecture: Agent-in-Sandbox vs Sandbox-as-Tool¶

    Two dominant patterns for isolating agent execution, with distinct tradeoffs:

    Agent-in-sandbox — the agent process runs inside the container/VM. Mirrors a remote dev environment. Tradeoffs: credentials must be placed inside the sandbox (broader blast radius on compromise); iteration is slower due to image rebuilds; all agent code runs with container-level privileges.

    Sandbox-as-tool — the agent runs outside; the sandbox is invoked as a tool for code execution. Tradeoffs: API keys stay outside the sandbox (better security boundary); faster harness iteration; but network latency on every execution call, requiring careful session design to avoid excessive round trips.

    A third option is emerging: hosted shells (provider-managed sandboxes) such as OpenAI's container_auto shell tool and Microsoft's hosted shell environments. These shift sandbox lifecycle management to the provider but reduce control over the execution environment.

    Key: The choice is not "sandbox or not" — it's where the trust boundary sits. If the agent has shell access, something must be sandboxed. The question is whether the agent lives inside or outside that boundary.

    Tool-Surface Scaling Patterns¶

    "Static tool schemas loaded at agent start" is becoming an anti-pattern for large tool ecosystems. Three scaling patterns are converging:

    1. Lazy loading via tool search / namespaces — tools and MCP servers are registered but their parameter schemas are deferred until the agent actually needs them. OpenAI's tool_search with defer_loading: true is the canonical example. Guidance: keep namespaces small (OpenAI Agents SDK, early 2026).

    2. Skills / progressive disclosure — only skill metadata (name + one-line description) loads at startup; full instructions, tool subsets, and resources load on activation. The Agent Skills spec (SKILL.md with YAML frontmatter) standardises this pattern. Skills are solidifying as a shared abstraction across agent stacks. Practical usage patterns now include progressive disclosure, trace inspection, session distillation, CI-triggered skills, and self-improving skills (mstockton, Mar 2026). Anthropic's Claude Code team clarifies that a skill is not just a text snippet but a folder with scripts, assets, and data, and that the key description field should specify when to trigger it, not just what it does (Anthropic Claude Code, Mar 2026). On the distribution side, RhysSullivan suggests that distributing skills via MCP resources may solve staleness and versioning problems, since MCP already provides a protocol for dynamic resource discovery (RhysSullivan, Mar 2026).

    3. Bounded tool growth — research harness architectures explicitly call out that unbounded MCP discovery can consume large fractions of the context budget. The fix: retrieval-style tool selection surfaces with trace-informed pruning of rarely-used tools.

    4. Agent control flow as state machine — a quiet but important shift: teams are formalizing agent behavior as explicit state machines rather than relying on free-form reasoning chains. The pattern is state → allowed actions → transition rules → next state, with transitions enforced via code, not prompt. A research agent, for example, moves through search → extract → synthesize → validate states, each with a constrained action set and deterministic transition conditions. Benefits: debuggability increases dramatically, eval becomes deterministic (you can test each state independently), and patching a broken behavior is a targeted state/transition fix rather than a prompt rewrite that risks destabilizing unrelated behaviors. Under this framing, prompts become local policies within states — they govern how the model behaves in a given state, but do not control the overall flow (synthesized from agent system design research + operator discussions, 2025–2026). A specific technique within this pattern is logit masking (mask, don't remove): Manus's production experience validates that dynamically adding or removing tools mid-iteration is counterproductive for two reasons — it invalidates the KV-cache (tool definitions sit near the front of the serialized context), and previous action-observation pairs referencing now-undefined tools confuse the model into schema violations or hallucinated actions. The fix: keep all tools present but use a context-aware state machine that masks token logits during decoding to prevent or enforce selection of specific actions. In practice, most providers support response prefill as the mechanism, with three modes: Auto (model may or may not call a function — prefill only the reply prefix), Required (model must call a function — prefill up to the tool call token), and Specified (model must call from a subset — prefill up to the function name prefix, e.g., {"name": "browser_"). Manus deliberately designs action names with consistent prefixes — all browser tools start with browser_, command-line tools with shell_ — enabling group-level enforcement without stateful logits processors (Yichao 'Peak' Ji, Manus, Jul 2025).

    5. Tool reliability scoring and dynamic fallback — production agent stacks are adding a new component: per-tool reliability tracking. For each tool, the harness records success rate, latency distribution, and failure modes over time. This data feeds routing decisions: if tool_A reliability < threshold → fallback to tool_B. The result is dynamic tool selection that improves robustness — tools are no longer binary (available/unavailable) but probabilistic, with the harness treating tool availability as a confidence-weighted signal rather than a boolean. This complements the tool registry and tool router modules (Modules 3–4 in the Component Catalogue) by adding a runtime quality dimension to the static schema layer (synthesized from agent system design research + operator discussions, 2025–2026).

    Key: The direction of travel is clear — just-in-time tool/context loading based on current state, not fixed tool menus. Expect "static tool schemas at agent start" to be viewed as a baseline anti-pattern within the next year. State machines provide the control structure; tool reliability scoring provides the runtime quality signal.

    Context Rot and Harness Countermeasures¶

    Context rot describes how agent performance degrades as the context window fills — models become worse at reasoning and completing tasks as accumulated tool outputs, conversation history, and stale instructions crowd out useful signal. Context is a precious and scarce resource, making harnesses fundamentally delivery mechanisms for good context engineering (LangChain, "Anatomy of an Agent Harness", Mar 2026).

    Three harness-level strategies address context rot:

    1. Compaction — when context approaches capacity (~85% threshold), the harness summarises and offloads the existing window so the agent can continue working. Without compaction, the API errors or the agent loses coherence. See the dedicated prompt caching section below for cache-safe compaction design.

    2. Tool-call offloading — large tool outputs noisily clutter context without providing useful information. The harness keeps only the head and tail tokens of outputs above a threshold and offloads the full result to the filesystem for on-demand access.

    3. Skills / progressive disclosure — too many tools or MCP servers loaded into context on agent start degrades performance before the agent begins working. Skills solve this by loading only metadata (name + one-line description) at startup; full instructions and tool subsets load on activation. The model didn't choose to have all tool schemas in context — the harness protects it via just-in-time loading.

    SkillNet extends the skills concept to an open infrastructure for creating, evaluating, and organising AI skills at scale. It structures skills within a unified ontology supporting creation from heterogeneous sources, rich relational connections, and multi-dimensional evaluation across Safety, Completeness, Executability, Maintainability, and Cost-awareness (SCEMCE). On ALFWorld, WebShop, and ScienceWorld, SkillNet improves average rewards by 40% and reduces execution steps by 30% across multiple backbone models (arXiv, Mar 2026).

    The Filesystem as Foundational Primitive¶

    The filesystem is arguably the most foundational harness primitive because of what it unlocks as derived capabilities: agents get a workspace to read data, code, and documentation; work can be incrementally offloaded instead of holding everything in context; intermediate outputs persist across sessions; multiple agents and humans coordinate through shared files (the basis of Agent Teams architectures); and git adds versioning so agents can track work, roll back errors, and branch experiments. The filesystem also enables memory — harnesses support memory file standards like AGENTS.md or CLAUDE.md that get injected into context on start, creating a form of continual learning where agents durably store knowledge from one session and inject it into future sessions (LangChain, "Anatomy of an Agent Harness", Mar 2026).

    Manus takes the filesystem further, treating it as the ultimate context — unlimited in size, persistent, and directly operable by the agent. The critical design principle: all compression strategies must be restorable. A web page's content can be dropped from context as long as the URL is preserved; a document's body can be omitted if its sandbox path remains available. This allows the agent to shrink context length aggressively without permanently losing information — any dropped content can be re-read on demand. The distinction matters: irreversible compression carries risk because you cannot predict which observation might become critical ten steps later, but restorable compression (drop content, keep reference) is safe by construction (Yichao 'Peak' Ji, Manus, Jul 2025).

    Attention Manipulation Through Recitation¶

    A complementary strategy to compaction and offloading is recitation — deliberately rewriting a structured plan (e.g., a todo.md file) at the end of the context on each iteration so that the agent's global objectives remain in the model's recent attention span. At Manus, a typical task requires ~50 tool calls on average, making the agent vulnerable to drifting off-topic or forgetting earlier goals. By continuously updating a todo list and checking off completed items, the agent pushes the global plan into the most-attended positions, avoiding "lost-in-the-middle" degradation and reducing goal misalignment — without architectural changes to the model. This is effectively natural-language attention biasing through context placement (Yichao 'Peak' Ji, Manus, Jul 2025).

    Error Retention as Context Signal¶

    A common but counterproductive impulse is to clean up failed actions — retrying, resetting state, or removing error traces from context. This erases evidence the model needs to adapt. Manus's production experience shows that leaving wrong turns in context is one of the most effective ways to improve agent behaviour: when the model sees a failed action and the resulting stack trace or error observation, it implicitly shifts its prior away from similar actions, reducing repeated mistakes. Error recovery is one of the clearest indicators of true agentic behaviour, yet it remains underrepresented in benchmarks that focus on task success under ideal conditions (Yichao 'Peak' Ji, Manus, Jul 2025).

    The Few-Shot Trap¶

    Few-shot prompting can backfire in agentic loops. When context accumulates many similar action-observation pairs — e.g., processing a batch of 20 resumes — the model mimics the pattern even when it's no longer optimal, leading to drift, overgeneralization, or hallucination. The fix: introduce structured variation in actions and observations — different serialization templates, alternate phrasing, minor noise in order or formatting. This controlled randomness breaks the repetition pattern and keeps the model's attention responsive to actual task state rather than surface-level pattern matching. The more uniform the context, the more brittle the agent becomes (Yichao 'Peak' Ji, Manus, Jul 2025).

    The Ralph Loop¶

    The Ralph Loop is a harness pattern for multi-session continuation: a hook intercepts the model's exit attempt and reinjects the original prompt in a clean context window, forcing the agent to continue working against a completion goal. The filesystem makes this possible — each iteration starts with fresh context but reads durable state from the previous iteration. This addresses the failure mode where agents prematurely declare tasks complete or lose coherence after context fills (LangChain, "Anatomy of an Agent Harness", Mar 2026).

    Prompt Caching as Harness Architecture¶

    Long-running agentic products are made feasible by prompt caching — reusing computation from previous roundtrips to decrease latency and cost. The KV-cache hit rate is arguably the single most important metric for a production-stage AI agent, directly affecting both latency and cost. Agent loops are heavily skewed toward prefilling: at Manus, the average input-to-output token ratio is 100:1, making cache efficiency the dominant cost driver. With Claude Sonnet, cached input tokens cost $0.30/MTok versus $3/MTok uncached — a 10× difference (Yichao 'Peak' Ji, Manus, Jul 2025). At Claude Code, the entire harness is built around prompt caching from day one: a high cache hit rate directly enables more generous rate limits on subscription plans, and the team runs alerts on cache hit rate and declares SEVs if it drops too low (Anthropic, Claude Code team, Mar 2026).

    The core mechanism: the API caches everything from the start of the request up to each cache_control breakpoint via prefix matching. Any change anywhere in the prefix invalidates everything after it. This single constraint drives the entire harness design.

    Prompt Layout for Maximum Cache Reuse¶

    Order matters — static content first, dynamic content last. Claude Code's layout:

    1. Static system prompt & tools — globally cached across all users and sessions
    2. CLAUDE.md — cached within a project
    3. Session context — cached within a session
    4. Conversation messages — new per turn

    This maximises shared prefix length across sessions. The ordering is surprisingly fragile — the Claude Code team has broken caching by putting detailed timestamps in the static system prompt, shuffling tool definitions non-deterministically, and updating tool parameters (e.g. which agents the AgentTool can call) (Anthropic, Claude Code team, Mar 2026).

    Use Messages, Not Prompt Mutations¶

    When information in the prompt becomes stale (e.g. the current time, or a file the user changed), updating the system prompt causes a cache miss across the entire prefix. The solution: pass updates via messages in the next turn instead. Claude Code injects <system-reminder> tags in user messages or tool results with updated information, preserving the cached prefix while keeping the model informed.

    Never Change Tools or Models Mid-Session¶

    Two of the most common ways to break prompt caching:

    Tool changes — adding or removing a tool mid-conversation invalidates the cache for the entire session, because tools are part of the cached prefix. The intuitive approach (only expose tools the model needs right now) is an anti-pattern. Instead, keep all tools present at all times and use other mechanisms to control behaviour.

    Model switches — prompt caches are unique to each model. If you're 100k tokens into a conversation with Opus and want to ask an easy question, switching to Haiku is more expensive than staying on Opus because the entire cache must be rebuilt. The right pattern for model switching is subagents: the primary model prepares a handoff message to a cheaper model for a bounded task. Claude Code does this with Explore agents, which use Haiku with their own fresh cache (Anthropic, Claude Code team, Mar 2026).

    Feature Design Around Cache Constraints¶

    Two Claude Code features illustrate how product design should follow caching constraints rather than fight them:

    Plan Mode — the intuitive implementation would swap the tool set to read-only tools when the user enters plan mode. This breaks the cache. Instead, Claude Code keeps all tools present and uses EnterPlanMode / ExitPlanMode as tools themselves. When plan mode activates, the agent receives a system message via the conversation (not a prompt change) explaining the constraints. Bonus: because EnterPlanMode is a callable tool, the agent can autonomously enter plan mode when it detects a hard problem — no cache break required.

    Tool Search (defer_loading) — Claude Code can have dozens of MCP tools loaded, and including full schemas for all of them in every request is expensive. But removing unused tools mid-conversation breaks the cache. The solution: send lightweight stubs — just the tool name with defer_loading: true — that the model can discover via a ToolSearch tool when needed. Full tool schemas load only on selection. The cached prefix stays stable because the same stubs are always present in the same order (Anthropic, Claude Code team, Mar 2026).

    Cache-Safe Compaction¶

    Compaction — summarising the conversation when the context window fills — has unintuitive caching edge cases. The naive implementation sends the conversation to the model with a different system prompt and no tools to generate a summary. This shares zero prefix with the main conversation, so you pay full price for all input tokens.

    Claude Code's solution: the compaction call uses the exact same system prompt, user context, system context, and tool definitions as the parent conversation. The parent's conversation messages are prepended, and the compaction prompt is appended as a new user message at the end. From the API's perspective, this request is nearly identical to the parent's last call — same prefix, same tools, same history — so the cached prefix is fully reused. The only uncached tokens are the compaction prompt itself.

    This requires reserving a compaction buffer — enough room in the context window for the compaction instruction and the summary output tokens. Based on these learnings, Anthropic built compaction directly into the API as a first-class feature (Anthropic, Claude Code team, Mar 2026).

    Operational Lessons¶

    Five rules that emerged from optimising prompt caching at scale:

    1. Prompt caching is a prefix match — any change anywhere in the prefix invalidates everything after it. Design the entire system around this constraint; get the ordering right and most caching works for free.
    2. Use messages instead of system prompt changes — state transitions (plan mode, updated timestamps, changed files) belong in conversation messages, not prompt mutations.
    3. Never change tools or models mid-conversation — use tools to model state transitions (plan mode) rather than changing the tool set. Defer tool loading instead of removing tools.
    4. Monitor cache hit rate like uptime — a few percentage points of cache miss rate dramatically affect cost and latency. Alert on it, treat regressions as incidents.
    5. Fork operations must share the parent's prefix — any side computation (compaction, summarisation, skill execution) should use identical cache-safe parameters to get cache hits on the parent's prefix.
    6. Make context append-only — avoid modifying previous actions or observations. Ensure serialization is deterministic — many languages and libraries don't guarantee stable key ordering when serializing JSON, which silently breaks the cache (Yichao 'Peak' Ji, Manus, Jul 2025).
    7. Route requests consistently in distributed setups — when self-hosting with vLLM or similar, use session IDs to route requests to the same worker so KV-cache state is reused across turns (Yichao 'Peak' Ji, Manus, Jul 2025).

    Key: Prompt caching is not an optimisation you bolt on after building an agent — it is a structural constraint that must inform the harness design from the start. Claude Code's entire prompt layout, tool management, feature design, and compaction strategy all follow from one rule: preserve the prefix.

    Evaluation Harnesses¶

    An evaluation harness is distinct from a runtime harness but must be tightly connected to it. The eval harness runs agent tasks at scale, records full traces/trajectories, grades outcomes, and aggregates results. Crucially, when you evaluate an agent, you are evaluating the harness + model together, not the model in isolation (Anthropic, early 2026).

    Evaluation as CI Gate¶

    The direction of travel is to treat evaluation harnesses as CI gates — a code/prompt/config change triggers offline agent evals, and results must pass a quality gate before deployment. Harbor explicitly provides job config files (job.yaml) for this pattern. The minimal pipeline: change → build → eval harness runs → quality gate → deploy → production trace mining → regression suite updates → re-eval.

    Experiment Design for Agentic Evaluation¶

    Evaluation is not just collecting logs and success metrics — it is validating hypotheses and comparing approaches through controlled experiments. The framing from Prime RL applies: "environments and evals are two sides of the same coin" — an evaluation harness is structurally identical to an RL environment, with observations (prompts), actions (agent outputs), and reward functions (metrics) (@neural_avb, Paper Breakdown, Mar 2026).

    A six-step experiment design workflow for agentic harness evaluation:

    1. Scope the target module. Most agentic pipelines have multiple collaborating agents. Evaluating the entire pipeline at once produces too many moving variables for actionable insights. Treat each agent as a separate evaluation harness. Prioritise modules where: (a) you've made the most unvalidated assumptions, (b) the module sits earliest in the pipeline (errors propagate downstream), or (c) you have a clear optimisation vector.

    2. Define the goal and hypothesis. Four universal optimisation axes — accuracy, latency, cost, and code quality — but pick one primary target while keeping the others within acceptable bounds. Having a clear hypothesis and a threshold for action before running experiments prevents post-hoc rationalisation.

    3. Isolate the black box and independent variables. Extract the module as a clean function (inputs in, outputs out) with no internal plumbing dependencies. Then identify the knobs — the independent variables you're controlling from outside (model name, system prompt variant, tool configuration, feature flags). Keep knobs to 2–3 maximum to maintain interpretability. Critically, disable persistence layers (caches, database writes) unless you're specifically testing multi-turn cache behaviour. Every test case must be transactional — test case 10 should have zero advantage or disadvantage over test case 4 (@neural_avb, Paper Breakdown, Mar 2026).

    4. Design test cases from production data. The evaluation is only as good as the dataset. Preferred sources in order: (a) production logs — the gold standard, because they reflect real user behaviour; (b) synthetic generation via LLM if no production data exists; (c) hand-written cases as a last resort. Quality test cases must be deduplicated, diverse (avoid oversampling a single subdomain that biases the experiment), and ideally include ground-truth outputs — at minimum, the current production outputs serve as a drift baseline.

    5. Choose metrics: deterministic first. Two categories: deterministic metrics (string match, valid JSON, length constraints, regex format validation, precision/recall/IOU) and probabilistic metrics (LLM-as-a-judge grading). Use deterministic wherever possible — cheaper, faster, and 100% reliable. Match metric type to agent type:

    Agent type Recommended metrics
    Retrieval agent Precision, recall, IOU scores
    Response agent LLM-as-a-judge (helpfulness, accuracy, tone)
    Task agent Tool call statistics, verifiable environment success/fail
    Citation agent Regex format validation, source accuracy
    Coding agent Test pass rate, structured output validation

    Regardless of agent type, always record three additional signals: total walltime, completion token usage, and total cost (@neural_avb, Paper Breakdown, Mar 2026).

    6. Visualise and interpret. Bar graphs for response times, scatter plots for Cost-vs-IOU or Walltime-vs-IOU tradeoff frontiers, box plots for distribution analysis. The goal: models with narrow distributions and high means — consistency matters as much as peak performance.

    Eval–RL Convergence¶

    Evaluation harnesses and RL environments are structurally equivalent. The test cases are observations, the agent outputs are actions, and the metrics are reward signals. This means a well-designed eval harness can double as an RL training environment — enabling prompt optimisation (GEPA) or end-to-end RL training of smaller specialised agents on your specific harness. Harbor already exploits this convergence, with unexpected uses including RL rollouts, SFT trace generation, and prompt optimisation.

    Key: The practical payoff of disciplined experiment design: Paper Breakdown replaced gpt-5-mini with gemini-3-flash-lite for its retrieval subagent — faster, cheaper, and with a discovered emergent behaviour (auxiliary findings for future subagent calls) that further reduced downstream costs. This trait was invisible without controlled experimentation. Once the eval harness exists, re-running it on every new model drop becomes trivial (@neural_avb, Paper Breakdown, Mar 2026).

    Long-Running Agent Harness Patterns¶

    The Session Continuity Problem¶

    Long-running agents face a fundamental challenge: they operate in discrete sessions with context windows, and each new session begins without memory of prior work. The analogy: a software project staffed by engineers working in shifts, where each new engineer arrives with no memory of what happened on the previous shift (Justin Young, Anthropic, Nov 2025).

    Anthropic's solution in the Claude Agent SDK is a dual-agent architecture:

    • Initializer agent — runs once at project start to establish the environment: creates an init.sh script for the dev server, a claude-progress.txt file for logging work, and an initial git commit documenting added files
    • Coding agent — runs in subsequent sessions, making incremental progress on single features, leaving the codebase production-ready, and documenting state for the next session

    Observed Failure Modes¶

    Four failure modes emerged repeatedly in Anthropic's testing (Justin Young, Anthropic, Nov 2025):

    Premature victory declaration — the agent declares the project complete after partial implementation. Fix: create a comprehensive feature list file with all requirements marked "failing" initially. The agent must flip each to "passing" only after verified end-to-end testing.

    One-shot overreach — the agent tries to build the entire app at once, exhausting context mid-implementation. Fix: prompt agents to work on one feature per session. Incremental progress across sessions beats ambitious single-session attempts.

    Undocumented progress — code changes left without documentation or testing, making the next session's agent unable to understand what was done. Fix: require git commits with descriptive messages plus progress file updates at every meaningful checkpoint.

    Incomplete testing — features marked complete without end-to-end verification. Fix: explicit browser automation (Puppeteer MCP) for human-like testing. The agent must actually navigate the UI, click buttons, and verify outcomes — not just check that code compiles.

    Session Startup Protocol¶

    Every coding session begins with a deterministic startup sequence (Justin Young, Anthropic, Nov 2025):

    1. Run pwd to verify working directory
    2. Read git logs and progress files to understand current state
    3. Read feature list and select highest-priority incomplete feature
    4. Run init.sh to start the development server
    5. Test basic functionality before starting new work

    This protocol eliminates a class of failures where the agent starts coding without understanding project state, duplicates work, or builds on a broken foundation.

    Feature List as Harness Contract¶

    Anthropic found that using JSON over markdown for feature tracking reduced inappropriate modification rates. The feature list acts as a contract between sessions — a structured specification of what "done" looks like:

    {
  "category": "functional",
  "description": "New chat button creates a fresh conversation",
  "steps": [
    "Navigate to main interface",
    "Click the 'New Chat' button",
    "Verify a new conversation is created",
    "Check that chat area shows welcome state",
    "Verify conversation appears in sidebar"
  ],
  "passes": false
}

    Critical instruction: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." Without this constraint, agents optimise for "passing" by weakening the test rather than fixing the code.

    Git as Recovery Mechanism¶

    The agent uses git not just for documentation but as a recovery tool — reverting bad changes to restore working states. This is a concrete instance of the broader principle that harness engineering should give agents rollback mechanisms, not just forward execution.

    Remaining Limitations (Nov 2025 Harness)¶

    • Browser-native alert modals are invisible through Puppeteer MCP
    • Vision limitations prevent detection of certain UI bugs (layout drift, subtle colour issues)
    • Research optimised for full-stack web development; generalisation to scientific research and financial modelling remains untested

    Key: The Anthropic findings validate a core harness principle — the model's reasoning capability is not the bottleneck. Session continuity, state management, verification loops, and incremental progress contracts are what separate a working long-running agent from a demo that collapses after one turn.

    Evolution: Three-Agent GAN-Inspired Architecture (Mar 2026)¶

    A follow-up effort at Anthropic extended the dual-agent harness to a three-agent architecture inspired by Generative Adversarial Networks, addressing two failure modes the earlier harness left unsolved: self-evaluation leniency (agents confidently praise their own mediocre work) and coherence loss on multi-hour builds (Prithvi Rajasekaran, Anthropic, "Harness design for long-running application development", Mar 2026 — https://www.anthropic.com/engineering/harness-design-long-running-apps).

    The three agents:

    • Planner — takes a 1–4 sentence user prompt and expands it into a full product spec. Prompted to be ambitious about scope but to stay focused on product context and high-level technical design rather than granular implementation details — because errors in detailed upfront specs cascade into downstream implementation. Also instructed to weave AI features into specs.
    • Generator — implements the spec in sprints (one feature at a time), using a React/Vite/FastAPI/SQLite stack. Self-evaluates after each sprint before handing off to QA. Has git for version control.
    • Evaluator — uses Playwright MCP to interactively click through the running application (navigating pages, screenshotting, studying implementations) before scoring each sprint against grading criteria and filing specific bugs. Does not just review code or static screenshots — it exercises the app like a user.

    Context anxiety: a distinct failure mode. Beyond generic context rot, some models exhibit "context anxiety" — premature wrap-up behaviour as they approach what they believe is their context limit. Sonnet 4.5 exhibited this strongly enough that compaction alone was insufficient; context resets (clearing the window entirely and starting a fresh agent with a structured handoff artifact) were essential. Context resets differ from compaction: compaction summarises in place so the same agent continues, but doesn't provide a clean slate, so context anxiety can persist. Resets provide the clean slate at the cost of handoff overhead. Opus 4.5 largely removed context anxiety natively, enabling compaction-only harnesses without resets — eliminating the orchestration complexity, token overhead, and latency that resets introduced.

    Self-evaluation failure and the generator-evaluator separation. When asked to evaluate their own work, agents respond by confidently praising it — even when quality is obviously mediocre. This is particularly pronounced for subjective tasks (design quality) but persists even on verifiable tasks. The critical insight: tuning a standalone evaluator to be skeptical is far more tractable than making a generator critical of its own work. Once external feedback exists, the generator has something concrete to iterate against. The separation doesn't eliminate leniency on its own — the evaluator is still an LLM inclined to be generous toward LLM outputs — but it makes the tuning problem tractable.

    Sprint contracts. Before each sprint, the generator and evaluator negotiate a sprint contract — agreeing on testable "done" criteria before any code is written. The contract bridges the gap between the planner's intentionally high-level spec and verifiable implementation. Sprint 3 alone had 27 criteria covering the level editor. Communication happens via files: one agent writes a file, the other reads and responds. The evaluator's QA findings were specific enough to act on without extra investigation — e.g., identifying that a fillRectangle function exists but isn't triggered on mouseUp, or that a FastAPI route ordering bug causes a 422 by matching 'reorder' as an integer frame_id.

    Making subjective quality gradable. For frontend design, the evaluator used four grading criteria — design quality, originality, craft, and functionality — weighted toward design quality and originality (where Claude defaulted to bland outputs) rather than craft and functionality (where it already scored well). Criteria explicitly penalized "AI slop" patterns (purple gradients over white cards, template layouts, library defaults). The evaluator was calibrated with few-shot examples and detailed score breakdowns. Runs of 5–15 iterations per generation, up to 4 hours each, with the generator making strategic decisions after each evaluation: refine the current direction if scores trend well, or pivot to an entirely different aesthetic. In one example (Dutch art museum site), iteration 10 scrapped the existing clean dark-themed landing page and reimagined it as a 3D spatial gallery with a checkered floor rendered in CSS perspective and doorway-based navigation — a creative leap not seen from single-pass generation.

    Concrete cost/quality benchmarks. For a 2D retro game maker from a one-line prompt:

    Harness Duration Cost Outcome
    Solo agent 20 min $9 UI functional but clunky, core game runtime broken (entities appeared but nothing responded to input)
    Three-agent harness (Opus 4.5) 6 hr $200 Full viewport canvas, consistent visual identity, richer editors, working AI integration, playable game with physics

    For a browser-based DAW (Digital Audio Workstation) with the simplified harness on Opus 4.6:

    Phase Duration Cost
    Planner 4.7 min $0.46
    Build round 1 2 hr 7 min $71.08
    QA round 1 8.8 min $3.24
    Build round 2 1 hr 2 min $36.89
    QA round 2 6.8 min $3.09
    Build round 3 10.9 min $5.88
    QA round 3 9.6 min $4.06
    Total 3 hr 50 min $124.70

    Harness Simplification as Models Improve¶

    Every component in a harness encodes an assumption about what the model cannot do on its own, and those assumptions are worth stress-testing — both because they may be incorrect and because they go stale as models improve. The principle from Anthropic's "Building Effective Agents": "find the simplest solution possible, and only increase complexity when needed."

    With Opus 4.6 (which plans more carefully, sustains agentic tasks longer, operates more reliably in larger codebases, and has better self-debugging), the harness was simplified:

    • Sprint construct removed — Opus 4.6 could coherently build for 2+ hours without sprint decomposition that Opus 4.5 required.
    • Evaluator moved to single end-pass — instead of per-sprint QA. The evaluator's value became conditional on task difficulty: for tasks within the model's reliable baseline capability, the evaluator was unnecessary overhead; for tasks at the edge of capability, it continued to provide real lift.
    • Context resets eliminated — Opus 4.5/4.6 removed context anxiety, so the Claude Agent SDK's automatic compaction handled context growth without full resets.

    The practical implication: the evaluator is not a fixed yes-or-no decision — it is worth the cost when the task sits beyond what the current model does reliably solo. As models improve, the boundary moves outward, and components that were once load-bearing become optional. The space of interesting harness combinations does not shrink as models improve — it moves, and the engineering work is to keep finding the next novel combination.

    Key: The Nov 2025 → Mar 2026 evolution demonstrates the harness lifecycle in practice: build scaffolding for current model limitations, re-examine when new models land, strip what's no longer load-bearing, add new components that unlock capabilities previously out of reach. The three-agent pattern (planner, generator, evaluator) and the GAN-inspired feedback loop are the current frontier for multi-hour autonomous coding.

    Azure Harness Architecture¶

    On Azure, the clean mental model is: Foundry/Agent Framework gives agent primitives; the harness is the engineered wrapper that makes those primitives deterministic, inspectable, and safe for business workflows. Microsoft Agent Framework positions itself as the successor to Semantic Kernel and AutoGen, with session state, telemetry, and workflow control; Foundry Agent Service is the managed runtime for building and operating agents across dev, deployment, and production (Microsoft Learn, Mar 2026).

    Two-Speed Architecture¶

    The pragmatic approach — demo both paths, but build only one real harness:

    • Path A (30-minute proof): Foundry Agent Service + hosted agent + playground. Managed hosting, built-in tools, playground testing. The hosted-agent quickstart deploys a containerized agent via azd up and validates in the Foundry playground. Good demo optics, fast time-to-value.
    • Path B (real harness): Agent Framework workflow in code, deployed on Azure Functions Durable or App Service, with Foundry traces/evals wired in. Code-first orchestration, long-running workflows, event triggers, pause/resume, deterministic flow control. This is the answer to "can this be productionised?"

    Foundry's App Service tutorial frames the trade-off explicitly: code-first frameworks (LangGraph, Agent Framework) give more control and speed locally, while Foundry Agent Service gives managed integration, playground testing, autoscaling, and built-in guardrails/identity (Microsoft Learn, Mar 2026).

    Proving a Harness — The Five-Screen Demo¶

    Do not demo a generic assistant. Demo a narrow but complete harness. The proof pattern: one user request, one deterministic route, two tools, one checker/verifier, one visible trace, one evaluation report.

    Show five screens in order (Microsoft Learn, Mar 2026):

    1. Architecture slide — one-page diagram: user → harness controller → agents/tools → checker → logs/evals
    2. Live run — submit a request requiring at least one tool call
    3. Trace view — execution trace with spans for LLM calls, tool calls, and agent decisions via Foundry/OpenTelemetry
    4. Failure injection — break one tool, show the harness retries/falls back/returns a controlled error instead of hallucinating — this is the real harness moment
    5. Eval report — tiny JSONL test set with metrics (groundedness, relevance, tool-call accuracy, task completion) via Azure Evaluation SDK

    Once you show this sequence, the audience stops seeing "AI demo" and starts seeing "software system."

    Concrete Demo: "Ops Resolution Harness"¶

    • Input: "Customer shipment delayed; explain cause and next action."
    • Agent 1: classify request
    • Agent 2: retrieve shipment facts from mock API / document store
    • Agent 3: recommend action
    • Checker agent: validate groundedness and whether required fields are present
    • Final answer: structured response + confidence + cited tool outputs

    This demonstrates routing, tool use, multi-step orchestration, verification, and traceability while avoiding the impossible promise of full autonomy. Microsoft explicitly warns against complex nondeterministic patterns where deterministic routing suffices; for demos, deterministic wins (Microsoft Learn, Mar 2026).

    Bounded Autonomy Pattern¶

    The most effective operating model for agentic coding is not full autonomy but bounded autonomy — a repeating cycle where humans establish architectural intent and agents accelerate execution within that frame (Sam Breed, Anthropic, Mar 2026). The cycle:

    1. Human seeds — choose frameworks, run init commands, establish architectural decisions manually
    2. Agent plans and executes — within a bounded workspace (typically a git worktree), the agent writes a spec and implements against it
    3. Verification is explicit — a verifier pass checks the output before merge
    4. Scope stays PR-sized — work stops at natural merge points rather than letting one plan sprawl
    5. Context resets — merge, archive the worktree, start a fresh workspace for the next unit of work

    The natural operating unit is one pull request, not one feature or one session. PR-sized scoping reduces stale context, prevents plan invalidation, and makes verification tractable. When a task is larger than one PR, decompose it into independent PR-sized chunks that can be parallelized across worktrees.

    Coordinator / Implementer / Verifier¶

    A concrete three-role orchestration pattern for this cycle:

    • Coordinator — plans the work, writes the spec, decomposes into tasks, dispatches to implementers
    • Implementer — executes a single bounded task (one file, one component, one endpoint)
    • Verifier — checks the output against the spec, runs tests, validates correctness

    The coordinator can dispatch parallel implementers against independent tasks once shared components (e.g., a reusable layout shell) are in place. The system shines in parallelization — the coordinator identifies which tasks are independent, launches them concurrently in separate worktrees, and the verifier validates each before merge.

    SDLC Specialist Agents¶

    Beyond general-purpose coding agents, the bounded autonomy model enables specialist agents wired into specific SDLC surfaces:

    • PR Shepherd — monitors PR comments and CI feedback, iterates toward green automatically. Attaches to existing review/CI infrastructure rather than replacing it (Sam Breed, Anthropic, Mar 2026).
    • Sentry issue resolver — ingests Sentry issue context (stack traces, error metadata) and generates fix workspaces. Converts production errors into bounded agent tasks with well-defined acceptance criteria.

    These specialists are closer to production value than general-purpose coding demos because they attach AI to existing SDLC pain points with clear success metrics (CI green, error resolved) rather than open-ended generation.

    Context Quality Over Context Quantity¶

    Even with large context windows, the right context outperforms maximal context. Smaller, accurate task context gives faster and more reliable agent behaviour than stuffing the window with everything available. This reinforces the bounded autonomy cycle — each fresh workspace starts with precisely the context needed for one PR-sized task, not the accumulated state of an entire project history (Sam Breed, Anthropic, Mar 2026).

    Harness Design Principles¶

    These principles emerge across Anthropic's findings, Azure's architecture, and the broader production patterns documented in the LLM Agentic Systems reference:

    1. Session state is not optional — agents that cannot resume from where they left off will duplicate work, contradict prior decisions, or silently regress. Git, progress files, and structured feature lists are minimum viable session state.
    2. Incremental over ambitious — one feature per session, one verified step at a time. The failure mode is not "too slow" but "collapsed mid-attempt."
    3. Verification must be structural, not verbal — the agent saying "it works" is not verification. Browser automation, test suites, schema validation, and eval datasets are verification. Anything the agent can hallucinate is not a check.
    4. JSON over prose for contracts — structured formats resist inappropriate modification better than natural language. Feature lists, eval schemas, and tool contracts should be machine-readable.
    5. Rollback is a first-class capability — git revert, state snapshots, and checkpoint mechanisms prevent a single bad step from corrupting the entire trajectory.
    6. The harness determines demo vs product — not the model, not the prompt, not the tools. The control envelope around them is what makes the difference.

    Future Directions¶

    Four trends emerging from the early 2026 literature:

    1. Automatic harness synthesis (AutoHarness) — an LLM iteratively synthesises a code harness that prevents illegal actions. In extreme cases, the entire policy is generated in code, avoiding LLM decision-making at runtime entirely. "Harness generation" becomes a performance + safety lever, not just a dev-ops task (OpenDev, early 2026).

    2. Harness–model co-evolution and the recursive coding loop — agent products like Claude Code and Codex are post-trained with their harnesses in the loop. Useful primitives get discovered, added to the harness, and used when training the next generation of models. This recursive nature — agentic coding improving agent/LLM training — has emerged as a key acceleration mechanism: Claude writes 70-90% of code for future Anthropic models, MiniMax positioned M2.7 as the first model that "deeply participated in its own evolution" via autonomous iteration (collecting feedback, building eval sets, iterating on skills/MCP), and Cursor's Composer 2 attributed its gains to its first continued pretraining run feeding a stronger base into RL (Latent Space AINews, Mar 2026). swyx's retrospective on "Rise of the AI Engineer" (2023) notes this recursive loop was almost completely missed in the original thesis, which framed "1+2=3" (LLM-powered software > LLMs or software alone) — essentially presaging harness engineering — but underestimated the importance and immediacy of models contributing to their own training pipelines (Latent Space, Mar 2026). But this co-evolution creates overfitting to specific harness patterns — changing tool logic leads to worse model performance. A concrete example: the Codex-5.3 prompting guide documents how models become dependent on the specific apply_patch tool logic for file editing; a truly general model should handle patch format changes easily, but harness-in-the-loop training creates brittleness (LangChain, "Anatomy of an Agent Harness", Mar 2026). Critically, this doesn't mean the best harness for your task is the one a model was post-trained with — on Terminal-Bench 2.0, Opus 4.6 in Claude Code scores far below Opus 4.6 in other harnesses, and LangChain moved from Top 30 to Top 5 by changing only the harness. There is significant performance to be gained from harness optimisation independent of model choice.

    3. Dynamic tool assembly as default — just-in-time tool/context loading based on current state/tenant/project will replace fixed tool menus. Retrieval-style tool selection surfaces (namespaces, MCP servers, skills) plus trace-informed pruning will become standard. LangChain is actively exploring harnesses that dynamically assemble the right tools and context just-in-time for a given task instead of being pre-configured (LangChain, "Anatomy of an Agent Harness", Mar 2026).

    4. Eval–training harness convergence — the same task definitions will power offline evaluation, regression CI, and online training signals. Harbor already sits at this intersection (unexpected uses include RL rollouts, SFT trace generation, prompt optimisation). Versioned environments and budget controls (VeRO-style) will become standard infrastructure.

    5. Parallel agent orchestration at scale — orchestrating hundreds of agents working in parallel on a shared codebase is an open problem. Current worktree-based isolation works for small parallelism but breaks down at scale due to merge conflicts, shared state coordination, and resource contention.

    6. Self-diagnosing harnesses — agents that analyse their own execution traces to identify and fix harness-level failure modes, creating a meta-loop where the harness improves itself based on observed agent behaviour (LangChain, "Anatomy of an Agent Harness", Mar 2026).

    7. Secure execution as first-class product feature — LangChain's LangSmith Sandboxes provide secure ephemeral code execution environments, reflecting Harrison Chase's thesis that "more and more agents will write and execute code" (@hwchase17, Jun 2026). OpenAI's Codex now supports subagents with GPT-5.4 mini explicitly optimised for that use case. The convergence across vendors is clear: agent value increasingly depends on safe execution environments, composable skills/plugins, and workflow-native surfaces rather than raw benchmark gains alone.

    8. Agent lifecycle infrastructure — OpenAI Symphony is an open-source framework for managing autonomous AI coding agents through structured "implementation runs." Built on Elixir and the Erlang/BEAM runtime for agent lifecycle management, it is designed to bridge project management tools and code execution — treating agent orchestration as a runtime systems problem rather than a prompt engineering problem (OpenAI, Mar 2026).

    9. Open harness convergence on model + runtime + harness — the "open coding agent" ecosystem is becoming legible, with increasing convergence on patterns: model-agnostic harnesses, structured skills, filesystem/state abstractions, and ephemeral cloud or local execution. LangChain's Open SWE and Deep Agents, Hermes Agent's plugin system, and Hugging Face's local coding agent all embody this pattern. The frontier is no longer just open-weight models — it is open harnesses and runtime layers for actually deploying agents (@hwchase17, @UnslothAI, @huggingface, Jun 2026). Harrison Chase published a walkthrough framing Claude Code, OpenClaw, Manus, and similar systems as the same three-part decomposition: open model + runtime + harness, using Nemotron 3, NVIDIA's OpenShell, and LangChain's DeepAgents as concrete examples (Harrison Chase, LangChain, Mar 2026). Related infrastructure releases reinforce this convergence: LangSmith Sandboxes for secure code execution, LangSmith Polly GA as an in-product debugging and improvement assistant, and a new LangChain guide on production observability for agents — all filling out the runtime and evidence layers of the shared decomposition (LangChain, Mar 2026).
